Lab 5: a conjugate-gradient solver

Lab 3's stencil marched a rod forward in time. Most stencils on a supercomputer do something else: they are the matrix inside an iterative solver. This lab solves a 3-D Poisson problem with conjugate gradient (CG) on a grid of PEs. The program combines three modules, memcpy plus two SDK libraries, so its main lesson is composition: how modules share one PE's colors, tasks and queues. Then we measure where an iteration's cycles go, and why every iteration waits for one global sum.

After this lab you can

  • Write CG and sort its steps into local, neighbour and global work, and say which one limits a wafer-sized solve.
  • Combine library modules on one PE: give each its colors, task IDs, queues and DSRs, and check the budget.
  • Explain how the SDK's allreduce reroutes one color three times per call, and why it acts as a barrier.
  • Compare a host-driven loop with an on-device loop in simulated cycles, and estimate the gap on a real system.
  • Measure a per-iteration cost split with the TSC and predict how it scales with the grid and the column height.

The problem and the CG algorithm

Take the Poisson equation −∇²u = f on a box, with u = 0 on the boundary. The 7-point finite-difference stencil turns it into a linear system A u = b. Each row of A has 6 on the diagonal and −1 for each of the six neighbours (west, east, south, north, below, above); neighbours outside the box drop out. A is symmetric and positive definite, so conjugate gradient applies. With 125 unknowns you could invert A; with a billion you cannot even store it. CG never forms A. It only needs to apply it, and applying A is exactly a stencil.

Here is CG in numpy. It is the reference that run.py checks the device against, and it follows Golub and Van Loan's Algorithm 10.2.1, as the SDK benchmark does:

def cg_numpy(max_ite):
    x = x0.copy(); r = b - A(x); rho = np.vdot(r, r); k = 0
    while rho > tol * tol and k < max_ite:
        k += 1
        p = r.copy() if k == 1 else r + (rho / rho_old) * p   # axpy           local
        w = A(p)                                             # stencil SpMV   neighbours
        alpha = rho / np.vdot(p, w)                          # dot product    GLOBAL
        x = x + alpha * p;  r = r - alpha * w                # 2 axpy         local
        rho_old, rho = rho, np.vdot(r, r)                    # dot product    GLOBAL
    return x

Here A(v) applies the stencil, x0 is the starting guess (zero), and tol = EPS·|b|, so the loop stops when the residual |r| ≤ EPS·|b|. The denominator of α, ⟨p, w⟩ = ⟨p, A p⟩, is called η (eta) in the device code. The device splits each iteration into four phases, which the profile below times separately:

How many iterations? CG's error shrinks at least as fast as 2·((√κ − 1)/(√κ + 1))k, where κ = λmax/λmin is A's condition number (Golub and Van Loan, Theorem 10.2.6). For this A on an N × N × N box, λ = 6 ∓ 6·cos(π/(N+1)), so κ = cot²(π/(2N+2)): 13.9 at N = 5, 32.2 at N = 8, 67.8 at N = 12 Derived. The SDK benchmark prints the same 0.80 and 11.20 extreme eigenvalues for its 5 × 5 × 5 case SDK 2.10.1. √κ grows like N, so on a cube the iteration count grows in proportion to the side. That holds only when all three sides grow. For a W × H × Z box, λmin = Σ 2(1 − cos(π/(n+1))) over the three sides, and the z term never shrinks if Z stays fixed: with Z = 5, κ can never exceed about 44, however wide the grid Derived. Keep both cases in mind for the scaling section.

Mapping onto the wafer

The SDK's 3-D stencils, and this lab, use the pencil decomposition from Lab 3's last table. The box is W × H × Z cells. PE (px, py) owns the whole z-column at (x = px, y = py), Z cells long, of every vector. A PE stores five vectors (b, x, p, w, r), so 20·Z bytes, plus 7 stencil coefficients.

  • SpMV, w = A p. The z-neighbours are in local memory, so the z part of the stencil is three @fmacs over shifted DSDs. The x/y part needs the four neighbouring columns. The library sends p to the east, west, north and south in blocks of BLOCK_SIZE wavelets, receives the four neighbours' blocks, and adds them in with four more @fmacs.
  • Dot products. Each PE sums over its own column (@map, as in the SDK's blas.csl), then the allreduce adds the W·H partial sums and returns the total to every PE. A single wavelet travels.
  • axpys. Purely local @fmacs. α and β are scalars that every PE computes from the same allreduced values, so every PE takes the same decision without any extra message.

Composing modules

Labs 1–3 wrote every line on the PE themselves, apart from memcpy. Lab 4 imported one library, <collectives_2d>, twice (one instance per axis), kept a resource-map comment as its budget sheet and checked it with a five-step procedure (Chapter 14, design method). Lab 4 shared one PE between memcpy and one library; here two different libraries, written by different people, compete for the same slots. This program writes about 300 lines of CSL and imports about 2,200 (2,900 counting both chips' variants of the stencil): the SDK's benchmark-libs/stencil_3d_7pts (the SpMV) and benchmark-libs/allreduce (the global sums), each with a layout half and a PE half. The libraries live in course/programs/07-cg/lib/, copied from SDK 2.10.1 with an attribution header.

Three rules make composition work.

  1. The top level owns every hardware ID. A library takes the colors, local task IDs, queues and DSR numbers it uses as parameters (on WSE-3 the stencil also takes its microthread), and never picks its own. The layout comment in layout.csl is the ledger, the same budget sheet Lab 4 kept: stencil colors 0–7 and tasks 14–16; allreduce color 8 and tasks 17–20; the program's own state-machine task 12; queues 0–1 for memcpy, 2 for allreduce, 4–7 for the stencil.
  2. Two halves, two kinds of parameter. A layout half runs at compile time for each (px, py) and returns a struct (for the stencil, the color parity of each direction, as in Lab 3's figure). The PE half takes that struct plus everything that is a property of the PE program, such as queue numbers.
  3. Libraries hand control back through a callback. Neither library knows about the host. When spmv() or allreduce() finishes, it calls the function it was given. The SDK's host-driven kernel passes sys_mod.unblock_cmd_stream; its device-driven kernel passes a function that activates the next state. This program passes phase_done(), which does either (two loops, below). That one indirection is the whole difference between the two loops below.

The allreduce every iteration waits on

A global sum over a 2-D grid needs a route for every partial sum to reach one PE and a route for the result to reach everyone. Lab 2 built a row reduce on two alternating colors and a broadcast on a multicast route, each with static routes. The SDK's allreduce does all three stages with one color, and rewrites that color's routes between stages:

  1. Row reduce. Routes: every PE forwards from west to east (switch position 0), and the last PE in the row delivers to its CE. Every PE except the last sends its value, then a switch-advance control wavelet (Chapter 4). All PEs push at once, but each value waits in its own output queue until its router's switch points at the RAMP (its own CE). The control wavelet behind a value carries two commands (switch_cmd_11, with the routes in ring mode): one sets the sender's own router back from "take from my CE" (position 1) to "forward from the west" (position 0), the other moves the next router to position 1, which releases the next PE's waiting value. So values arrive at the last PE one at a time, farthest first and nearest last. The last PE adds them as they arrive with an asynchronous @fadds from the fabric, W − 1 times. The first PE then sends a teardown wavelet.
  2. Column reduce. The same, north to south. Every column runs it at once (the library sets the column routes from the row index only), but only the last column's sum is used: H − 1 row sums reach the bottom-right PE. The other columns' bottom PEs add stale values, which the broadcast then overwrites. Because the columns run in parallel, this costs nothing extra.
  3. Broadcast. The bottom-right PE sends the sum north up the last column, and every PE in that column sends it west along its row, by multicast routes (Lab 2's mechanism). Then a teardown.

Between stages each PE calls reset_routes, clears its switch position and exits teardown mode on that color (tile_config). The teardown wavelet is how the PEs agree that a stage is over. This is the same sequence as Chapter 14's <collectives_2d>: the operation blocks a lock task (C_LOCK), the teardown handler (task 29) activates it, the stage's own work unblocks it when it has finished, and only with both does the lock task run and move the state machine on (the block + activate join of Chapter 5). Two things are new here: one color is reused for three stages, and a state machine chains them (row, column, broadcast, then f_callback). That is why it needs only one color, one queue and four task IDs. The cost is that a stage can only start once the previous one has drained, so the three stages run strictly one after another, and every message is a single wavelet whose cost is almost all latency.

Why the allreduce is a barrier

No PE gets the sum back until the broadcast reaches it, and the broadcast cannot start until the bottom-right PE has every row's partial sum. So no PE leaves an allreduce before the last PE has entered it. A PE that reaches the allreduce early just waits inside it. You can see this in the profile. Every PE spending the same 4,574 cycles per iteration on the default 5 × 5 grid is what any loop with a global barrier shows in steady state, so it is not the evidence. The evidence is the spread: the share spent inside the allreduce varies from PE to PE by 228 cycles (1,898 to 2,126) Measured, although every PE does the same allreduce work. The PEs that finished their own phases early absorb the difference as waiting inside the call.

The SDK also ships a general-purpose 2-D library, <collectives_2d>, introduced in Chapter 12. It uses two colors per dimension and also rewrites routes at runtime; Chapter 14 uses it for SUMMA's row and column broadcasts and goes into its parameters. Chapter 12 measured its fixed overhead at about 700 cycles per operation Measured, the same order as the allreduce here.

The PE program holds both loops. The four phases of an iteration are ordinary functions, as are the three set-up phases (init, w = A x0, and the first residual with its ρ allreduce). Each one either finishes by itself (update_p) or ends by calling a library that finishes later (spmv_Ap ends in the stencil, eta_dot and update_x_r_rho in the allreduce). Either way control comes back to phase_done().

const B_AXPY: u16 = 0;  const B_SPMV: u16 = 1;  const B_DOT: u16 = 2;
const B_ALLREDUCE: u16 = 3;  const B_CONTROL: u16 = 4;
var prof = @zeros([5]u32);           // cycles per bucket, summed over iterations 1..k
var bucket: u16 = B_CONTROL;
var t_last: u32 = 0;
var rho_hist = @zeros([MAX_ITE + 1]f32);   // rho after iteration 0..k
var t_hist = @zeros([MAX_ITE + 1]u32);     // TSC (low 32 bits) at the same moments
var tsc = @zeros([timestamp.tsc_size_words]u16);

fn now() u32 {
  timestamp.get_timestamp(&tsc);
  return @as(u32, tsc[0]) | (@as(u32, tsc[1]) << 16);
}

// Close the running bucket and open the next one. Compiled out when PROFILE = 0.
fn mark(next: u16) void {
  if (PROFILE != 0) {
    const t = now();
    prof[bucket] += t - t_last;
    t_last = t;
    bucket = next;
  }
}

// rho has just been allreduced: log it, with the time, for the convergence plot.
fn record() void {
  rho_hist[k] = rho[0];
  t_hist[k] = now();
  if (k == 0) {                      // profile iterations only, not the set-up
    for (@range(u16, 5)) |i| { prof[i] = 0; }
    t_last = t_hist[0];
    bucket = B_CONTROL;
  }
}

// ---------------- the phases ----------------
const PH_INIT: i16 = 0;      const PH_SPMV_AX: i16 = 1;  const PH_RESIDUAL: i16 = 2;
const PH_UPDATE_P: i16 = 3;  const PH_SPMV_AP: i16 = 4;  const PH_ETA: i16 = 5;
const PH_UPDATE_XR: i16 = 6;
var phase: i16 = PH_INIT;            // the phase that is running or has just finished

// Every phase ends here, directly or as a library's callback.
fn phase_done() void {
  if (phase == PH_RESIDUAL or phase == PH_UPDATE_XR) { record(); }
  mark(B_CONTROL);
  if (device_loop) {
    @activate(STATE);                // the state machine starts the next phase
  } else {
    sys_mod.unblock_cmd_stream();    // the host's next command (launch or copy) can now run
  }
}

}

  k = 0;
  const len = @bitcast(u16, n);
  dsd_b = @set_dsd_length(dsd_b, len);  dsd_x = @set_dsd_length(dsd_x, len);
  dsd_p = @set_dsd_length(dsd_p, len);  dsd_w = @set_dsd_length(dsd_w, len);
  dsd_r = @set_dsd_length(dsd_r, len);
  for (@range(i16, MAX_ITE + 1)) |i| { rho_hist[i] = 0.0; t_hist[i] = 0; }
  timestamp.enable_tsc();
  phase_done();
}

fn spmv_Ax() void {                  // w = A x0
  phase = PH_SPMV_AX;
  stencil_mod.spmv(n, &coeff, &x, &w);
}

fn residual() void {                 // r = b - w; rho = <r, r>
  phase = PH_RESIDUAL;
  @fsubs(dsd_r, dsd_b, dsd_w);
  rho[0] = local_dot(&r, &r);
  reduce_mod.allreduce(1, &rho, reduce_mod.TYPE_BINARY_OP.ADD);
}

fn update_p() void {                 // p = r (first iteration) or p = r + beta p
  phase = PH_UPDATE_P;
  mark(B_AXPY);
  k += 1;
  if (k == 1) {
    @fmovs(dsd_p, dsd_r);
  } else {
    @fmacs(dsd_p, dsd_r, dsd_p, rho[0] / rho_old);
  }
  phase_done();
}

fn spmv_Ap() void {                  // w = A p
  phase = PH_SPMV_AP;
  mark(B_SPMV);
  stencil_mod.spmv(n, &coeff, &p, &w);
}

fn eta_dot() void {                  // eta = <p, w>, summed over all PEs
  phase = PH_ETA;
  mark(B_DOT);
  eta[0] = local_dot(&p, &w);
  mark(B_ALLREDUCE);
  reduce_mod.allreduce(1, &eta, reduce_mod.TYPE_BINARY_OP.ADD);
}

fn update_x_r_rho() void {
  phase = PH_UPDATE_XR;
  mark(B_AXPY);
  const alpha = rho[0] / eta[0];
  @fmacs(dsd_x, dsd_x, dsd_p, alpha);
  @fmacs(dsd_r, dsd_r, dsd_w, -alpha);
  rho_old = rho[0];
  mark(B_DOT);
  rho[0] = local_dot(&r, &r);
  mark(B_ALLREDUCE);
  reduce_mod.allreduce(1, &rho, reduce_mod.TYPE_BINARY_OP.ADD);
}

// ---------------- host-driven loop: the host calls each phase ----------------
fn f_init(size: i16) void { device_loop = false; init(size); }
fn f_spmv_Ax() void { spmv_Ax(); }
fn f_residual() void { residual(); }
fn f_update_p() void { update_p(); }
fn f_spmv_Ap() void { spmv_Ap(); }
fn f_eta() void { eta_dot(); }
fn f_update_x_r_rho() void { update_x_r_rho(); }

// ---------------- device-driven loop: one RPC, a task picks each next phase ----------------
fn f_cg(size: i16, tol_val: f32, max_ite_val: i16) void {
  tol = tol_val;
  max_ite = max_ite_val;
  device_loop = true;
  init(size);                        // ends in phase_done(), which activates STATE
}

task next_phase() void {
  if (phase == PH_INIT) {
    spmv_Ax();
  } else if (phase == PH_SPMV_AX) {
    residual();
  } else if (phase == PH_RESIDUAL or phase == PH_UPDATE_XR) {
    if (rho[0] > tol * tol and k < max_ite) {   // every PE sees the same rho: same decision
      update_p();
    } else {
      device_loop = false;
      sys_mod.unblock_cmd_stream();  // solve finished: the host's next command (the copies) can run
    }
  } else if (phase == PH_UPDATE_P) {
    spmv_Ap();
  } else if (phase == PH_SPMV_AP) {
    eta_dot();
  } else {                           // PH_ETA
    update_x_r_rho();
  }
}

Two loops, one program

The only difference between the loops is what phase_done() does next.

  • Host-driven. The host calls f_update_p, f_spmv_Ap, f_eta and f_update_x_r_rho one after another with launch(…, nonblock=False), then copies rho back and decides whether to go on. phase_done() calls unblock_cmd_stream(). launch() itself returns to Python at once; what waits is the host's next command (the next launch, or the copy of ρ), which memcpy holds back until every PE has unblocked the command stream, so no phase starts before the previous one has finished everywhere (Chapter 7). This is the SDK's run.py with kernel.csl, and it is how you would first port a CG written in numpy: the loop stays in Python.
  • Device-driven. The host makes one call, f_cg. Now phase_done() activates task STATE (next_phase), which looks at the phase that just finished and starts the next one. After the ⟨r, r⟩ allreduce it tests the stopping rule itself. Why activate a task instead of calling the next phase directly? When a library calls f_callback, it is still running inside one of its own tasks (the allreduce's state-entry task at its DONE state, the stencil's f_comm). Calling update_p() from there would start the next library operation, or re-enter the same library, before that task has returned. @activate(STATE) lets the library's task finish first; the task picker then starts the next phase cleanly (Chapter 5's state machines). The SDK's kernel_cg.csl does the same. That is the SDK's device_run.py with kernel_cg.csl.

The device loop decides when to stop without any extra message because the allreduce leaves the same ρ on every PE, so every PE takes the same branch at the same iteration. run.py checks that all W·H copies of the ρ history are identical. Unlike Lab 3's step chain, the iteration here is gated by the allreduce, a global barrier, rather than by neighbours. Each phase ends in exactly one callback, so one phase variable is enough to know where the loop is, where Lab 3 needed a pending count of four transfers, and no PE can run an iteration ahead.

# The matrix: 3-D Laplacian, 6 on the diagonal and -1 for each of the 6 neighbours,
# zero (Dirichlet) outside the H x W x Z box. Symmetric positive definite, so CG applies.
coeff = np.array([-1, -1, -1, -1, -1, -1, 6], dtype=np.float32)   # W E S N bottom top centre
def A(v):
    y = np.float32(6) * v
    for ax in range(3):
        sl = [slice(None)] * 3; sr = [slice(None)] * 3
        sl[ax] = slice(1, None); sr[ax] = slice(None, -1)
        y[tuple(sl)] -= v[tuple(sr)]; y[tuple(sr)] -= v[tuple(sl)]
    return y

b = np.random.default_rng(15).random((H, W, Z), dtype=np.float32)   # [py][px][z]
x0 = np.zeros_like(b)
tol = np.float32(args.eps * np.linalg.norm(b))

def cg_numpy(max_ite):                # the same recurrence, in f32
    x = x0.copy(); r = b - A(x); rho = np.vdot(r, r); hist = [rho]; k = 0
    while rho > tol * tol and k < max_ite:
        k += 1
        pp = r.copy() if k == 1 else r + (rho / rho_old) * pp
        w = A(pp); alpha = rho / np.vdot(pp, w)
        x = x + alpha * pp; r = r - alpha * w
        rho_old, rho = rho, np.vdot(r, r); hist.append(rho)
    return x, np.array(hist, dtype=np.float32)
HOST_ITE = min(args.host_ite, ITE)
ref = {'host': cg_numpy(HOST_ITE), 'device': cg_numpy(ITE)}

    out = np.zeros((h or H) * (w or W) * n, dtype=dt)
    rt.memcpy_d2h(out, rt.get_id(sym), 0, 0, w or W, h or H, n, **f32)

h2d('b', b, Z); h2d('coeff', np.broadcast_to(coeff, (H, W, 7)), 7)

    x = d2h('x', Z)
    th = d2h('t_hist', ITE + 1, np.uint32).astype(np.int64)

rt.stop()

Four things stand out.

  2. The allreduce costs as much as the SpMV, for two single-float sums. As the scaling section shows, that cost grows with the grid's side while the SpMV's does not.
  3. Every PE takes the same time per iteration. All 25 PEs measured exactly 4,574 cycles per iteration, but their allreduce share ranged from 1,898 to 2,126 Measured. The allreduce is a barrier: PEs that finish their own work early wait inside it.
  4. Profiling is not free. With PROFILE=0 the device loop takes 4,261 cycles per iteration on WSE-3 (3,782 on WSE-2), so the eleven mark() calls per iteration (seven in the phases, one in each of the four phase_done() calls) cost about 310–400 cycles, roughly 30–35 cycles each, 7–10% Measured. That is more than a bare timestamp read because each mark() also joins the counter words into a 32-bit time, subtracts the last stamp and adds the difference into a bucket in memory (Appendix C). Host loop or device loop

In the simulator the host loop costs 1,224 extra cycles per iteration on WSE-3 and about 1,140–1,150 on WSE-2 (run to run), essentially all of it in the control bucket: control rises by 1,262 cycles on WSE-3 while the axpy and allreduce buckets fall slightly Measured. The simulator charges only the device side of each launch: memcpy's command task decoding the RPC and the unblock_cmd_stream() at the end, five times per iteration (four launches and one copy of ρ). That is about 1,224 / 5 ≈ 245 device cycles per command Derived, the same fixed per-command cost that dominates small copies in Chapter 7's memcpy experiment. The host side costs nothing in simulated time, because the simulator has no network. With 15 host iterations instead of 3 the per-iteration figure is 5,783 instead of 5,798, and repeated 3-iteration runs gave 5,790–5,798, so it is stable to about 0.3% Measured; the device-loop figure repeated exactly.

On a real system each of those five commands crosses the network. Chapter 7 uses the SDK's figure of about 200 µs of overhead per transfer SDK 2.10.1. Five per iteration is about 1 ms, against 4,261 cycles ≈ 5 µs for the iteration itself at the SDK's 850 MHz, so a host-driven CG would spend about 99.5% of its time waiting for the host Derived. The simulator's 27% gap understates the real one by two orders of magnitude.

That model assumes every command is a full, synchronous round trip, which is how run.py drives it (nonblock=False). The obvious first improvement is to queue the four launches with nonblock=True and block only on the copy of ρ, which the host needs before it can decide whether to go on. If the 200 µs is mostly latency that overlaps, that leaves about one round trip per iteration; if it is per-command work, nothing is saved. So a non-blocking host loop costs somewhere between about 200 µs and 1 ms per iteration Derived, still 40 to 200 times the 5 µs iteration. For any iterative solver, put the loop on the device, and copy results back once at the end.

How it scales

Two knobs change the cost of an iteration: the grid of PEs (W × H) and the column on each PE (Z). They act on different phases.

Grid size. With Z = 5 fixed, the stencil, axpy and dot phases take the same cycles on every grid from 3 × 3 to 16 × 16: each PE does the same local work and talks to the same four neighbours. Only the allreduce grows Measured, WSE-3, 6 iterations each:

On WSE-2 the allreduce grows from 1,561 cycles at 5 × 5 to 2,705 at 12 × 12, about 82 cycles per PE of W + H against 94 on WSE-3 Measured. Halving the coefficients (two calls per iteration), each call costs about 50 cycles per PE along a row and 44 along a column Derived. A router hop costs 2 cycles on WSE-3 (Chapter 4), so distance is not what costs. In the row and column reduce stages each PE's message reaches the last PE separately, with its own send, switch-advance wavelet and fabric add, so the cost is per contributing PE, not per hop. That makes this allreduce linear in the grid's side, and serial.

Column length. With the grid fixed at 5 × 5, the allreduce stays at 1,898 cycles whatever Z is, and the stencil grows (Z is cells per PE; the last three columns are the stencil SpMV, the two local dots and the three axpys, in cycles per iteration) Measured, WSE-3:

Anatomy of one block: why a message costs ≈ 65 cycles here and ≈ 15 in Lab 3. Lab 3 issued its four single-wavelet transfers at once, each on its own microthread with its own completion task, so their latencies overlapped (Chapter 13). The library does every step one at a time. In lib/stencil_3d_7pts/wse3/pe.csl SDK 2.10.1:

  1. Task f_comm starts the block by activating the send task and the receive task.
  2. f_send sends one direction (east, then west, north, south) as an asynchronous @mov32 on microthread 3. Its completion re-activates f_send, which only then issues the next direction. Four sends strictly in series, plus one more run to note that the chain is done.
  3. f_recv does the same for the receives, one direction at a time in a fixed order (west, east, south, north), each an asynchronous @mov32 from the fabric into that direction's buffer.
  4. When both chains are done (count_send_recv ≥ 2), compute_and_next_send_recv() runs the four synchronous @fmacs of laplacian_xy() for this block and activates f_comm for the next one.

That is about 11 task runs, 8 transfer starts and 4 @fmacs starts per block, nearly all in series. At Lab 3's ≈ 15–20 cycles per task run or instruction start, about two dozen of them land near the measured 500–530 cycles per block Derived (an estimate, not a trace). The sends are serialised on one explicit microthread on purpose: it guarantees that two transfers never collide on a microthread, the failure that hung Lab 3's first version (Chapter 13, "How the SDK's stencils differ"). Chapter 13 measured this library on its own too: at Z = 200 on 5 × 5 PEs one SpMV took 4,206 cycles with one block per direction and 8,078 with ten Measured (Chapter 13 review run, WSE-3), the same per-message law as the table above.

What BLOCK costs, and how long a column can be. BLOCK_SIZE sizes the library's four receive buffers, one per direction (west_buf … north_buf in wse3/pe.csl), so they take 16·BLOCK bytes: 1.6 KB at BLOCK = 100 Derived. That 1.6 KB buys a 4.9× faster iteration at Z = 100 (32,004 → 6,573 cycles). We measured the cap by compiling ever-longer columns on a 5 × 5 grid: the program links up to Z ≈ 1,835 cells per PE on WSE-3 with BLOCK = 2 (≈ 1,757 with BLOCK = 100, the 1.6 KB difference) and ≈ 1,978 on WSE-2, and fails above with ran out of PE memory Measured. Five vectors at 4 bytes take 20 bytes per cell, so that is ≈ 37 KB of vectors after the code of three modules. A minimal program leaves about 44.5 KB for arrays on WSE-3 (Chapter 3), so the three modules' code, buffers and task table, plus this program's history arrays, cost about 8 KB more than a minimal program Derived. BLOCK is therefore a latency knob that is nearly free in memory. The SDK ships BLOCK_SIZE:2 SDK 2.10.1, and this program keeps that default as BLOCK. A small block does not buy overlap: the library finishes all of a block's sends and receives before it runs that block's @fmacs (anatomy above). One untested reason for the small default is queue depth: memcpy gives input queues 4–7, the ones the stencil receives on, a depth of 2 wavelets SDK 2.10.1, so a 2-wavelet block fits in one queue Unverified. At ≈ 1,800 cells per PE a whole wafer of about 900,000 PEs holds about 1.6 × 10⁹ unknowns Derived, the billion the problem section said you could not store as a matrix.

The two local dots are scalar @map loops (Chapter 6): @map calls its scalar function once per element, so they cost together about 10 cycles per cell, so at Z = 100 they cost 1,115 cycles: more than half the whole one-block stencil (1,957) and more than the three axpys (898, the slow case explained next) Measured. A DSD-based dot would probably cost far less per cell; we did not try one. At BLOCK=100 the centre PE's allreduce also rose from 1,898 to 2,292 cycles. Over all 25 PEs it ranged from 1,951 to 2,438, against 1,898–2,236 at BLOCK = 2 Measured: the fastest PE's allreduce barely moved, so the extra cycles on the centre PE are mostly waiting at the barrier for PEs whose stencil phase finished later.

Why the axpy column jumps. The axpy cost does not grow smoothly with Z: about 5.9 cycles per extra cell from Z = 5 to 20, 2.4 from 20 to 50, and 7.7 from 50 to 100 (table above). A check run at Z = 22 gave 408 cycles against 441 at Z = 20: two more cells, fewer cycles Measured (round-4 audit run, WSE-3, 5 × 5, 6 iterations). The cause is the operand rule of Chapter 6: an f32 @fmacs runs at 1 element per cycle, but at 2 cycles per element when its two source streams start at addresses equal mod 16 bytes (the same bank). The five vectors are [MAX_ZDIM]f32 arrays, and here MAX_ZDIM = Z. If the compiler places them back to back, as the numbers suggest, the x and r updates read vectors 4·Z bytes apart and the p update (p and r) 8·Z bytes apart. That makes 3, 6, 4 and 6 cycles per cell for the three axpys at Z = 5, 20, 50 and 100, and 4 at Z = 22, which predicts steps of 7, 2.7 and 8 cycles per cell and −32 cycles from Z = 20 to 22, against the measured 5.9, 2.4, 7.7 and −33 Derived. So at Z = 100 the axpys run at the slow rate, and an odd MAX_ZDIM (pad the column by one cell) should make all three fast, roughly 300 cycles fewer per iteration Derived, not measured. Pad and measure.

How far from peak. One iteration does about 23 flops per cell: 13 in the stencil, 2 × 2 in the dots, 3 × 2 in the axpys. The default run does 5 × 23 = 115 flops per PE in 4,574 cycles, about 0.025 flops per cycle, or 1.3% of the 2 flops per cycle of one f32 multiply-add per cycle Derived. At Z = 100 with BLOCK = 100 it is about 2,300 flops in 6,573 cycles, about 17% Derived. The default lab sits deep in the latency-bound regime; real stencil codes put hundreds to thousands of cells on each PE.

CG usually beats its bound because the bound uses only κ, the ratio of the extreme eigenvalues. CG adapts to the whole distribution of eigenvalues (and to which eigenvectors b contains): once it has resolved the extreme ones, it speeds up.

f32 at scale

The bounds and the stopping rule assume exact arithmetic. CG updates r by recurrence (r −= α w), and in f32 that recursive residual drifts away from the true one, b − A x, as κ grows. In the same numpy f32 recurrence the recursive residual reaches 1e-5 on every cube, but the true residual |b − A x|/|b| is 5.7e-6 at 5³, 2.0e-5 at 24³ and 8.9e-5 at 48³ Derived. On this lab's sizes the two agree (the run prints both). At wafer scale (κ ≈ 12,000 for 950 × 950 × 100) expect worse: check the true residual, recompute r = b − A x every so often (residual replacement), and consider accumulating the dot products in higher precision. The order of the allreduce's sum also changes the rounding, so a different grid shape gives slightly different iterates.

The scaling law of this solver

Two cases, both driven by the allreduce.

  • Wider grid, fixed column (weak scaling: W = H = N, Z fixed). The SpMV, dots and axpys cost the same on every grid; the allreduce grows like N. The iteration count rises at first and then levels off (about 40 at Z = 5, table above). So the time per solve grows linearly with the side, all of it through the allreduce. At 16 × 16 PEs the two allreduces already take 60% of an iteration (3,966 of 6,650 cycles) Measured.
  • Growing cube (W = H = Z = N). Now the iterations grow like N too, and so does the stencil (Z = N cells per PE). Time per solve grows like N², asymptotically, once the allreduce dominates; at the sizes we ran, the other phases still matter.

Extrapolated to a whole wafer (about 900,000 PEs Vendor, say 950 × 950; the SDK-visible CS-3 fabric is not published, and CS-2's is about 743 × 992 ≈ 737k PEs, Chapter 13) the fit gives roughly 180,000 cycles of allreduce per iteration, against about 2,700 cycles of other work at Z = 5 and about 30,000 at Z = 100 Derived. That is an extrapolation sixty times beyond the largest grid we simulated, and it describes this library, not the fabric. The library reduces one PE's value at a time, about 50 cycles per PE per call. The course's own measurements give lower costs per PE for one 950-PE row stage Derived:

Hand-built reductions on real hardware get close to that floor. The SC20 CS-1 paper (Rocki et al., arXiv:2010.03660) reports a scalar AllReduce over about 380,000 cores in under 1.5 µs, with a cycle count only about 10% above the fabric's diameter Indep, SC20. On a fabric about √380,000 ≈ 620 cores on a side the diameter is about 1,200 hops, so that is roughly 1,300–1,400 cycles, against this library's extrapolated 90,000 per call Derived. Its design is a streaming chain into two receiving cores per row, because "a core can add two 32-bit quantities per cycle but can receive only one from the fabric". That is the same streaming-versus-one-message-per-PE difference as between Chapter 12's chain and this library. The same paper's BiCGStab ran at about a third of peak (Chapter 18), so well-built global reductions need not dominate at wafer scale.

So algorithms for big wafers attack the global sums: faster reductions (streaming chains, trees whose cost grows with hops rather than with PEs), more cells per PE so the local work outweighs the sum, CG variants that merge the two dot products into one reduction per iteration (Chronopoulos–Gear, exercise 3), and pipelined CG (Ghysels–Vanroose), which overlaps the reduction with the next SpMV. Overlap needs every slot of the two libraries disjoint on both chips (the WSE-2 shared-queue experiment above would then break) and a phase_done() that waits for both, which is exactly the two-bit join of Chapter 14 (block one task, activate it from each finished operation). Preconditioning is no shortcut here: the SDK's preconditioned CG uses Jacobi SDK 2.10.1, and with a constant diagonal of 6 Jacobi only rescales A, leaving κ and the iteration count unchanged. Stronger preconditioners (multigrid, incomplete factorisations) need more global or recursive communication, which meets the same cost.

Check yourself

Which CG steps need data from more than one PE, and what kind?

The stencil (w = A p) needs the four neighbouring PEs' columns. The two dot products need every PE: a local sum, then an allreduce. The axpys are local.

Why does no library in this program choose its own colors or task IDs?

Several modules share one PE. Only the top level sees all of them, so it hands each its slots as parameters and keeps the ledger. A clash on a color, task ID or initialized queue is then a compile error at a single place.

How does each PE know when to stop the device loop without asking the host?

The allreduce leaves the same ρ = ⟨r, r⟩ on every PE, so every PE evaluates the same test with the same values and stops at the same iteration.

All 25 PEs take exactly 4,574 cycles per iteration, but their allreduce times differ by 228 cycles. Why?

The allreduce is a barrier: no PE gets the sum back until all have contributed. A PE that reaches it early waits inside it, so the waiting shows up in its allreduce bucket and the iteration time comes out the same everywhere.

The simulator says the host loop costs 27% more per iteration. Why is that misleading for a real system?

The simulator only charges the device's part of each launch. On a real system each of the five host commands per iteration (four launches and one copy of ρ) has about 200 µs of overhead: 5 × 200 µs ≈ 1 ms, against 4,261 cycles / 850 MHz ≈ 5 µs for the iteration itself. So the host loop is roughly 200 times slower, not 27%. Non-blocking launches can cut that to about one round trip, still ~40×.

You double both W and H, keeping Z = 5. What happens to the time per iteration, and to the time per solve?

Per iteration only the allreduce grows, by about 100·W + 88·H more cycles. The iteration count rises only a little and then levels off: with Z fixed, κ is capped (about 44 for Z = 5), so going from 5 × 5 to 10 × 10 takes CG from 15 to 24 iterations, and no grid needs more than about 40. So the time per solve grows roughly linearly with the side, through the allreduce. Only if Z grows too (a growing cube) do the iterations grow like the side as well, giving roughly the square.

You copy the SDK's stencil library into lib/ and cslc fails with Unable to open ./wse3/pe.csl. Why, and what is the fix?

cslc resolves an import path relative to the directory of the top-level layout.csl, not the importing file, so the dispatch file's "wse3/pe.csl" is looked for next to the layout. Change the path to "lib/stencil_3d_7pts/wse3/pe.csl" (or pass --import-path; the container only mounts the current directory).

At Z = 100, what does BLOCK = 100 instead of 2 save, and what does it cost?

It saves about 26,000 stencil cycles per iteration (27,782 → 1,957), because each PE sends one message per direction instead of 50. It costs four receive buffers of BLOCK floats, 16·BLOCK bytes ≈ 1.6 KB, which lowers the longest column that fits by about 80 cells.
