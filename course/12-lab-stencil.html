Lab 3: a heat stencil, measured

The capstone program simulates heat flowing along a rod split across a row of PEs. It needs everything from Part II: two-way neighbour traffic on four colors, asynchronous transfers, completion tasks counted into a step, and an iterative state machine. Then we time each step inside the kernel and take the cost apart, cycle by cycle.

After this lab you can

  • Decompose a grid over PEs with ghost cells and a halo exchange.
  • Drive an iterative algorithm entirely from tasks, and explain why it cannot race or hang.
  • Time a kernel with the on-tile timestamp counter, fit a performance model, and say where each cycle goes.

The problem

Explicit finite differences for the 1-D heat equation: every timestep, each cell moves toward the average of its neighbours,

u'[i] = u[i] + α · (u[i-1] − 2·u[i] + u[i+1])        α = 0.25, ends held at 1.0 and 0.0

The rod has P × n cells. PE k owns cells k·n … k·n+n−1 and stores them in u[1..n], with ghost cells u[0] and u[n+1] holding copies of its neighbours' edge cells. Each step, every PE sends its first cell west and its last cell east, receives the neighbours' edge cells into its ghosts, then updates.

The code

The layout gives every PE its four colors by parity, exactly as in the figure, and only routes the directions a PE actually has: the first PE has no west neighbour (has_w = false) and the last has no east neighbour.

course/programs/04-heat-stencil/layout.csl
// 04-heat-stencil: explicit 1-D heat equation  u' = u + alpha * (u[i-1] - 2u[i] + u[i+1])
// on a rod split across P PEs (n cells each). Every timestep each PE swaps its
// edge cells with both neighbours (halo exchange), then updates its cells.
// Teaches: bidirectional neighbour traffic, 4 colors, async-op completion
// counting with local tasks, iterative task-driven control flow.
param P: i16;
param n: i16;

// Eastward traffic uses E0/E1, westward W0/W1, alternating by column parity.
const E0: color = @get_color(0);
const E1: color = @get_color(1);
const W0: color = @get_color(2);
const W1: color = @get_color(3);

const memcpy = @import_module("<memcpy/get_params>", .{ .width = P, .height = 1 });

layout {
  @set_rectangle(P, 1);
  for (@range(i16, P)) |x| {
    const even = (x % 2 == 0);
    const send_e = if (even) E0 else E1;   // I send my last cell EAST on this
    const recv_w = if (even) E1 else E0;   // my west neighbour's send_e
    const send_w = if (even) W0 else W1;   // I send my first cell WEST on this
    const recv_e = if (even) W1 else W0;   // my east neighbour's send_w
    const has_w = x > 0;
    const has_e = x < P - 1;

    @set_tile_code(x, 0, "pe_program.csl", .{
      .memcpy_params = memcpy.get_params(x), .n = n, .has_w = has_w, .has_e = has_e,
      .send_e = send_e, .recv_w = recv_w, .send_w = send_w, .recv_e = recv_e });

    if (has_e) {
      @set_color_config(x, 0, send_e, .{ .routes = .{ .rx = .{RAMP}, .tx = .{EAST} } });
      @set_color_config(x, 0, recv_e, .{ .routes = .{ .rx = .{EAST}, .tx = .{RAMP} } });
    }
    if (has_w) {
      @set_color_config(x, 0, send_w, .{ .routes = .{ .rx = .{RAMP}, .tx = .{WEST} } });
      @set_color_config(x, 0, recv_w, .{ .routes = .{ .rx = .{WEST}, .tx = .{RAMP} } });
    }
  }
  @export_name("u", [*]f32, true);
  @export_name("tsc", [*]u16, true);        // TSC start/end, 6 x u16 per PE
  @export_name("run", fn(u32, f32)void);    // (timesteps, alpha)
  @export_name("pack", fn()void);           // copy timestamps into tsc
}

The PE program uses hardware queues 2–5 (queues 0 and 1 belong to memcpy, Chapter 5) and local task IDs 10–13, inside the 8–20 range that is safe for user tasks. It also carries a few lines of timing code, which the measurement section explains.

course/programs/04-heat-stencil/pe_program.csl
param memcpy_params;
param n: i16;
param has_w: bool;
param has_e: bool;
param send_e: color;
param recv_w: color;
param send_w: color;
param recv_e: color;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// In-kernel timing with the tile's timestamp counter (TSC), as the SDK
// benchmarks do: t0 when run() starts, t1 just before the last step unblocks
// the host. Each timestamp is 48 bits in three u16 words.
const timestamp = @import_module("<time>");
var t0 = @zeros([3]u16);
var t1 = @zeros([3]u16);
var tsc = @zeros([6]u16);              // t0 then t1, exported for the host
var tsc_ptr: [*]u16 = &tsc;

// u[0] and u[n+1] are ghost cells holding the neighbours' edge values
// (or the fixed boundary temperature at the two ends of the rod).
var u: [n + 2]f32;
var u_ptr: [*]f32 = &u;
var lap: [n]f32;

const left  = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i] });
const mid   = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i + 1] });
const right = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i + 2] });
const lap_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> lap[i] });

const first_cell = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{1} -> u[1] });
const last_cell  = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{1} -> u[n] });
const ghost_w    = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{1} -> u[0] });
const ghost_e    = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{1} -> u[n + 1] });

// One hardware queue per direction (WSE-3 binds each queue to one color).
// Queues 0/1 belong to memcpy. All four IDs differ: an async fabric op runs on
// the microthread whose ID equals its queue ID (always on WSE-2; the default on
// WSE-3 unless you pass .ut_id), and two concurrent ops must not share a
// microthread (output queue 2 + input queue 2 would both use microthread 2:
// the simulator aborts with "trying to term ut_instr[..], but it's not ours").
const oq_e = @get_output_queue(2);
const oq_w = @get_output_queue(3);
const iq_w = @get_input_queue(4);
const iq_e = @get_input_queue(5);

fn fabout(comptime q: output_queue, comptime c: color) fabout_dsd {
  return @get_dsd(fabout_dsd, if (@is_arch("wse3")) .{ .extent = 1, .output_queue = q }
                              else .{ .extent = 1, .output_queue = q, .fabric_color = c });
}
const to_e   = fabout(oq_e, send_e);
const to_w   = fabout(oq_w, send_w);
const from_w = @get_dsd(fabin_dsd, .{ .extent = 1, .input_queue = iq_w });
const from_e = @get_dsd(fabin_dsd, .{ .extent = 1, .input_queue = iq_e });

// Each async op activates its own local task when it completes. (Activating
// one task several times before it runs would collapse into a single run,
// so we use one task per op and count.)
const done_se: local_task_id = @get_local_task_id(10);
const done_sw: local_task_id = @get_local_task_id(11);
const done_rw: local_task_id = @get_local_task_id(12);
const done_re: local_task_id = @get_local_task_id(13);

const ops_per_step: i16 = (if (has_e) 2 else 0) + (if (has_w) 2 else 0);
var pending: i16 = 0;
var steps: u32 = 0;
var step: u32 = 0;
var alpha: f32 = 0.0;

fn start_step() void {
  pending = ops_per_step;
  if (pending == 0) { update(); return; }            // P == 1: no neighbours
  if (has_e) {
    @fmovs(to_e, last_cell, .{ .async = true, .activate = done_se });   // send u[n] east
    @fmovs(ghost_e, from_e, .{ .async = true, .activate = done_re });   // recv u[n+1]
  }
  if (has_w) {
    @fmovs(to_w, first_cell, .{ .async = true, .activate = done_sw });  // send u[1] west
    @fmovs(ghost_w, from_w, .{ .async = true, .activate = done_rw });   // recv u[0]
  }
}

fn update() void {
  // lap = u[i-1] + u[i+1] - 2 u[i];   u[i] += alpha * lap   (3 vector instructions)
  @fadds(lap_dsd, left, right);
  @fmacs(lap_dsd, lap_dsd, mid, -2.0);
  @fmacs(mid, mid, lap_dsd, alpha);
  step += 1;
  if (step < steps) start_step() else finish();
}

// Keep this tiny: helpers are inlined into every completion task, so code
// here makes every step slower. Copying the timestamps is done in pack().
fn finish() void {
  timestamp.get_timestamp(&t1);
  sys_mod.unblock_cmd_stream();
}

fn op_done() void {
  pending -= 1;
  if (pending == 0) update();      // all 4 halo transfers finished -> compute
}
task t_se() void { op_done(); }
task t_sw() void { op_done(); }
task t_rw() void { op_done(); }
task t_re() void { op_done(); }

fn run(T: u32, a: f32) void {
  steps = T; step = 0; alpha = a;
  timestamp.enable_tsc();
  timestamp.get_timestamp(&t0);
  if (steps == 0) { finish(); } else { start_step(); }
}

// Separate RPC, called after run(): copy both timestamps into the export.
fn pack() void {
  tsc[0] = t0[0]; tsc[1] = t0[1]; tsc[2] = t0[2];
  tsc[3] = t1[0]; tsc[4] = t1[1]; tsc[5] = t1[2];
  sys_mod.unblock_cmd_stream();
}

comptime {
  @bind_local_task(t_se, done_se);
  @bind_local_task(t_sw, done_sw);
  @bind_local_task(t_rw, done_rw);
  @bind_local_task(t_re, done_re);
  if (has_e) {
    @initialize_queue(oq_e, if (@is_arch("wse3")) .{ .color = send_e } else .{});
    @initialize_queue(iq_e, .{ .color = recv_e });
  }
  if (has_w) {
    @initialize_queue(oq_w, if (@is_arch("wse3")) .{ .color = send_w } else .{});
    @initialize_queue(iq_w, .{ .color = recv_w });
  }
  @export_symbol(u_ptr, "u");
  @export_symbol(tsc_ptr, "tsc");
  @export_symbol(run);
  @export_symbol(pack);
}

One timestep, step by step

There is no loop anywhere in pe_program.csl. The iteration is a chain of tasks that keeps re-arming itself:

  1. Host → run(T, α). memcpy's command task calls this RPC (Chapter 7). It stores T and α, reads the timestamp counter into t0, and calls start_step(). Then it returns without unblocking the command stream, so the host's launch(..., nonblock=False) keeps waiting.
  2. start_step() sets pending = ops_per_step (4 for an interior PE, 2 for an end PE) and launches up to four asynchronous @fmovs: send u[n] east, receive into u[n+1], send u[1] west, receive into u[0]. Each moves a single wavelet (.extent = 1), each runs on its own microthread, and each names its own completion task with .activate. The function returns at once and the CE goes back to the task picker.
  3. Completions. As each transfer finishes, the hardware activates its task (t_se, t_sw, t_rw or t_re). The task runs and calls op_done(), which decrements pending. These four are the only tasks in the program; start_step, update, op_done and finish are ordinary functions that run inside whichever task called them.
  4. Last completion → update(). When pending reaches 0, both ghosts hold fresh neighbour values and both sends have left. Three vector (DSD) instructions compute lap and update u[1..n].
  5. Next step or finish. update() calls start_step() again, back to step 2. That is not deep recursion: start_step() only issues four asynchronous operations and returns, so the task ends. After the last step update() calls finish(), which reads t1 and calls unblock_cmd_stream(). Only then does the host's launch return and the device-to-host copy of u run. That is why the host can never read a half-finished rod.

The ends of the rod. PE 0 has has_w = false, so it never issues a west receive and never writes u[0]. The 1.0 the host copied there stays put, and update() reads it every step: that is the fixed (Dirichlet) boundary. The last PE's u[n+1] = 0.0 works the same way. With STEPS=0, run() calls finish() directly and no step machinery runs.

Why the step logic looks like this
  • One task per operation. Activating a task sets a single bit (Chapter 5). If all four completions activated the same task, two of them could land before it ran, giving one run instead of two. pending would then stop at 1 or more and the program would hang. Four tasks, one per operation, cannot collapse.
  • Sends are counted too. update() overwrites u[1] and u[n], the cells the sends read. Waiting for the sends to complete guarantees each neighbour gets this step's value, and that the output queue is free before the next step's send reuses it.
  • No race on the ghosts. If a neighbour finishes first and sends its next edge cell early, that wavelet waits in this PE's input queue (and, if needed, in the routers behind it) until this PE issues its next receive. The fabric is lossless with back-pressure, so neighbours stay at most one step apart without any barrier.
  • Counter first. pending is set before any operation is launched. A completion task cannot run while start_step() is still running (one task at a time on the CE), but setting the counter first keeps the code correct even if that ever changes.

The host script uploads each PE's slice with its ghosts, launches run, reads the rod back, then calls a second RPC, pack, to fetch the timestamps. It checks the device result against numpy.

course/programs/04-heat-stencil/run.py
#!/usr/bin/env cs_python
import argparse, json
import numpy as np
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder  # pylint: disable=no-name-in-module

p = argparse.ArgumentParser(); p.add_argument('--name'); p.add_argument('--cmaddr')
p.add_argument('--steps', type=int, default=50); p.add_argument('--alpha', type=float, default=0.25)
args = p.parse_args()
prm = json.load(open(f"{args.name}/out.json"))['params']
P, n = int(prm['P']), int(prm['n'])
L = P * n

# Global rod with fixed boundary temperatures: g[0] = 1.0 (hot end), g[L+1] = 0.0
g = np.zeros(L + 2, dtype=np.float32); g[0] = 1.0
g[1 + L // 2 - 2 : 1 + L // 2 + 2] = 5.0                 # a hot spot in the middle

# Each PE gets its n cells plus the two neighbouring cells as ghosts.
local = np.stack([g[x * n : x * n + n + 2] for x in range(P)]).astype(np.float32)

rt = SdkRuntime(args.name, cmaddr=args.cmaddr)
us = rt.get_id('u')
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
rt.memcpy_h2d(us, local.ravel(), 0, 0, P, 1, n + 2, **kw)
rt.launch('run', np.uint32(args.steps), np.float32(args.alpha), nonblock=False)
res = np.zeros(P * (n + 2), dtype=np.float32)
rt.memcpy_d2h(res, us, 0, 0, P, 1, n + 2, **kw)
# Kernel timing: read each PE's TSC at run() start and at the final unblock.
# Each PE's counter starts when the launch reaches it, so only compare two
# readings from the SAME PE; we report one interior PE.
rt.launch('pack', nonblock=False)
tw = np.zeros(P * 6, dtype=np.uint32)        # one u16 per 32-bit word
rt.memcpy_d2h(tw, rt.get_id('tsc'), 0, 0, P, 1, 6, streaming=False,
              order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_16BIT, nonblock=False)
rt.stop()
tw = (tw & 0xffff).astype(np.int64).reshape(P, 6)
t_start = tw[:, 0] | (tw[:, 1] << 16) | (tw[:, 2] << 32)
t_end = tw[:, 3] | (tw[:, 4] << 16) | (tw[:, 5] << 32)
pe = 1 if P > 2 else 0                       # an interior PE when there is one
kern = int(t_end[pe] - t_start[pe])
device = res.reshape(P, n + 2)[:, 1:-1].ravel()

# Reference: identical f32 arithmetic on the host
ref = g.copy(); a = np.float32(args.alpha)
for _ in range(args.steps):
    lap = (ref[:-2] + ref[2:]) + np.float32(-2.0) * ref[1:-1]
    ref[1:-1] = ref[1:-1] + a * lap
np.testing.assert_allclose(device, ref[1:-1], rtol=1e-5, atol=1e-6)
print(f"{P} PEs x {n} cells, {args.steps} steps; temperature profile (every {max(1, L // 16)}th cell):")
print(np.array2string(device[:: max(1, L // 16)], precision=3))
print(f"kernel time on PE {pe} (TSC): {kern} cycles for {args.steps} steps"
      + (f" = {kern / args.steps:.1f} cycles per step" if args.steps else ""))
print("SUCCESS!")

The hang

Chapters 3 and 5 described this failure; here is the code that caused it. The first version used output queues 2/3 and input queues 2/3. It compiled, then cs_python never returned. sim.log showed that the simulator had already stopped with a fatal error: FATAL: P5.1: … trying to term ut_instr[3], but it's not ours, followed by Stopping due to fatal error, at cycle 2,123 on WSE-3 and 2,125 on WSE-2 (2,367 and 2,148 with this chapter's timing code added) Measured. It fails the same way on both chips.

The reason: an asynchronous fabric operation runs on the microthread whose ID equals its queue ID. On WSE-2 that rule is fixed; on WSE-3 it is the default when you give no .ut_id. So the east send (output queue 2) and the west receive (input queue 2) both claimed microthread 2, and the west send and east receive both claimed microthread 3. Moving the input queues to 4/5 fixes it on both chips. On WSE-3 only, keeping queues 2/3 and adding .ut_id = @get_ut_id(4) / @get_ut_id(5) to the two receives also fixes it Measured.

Rule: give every concurrently active fabric operation its own microthread, and when a run hangs, read sim.log first. Try it: change @get_input_queue(4)/(5) back to 2/3, rerun, kill the hung host script, and search sim.log for FATAL. The timeline below replays the clash.

Measuring a timestep

Time it inside the kernel

The SDK's own stencil benchmarks time kernels with each tile's timestamp counter (TSC), and so does this program. run() calls timestamp.enable_tsc() and get_timestamp(&t0); finish() calls get_timestamp(&t1) just before it unblocks the host. A timestamp is 48 bits in three u16 words. A separate RPC, pack(), copies the six words into an exported array, and the host reads them with a 16-bit memcpy (each u16 arrives in the low half of a 32-bit word, Chapter 3) and reassembles w0 | w1<<16 | w2<<32.

Two rules. First, only subtract readings from the same PE: each PE's counter starts when the launch reaches it, so counters on different PEs are not aligned. The program reports PE 1, an interior PE. Second, one run's t1 − t0 divided by the step count includes a few dozen cycles of start-up (entering run(), the first issue, the final timestamp), which is why the output above shows 131.0 rather than 130.2. For the exact per-step cost, run two step counts and take the slope:

TSC readings repeat to the cycle across reruns and machine load Measured.

Why not difference the simulator's total cycles?

Every run also writes sim_stats.json, whose cycle_count covers the whole simulation, host transfers included. Differencing two totals looks like it should isolate the kernel, but it is noisy. The total includes cycles where the fabric sits idle waiting for the host process, so it moves with host load. In this lab's own runs, the identical 10-step build at P = 8, n = 4 reported 5,260 cycles on a quiet machine and 8,905 on a loaded one (idle_ce_cycles 50 vs 3,688), while its TSC kernel time was 1,029 both times Measured. A 0-step baseline is worse still: run() skips the step machinery, the first few steps hide under the fixed launch and readback latency, and the 0-step total itself varied by hundreds of cycles between identical runs. Use whole-run totals for whole-run questions, and the TSC for the kernel.

The inlining trap

CSL inlines helper functions into every task that calls them. finish() is called from update(), which is called from op_done(), which sits inside all four completion tasks. So code that runs once, at the last step, still makes every task bigger and every step slower. Copying the six timestamp words inside finish() instead of in a separate RPC raised the cost from 130.2 to 167.0 cycles per step Measured; each completion task grew from 176 to 212 bytes in the ELF (readelf -sW out/bin/out_3_0.elf). Moving the copy into pack(), the SDK's own pattern, restored 130. Keep instrumentation and epilogue code out of the hot tasks.

What the numbers say

  • About 90 cycles per step, plus 2.5 per cell. On WSE-3 the three points fit cycles/step = 90.2 + 2.5·n exactly (100.2, 130.2, 250.2). The 2.5 per cell is the three vector instructions streaming at their measured rates: @fadds moves 2 f32 elements per cycle on WSE-3 (0.5 cycles per cell), and each @fmacs moves 1 per cycle (1 + 1). Keeping only the @fadds leaves a slope of exactly 0.5 cycles per cell, and keeping only one @fmacs leaves exactly 1.0 Measured, on both chips.
  • Weak scaling is flat. 8 PEs and 16 PEs cost the same per step (130.2 vs 130.8; across the interior PEs of the 16-PE row the slope ranges 130.2–130.8). Every PE talks only to its neighbours, so adding PEs adds no work to anyone. This is the property that lets a stencil scale to the whole wafer, hundreds of thousands of PEs.
  • P = 2 is cheaper (101.0) because both PEs are ends with one neighbour: two transfers per step instead of four, saving 29 cycles. With P ≥ 3 the end PEs are also cheaper, but it does not help: each PE waits for its neighbours' wavelets, so the whole row moves at the pace of its interior PEs.
  • WSE-2 and WSE-3 land within 3 % (134.1 vs 130.2), but with a different split. On WSE-2 the per-step part is larger (≈94 vs 90; ≈80 vs 71 with the vector instructions removed) and the compute is slightly cheaper (54 vs 59 cycles at n = 16), because each vector instruction starts in about 5 cycles instead of 6. The per-cell slope is 2.5 on both: in this kernel @fadds streams 2 elements per cycle on WSE-2 too Measured. (Chapter 6's isolated measurement found 1 per cycle on WSE-2; the operand pattern here differs, and we have not isolated why.) f32 work gains nothing from WSE-3's wider FP16 SIMD.

Where the 90 cycles go

Removing pieces of the program one at a time takes the fixed part apart Measured → Derived, WSE-3, n = 16:

  • With the three vector instructions removed, a step costs 71.2: four transfers, four completion tasks, and the step bookkeeping.
  • Going from four transfers to two (P = 2) saves 29.2, so each async transfer costs ≈14.6 cycles including its completion task and op_done(). Four of them make 58.4, which leaves ≈13 cycles of step bookkeeping (the update()/start_step() call chain and the branch).
  • The compute at n = 16 is 130.2 − 71.2 = 59 = 40 (2.5·16 streaming) + ≈19 of start-up, about 6 per vector instruction. Keeping one instruction at a time confirms it: @fadds alone adds 8 + 6 cycles at n = 16 and one @fmacs adds 16 + 6 Measured. About a fifth of the "fixed" cost is therefore compute start-up, not communication. (Chapter 6 measured about 15 cycles to start an isolated op; inside this task the three consecutive instructions start faster. We have not isolated why.)

Almost none of this is wire time: a single wavelet crosses one hop in a cycle or two. The cost is the CE running a task for each transfer that finishes, one at a time, plus a few cycles to start each vector instruction. Halo width confirms it: sending 4 or 16 wavelets per direction instead of 1 costs only about 1 cycle per extra word, against ≈14.6 per extra message Measured (review measurements, TSC). Fewer, larger messages and fewer, longer instructions are the levers.

Use the model

The bar splits one WSE-3 step of 90 + 2.5·n cycles into its parts. The curve (log scale) bends from "flat at 90" to "proportional to n". The 850 MHz clock is the SDK benchmarks' own assumption; no official WSE-3 clock is published. Whole-wafer figures are Derived (see caveats below).

The lesson is surface-to-volume. With 16 cells per PE, about 70 % of each step is messages, tasks and instruction start-up. With thousands of cells per PE, compute dominates. Memory caps n: u and lap take 8 bytes per cell, and cslc links this program up to about n = 5,450 on WSE-3 (5,500 without the timing code) and fails above that with "ran out of PE memory"; WSE-2 fits about 5,650 Measured. That is ≈43 KB of arrays, after code, the task table and the memcpy runtime.

Does overlapping communication help?

On a GPU or with MPI you would compute the interior while the halo is in flight. Measured here, it makes things slower. A correct version that computes the interior Laplacian (n − 2 cells, two vector instructions) right after issuing the four transfers, then the two edge Laplacians with a 2-element strided DSD once the ghosts arrive, then one @fmacs over all n cells, costs 178.0 cycles per step against 130.2 Measured, and still matches numpy. There is almost no latency to hide: the four completion tasks already run back to back, and they cannot run at all while the CE is busy with the interior instructions. Meanwhile the change added two vector instructions (≈6 cycles each to start) and made every inlined completion task larger. Overlap pays off when transfers are long (many wavelets per message), or when the receive itself does the arithmetic.

Scaling up Derived

Whole wafer. A CS-2's SDK-visible fabric is 750 × 994, and the program rectangle must be at least 7 columns narrower and 2 rows shorter, so about 743 × 992 ≈ 737k PEs SDK. With 90 + 2.5·n cycles per step at 850 MHz and 5 flops per cell (one add, two multiply-adds):

  • n = 16: 130 cycles = 0.15 µs per step, 6.5 M steps/s on 11.8 M cells, ≈0.38 PFLOP/s f32.
  • n = 5,450: ≈13,700 cycles = 16 µs per step on 4 G cells, ≈1.2 PFLOP/s, close to the 2 flops/cycle/PE × 737k × 0.85 GHz ≈ 1.25 PFLOP/s that the 2.5-cycle slope allows.

Caveats: these are simulator cycles and an assumed clock; WSE-3's user-visible fabric size is not published (its 900k-core figure is Vendor); a 1-D chain across a 2-D wafer must snake back and forth, so the turn PEs need north/south routes (still one hop, so the model should hold, but the layout code changes); host I/O is excluded; and a 1-D rod is a toy, since real codes are 3-D pencils. For comparison, a CS-1 BiCGSTAB solve on a 7-point stencil reached about 0.86 PFLOP/s, roughly a third of peak Measured by Cerebras/NETL authors, arXiv:2010.03660.

2-D and 3-D. A 2-D tile of n × m cells needs 4 messages per step and 8 colors (4 directions × 2 parities); its east/west edges are strided columns (a mem1d_dsd with stride n). The constants above predict roughly 4 × 14.6 + 13 + about 1 cycle per edge word + 5 instructions × (6 + the streaming cost). On WSE-3, eight concurrent async operations would need eight microthreads beyond memcpy's, which is why the 7-point library serialises its sends.

Check yourself

Why can't the four completions share one task that decrements pending?

Activation is a single bit. Two completions that land before the task runs give one run, so pending would never reach 0 and the program would hang.

PE 3 finishes step 7 before PE 4. What happens to the edge cell PE 3 sends east for step 8?

It waits in PE 4's input queue (and, if needed, in the routers behind it) until PE 4 issues its step-8 receive. Back-pressure keeps neighbours at most one step apart.

Why does the host's launch('run', …) return only after the last step?

run() returns without calling unblock_cmd_stream(). Only finish(), reached from the last update(), unblocks the command stream, and nonblock=False waits for that.

You subtract PE 3's start timestamp from PE 5's end timestamp. What is wrong?

Each PE's counter starts when the launch reaches it, so readings from different PEs are not on the same clock. Subtract readings from the same PE.

At n = 16, roughly how many of the 130 cycles are wire time?

Almost none. About 58 are four transfers with their completion tasks, 13 are bookkeeping, 19 are instruction start-up and 40 are streaming the 16 cells through three vector instructions.

Why did overlapping the interior update with the halo exchange make the step slower?

The completion tasks cannot run until the interior instructions finish, so nothing was hidden, and the change added two vector instructions with their start-up cost and made every inlined task larger.
