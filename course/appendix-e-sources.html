How provenance tags work

A tag follows the number or sentence it qualifies. In a table it applies to the cell it sits in. The tag's colour gives the class; the label inside can add the specific source ("Vendor, HC22", "SDK 2.10.1, topic-15") or say that the figure came second-hand ("Vendor via secondary").

Some became reachable later: in the November 2026 review, cerebras.ai's Llama 405B post and the Cerebras training docs (the cb16 format page) were fetched directly, and the figures taken from them were upgraded in their chapters. And the simulator is not hardware: no measured number here is a silicon measurement.

How to check a figure

  1. Read the tag. Measured and SDK figures can be checked locally. Vendor, Indep and Analyst figures point to a document. Derived figures point to their inputs.
  2. Find the source. Use the label and the bibliography. Prefer the primary document (the Hot Chips deck, not the article about it).
  3. Match the conditions. Which generation (WSE-2, WSE-3, WSE-3T)? Which precision, dense or sparse? Shipping or announced? Per chip, per system or per rack? Which spec revision (Rubin HBM4 went from 22 to 19.2 TB/s after announcement)?
  4. Redo the arithmetic for Derived figures, and check the tag on each input as well.
  5. Re-run Measured figures: each lab's commands.sh honours ARCH=wse2|wse3. Time kernels with the on-tile <time> counter on one PE (Appendix C). For a single DSD op, the ready-made harness is programs/01-saxpy/timed (bash commands.sh N HALF PAD; swap the one op line to time a different op), as issue 2 shows. Whole-run cycle counts vary with host load, by a few percent and sometimes much more.
  6. Look for a later correction. When a later measurement overturned an earlier figure, every chapter that used it was corrected, and the open questions that remain are in Open factual issues below. If two chapters still disagree, the one that cites a measurement or a primary document wins.

Worked example: one sentence from Chapter 2

Chapter 2, "The numbers, generation by generation": "WSE-2 is the one generation with an official clock, 1.1 GHz Vendor (HC22): 850k × 4 × 2 × 1.1 GHz ≈ 7.5 PF, exactly the HC22 dense figure Derived."
  1. Read the tags. Two claims: a Vendor clock and a Derived peak that is compared with a Vendor dense figure. The clock and the dense figure need a document; the peak needs its inputs.
  2. Find the source. "HC22" is Hot Chips 2022 (its proceedings are numbered HC34). The bibliography lists it as Sean Lie's Hot Chips 34 slides, cited by the report and the WSE hardware note. That is a primary document, so no hunt for a better one. The same deck carries the dense figure: "75 PFLOPS FP16 Sparse / 7.5 PFLOPS FP16 Dense" Vendor (HC22).
  3. Match the conditions. The deck gives the WSE-2 clock, not the WSE-3 one: the sentence says so, and the next one in the chapter says no WSE-3 clock is published. 7.5 PF is dense FP16; the 75 PF in the table above it is the sparse headline, a different quantity.
  4. Redo the arithmetic. 850,000 PEs × 4 FP16 lanes × 2 FLOPs per FMA × 1.1 × 109 Hz = 7.48 × 1015 FLOP/s ≈ 7.5 PF. The sum is right. Now check each input's tag: 850,000 cores and 1.1 GHz are Vendor, but the "4 lanes" comes from a secondary source (Chapter 3's per-PE table tags it Secondary), and it is in the flagged list below. Run the sum backwards and the Vendor numbers alone fix the width: 7.5 PF ÷ (850,000 × 2 × 1.1 GHz) = 4.0 FP16 multiply-adds per PE per cycle Derived. So the match is a real check on the lane count, not one estimate checked against another.
  5. Re-run. The lane count can also be tested in the simulator. One f16 @fmach over 1,024 elements on WSE-2 takes 270 cycles when its two sources start 8 bytes apart, about 3.8 elements per cycle; laid out with the sources 0 or 4 bytes apart (as in Lab 1, same bank, and Chapter 6's rate table, 2 banks apart) it takes 526, about 2 per cycle Measured, TSC, WSE-2 (issue 2 below, Chapter 6). An op that sustains ~4 f16 elements per cycle needs at least 4 lanes, so the simulator supports the Secondary "4 lanes", and 7.5 PF is a peak a well-placed DSD op nearly reaches. The older "~2 per cycle on WSE-2" was a placement artefact, not a lane count.
  6. Look for a correction. An earlier draft of the research said no clock was published for any generation; the 1.1 GHz replaced that. And an earlier version of this example read the 2-per-cycle placement artefact as "half the lanes". The clock stands, and the lane count is now backed by the Vendor dense figure and a Measured rate; the Secondary tag on it in Chapter 3 is the one input still worth replacing with a primary source.

Unverified and second-hand figures

This list is generated, not written by hand. A script reads every course page in the order of the navigation, finds each static provenance tag, and takes the sentence (or table row) the tag qualifies as the claim. It flags every Unverified tag; every tag whose label says the figure came "via" press, a forum, a search extract, a reprint or an interview, or calls it "secondary"; and every Press-labelled third-party tag (a write-up, not a measurement). Tag keys that only explain the colours are skipped. The "why" column comes from the tag's class and label; "what would settle it" comes from what the claim is about, then its section, then the chapter's subject. The page link goes to the nearest section and, in browsers that support text fragments, highlights the start of the claim.

The script is course/tools/scan_tags.py in the course's source; --check prints the per-page counts and --list every flagged row. Tags drawn at run time by widget scripts (for example the readouts in Chapter 18's calculators) are not counted.

1. The SRAM bank model

Measured
cs_readelf --sym lists the banks each symbol occupies with 16-bit granularity on both chips: a 2-byte variable at 0xcb0, 0xcb4, 0xcb8, 0xcbc lands in banks 0, 2, 4, 6, so bank = (byte address ÷ 2) mod 8, a 16-byte stripe SDK 2.10.1, cs_readelf. The cs_readelf man page says the bank is "determined by bits [3:1] of the address" and that a 32-bit read "is broken into two 16-bit reads" SDK 2.10.1. The single-tile-matvec benchmark pads rows to 16 B to avoid bank conflicts; FIFO_MIN_ALIGNMENT is 16 on WSE-3 and 8 on WSE-2 SDK 2.10.1.
The conflict
Academic descriptions say eight 6 KB banks, each 32 bits wide, with successive 32-bit words in successive banks, a 32-byte stripe Secondary (arXiv 2605.07954, 2209.15040, via search extracts). Chapter 3 presents both models.
Unknown
The physical bank width, and whether the SDK's 16-bit numbering is a logical view of 32-bit banks.
Would settle it
A Cerebras hardware document, or a stride sweep in 2-byte steps that separates a 16-byte from a 32-byte stripe.

2. Operand placement sets DSD op rates

This issue used to be two: the bank-clash rule and "why @fadds runs twice as fast on WSE-2 in Lab 3". One set of runs answers both, so they are merged. The canonical table and an interactive bank ruler are in Chapter 6, "Which bank does an operand start in?"; the glossary has the short form.

Documented
The cs_readelf man page:
"Bank conflicts where concurrent reads and writes target the same bank or the same bank modulo 4 may result in cycle delays."
SDK 2.10.1, cs_readelf --help With 16-bit banks (issue 1) an f32 word spans two banks, so the 8 banks repeat every 16 bytes: two streams whose start addresses are equal mod 16 B start in the same bank, and two that start 8 B apart start in banks b and b + 4, "the same bank modulo 4".

Reading it
One rule covers every 1,024-element cell: rates are layout-dependent; peak needs the two source streams in opposite halves of the 16-byte bank cycle (8 B apart); the same bank halves the rate. In place, WSE-3's only sensitive op is f32 FMAC, and only to the same bank. On WSE-2 the ops that read 2 f32 or 4 f16 elements per stream per cycle (@fadds, @fmach) are fast only at 8 B. So the man page's "same bank modulo 4" offset is the one fast placement on WSE-2, the opposite of a conflict. A reading that fits every WSE-2 cell: each stream reads a window of (rate × element size) bytes per cycle, 8 B for these two ops, and the op stalls when the two windows share a bank; at 8 B apart they never do Derived, hypothesis. It does not explain WSE-3, where those ops are not slowed in place. With a separate destination array (Ch. 6 rate table), WSE-3 f16 @fmach slows from 272 to 310 cycles and @faddh runs at 310 (≈3.5 per cycle) Measured, so the destination's placement matters too.
What this means
  1. On WSE-2, put two source streams 8 bytes apart (PAD 2 for f32) and f32 adds and f16 FMACs double: 1 → 2 and 2 → ≈4 per cycle.
  2. On WSE-3, in place, those ops do not move; only an f32 FMAC with both sources in the same bank slows, to 0.5 per cycle. With a separate destination the f16 ops do slow (272 → 310 cycles for @fmach), so the destination's placement matters too.
  3. That is why Lab 3's add is fast on both chips (u[i] and u[i + 2] are 8 B apart), why Lab 1's FMAC is slow until padded, and why "WSE-2 f16 = 2 per cycle" (Chapters 3, 6 and 11 before this round) is a layout, not a rate: Chapter 6's and Lab 1's operands are 4 B and 0 B apart. The worked example above uses the fast cell to support the 4-lane width.
Unknown
What the "modulo 4" clause covers (a read against a concurrent write, other ops, or a hardware case the simulator does not model); why WSE-3 shows none of the WSE-2 pattern; f16 sources an odd number of banks apart; why the chips differ at N = 64; and why strides 4 and 8 differ. None of this has been checked on hardware.
Would settle it
The same offset test with the destination 2 words away from a source; the WSE-2 f16 runs with the instruction trace on (SIMFABRIC_DEBUG=inst_trace) to see which reads stall; an odd-bank test that takes both sources as offset views of one f16 array (as Lab 3 does), since separate arrays cannot start 2 B apart; or a fuller statement from Cerebras. 5. The units of a DSD's .index

Known
In the SDK, tutorials/sdklayout-05-gemv/gemv.csl (a dense GEMV over f32 data) passes .index = 2 * idx to @fmacs, and benchmarks/gemv-checkerboard-pattern/pe.csl passes .index = idx to @fmach on f16 data SDK 2.10.1. Both fit an index counted in 16-bit words Derived (Ch. 6).
Measured
@fmovs(y_dsd, x_dsd, .{ .index = 1 }) on f32 x (declared with .wavelet_index_offset = true), WSE-3, N = 8: the simulator stops with "MEM[0611] is not 32-bit aligned". x starts at byte 0xc20, which is 16-bit word 0x610, so .index = 1 moved the access by one 16-bit word Measured, simulator, cs_readelf --sym. So .index counts 16-bit words, and f32 data needs an even index (the GEMV tutorial's 2 * idx).
Unknown
What silicon does with an odd f32 index (the simulator treats it as a fatal misaligned access). The builtin reference that states the unit was unreachable.
Would settle it
For silicon, a run on hardware or the online builtin reference. To repeat the simulator test: in the Program 01 harness (programs/01-saxpy/timed), declare x_dsd with .wavelet_index_offset = true, replace the op line with @fmovs(y_dsd, x_dsd, .{ .index = 1 }) and run bash commands.sh 8 0 0. The run ends in a fatal error: read it in sim.log, then kill the host (run.py waits forever for a result that never comes). Compare the faulting MEM[…] word with x's address from cs_readelf --sym out/bin/out_0_0.elf (bytes; divide by 2 for 16-bit words).

6. What @fscales and @fnorms compute

Known
Both exist: csl-libs/dsd_ops.csl maps scale to @fscaleh/@fscales and norm to @fnormh/@fnorms, next to a separate mul → @fmuls SDK 2.10.1. The standard library shows what they do. LIB/math.csl defines fscale_f32(f: f32, s: i16): at compile time it returns f * internal.pow2i_f32(s), at run time it calls @fscales(&r, f, s) SDK 2.10.1, math.csl. So scale is ldexp, f · 2s with an i16 exponent, not a general multiply by a scalar. internal.fnorm (which calls dsd_ops.norm) is used as fnorm(x) - 1.0 before a log polynomial, and in the square roots, where the exponent is taken separately, one doubling is followed by the comment "so x_norm in [1,4)" SDK 2.10.1, math.csl. So norm returns the significand normalised into [1, 2), like the mantissa from frexp, not a vector norm Derived from SDK code. Chapter 6 covers the builtins.
Unknown
The edge cases: what norm returns for zero, infinities and denormals, and how scale rounds or saturates when 2s under- or overflows.
Would settle it
The builtin reference, or a one-PE run of @fnorms and @fscales on 0, a denormal, ±∞ and a large s, with the results copied back by memcpy.

Other items are still open but are gaps rather than disagreements: the cost of a task per wavelet, back-pressure figures that were not re-run, csdb's workflow for a halted simulation, and the task picker's tie rule. The chapters that touch them say so where they come up.
