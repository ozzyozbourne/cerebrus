Sources and unverified figures

Every number in this course carries a small coloured tag that says where it came from. This appendix explains the tags, lists the sources behind them, and keeps a generated list of every figure the course could not confirm, with what would settle each one. It ends with the open technical questions that the course's own simulator measurements raised but could not answer.

After this appendix you can

  • Check a figure yourself, from its tag back to a primary document or a simulator run.
  • Find every Unverified or second-hand figure in the course, and the evidence that would settle it.
  • Name the seven open questions about the PE and fabric that the measurements left open.

How provenance tags work

A tag follows the number or sentence it qualifies. In a table it applies to the cell it sits in. The tag's colour gives the class; the label inside can add the specific source ("Vendor, HC22", "SDK 2.10.1, topic-15").

TagMeansHow much weight it bears
MeasuredRun during this course's build in the Cerebras SDK 2.10.1 simulator (or compiled with cslc). The text says which chip (WSE-2 or WSE-3) and size.High for the simulator. It is cycle-level, but it is not silicon: host I/O timing and anything outside the fabric are modelled.
SDK 2.10.1Read directly from the installed SDK: tutorial READMEs, benchmark code, the CSL standard library in the container image, tool output.High for programming facts. The SDK is the vendor's own working code.
VendorPublished or presented by Cerebras, NVIDIA or Tenstorrent (datasheets, Hot Chips decks, ISA docs, press releases).Accurate about what was claimed. Check the precision, sparsity, date and "announced vs shipping".
Vendor via secondaryA vendor figure that reached the course through press, a forum, a search-engine extract or a reprint, because the vendor's page was unreachable.Probably right, but the wording, units or revision may have shifted. Listed below.
IndepA third-party measurement (Artificial Analysis, Chips and Cheese, peer-reviewed papers). "Secondary" uses the same colour for third-party descriptions that are not measurements.Good evidence for what was measured. Check the configuration.
AnalystA third-party estimate, not a measurement (SemiAnalysis, Futurum, GPU-cloud blogs).A reasoned guess. Often the only dense-FLOP figure available.
DerivedArithmetic done in this course from tagged inputs. The inputs are next to it.As good as its inputs. Re-do the sum.
UnverifiedNo reachable source confirmed it. Kept because it is useful background, and listed below.Treat as a lead, not a fact.

Two limits applied throughout the build. Most vendor documentation sites (sdk.cerebras.ai, cerebras.ai, docs.tenstorrent.com, most NVIDIA pages) could not be fetched from the build environment, so many web facts came from search extracts of the cited pages. And the simulator is not hardware: no measured number here is a silicon measurement.

How to check a figure

  1. Read the tag. Measured and SDK figures can be checked locally. Vendor, Indep and Analyst figures point to a document. Derived figures point to their inputs.
  2. Find the source. Use the label and the bibliography below. Prefer the primary document (the Hot Chips deck, not the article about it).
  3. Match the conditions. Which generation (WSE-2, WSE-3, WSE-3T)? Which precision, dense or sparse? Shipping or announced? Per chip, per system or per rack? Which spec revision (Rubin HBM4 went from 22 to 19.2 TB/s after announcement)?
  4. Redo the arithmetic for Derived figures, with your own inputs if they differ.
  5. Re-run Measured figures: each lab's commands.sh honours ARCH=wse2|wse3. Time kernels with the on-tile <time> counter on one PE (Appendix C). Whole-run cycle counts vary by 1–4% with host load.
  6. Check the canonical list. The course keeps one record of cross-chapter corrections (reviews/CROSS_CHAPTER_NOTES.md, items 1–24). Where a chapter and that list disagree, the list wins.

Open factual issues

These came out of the course's own measurements, not out of the press. Each one is a place where the simulator showed something that no reachable document explains. They are listed so that a reader with access to Cerebras documentation, or the time to run one more experiment, can close them. Chapter numbers are current; the review files that recorded them use the older numbering.

1. The SRAM bank model

Measured
cs_readelf --sym lists the banks each symbol occupies with 16-bit granularity on both chips: a 2-byte variable at 0xcb0, 0xcb4, 0xcb8, 0xcbc lands in banks 0, 2, 4, 6, so bank = (byte address ÷ 2) mod 8, a 16-byte stripe SDK 2.10.1, cs_readelf. The cs_readelf man page says the bank is "determined by bits [3:1] of the address" and that a 32-bit read "is broken into two 16-bit reads" SDK 2.10.1. The single-tile-matvec benchmark pads rows to 16 B to avoid bank conflicts; FIFO_MIN_ALIGNMENT is 16 on WSE-3 and 8 on WSE-2 SDK 2.10.1.
The conflict
Academic descriptions say eight 6 KB banks, each 32 bits wide, with successive 32-bit words in successive banks, a 32-byte stripe Secondary (arXiv 2605.07954, 2209.15040, via search extracts). Chapter 3 presents both models.
Unknown
The physical bank width, and whether the SDK's 16-bit numbering is a logical view of 32-bit banks.
Would settle it
A Cerebras hardware document, or a stride sweep in 2-byte steps that separates a 16-byte from a 32-byte stripe.

2. The bank- and operand-clash rule

Measured
Program 01's @fmacs costs 2 cycles per element when x and y sit back to back, and 1 per element after padding one word between them, on both chips (f32, N = 1,024: 2,063 → 1,039 cycles WSE-3, 2,062 → 1,038 WSE-2) Measured, TSC (Ch. 11). Separately, @fmacs over 1,024 elements runs at half speed (2,064 vs 1,040 cycles, both chips) exactly when its two source streams start at addresses equal mod 4 words; @fadds shows no penalty in the same layouts Measured (Ch. 6). At N = 64 the unpadded case conflicts on WSE-3 (143 cycles) but not on WSE-2 (78) Measured. Strides 4 and 8 cost differently although they touch the same banks.
Unknown
The rule itself; why "mod 4 words" when there are 8 banks; why the chips differ at N = 64. The course says "pad and measure".
Would settle it
A sweep of source offsets × strides × ops on both chips with the instruction trace on, or a vendor statement of the rule.

3. The WSE-2 @fadds rate

Measured
Memory to memory, 1,024 f32 elements with operands 1,025 words apart: @fadds takes 1,039 cycles on WSE-2 (1 element/cycle) and 528 on WSE-3 (2/cycle) Measured (Ch. 6). In Lab 3's kernel on WSE-2 the fadds-only slope is 0.5 cycles per cell (2/cycle), where both sources are offset views of one array Measured (Ch. 13).
Unknown
Why the same op runs twice as fast in Lab 3. The operand pattern probably matters; no mechanism is known.
Would settle it
Repeat the isolated test on WSE-2 with both sources as offset views of one array, then compare instruction traces.

4. The WSE-2 hop-timing floor

Measured
Pure router round trips with one wavelet: WSE-2 36 / 48 / 96 / 160 cycles at P = 2 / 8 / 32 / 64 (1.0 cycle/hop); WSE-3 44 / 68 / 164 / 292 (2.0 cycles/hop) Measured (Ch. 4). With 64 wavelets WSE-2 stays near 160 cycles up to P = 32, about 2 cycles per wavelet. In Lab 2's chain the WSE-2 round trips have a ~90-cycle floor for P ≤ 8, so its hop cost is fitted from P ≥ 12 only Measured (Ch. 12).
Unknown
The cause of the floor and of the 2 cycles per streamed wavelet. "Each PE's clock starts one hop later" fits the numbers but is only Derived.
Would settle it
An instruction trace (SIMFABRIC_DEBUG=inst_trace) of the round trip on WSE-2 at P = 4, 8 and 12.

5. Do microthreads share one datapath?

Known
A PE runs up to eight microthreads Vendor, and the main thread's priority relative to them can be set SDK 2.10.1. That they share a single datapath, interleaved by operand readiness, comes from one secondary source Secondary (Ch. 3).
Measured
Nothing yet. An attempt during the Chapter 3 fixes stalled.
Would settle it
Time two async @fadds on different microthreads with the TSC, against the same two run back to back. A total near the sum means one shared datapath.

6. The units of a DSD's .index

Known
The SDK's sparse examples pass .index = 2*idx for f32 data, so the unit is inferred to be 16-bit words Derived (Ch. 6).
Unknown
The builtin reference that states it was unreachable.
Would settle it
The online builtin reference, or a one-PE test that writes with .index = 1 on f32 data and checks which half-word moves.

7. What @fscales and @fnorms compute

Known
Both exist: csl-libs/dsd_ops.csl maps scale to @fscaleh/@fscales and norm to @fnormh/@fnorms, next to a separate mul → @fmuls SDK 2.10.1. Chapter 6 tags their meaning Unverified.
Unknown
Whether scale differs from @fmuls with a scalar operand, and what norm returns (a norm, or a normalisation).
Would settle it
The builtin reference, or a simulator run on known inputs (e.g. [3, 4]).
