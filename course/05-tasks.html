Chapter 5 · Part II · The machine

Tasks: computing on arrival

A PE has no operating system, no threads and no main loop. Its code is a set of short handlers called tasks. Data arriving from the fabric, or an operation finishing, marks a task as ready; the hardware runs ready tasks one at a time, each to completion. This is the execution model you program against.

If you know JavaScript or interrupt handlers, you already know this model. Each task is like a callback on an event loop, or a short interrupt service routine. It runs, returns, and must never spin waiting for something; the hardware picker then chooses the next ready task. The hardware offers nothing more: a PE has 48 KB of memory Vendor, no MMU and no context-switch machinery for user code, so there is no saved state to resume a paused task from. In exchange, scheduling is a hardware lookup, and work can start as soon as its data arrives. That is the dataflow idea behind the whole wafer.

After this chapter you can

  • Name the four ways a task gets activated (wavelet, @activate or async completion, control wavelet, the teardown task) and the task kind each one starts.
  • Describe the per-task hardware state (one activated bit, one blocked bit) and predict when two activations collapse into one run.
  • Use @activate, @block/@unblock and .activate/.unblock on async ops to build control flow: callbacks, joins and state machines.
  • Budget task IDs and queues on WSE-2 and WSE-3, and avoid the two WSE-3 traps: queue-bound data tasks and shared microthreads.

Preview: async operations (full story in Chapter 6). The CE can launch a vector instruction, such as "copy 64 words from memory out onto the fabric", and carry on without waiting for it. The operation runs on one of the PE's 8 microthreads (Chapter 3), hardware slots that each drive one vector operation, while the CE goes back to the picker. You ask for this with .async = true, and you name the task to run when it ends with .activate = some_task. The operands are DSDs, descriptors of a memory array or of a fabric stream. A fabric DSD (fabin_dsd to receive, fabout_dsd to send) moves many wavelets with one instruction instead of running a data task per wavelet. For this chapter you need one fact: an async op is work in flight, and its completion is an event that activates a local task.

Control tasks and sentinels

How does a streaming receiver know the stream has ended? The standard answer is a sentinel. The sender streams N data wavelets on color c, then one control wavelet whose payload names a control-task ID. The receiver's data task handles the N values; the control wavelet activates the task bound to that ID, which now knows the stream is complete. A control-task ID is not a color, so it needs no route SDK 2.10.1, topic-05. The compiler accepts control-task IDs in the range 0–63 (it rejects 64 with "expected control task ID in the range [0,64)") Measured, cslc 2.10.1. memcpy uses 33–37 and 40 (Chapter 7); the topic-05 sentinel uses 43.

sentinel pattern, condensed from SDK topic-05 and topic-07
const ctrl = @import_module("<control>");
const done_id: control_task_id = @get_control_task_id(43);   // > 31 is fine for control tasks

// sender, after the last data wavelet:
@mov32(tx_ctrl_dsd, ctrl.encode_single_payload(ctrl.opcode.SWITCH_ADV, false, done_id, 0));

// receiver:
task send_result(payload: u16) void { /* stream complete: reply to host */ }
comptime { @bind_control_task(send_result, done_id); }

The same control wavelet also advances any router switch it passes, which is how Chapter 4's switches are driven. Its own payload follows the old switch position SDK 2.10.1, topic-07.

What the hardware stores, and the rules that follow

For each task ID the PE keeps two bits: activated and blocked. The picker considers only IDs with activated = 1 and blocked = 0. Setting the activated bit when it is already 1 changes nothing. The SDK's own 25-point stencil says so in a comment: "the hardware does not queue activations (instead, the hardware uses a single bit to track task activations)" SDK 2.10.1, benchmarks/25-pt-stencil/task.csl. The two-bits-per-ID picture is how the SDK comments describe it; the register layout behind it is not documented Derived.

  • Run to completion. A task must not wait. A synchronous fabric op inside a task does wait, in the instruction, and if the data it waits for needs another task to run first, the PE deadlocks. SDK pipeline-01 shows exactly this: with a blocking @add16(outDsd, inDsd, 1), "The CE has no resource to run the H2D command received by the router, so it stalls" SDK 2.10.1, pipeline-01. Start long work asynchronously and let its completion activate a different task.
  • Tasks do not call tasks; they activate them, and activation is a single bit. For local tasks the bit is all there is: two @activates, or two async completions, that land before the task runs give one run. Data tasks behave differently because the input queue sits behind the bit. Each wavelet waits in the queue, and the data task runs once per wavelet: program 02 sends 100 wavelets and on_value counts exactly 100 Measured. The rule of thumb: events that carry data are buffered; events that carry no data collapse.
  • Blocking. @block(id) stops a task from being picked even if it is activated; @unblock(id) releases it. If a fabric DSD is to read a queue, you must block that queue's data task; otherwise the task fires on each wavelet and consumes it first SDK 2.10.1, pipeline-01. Blocked wavelets wait in the queue. When the queue fills, the lossless fabric pushes back-pressure upstream until the sender stalls. Queues are small: one SDK example "stalls when size exceeds 14" wavelets SDK 2.10.1, pipeline-01.
  • Self-start and self-send. @activate(id) inside a comptime block (code the compiler runs to set up bindings, Chapter 10) runs that task at program start. A PE can also feed its own data task by routing a color RAMP → RAMP, which "immediately sends them back to the compute element" SDK 2.10.1, topic-09.

Tasks are entry points; functions do the work

Tasks are only the entry points the hardware can start. Inside a task you call ordinary CSL fns as on any CPU, synchronously and on the same stack. A function such as Lab 3's update() runs as part of whichever task called it. Lab 3 has exactly four tasks (t_se, t_sw, t_rw, t_re); start_step, update and op_done are plain functions, and the host-callable run is a function that memcpy's own command task calls (Chapter 7). The state between hand-offs is just globals such as pending and step. Task IDs are scarce (see the budget below), so make something a task only if the hardware has to start it.

Control flow in a dozen lines, condensed from Lab 3 and SDK pipeline-01:

control flow with local tasks (sketch)
const done_id: local_task_id = @get_local_task_id(10);
const kick_id: local_task_id = @get_local_task_id(11);

task on_done() void { /* runs once the async op has finished */ }

fn start() void {             // a plain function, not a task
  @fmovs(out_dsd, buf_dsd, .{ .async = true, .activate = done_id });   // completion -> on_done
}
task kick() void { start(); }    // started by @activate(kick_id) from any task

comptime {
  @bind_local_task(on_done, done_id);
  @bind_local_task(kick, kick_id);
  @activate(kick_id);            // run kick() at program start
  @block(h2d_task_id);           // let a fabin_dsd, not the data task, consume these wavelets
}

An async op can instead say .unblock = id. Use it when the task is (or will be) activated by something else and should run only once a transfer has finished. That gives you a join, the next idea.

Block + activate = join

Because the picker needs both activated = 1 and blocked = 0, the two bits form a hardware AND gate. The SDK uses it to make a task run only after two independent events, in either order:

  1. an operation starts and blocks task L;
  2. a different event activates L (it stays pending, because L is blocked);
  3. the operation finishes and unblocks L (.unblock = L);
  4. L runs only now, whichever of 2 and 3 came first.

memcpy itself works this way: "H2D blocks SYS_UBLK_C22 in the beginning, H2D unblocks SYS_UBLK_C22 when operation is done, teardown handler of H2D activates SYS_UBLK_C22" SDK 2.10.1, memcpy/sys_params.csl. The hypersparse SpMV benchmark uses the same lock: "LOCK runs only if teardown is received and the operation is done" SDK 2.10.1, spmv-hypersparse. Lab 3 uses the other tool, counting completions in pending.

The picker in action: why Lab 3 uses four completion tasks

One timestep of the Lab 3 heat stencil launches four async transfers (send east, send west, receive from west, receive from east). Each completion must decrement pending; when it hits 0 the PE updates its cells. Give all four ops one shared completion task and two completions that land before it runs merge into one, so pending never reaches 0. Whether that happens depends on timing, which is why the SDK's comment says that activating a task several times "does not guarantee" several runs.

Task picker: shared versus per-op completion tasks

The SDK's own 25-point stencil uses one completion task per transfer for exactly this reason SDK 2.10.1, benchmarks/25-pt-stencil. We also ran the real thing: Lab 3 with all four ops pointing .activate at one task stalls on both WSE-2 and WSE-3, and the host runtime gives up with "the received length (0 bytes) is not expected (576 bytes), could be a kernel stall" Measured, simulator, P = 8, n = 16.

When several tasks are ready

The picker is not purely first-come. The CSL library exposes a task-priority register: two 16-bit config words at 0x7e08/0x7e09 that together hold one bit per task ID, HIGH = 1 or LOW = 0. tile_config.task_priority.set_task_priority(id) and clear_task_priority(id) set the bit, at comptime or at run time ("updates … may take a few clock cycles to take effect"). For wavelet-activated tasks, control tasks included, you set the priority on the color (WSE-2) or the input queue (WSE-3) that carries the wavelets SDK 2.10.1, csl-libs tile_config/task_priority. Because the vector has 32 bits, only IDs 0–31 can be prioritised Derived.

A second knob, main_thread_priority.update_main_thread_priority(level), sets how the main thread (the one running your task code) ranks against microthreads. Async ops can be marked .priority = .{ .high = true } or .{ .medium = true } SDK 2.10.1, csl-libs and spmv-hypersparse.

What this means in practice.

  • Trap 1: queue-bound data tasks. WSE-2 code that binds a data task straight to a color does not compile for WSE-3: @get_data_task_id(color) fails with "expected 'input_queue' expression, got: 'color'" Measured, cslc 2.10.1. That is the friendly trap: the compiler catches it.
  • Trap 2: shared microthreads. Two concurrent async ops on the same microthread compile cleanly and then fail at run time (the callout below). Nothing warns you at build time.

The idiom that makes one source file serve both chips (@is_arch selects the per-chip form; programs 02–05 all use it):

pe_program.csl (Lab 1, program 02), excerpt, simplified
const h2d_iq: input_queue = @get_input_queue(2);   // queues 0,1 belong to memcpy on WSE-3
const recv_task_id: data_task_id =
  if (@is_arch("wse2")) @get_data_task_id(h2d_color)   // WSE-2: task ID == color
  else @get_data_task_id(h2d_iq);                     // WSE-3: task ID == input queue

task on_value(v: f32) void { stats[0] += v; /* … */ count[0] += 1; }

comptime {
  @bind_data_task(on_value, recv_task_id);
  @initialize_queue(h2d_iq, .{ .color = h2d_color });
}

memcpy is the SDK's host-to-device runtime; it owns some colors, queues and task IDs (Chapter 7).

A real hang from this course The first version of Lab 3 used output queues 2, 3 and input queues 2, 3. It compiled cleanly, and then it failed at run time. An async fabric op with no explicit .ut_id runs on the microthread whose ID matches its queue (always on WSE-2, by default on WSE-3). So "send east" (output queue 2) and "receive from west" (input queue 2) both wanted microthread 2, and "send west" and "receive from east" both wanted microthread 3. The SDK states the rule: "two operations cannot concurrently use the same microthread" SDK 2.10.1, topic-15.

We rebuilt that version to check. It fails the same way on both chips: sim.log ends with FATAL: … trying to term ut_instr[3], but it's not ours at cycle 2,123 on WSE-3 and 2,125 on WSE-2, and the host script then waits forever Measured, simulator, P = 8, n = 16. Renumbering the input queues to 4 and 5 fixed it on both chips Measured. Keeping input queues 2, 3 and giving the receives .ut_id 4 and 5 also works on WSE-3 Measured.

Why the compiler cannot help. Whether two ops overlap in time is a run-time fact, so the program builds cleanly. The tell is a simulator that stops advancing with an async op still pending; look at the end of sim.log and at the instruction trace (Chapter 10). Cerebras's own WSE-2 25-point stencil follows the same convention: "FD uses input_queue = 4,5,6,7 … .input_queue = 4 + queueId, .output_queue = queueId" SDK 2.10.1, 25-pt-stencil/task.csl.

Reusing a queue on WSE-3: @queue_flush and teardown task 29

On WSE-3 each output queue is bound to one color. To send on a new color you must wait until the queue is empty, and an async op's completion only means "the microthread pushed all of its data into the output queue; the queue may not be empty yet". The hardware helps: after @queue_flush(oq), "When oq becomes empty, WSE-3 will trigger the special teardown task 29, the same way a teardown wavelet does" SDK 2.10.1, topic-16. This is the fourth activation source in the table above. The sequence:

  1. send data 1 on oq; its completion task runs;
  2. the completion task calls @queue_flush(oq) (never before the send starts, or task 29 may fire at once on the still-empty queue);
  3. oq drains into the router; the hardware activates task 29;
  4. task 29 calls the handler you registered with @set_empty_queue_handler(foo, oq);
  5. foo rebinds oq to the new color, activates the next send, and calls queue_flush.exit(oq), otherwise task 29 will keep calling it.

Input queues need no flush: by the time a receive's completion task runs, the queue is already empty SDK 2.10.1, topic-16. Because memcpy registers handlers on task 29, you cannot bind your own task there (the compiler says "cannot bind task to teardown task ID '29'") Measured, cslc 2.10.1.

Tasks as a state machine

Because tasks cannot block, iterative algorithms become state machines. Lab 3's per-PE control flow:

Check yourself

A data task does heavy work per wavelet and wavelets arrive faster than it runs. What happens?

Wavelets back up in the input queue, which holds only a handful (one SDK example stalls past 14), and then in the routers behind it. The fabric is lossless, so the sender eventually stalls. That is back-pressure, not data loss.

Why must a task not "wait for" a transfer?

Tasks run to completion and there is only one CE main thread. While one task spins, no other task can run, including the one that would deliver the data, so the PE deadlocks. Start the transfer async and let its completion activate another task. (The host runtime, memcpy, also needs the CE; Chapter 7.)

Two async receives both use .activate = done and finish one cycle apart, before done runs. How many times does done run, and how do you fix it?

Once, because activation is a single bit. Give each op its own local task, as Lab 3 and the SDK's 25-point stencil do, or use a block + activate join.

Three wavelets reach a data task's input queue before it runs. How many times does it run?

Three. Events that carry data are buffered in the queue; only data-less events (@activate, async completions) collapse.

On WSE-3 you send on output queue 3 and receive on input queue 3 at the same time, with no .ut_id. What happens?

Both default to microthread 3. Two ops cannot use one microthread at once, so the program builds and then fails at run time (in our simulator run: a FATAL in sim.log, and a host that waits forever). Renumber a queue or set .ut_id. The same pairing fails on WSE-2, where microthread = queue ID always.

Your WSE-2 program uses data task ID 5 for color 5. What changes on WSE-3?

Bind color 5 to an input queue (say queue 2, not 0 or 1, which memcpy uses on WSE-3) with @initialize_queue, and bind the task to @get_data_task_id(queue) instead of the color. If you forget, the compiler stops you.

Convert for (s = 0; s < T; s++) { exchange(); update(); } into tasks. Which pieces are tasks and which are functions?

Only the completion handlers need to be tasks. start_step and update are functions, and the loop counter is a global checked at the end of update.

How many independent completion tasks can a WSE-3 PE have alongside memcpy?

At most 18 (IDs 8–23, 25, 26), or 15 if you also avoid 21–23 as the SDK's topic-09 map suggests. Data tasks are counted separately: at most 6 (input queues 2–7).

You want a task to run only after both a teardown event and an async op have happened, in either order. How?

Block the task when the op starts, let the other event @activate it, and give the op .unblock = task. The picker needs activated ∧ unblocked, so it runs only after both.
