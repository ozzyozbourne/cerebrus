Tasks: computing on arrival

A PE has no operating system, no threads and no main loop. Its code is a set of short handlers called tasks. Data arriving from the fabric, or an operation finishing, marks a task as ready; the hardware runs ready tasks one at a time, each to completion. This is the execution model you program against.

After this chapter you can

  • Distinguish data, local and control tasks and say what activates each.
  • Use @activate, @block/@unblock and async-op completion to build control flow.
  • Avoid the two WSE-3 traps: queue-bound data tasks and microthread sharing.

Rules that follow from the hardware SDK 2.10.1:

  • Run to completion. A task cannot wait. Long work is started asynchronously (a DSD op with .async = true) and a different task runs when it finishes.
  • Tasks do not call tasks. They activate them. Activation is a flag: activating an already-activated task does not queue a second run.
  • Back-pressure. @block(id) stops a task from being picked even if activated; @unblock(id) releases it. A blocked data task leaves wavelets waiting in the queue — which is how a fabric DSD can consume them instead.

Task picker: why Lab 3 uses four completion tasks

One timestep of the heat stencil launches four async transfers (send east, send west, receive from west, receive from east). Each completion must decrement pending; when it hits 0 the PE updates its cells. Compare one shared completion task with one task per transfer.

The idiom that makes one source file serve both chips — used in every program in this course:

pe_program.csl (Lab 1, program 02)
const h2d_iq: input_queue = @get_input_queue(2);   // queues 0,1 belong to memcpy on WSE-3
const recv_task_id: data_task_id =
  if (@is_arch("wse2")) @get_data_task_id(h2d_color)   // WSE-2: task ID == color
  else @get_data_task_id(h2d_iq);                     // WSE-3: task ID == input queue

task on_value(v: f32) void { stats[0] += v; count[0] += 1; }

comptime {
  @bind_data_task(on_value, recv_task_id);
  @initialize_queue(h2d_iq, .{ .color = h2d_color });
}
A real hang from this course The first version of Lab 3 used output queues 2, 3 and input queues 2, 3. It compiled cleanly and then the simulator stalled forever at cycle 1,894. On WSE-3 an async fabric op runs on the microthread matching its queue ID, so "send east" (output queue 2) and "receive from west" (input queue 2) both wanted microthread 2. Renumbering the input queues to 4 and 5 fixed it Measured. The SDK states the rule: "two operations cannot concurrently use the same microthread".

Tasks as a state machine

Because tasks cannot block, iterative algorithms become state machines. Lab 3's per-PE control flow:

Check yourself

A data task does heavy work per wavelet and wavelets arrive faster than it runs. What happens?

Wavelets back up in the input queue and then in the routers behind it; the fabric is lossless, so the sender eventually stalls. That is back-pressure, not data loss.

Why must a task not "wait for" a transfer?

Tasks run to completion and the CE is needed for other tasks (including the memcpy runtime). Start the transfer asynchronously and let its completion activate another task.

Your WSE-2 program uses data task ID 5 for color 5. What changes on WSE-3?

Bind color 5 to an input queue (say queue 2) with @initialize_queue, and bind the task to @get_data_task_id(queue) instead of the color.
