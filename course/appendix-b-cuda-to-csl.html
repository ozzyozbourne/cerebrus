Appendix B · Reference

CUDA to CSL, budgets and constants

Three reference cards for writing your own kernel: a map from CUDA concepts to their CSL and wafer equivalents (and to TT-Metalium), a budget card for one PE on WSE-3 and WSE-2 with a checker for your design, and the cost constants this course measured in the SDK simulator.

Use this appendix to

  • Translate a CUDA habit (a launch, a barrier, an atomic, occupancy) into what you actually do on the wafer, or learn that there is no equivalent and why.
  • Check a kernel design against every per-PE limit before you write it: memory, colors, task IDs, queues, microthreads and routes.
  • Estimate a kernel's cycle count from measured constants, and know which chapter measured each one.

Tags as in the chapters: Vendor Independent SDK 2.10.1 Measured Derived Unverified. Every number here is copied from the linked chapter or from the course's cross-chapter notes; nothing new was measured for this page. Terms are defined in Appendix A.

CUDA → CSL → TT-Metalium

The short version: CUDA launches many identical threads over one shared memory and lets hardware schedule and cache. CSL places a resident program on every PE, gives each one private memory, and moves data only along routes you declared. TT-Metalium sits between: per-core programs and explicit transfers, but large local memory and GDDR6 beside the chip that every core reaches over the NoC (Chapter 18, Ch. 16). Rows marked no equivalent are where CUDA intuition misleads.

One kernel, both ways: SAXPY

The same y = a·x + y in CUDA and in the course's program 01 (Chapter 10 tours its three files line by line, Ch. 10). The list under the code names the Rosetta row each line maps to. The CSL is trimmed to the lines that matter; the full files are in course/programs/01-saxpy/.

CUDA

saxpy.cu: kernel
__global__ void saxpy(int n, float a,
                      const float *x, float *y) {
  // grid-stride loop, one element per thread
  for (int i = blockIdx.x*blockDim.x + threadIdx.x;
       i < n; i += gridDim.x*blockDim.x)
    y[i] = a * x[i] + y[i];
}
saxpy.cu: host
cudaMalloc(&dx, n*4); cudaMalloc(&dy, n*4);
cudaMemcpy(dx, x, n*4, cudaMemcpyHostToDevice);
cudaMemcpy(dy, y, n*4, cudaMemcpyHostToDevice);
saxpy<<<blocks, 256>>>(n, 2.5f, dx, dy);
cudaMemcpy(y, dy, n*4, cudaMemcpyDeviceToHost);

CSL + host Python (program 01)

layout.csl
param N: i16;              // --params=N:64
layout {
  @set_rectangle(1, 1);    // the "grid"
  @set_tile_code(0, 0, "pe_program.csl",
                 .{ …, .N = N });
  @export_name("x", [*]f32, true); // names the
  @export_name("y", [*]f32, true); // host can use
  @export_name("saxpy", fn(f32)void); // RPC
}
pe_program.csl
var x: [N]f32;   // static: no cudaMalloc
var y: [N]f32;
var x_ptr: [*]f32 = &x; var y_ptr: [*]f32 = &y;
const x_dsd = @get_dsd(mem1d_dsd,
    .{ .tensor_access = |i|{N} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd,
    .{ .tensor_access = |i|{N} -> y[i] });
fn saxpy(a: f32) void {
  @fmacs(y_dsd, y_dsd, x_dsd, a); // the loop
  sys_mod.unblock_cmd_stream(); // host may go on
}
comptime {                       // bind the names
  @export_symbol(x_ptr, "x"); @export_symbol(y_ptr, "y");
  @export_symbol(saxpy);
}
run.py
xs, ys = rt.get_id('x'), rt.get_id('y') # ~ dx, dy
rt.load(); rt.run()      # resident from here
rt.memcpy_h2d(xs, x, 0, 0, 1, 1, N, **kw)
rt.memcpy_h2d(ys, y, 0, 0, 1, 1, N, **kw)
rt.launch('saxpy', a, nonblock=False) # <<<>>>
rt.memcpy_d2h(out, ys, 0, 0, 1, 1, N, **kw)

Line by line, with the Rosetta rows: the CUDA grid becomes @set_rectangle (grid row); cudaMalloc becomes static arrays placed at link time (cudaMalloc row); each cudaMemcpy becomes a memcpy_h2d/memcpy_d2h to a rectangle of PEs, here 1 × 1 with N elements per PE (cudaMemcpy row); <<<>>> becomes rt.launch, an RPC to a program that has been running since rt.run() (launch row); and the grid-stride loop with its thread index becomes the extent of one DSD, walked by a single @fmacs (grid-stride row). The device pointers dx and dy have a counterpart too: an array becomes an exported symbol, declared by @export_name in the layout and bound by @export_symbol in the PE program, and the host resolves it with rt.get_id('x'). The handle xs names "array x on every PE of the rectangle", not an address.

One line has no CUDA counterpart: unblock_cmd_stream(), which tells memcpy the RPC has finished so the host's next command can run. Without it the launch still returns: the next copy waits and fails after a few seconds (about 4–5 s) with “could be a kernel stall” Measured (Ch. 7).

From threadIdx to “which PE owns which slice”

Program 01 runs on one PE, so it never shows the two steps a CUDA programmer needs most: how the data is dealt across PEs, and how a PE learns where it sits. Here is the same SAXPY on a 4 × 1 rectangle. The PE program is program 01's, unchanged: its N is now the number of elements per PE. Only the layout and the host's copy change. (A sketch, not one of the course programs; it compiled and printed SUCCESS! on the WSE-3 simulator with 16 elements per PE Measured, SDK 2.10.1.)

CUDA: a thread computes its index

// global index of this thread
int i = blockIdx.x*blockDim.x + threadIdx.x;
if (i < n) y[i] = a * x[i] + y[i];
// x, y: one array in global memory;
// thread i picks element i out of it

CSL: the layout places, the host deals

layout.csl
param N_PE: i16;          // elements per PE
layout {
  @set_rectangle(4, 1);
  for (@range(i16, 4)) |x| { // "blockIdx"
    @set_tile_code(x, 0, "pe_program.csl",
      .{ .memcpy_params = memcpy.get_params(x),
         .N = N_PE });
  }
  … // same @export_name lines
}
run.py
# (x0, y0, width, height, elems per PE)
rt.memcpy_h2d(xs, x, 0, 0, 4, 1, N_PE, **kw)
rt.memcpy_h2d(ys, y, 0, 0, 4, 1, N_PE, **kw)

So CUDA's blockIdx becomes the layout loop's x, and threadIdx becomes the position inside the PE's DSD. SAXPY needs no index on the device at all: the slice a PE holds is its share of the work. When a PE must behave differently by position, the layout hands it a param, as program 03 does: its loop computes role = if (x == 0) 0 else if (x == P - 1) 2 else 1 (first, middle, last) and passes .role = role, or the PE reads its coordinate at run time, as <collectives_2d> does in Lab 4. Params cost one ELF per distinct value set; a run-time coordinate keeps one ELF for all (Ch. 10).

Budget checker: will my kernel fit on one PE?

Enter what one PE of your kernel needs, or load a course program. Lists are comma-separated IDs; ranges like 8-12 work. For async ops, write each concurrent op's queue as o2 (output queue 2) or i4 (input queue 4); on WSE-3 add :5 to give it .ut_id 5. Do not list streaming H2D/D2H colors under "colors you route"; count them in the streaming box. Every limit comes from the table above. OK means within the documented limit, not that the program is correct. Loading a preset explains what it shows; a WSE-3-only preset switches the chip and says so. Library modules are counted only through the IDs you hand them; their DSRs are not modelled (Lab 4’s preset shows the pattern; Ch. 15’s budget map does it for Lab 5).

Memory (per PE) FIFO buffers and timestamp arrays count as "other". Overhead defaults to the smallest measured program (SAXPY: 4,240 B WSE-3, ≈ 2,850 B WSE-2); it grows with code (matvec 4,636 / 3,134 B; Lab 3 up to ≈ 5.5 KB), so treat anything within 0.5 KB of 48 KB as "bisect". Right at the edge the overhead can be about 8 B smaller than this (alignment): SAXPY at N = 5,615 links at exactly 49,152 B.

Measured cost constants

Everything here was measured in the SDK 2.10.1 simulator by this course's chapters and reviews, on the PE's own timestamp counter unless the row says otherwise. Simulator cycles are a model, not silicon: “one hop per cycle” is a hardware-paper figure Indep, while the WSE-3 simulator models 2. To turn cycles into time, say which clock: WSE-3 has no published clock (the SDK assumes 850 MHz; press estimates put it near 1.4 GHz Analyst, unverified), WSE-2 runs at 1.1 GHz Vendor. Putting the constants to work

A first estimate for a kernel on one PE is the sum of:

  • its vector ops: start-up + elements ÷ rate. Use ≈ 15–17 cycles of start-up for an isolated op and ≈ 6 (WSE-3) for each further op in the same task. The 6 holds only for back-to-back ops on compile-time DSDs, with no scalar code between them and no loop;
  • ≈ 14.6 cycles per async transfer with its completion task, plus ≈ 13 cycles of step bookkeeping if the kernel is a task chain like Lab 3's;
  • ≈ 9 cycles (WSE-3) / 6 (WSE-2) per PE a value must pass through on the way;
  • ≈ 30 cycles per op when a scalar loop moves the DSD between ops (Ch. 6: 33–35 per step; Ch. 14: 2·Mt + 29 clashed, 1.25·Mt + 31 for odd Mt). Lab 4’s loop of 64 @fmacs at T = 8 takes 2,903 cycles, ≈ 64 × (2·8 + 29) = 2,880, not the 64 × (6 + 16) ≈ 1,400 that the in-task start-up would suggest Measured (Ch. 14).

Lab 3 on WSE-3 rebuilt from these: four transfers 4 × 14.6 = 58.4, bookkeeping 13, three consecutive op start-ups 3 × ≈ 6 = 19 (measured), so 58.4 + 13 + 19 ≈ 90 fixed; the per-cell slope 2.5 = 0.5 (@fadds at 2/cycle) + 1 + 1 (two @fmacs at 1/cycle). That is the measured 90 + 2.5·n Derived (Ch. 13). Using the isolated 15–17 for every op would give ≈ 108: the start-up value matters. Then measure on the TSC: the bank-clash and operand rules mean a first estimate can be off by 2×. To check the resources of the same design, use the budget checker; Ch. 14’s design method walks a full kernel through both.
