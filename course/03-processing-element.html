Chapter 3 · Part II · The machine

Inside a processing element

The wafer is 900,000 copies of one small computer. Each processing element (PE) is a compute engine with 48 KB of private memory, wired to a five-port router. Understand one PE and you understand the building block of everything else.

After this chapter you can

  • Draw a PE and name its parts: CE, SRAM banks, registers, DSRs, microthreads, router.
  • Budget a PE's 48 KB for code and data.
  • Explain why the WSE has no caches and why sparsity is "free".

The anatomy

Memory: 48 KB, one cycle, nothing else

The SRAM is 8 single-ported banks of 6 KB, interleaved by 32-bit word, single-cycle access. Interleaving lets a vector instruction read and write several consecutive words per cycle without bank conflicts. This 48 KB holds everything the PE knows: its code, its stack, its data, and the buffers the runtime needs. The SDK's own benchmarks keep data under about 46 KB, implying ~2 KB for code and runtime in those configurations SDK 2.10.1. A quick sanity check: 21 PB/s ÷ 900,000 PEs ≈ 23 GB/s per PE, a few 32-bit accesses per cycle at ~1 GHz Derived.

There is a tiny software-managed cache (256 B on WSE-2, 512 B on WSE-3) for hot values such as accumulators — "software-managed" meaning the compiler decides what goes there; nothing is cached automatically.

Compute: SIMD lanes driven by descriptors

The WSE-3 datapath is 8-way SIMD for FP16/BF16 and 16-way for INT8, up from 4-wide FP16 on earlier generations Vendor. You almost never write per-element loops: the CE executes a whole vector operation from one instruction whose operands are data structure descriptors held in the 48 DSRs — base address, length, stride (Chapter 6). It can run up to eight such operations at once, one per microthread. On WSE-3 microthread IDs are exposed to the programmer; two operations must never share one at the same time SDK 2.10.1 — a rule that caused a real hang in Lab 3.

Control: tasks, not a program counter marching through main

There is no operating system and no long-running main loop. Code is a set of tasks, and a hardware picker runs whichever task is activated and not blocked. Arriving data activates tasks. Chapter 5 is devoted to this.

Why no caches?

A cache exists to hide the distance between compute and a large, slow memory. On the WSE there is no large slow memory on the wafer: the "main memory" is the 48 KB beside the core, and it is already single-cycle. A hardware cache would add area and power to fix a problem the PE does not have. The cost moves to the programmer: whatever data a PE needs must already be in its 48 KB, or must arrive over the fabric.

Sparsity comes free with dataflow

Because computation is triggered by arriving data, a zero that is never sent never triggers work. Senders filter zeros; receivers only compute on what arrives. The SDK shows the software side: a wavelet is 32 bits, so a sparse value can travel as 16 bits of data plus a 16-bit index in the upper half SDK 2.10.1, topic-04. This mechanism is what Cerebras's sparse-FLOPS headline numbers assume.

Check yourself

Your PE program needs two 64 × 64 f32 matrices. Does it fit?

2 × 64 × 64 × 4 B = 32 KB. It fits in 48 KB, but leaves ~14 KB for code, runtime buffers and everything else. Two 96 × 96 matrices (72 KB) would not.

Why would a hardware cache be wasted on a PE?

Its only memory is already single-cycle SRAM beside it. There is no slower level to hide.

What limits how many vector operations a WSE-3 PE runs concurrently?

The 8 microthreads. Each async DSD operation occupies one, and two concurrent operations cannot share one.
