Chapter 3 · Part II · The machine

Inside a processing element

The WSE-3 wafer is about 900,000 copies of one small computer Vendor. Each processing element (PE) is a compute engine with 48 KB of private memory, wired to a five-port router. (Cerebras also calls it a core or a tile; this course says PE.) Understand one PE and you understand the building block of everything else.

After this chapter you can

  • Draw a PE, name its parts, and trace one wavelet through them.
  • Budget a PE's 48 KB with the real fixed overheads, and say which bank an address lands in.
  • Estimate how fast one PE runs an f32 or f16 kernel, and explain what eight microthreads do and do not buy.
  • Explain why the WSE has no caches, and how dataflow lets it skip zeros (and what that costs).

The anatomy

Wavelets, colors and the router, in one paragraph

PEs share no memory. They exchange wavelets: 32-bit messages that move about one router per cycle on hardware, according to the papers Indep; the WSE-3 simulator models 2 cycles per hop and the WSE-2 simulator 1 Measured, Chapter 4. Each wavelet carries a color, one of 24 tags SDK 2.10.1; at every router the color selects a pre-configured route, and at the receiver it selects what to do with the data. The router has five ports: N, E, S, W to the neighbours, and the RAMP down to its own CE. Chapter 4 covers routing in full. For now the key fact is that a wavelet coming down the RAMP is what wakes the CE.

At the bottom of the RAMP sit the CE's input and output queues: small hardware FIFOs, each bound to one color by the program. There are 8 input queues on both chips and 6 output queues on WSE-2, 8 on WSE-3 SDK 2.10.1, csl-libs/target, and each holds only a few wavelets (memcpy configures depths of 6, 4 and 2 for queues 0–1, 2–3 and 4–7) SDK 2.10.1, memcpy.csl. A queue is where an arriving wavelet waits until the CE takes it; on WSE-3 the input queue also names the data task it activates and the default microthread that consumes it (Chapter 5 follows that path in detail).

One wavelet's journey through a PE

Lab 2 (Chapter 12) sums a vector along a row of PEs from west to east. A middle PE runs one instruction, @fadds(out_dsd, in_dsd, v_dsd, .{ .async = true, .activate = exit_id }): "add what arrives from the west to my v, and send the sum east". Step through it; the parts involved light up in the diagram above.

Four terms the steps use before this chapter defines them: DSR, a register holding one array descriptor (address, length, stride; below) · microthread, a hardware slot that keeps one vector operation running in the background (below) · queue, a few-wavelet FIFO between the RAMP and the CE (above) · task, a short handler the hardware runs when it is activated (below, Chapter 5). The CSL spelling .async / .activate is taught in Chapter 6.

  1. Earlier, a task issued the @fadds. Its three operands (fabric-in, memory v, fabric-out) were loaded into DSRs and the operation was handed to a microthread. The task then ended; nothing waits in a loop.
  2. A wavelet arrives at the router's W port. The router looks up its color: "deliver to my own CE".
  3. It goes down the RAMP into one of the CE's input queues, drawn next to the RAMP (in Lab 2 the program bound queue 2 to that color).
  4. The microthread now has its fabric operand. The datapath adds it to v[i], read from the SRAM banks in one cycle.
  5. The sum goes into an output queue and back up the RAMP; the router sends it out of the E port on the next color.
  6. After the last element the microthread finishes and activates exit_id. The task picker runs that task once it is activated and not blocked.

Every later chapter zooms into one of these steps: routing (Chapter 4), tasks (Chapter 5), DSDs (Chapter 6).

Memory: 48 KB, one cycle, nothing else

The SRAM is 8 single-ported banks with single-cycle access Vendor, HC22, each 6 KB Academic papers. This 48 KB holds everything the PE knows: its code, its stack, its data, its task table and the buffers the runtime needs. Internally the PE addresses memory in 16-bit units: the CSL target library defines word_size = 2 and its registers as u16 SDK 2.10.1, csl-libs/target, so 48 KB is 24,576 words and an f32 is two of them.

Which bank does an address land in, and why it matters

Start with the effect. An f32 @fmacs over 1,024 elements takes about 1,040 cycles when its two source arrays start in different banks, and about 2,060 when they start in the same bank: half speed, on both chips Measured, simulator, SDK 2.10.1. That is a bank clash, and it is easy to hit by accident: Lab 1's SAXPY runs at 2 cycles per element until one pad word is added between its arrays (Chapter 11). So you need to know which bank an address lands in.

The SDK states the rule. The manual page of its cs_readelf tool says: "The bank a memory access lies in is determined by bits [3:1] of the address. So, for example, a 16-bit read of 0x1234 lies in bank 2. A 32-bit read of the same address is broken into two 16-bit reads, one from bank 2 and one from bank 3. Bank conflicts where concurrent reads and writes target the same bank or the same bank modulo 4 may result in cycle delays." SDK 2.10.1, cs_readelf(1). Its --sym output prints a "Banks" column for every variable, and in our builds it follows that rule: 2-byte variables at 0xe64, 0xe68, 0xe6c, 0xe70 sit in banks 2, 4, 6, 0 Measured, cslc 2.10.1 ELFs, WSE-2 and WSE-3.

In words: bank = (byte address ÷ 2) mod 8, a 16-byte cycle, so one f32 spans two banks and four consecutive f32s cover all eight. Two arrays whose start addresses are equal mod 16 bytes start in the same bank. The SDK's matvec benchmark pads rows to 16 bytes "to avoid bank conflicts", and the WSE-3 library sets FIFO_MIN_ALIGNMENT = 16 (WSE-2: 8) SDK 2.10.1, both consistent with a 16-byte cycle.

Sources differ on the physical layout

The research behind this course gives the bank layout as "successive 32-bit words in successive banks", from academic papers (arXiv:2605.07954, read through a search extract) Independent. That is not what cs_readelf reports. The two descriptions could be views of different things (address numbering versus physical bank width), but no source says so. One hint that 16-bit numbering is not the whole story: a contiguous f32 add moves at least 19 bytes per cycle (below), more than 8 banks × 16 bits per cycle could supply Derived. The physical bank width is not published. The explorer below lets you switch between the two models; the measurements in this chapter are explained by the SDK one.

The limit is in the datapath, or an FMA issue rate that is not documented Derived; what memory can do is slow an op down when two streams share a bank (box above). Memory is matched to the core, which is the WSE's answer to the memory wall.

There is also a tiny software-managed cache, 256 B on WSE-2 Vendor, HC22 and 512 B on WSE-3 Vendor, HC2024, for hot values such as accumulators. "Software-managed" means nothing is cached automatically by hardware. The public sources do not say how CSL exposes it, and the CSL standard library never mentions it; nothing in this course controls it.

Where the 48 KB goes: a real memory map

Here is the section layout of a compiled PE program, the SDK's single-tile matvec benchmark at N = 8 with the memcpy runtime, read with llvm-readelf -S and cs_readelf -m Measured, cslc 2.10.1. Its own arrays (A, x, y) are only 324 bytes: 64 + 8 + 8 f32 = 320 bytes, plus 4 because run.py allocates A as nb*padded_nb + 1 elements and writes the matrix from index 1, the one-element shift that keeps A and y out of the same bank SDK 2.10.1, single-tile-matvec/run.py. Yet the program uses 4,960 bytes on WSE-3 and 3,458 on WSE-2. The rest is fixed overhead: code (yours plus the memcpy runtime), runtime variables and, on WSE-3, a 1 KB task table.

Reading the section names: .text is machine code. .data holds variables with initial values and .bss zero-initialised ones (standard ELF names). .data.lo is data the linker places at the lowest addresses; it includes the 8-byte DSR images (__dsr_lowmeminit_* symbols), the initial descriptor values the runtime loads into DSRs. The task table is the hardware's map from task ID to handler address, 1 KB on WSE-3 (Chapter 5).

PE memory map

Two things stand out. The overhead is about 4.5 KB on WSE-3 (4,636 bytes; the cross-chapter notes round it to 4.6 kB) and 3.1 KB on WSE-2 (3,134 bytes) for the matvec benchmark at N = 8 Measured, and more code needs more. The smallest course program, SAXPY, needs less: 4,240 B on WSE-3 and about 2,850 B on WSE-2 (Appendix B). A capacity probe on WSE-3 confirms the ceiling: at N = 104 (A is 43,268 bytes: 104 × 104 + 1 f32, the +1 again being the shift) the program links and uses 48,736 of 49,152 bytes; at N = 106 the linker stops with ran out of PE memory for data (section .bss) and ran out of PE memory for task table Measured, cslc 2.10.1. So about 44,500 bytes (≈ 43.5 KB, "~44 KB") is usable for your arrays on WSE-3, consistent with the SDK benchmarks keeping data under 46 KB SDK 2.10.1, spmv-hypersparse. Second, the router tables, filters, queue configuration, the task active/blocked bits and the timestamp counter live at addresses above 48 KB, in a 64 KB address space: the CSL target library lists them as memory-mapped registers (for example TIMESTAMP_COUNTER, SWITCH_CONFIG, TASK_PRIORITY) SDK 2.10.1, csl-libs/target. Configuring the router or the task picker is just writing to an address.

Compute

SIMD lanes driven by descriptors

The WSE-3 datapath is 8-way SIMD for FP16/BF16 and 16-way for INT8 Vendor, HC2024, reportedly up from 4-wide FP16 on WSE-1/2 Secondary source. No f32 width is published. You almost never write per-element loops: the CE executes a whole vector operation from one instruction. The CE has 16 general-purpose registers (GPRs) for scalars and addresses, and 48 data-structure registers (DSRs) that each hold one data structure descriptor (DSD): base address, length, stride (Chapter 6) Vendor, HC2024.

DSRs are real, named registers that a program can load directly. The SDK's matvec benchmark loads A's descriptor once and lets it advance by itself (.save_address = true), so each @fmacs continues where the previous one stopped and A streams column by column SDK 2.10.1, single-tile-matvec:

const y_dest_dsr = @get_dsr(dsr_dest, 0);   // three roles: destination,
const y_src0_dsr = @get_dsr(dsr_src0, 0);   // source 0 and source 1
const A_src1_dsr = @get_dsr(dsr_src1, 0);
@load_to_dsr(A_src1_dsr, local_A_dsd, .{ .save_address = true });
@map(gemv_static_step_A, x_dsd);  // calls @fmacs(y_dest_dsr, y_src0_dsr, A_src1_dsr, curX)

Microthreads: overlap, not more FLOPs

A microthread is a hardware context that holds one in-flight vector operation: its DSD operands, its progress, and what to activate or unblock when it finishes. A PE has eight of them Vendor (WSE-2 blog), so up to eight vector operations can be in flight at once: for example receiving from the west, sending east and adding locally. They share the single datapath, and the hardware interleaves them according to which one has operands ready Secondary source. The main thread (the running task's own instructions) competes too: the SDK lets you set its priority from MEDIUM_LOW to HIGH relative to microthread priorities SDK 2.10.1, tile_config. The gain is overlap: waiting for wavelets no longer stalls the datapath. It is not 8× the FLOPs, since the measured f32 rate above is already the datapath's. Microthreads are not software threads either: there is no scheduler, stack or OS behind them.

You get a microthread by adding .async = true to an operation (Chapters 5 and 6). The compiler insists that such an operation has a fabric or DSR operand: an async @fadds on plain memory DSDs is rejected with "'async' requires at least one fabric or DSR operand" Measured, cslc 2.10.1.

Control: tasks, not a program counter marching through main

There is no operating system and no long-running main loop. Code is a set of tasks, and a hardware picker runs whichever task is activated and not blocked. Arriving data activates data tasks; other tasks are activated by code or by a finishing vector operation SDK 2.10.1. Chapter 5 is devoted to this.

Why no caches?

A cache exists to hide the distance between compute and a large, slow memory. On the WSE there is no large slow memory on the wafer: the "main memory" is the 48 KB beside the core, and it is already single-cycle. A hardware cache would add area and power to fix a problem the PE does not have. The cost moves to the programmer: whatever data a PE needs must already be in its 48 KB, or must arrive over the fabric.

Multiply out what that means for a whole wafer: 900,000 PEs × about 44.5 KB usable is about 40 GB that programs can fill, of the 44 GB headline Derived. A model larger than that cannot sit on one wafer, so Cerebras either streams the weights through the wafer layer by layer (training, MemoryX in Chapter 8) or pins them across several wafers and leaves whatever is free for the KV cache (inference, Chapter 8 and Chapter 9).

If you know CUDA

A PE is neither an SM nor a thread. Like an SM it has its own instruction stream, a scheduler (the task picker, Chapter 5) and fast local memory; like threads there are hundreds of thousands of them, but each runs its own program and none shares memory with another. The 48 KB is closer to __shared__ than to L1: software-managed, single-cycle, and the only memory the PE has. There is no L2 or HBM behind it, so what a GPU kernel would load from global memory must arrive as wavelets. The full mapping is in Appendix B.

The SDK's single-tile matvec benchmark makes this concrete by counting memory traffic two ways SDK 2.10.1. "Relative" is the minimum traffic on a traditional cached machine: read A and x once, keep the running y in registers or cache, write y once: 4(N² + 2N) bytes. "Absolute" is what the WSE kernel really does: it walks A column by column and reads and writes all of y for every column: 4(3N² + N) bytes. The difference is about y, not x; x is read once in both counts. Step through it:

Matvec memory-traffic stepper

y = A·x, one column per step: y += A[:, j] · x[j]. Orange cells are read this step, green are written. The cached machine keeps y on chip and writes it once at the end.

For N = 64 the benchmark reports 16,896 relative bytes against 49,408 absolute, 2.9× more, and still runs at about one multiply-add per cycle (4,214 cycles) Measured, simulator, WSE-3. Nothing absorbs the accumulator's reuse; the design bets that private single-cycle SRAM can serve the extra traffic, and here it does, at 11.7 bytes per cycle. The benchmark is written for CS-2 and converts cycles to seconds at 850 MHz SDK 2.10.1.

Sparsity: skipping zeros with dataflow

Because computation is triggered by arriving data, a zero that is never sent never triggers work. Senders filter zeros and receivers only compute on what arrives Vendor, HC22 / MICRO-54. This dataflow zero-skipping is a hardware feature, and it is what Cerebras's sparse-FLOPS headline numbers rely on. Those peaks count the skipped multiplies as if they were done, at an assumed sparsity ratio (Chapter 2). The SDK shows a software convention on top: a wavelet is 32 bits, so a sparse value can travel as 16 bits of data plus a 16-bit index in the upper half, and the receiving data task gets both halves as two arguments SDK 2.10.1, topic-04.

Sparse wavelet encoder

A 16-element i16 vector. Dense, it costs 16 wavelets and 16 task activations at the receiver. Sparse, each non-zero travels as one wavelet with its index in the upper 16 bits. Drag the sparsity, then click a wavelet to see its bits.

What skipping zeros costs.

  • The sender still has to look at every value to decide whether to send it.
  • Index plus value leaves only 16 bits for the value, so the f32 data every lab in this course uses does not fit. You would send f16/bf16 (losing precision) or spend two wavelets per value.
  • A 16-bit index covers any one PE's array (48 KB holds at most 24,576 16-bit values), but not a position in a large global tensor Derived. The tutorial declares it i16, so as written it covers 0–32,767.
  • Each non-zero is one data-task activation on the receiver, plus a scattered write (result[index] = wavelet_data), instead of one streaming vector op.
  • PEs that get more non-zeros finish last, so uneven sparsity becomes load imbalance.

Skipping zeros pays off when sparsity is high and unstructured enough that a dense SIMD op would mostly multiply zeros.

Check yourself

Your WSE-3 PE program needs two 64 × 64 f32 matrices. Does it fit?

2 × 64 × 64 × 4 B = 32 KB. It fits in 48 KB, but leaves only 16 KB, of which about 4.5 KB (4,636 B, measured on the matvec benchmark) is the fixed overhead of code, runtime and task table; the smallest course program, SAXPY, needs 4,240 B. That leaves about 11 KB for every other array, and more if your code is bigger. Two 96 × 96 matrices (72 KB) would not fit.

About how many cycles does a 64 × 64 f32 matvec take on one PE?

At about one multiply-add per cycle plus overheads: ≈ 54 + 64 + 4,096 ≈ 4,200. The simulator measured 4,214 on WSE-3 and 4,216 on WSE-2. WSE-3's wider SIMD does not help f32.

Eight microthreads: does that make a PE eight times faster?

No. They share one datapath. They let up to eight vector operations (usually ones started with .async = true) be in flight together, so sending, receiving and computing overlap and the datapath does not sit idle waiting for wavelets. Two in-flight operations may not use the same microthread.

In the matvec benchmark the WSE moves ~3× more bytes than a cached machine. Why is that acceptable?

The extra traffic is the y accumulator re-read and re-written for every column. It hits single-cycle SRAM private to that PE, and ~900k such SRAMs work in parallel, so there is no shared slow memory to protect. The measured run still does about one multiply-add per cycle.

An f32 array is walked with stride 4. Which banks does it touch under the SDK rule, and what does that cost?

An f32 at byte address a covers banks (a/2) mod 8 and the next one. With stride 4 the address advances 16 bytes per element, a full stripe, so every element lands in the same two banks (0 and 1 for an aligned start). The measured 256-element add took 546 cycles against 162 for stride 1 on WSE-3, about 3.4× slower.

A layer's activations are 90% zeros and stored as f32. Can you use the topic-04 index trick directly?

Not as is. Index plus value leaves only 16 bits for the value, so you would send f16/bf16 (losing precision) or spend two wavelets per value. You also pay one task activation and one scattered write per non-zero on the receiver.
