Host I/O and memcpy

The wafer has enormous internal bandwidth and a comparatively narrow door to the outside world. Every program in this course uses the SDK's memcpy runtime to get data on and off the wafer and to call device functions from Python. Knowing how it works inside explains several rules, and one bug we hit.

After this chapter you can

  • Estimate how long a host transfer takes, and say when the fixed per-transfer overhead dominates.
  • Name the columns memcpy adds around your rectangle (the memcpy frame) and compute the --fabric-dims and --fabric-offsets your program needs.
  • Trace how a host-to-device copy reaches the right PE: a demux down a column, then counter filters along each row.
  • Use the command stream correctly: every RPC must call unblock_cmd_stream() at the right moment, and commands run one at a time.
  • Choose between copy mode and streaming mode, and know why streaming needs a barrier before you read results and must send streams in the order the device consumes them.

The SDK's bandwidth benchmark puts it plainly (an I/O channel is one link into the frame described below): "The host connects the device via 100Gbps ethernets … The maximum bandwidth of a single channel is around 7Gbps … the overhead of TCP is about 200 us, a non-negligible cost when the transaction is small" SDK 2.10.1, bandwidth-test. Sixteen channels give at most about 14 GB/s, and only if channels scale linearly; that is more than one 100 GbE link carries (12.5 GB/s), so it assumes several links Derived. Filling 44 GB Vendor of on-wafer SRAM this way would take over three seconds Derived, while the SRAM itself can be read at 21 PB/s Vendor.

Two regimes follow. A big transfer is bandwidth-bound. A small one is overhead-bound: at 7 Gb/s, 200 µs is the time to move about 175 KB, so a single-channel transfer smaller than that spends more time on overhead than on data Derived. Program 01's 256-byte array costs about 200 µs to copy, an effective 1.3 MB/s Derived. The practical rules: batch data into few large copies, and keep the data that matters on the wafer (inference), or bring it in through dedicated hardware (MemoryX in training, Chapter 8).

The memcpy frame: what --memcpy adds

When you compile with --memcpy, cslc places extra PE programs in columns around your rectangle. We call them the memcpy frame. (Do not confuse it with the halo exchange of Chapter 13, where stencil neighbours swap edge cells; the SDK's own layout comments also call the outermost ring "halo".) The roles come from the library's layout files SDK 2.10.1 (runtime/layout_west_demux_cmdfan_multi.csl, layout_east_mux_multi.csl):

  • West, outside in: one halo column, then a demux adaptor (where the I/O link enters and which reconfigures the demux for each command), a demux (splits one host stream into per-row streams), and a command fan (forwards commands and data east into each row).
  • East: a mux (merges per-row results into one stream), a mux adaptor (where the link leaves, back to the host), and one halo column.
  • North and south: one halo row each.

So data from the host enters on the west, host-to-device (H2D), and results leave on the east, device-to-host (D2H). The arithmetic follows: west = 1 halo + 3 memcpy = 4 columns, so your (0,0) is fabric (4,1); east = 2 memcpy + 1 halo = 3; in total the fabric must be at least 7 columns wider and 2 rows taller than your rectangle SDK 2.10.1. The bandwidth benchmark computes exactly this, with fabric_offset_x = fabric_offset_y = 1 (the halo): core_fabric_offset_x = fabric_offset_x + 3 + width_west_buf, min_fabric_width = core_fabric_offset_x + width + 2 + 1 + width_east_buf, min_fabric_height = core_fabric_offset_y + height + 1 SDK 2.10.1, bandwidth-test/run.py:239–248. Compiling program 01 produced 3 west and 2 east frame programs (out/west/bin/*.elf, out/east/bin/*.elf) Measured, which matches.

  • Channels. Each channel is one I/O link with its own demux that serves a band of rows. For bandwidth-test at 5 rows, --channels=4 produced 4 demuxes over bands of 2, 1, 1 and 1 rows (out/west/out.json), and 11 west ELFs instead of 8. The column count did not change Measured.
  • Buffer columns. --width-west-buf and --width-east-buf insert FIFO columns so the link keeps flowing while your PEs are busy. Buffers shift your offset east by the same amount.

How a copy reaches its PE

A copy-mode memcpy_h2d to a w × h rectangle travels in two stages SDK 2.10.1 (runtime/demux.csl, memcpy/wse3/memcpyh2d.csl):

  1. Down the column. The link's stream enters the demux adaptor and is broadcast north to south through the demux column. Each demux PE has a counter filter (Chapter 4): a hardware counter that counts up by one on every wavelet, wraps from limit back to 0, and lets the wavelet through to the CE only when it reads 0. With h receiving rows, row y keeps wavelets y, y + h, y + 2h, … and turns them east into its row.
  2. Along the row. The command fan sends the row's wavelets east on color 23 to every PE in the row. Each PE has its own counter filter with limit = width − 1 and init_count = (limit + 1 − pid) % (limit + 1), so PE pid keeps every w-th wavelet, starting with wavelet pid. memcpy's task on that PE writes it into your exported array.

The direction matters. PE 1 on a row of 4 starts at (4 − 1) % 4 = 3. Counting up, it reads 3, 0, 1, 2, 3, 0, …, so it keeps wavelets 1, 5, 9, 13. Had it counted down from 3 it would keep wavelet 3 instead. The library's own table shows each PE's counter as the stream goes by (bold = kept) SDK 2.10.1, memcpy/wse3/memcpyh2d.csl:57–62:

wirex0x4x8x12x1x5x9x13…
PE 0 (init 0)01230123…
PE 1 (init 3)30123012…
PE 2 (init 2)23012301…
PE 3 (init 1)12301230…

What connects the host call to these filters. Nothing on the device is told "x0, y0, w, h" by magic; one host call sets everything up in this order SDK 2.10.1 (runtime/demux_adaptor.csl, layout_west_demux_cmdfan_multi.csl, memcpy/wse3/memcpy.csl):

  1. Command. memcpy_h2d(sym, A, x0, y0, w, h, l) becomes a command that enters on its own link (FABRIC_CMD) straight into the command fan, not through the demux, and is broadcast on color 22 into every row.
  2. Header. On the data link, the host runtime first sends the demux adaptor a small header: {enable_receiver[N], pes_per_receiver, pe_length}, that is, which rows get data, how many PEs per row, and how many wavelets per PE.
  3. Demux reconfigured. The adaptor sends the demux a teardown, the new configuration, and another teardown, so the demux column's filters now deal the stream over the h active rows.
  4. Row filters set. On every PE, memcpy's control task decodes the command. A PE in the region sets its counter filter from w and its own x (limit = w − 1, init_count above); a PE outside the region but in an active row only forwards; a PE in a row with no active PE unblocks color 22 at once.
  5. Data. The tensor itself streams in, sum(enable_receiver) × pes_per_receiver × pe_length wavelets, and each row's stream ends with a teardown wavelet that frees that row's command stream.

The library's own example: with 4 PEs and 4 elements each, the wire carries x0 x4 x8 x12 x1 x5 …, and PE 0 keeps x0, x1, x2, x3. Element j of every PE travels before element j + 1 of any PE. Step through it below.

Counter-filter step-through

Each step sends one wavelet. The highlighted demux PE and row PE are the ones whose counters read 0; every other PE in the active row forwards the wavelet and ticks. The host order decides which array element sits at each wire position.

The filter settings and the one-row example are from the library comments SDK 2.10.1. Combining the two stages into one wire order for h > 1 rows, and the host-index mapping, are Derived; the widget models one channel. ROW_MAJOR means the host array is A[h][w][l] in C order, so each PE's block is contiguous. COL_MAJOR means A[l][w][h], so element j of every PE is contiguous; the SDK builds it with loops l, w, h (bandwidth-test's hwl_2_oned_colmajor) or B.T.ravel() (row-col-broadcast) SDK 2.10.1. Notice that in COL_MAJOR the wire order equals the host order Derived.

Two consequences. First, the whole row takes part. If any PE in a row is in the copy region, every PE in that row sets its filter and forwards the data, so even a 1-PE copy occupies its row. Rows with no active PE skip the command at once SDK 2.10.1 (memcpy/wse3/memcpy.csl). So at any moment different PEs can be at different commands. What the host-level "one at a time" guarantees is per PE: each PE decodes commands in the order sent, and a later command reaches a PE only after that PE has finished every earlier one. Second, a copy completes on each PE only when its data is in memory. An active PE frees the command stream only after its write into your array finishes; a forwarding PE waits for the teardown wavelet that marks the end of the data SDK 2.10.1. That is why copy mode cannot race, as we will see.

The way back: how a D2H copy leaves the PEs

Copy-mode memcpy_d2h is not the H2D path run backwards, and the difference explains the experiment at the end of this chapter SDK 2.10.1 (memcpy/wse3/memcpyd2h.csl, memcpy.csl:391–399, sys_params.csl):

  1. One sender per row at a time. All PEs of a row share memcpy's D2H color 21, which runs east to the mux. At each PE that color has a switch with two positions: {rx = RAMP, tx = EAST} (this PE may send) and {rx = WEST, tx = EAST} (forward only). Only one PE of the row is in the "send" position.
  2. Round-robin by element. That PE's memcpy task sends its element j (one data wavelet), then a control wavelet that advances its own switch to "forward" and the next PE's to "send". The next PE then sends its element j, and so on along the row. The output therefore carries element j of every PE before element j + 1 of any PE, which is the same interleaving the H2D wire used. This is why color 21 is used: the library notes that only colors 0–9, 12, 13, 16, 17, 20 and 21 are switch-capable, and "D2H channel requires a switch, so we use color 21".
  3. Merge and leave. The mux column takes each row's output south to the mux adaptor, which sends it to the host. When the region's PEs have sent their last element, the first PE of the region sends a teardown, and each PE frees its command stream.
  4. Streaming D2H differs only at the start. Your output queue sends on your D2H color, which memcpy routes RAMP → RAMP back into input queue 0. memcpy's microthread then forwards each wavelet onto color 21 with the same {data, control} pairing.

The cost follows. Every element costs two wavelets on color 21 (data plus switch advance) and two task runs on the sending PE (memcpy's send-data and send-control tasks: the reserved local tasks 21 and 30 in the table above), and only one PE per row speaks at a time. H2D, by contrast, is one broadcast wavelet per element that each PE's filter accepts or forwards in hardware Derived.

What blocks, and where

nonblock=False does not mean the same thing for every call. A blocking memcpy_d2h must hand you data, so it returns only after every PE has run it. A blocking launch returns as soon as the RPC command has been sent. Three consequences:

  1. launch(..., nonblock=False) waits only for the command to be sent, not for your device function.
  2. The wait for the RPC happens inside the next command. That command cannot run on a PE until the PE calls unblock_cmd_stream(), so the host sits in the following memcpy (or launch) instead.
  3. A host wall-clock timer around launch() measures nothing. Time kernels on the device with the timestamp counter (Lab 3, Chapter 13), or accept that a timer around the next blocking call also includes the transfer.

We measured it: program 01 with saxpy made to loop its @fmacs 400 times (63,498 simulated cycles, WSE-3, SDK 2.10.1). launch() took 0.00 s of wall time and the following memcpy_d2h 5.06 s, the whole simulated run Measured. The labs follow the same rule. Their results are correct because the next command is what waits. In a host-driven loop such as Lab 5's CG, each phase's wait sits in the launch or copy that follows it, not in the launch that started the phase.

The keyword arguments are the command stream's knobs. order picks the host layout above. MEMCPY_32BIT moves 32-bit words. MEMCPY_16BIT exists too, but the host array is still 32-bit per element and the SDK tutorials strip the upper half afterwards with sdk_utils.memcpy_view SDK 2.10.1, topic-01. Every wavelet is 32 bits, so 16-bit data does not halve transfer time Derived. nonblock=True makes the call return a Task at once (wait with rt.task_wait(t) or poll rt.is_task_done(t)) SDK 2.10.1, SdkRuntime. That lets the runtime batch commands to save TCP overhead, but it never reorders them: they still run one at a time on the device. Other calls exist, among them call(name, u32_array) (an RPC with raw arguments, used by bandwidth-test), memcpy_h2d_rowbcast/colbcast and memcpy_h2d_stride.

If you know CUDA

memcpy_h2d is cudaMemcpy with the decomposition made explicit: you name a rectangle of PEs and the elements per PE. rt.launch() stands where <<<>>> does, but no threads start: it is an RPC queued in every PE's command stream, and the resident program's exported function runs once per PE. "Launch returned" only means the command was sent. As with an asynchronous CUDA launch, a kernel that never finishes shows up at the next copy, but where a CUDA cudaMemcpy would block forever, here, in the simulator, the copy errors after about 4 s with "could be a kernel stall" (Chapter 10). How hardware reports it we have not measured.

The command stream

Every host call becomes a short command on color 22, the command stream. The command fan broadcasts it into each row, and memcpy's control tasks on every PE decode it. A copy command carries the color or symbol, the region (px, py, w, h), the address, the elements per PE, a 16-bit flag and a copy type (dense, row broadcast, column broadcast, strided) SDK 2.10.1, sys_params.csl. An RPC carries a word count, the arguments and the function ID, all as 32-bit words SDK 2.10.1, memcpy.csl.

Commands are serialized per PE: a PE blocks color 22 while it handles a command and decodes the next one only after it is unblocked. For copies memcpy unblocks itself. For an RPC, your function must call sys_mod.unblock_cmd_stream(), directly or from a completion task: "The user must call unblock_cmd_stream() at the end of a RPC" SDK 2.10.1, memcpy.csl. If even one PE forgets, launch() still returns, but the next command never completes there. In the simulator the next memcpy then fails after about 4 s with "the received length (0 bytes) is not expected … could be a kernel stall", and no sim_stats.json is written, rather than hanging forever Measured (Chapter 10 and 11 reviews). Chapter 10's hang procedure shows how to find the PE.

Copy mode vs streaming mode

Copy mode (streaming=False) The host names an exported array. memcpy's own device tasks, running on your PE's CE and using colors 21–23 and queue 0, write or read it. The command does not complete on a PE until its data is in memory, so the next command always sees the data. Your code only exports the symbol, but it must leave the CE free for memcpy to run. Programs 01, 03, 04 and 05.
Streaming mode (streaming=True) The host passes a color ID instead of a symbol. Each element arrives as a wavelet on that color, and your data task (or a fabric DSD) must consume it. No launch is needed to start: arrival starts the computation (gemv-09) SDK 2.10.1. memcpy's job ends when the wavelets are handed to your queue. Processing them is your task's job, and memcpy cannot know when that is done. Program 02, which therefore still launches a wait_done barrier before reading results (below).
Use copy mode when…Use streaming mode when…
the data must sit in SRAM before compute starts (most kernels)each element can be consumed on arrival (reductions, pipelines)
the input fits in the PE's memorythe input is larger than memory, or you want to avoid buffering it
you want the simple, race-free pathyou accept the obligations: a data task or fabric DSD per color, a barrier before reading, and sending streams in the order the device consumes them

Where the streaming color comes from. You pick it at compile time, and it flows through three files. Copy and streaming share one host call; the color field decides which (IDs below 24 mean streaming) SDK 2.10.1, memcpyh2d.csl. memcpy accepts up to 4 streaming H2D and 4 streaming D2H colors (MEMCPYH2D_1…4, MEMCPYD2H_1…4) SDK 2.10.1, memcpy.csl. memcpy routes the color from the frame to your PEs, so you must not write routing for it: "The routing of the color MEMCPYH2D_DATA_1 must not be defined" SDK 2.10.1, topic-03. It comes out of your 0–19 budget. On the PE, the wavelet makes one extra trip through the router, and that trip is why the rule exists. memcpy's microthread 0 (UT0) takes each wavelet from color 23 off input queue 0, and sends it out through output queue 0, which memcpy has bound to your color. The wavelet goes down to the router, which turns it straight back up the ramp on your color (a RAMP → RAMP route that memcpy itself sets), into your own input queue, where your data task picks it up SDK 2.10.1, memcpy.csl:372–380. A route of yours for that color would conflict with memcpy's, and because the color really is routed on every PE, it uses up one of your 0–19.

Command-stream timeline: the bug we found in program 02

Program 02 (Lab 1) streams 100 values into a PE; a data task accumulates the sum and the sum of squares; then the host copies the statistics back. Toggle the barrier and press Play. Bar lengths are schematic; the values read are the measured ones.

What actually happened

Without the barrier the host read sum = 30.818176; the correct total was 26.137941. The value we got is exactly the float32 running sum after 95 of the 100 values. The count read by the next copy was already 100. At N = 500 the same experiment read the running sum after 495 values: again 5 short Measured. With the barrier, both N = 100 and N = 500 pass Measured.

The evidence shows that a streaming memcpy_h2d completes once memcpy has handed the last wavelet onward, not when your data tasks have processed it, so the next D2H copy raced the last few data tasks Derived. The library's own comment fits: "When UT0 is done, all data in IQ0 is drained, but OQ0 may not be empty" SDK 2.10.1, memcpy.csl, where UT0, IQ0 and OQ0 are memcpy's microthread 0, input queue 0 and output queue 0 (the figure above). Why about 5? On WSE-3, output queue 0 holds 2 wavelets and input queue 2, which program 02 uses, holds 4 SDK 2.10.1, memcpy.csl. Up to 6 values can therefore still be waiting when the copy reports done, which is consistent with the 5 we measured, though not a proof Derived.

Why could the D2H run before those 5 tasks? Chapter 5's run-to-completion rule says a task is never interrupted; it does not say which ready task runs next. When the D2H command's wavelet arrives on color 22, memcpy's control task for it becomes ready alongside the on_value tasks whose wavelets wait in input queue 2, and the task picker is not obliged to drain queue 2 first (Chapter 5, when several tasks are ready). Once memcpy's D2H tasks run, they read sum as it is at that moment Derived. The library guards its own side of the same hazard: "if D2H is after H2D, then we cannot guarantee OQ0 is empty, so D2H command must call QFLUSH(OQ0)" SDK 2.10.1, memcpy.csl:402–404. It flushes memcpy's queue, not yours, so your tasks still need the barrier.

The fix is an RPC that leaves the command stream blocked until the last data task runs. Both halves of the handshake:

course/programs/02-wavelet-tasks/pe_program.csl (excerpt)
task on_value(v: f32) void {
  ...                                       // update stats, count[0] += 1
  if (count[0] == @as(u32, N) and host_waiting) sys_mod.unblock_cmd_stream();
}
fn wait_done() void {
  if (count[0] == @as(u32, N)) { sys_mod.unblock_cmd_stream(); }  // already done
  else { host_waiting = true; }                                   // on_value() unblocks later
}

There is no race between the check and the flag. Tasks on a PE run to completion one at a time (Chapter 5), so on_value cannot run in the middle of wait_done.

Ordering matters too

Because commands are serialized, streams must be sent in the order the device consumes them. The SDK's gemv-09 tutorial warns: "If the b values were streamed in before x, the program would hang" SDK 2.10.1. The mechanism is back-pressure plus serialization Derived. The device's tasks wait for all of x before they consume b, so b's wavelets are not consumed. They fill the few-wavelet queues and back up through the frame to the link (Chapter 4's back-pressure). The b command therefore never completes. On the host, Python is still inside the blocking memcpy_h2d(b) call, so it never sends x. And even if x were sent, its wavelets would need the same demux and row path where b's stalled wavelets sit, and each PE decodes x only after it has finished b. Each side waits for the other. The program-02 race and this hang are one model: a streaming copy finishes when the device has accepted the last wavelet, not before the device has room and not after your task has run.

For inputs that every PE in a row or column needs, memcpy_h2d_rowbcast and colbcast let the host send one column (or row) of data instead of a replicated tensor. In the SDK's example a column of 4 values goes to a 3 × 4 region as 4 elements instead of 12, saving host bandwidth 3× (host-to-device only) SDK 2.10.1, row-col-broadcast. The command carries the broadcast type, and memcpy on the device does the rest.

Check yourself

Your RPC starts an async send and returns. Where should unblock_cmd_stream() go?

In the completion task the send activates (as in programs 03–05). Unblocking at the end of the RPC would let the next command run, whether a D2H copy or another launch reusing the same queue, while the send is still in flight.

Your program-03 variant has P = 10 PEs in one row. What --fabric-dims and --fabric-offsets do you pass, and why?

17,3 and 4,1. The frame adds 7 columns (west: 1 halo + demux adaptor + demux + command fan; east: mux + mux adaptor + 1 halo) and 2 halo rows. Your (0,0) sits after the four west columns and the top halo row.

A copy sends 4 elements to each of 4 PEs in one row. Which wire positions does PE 2 keep?

Positions 2, 6, 10 and 14. Its counter filter starts at (4 − 2) % 4 = 2, reaches 0 on the third wavelet and every fourth after that. In ROW_MAJOR those wavelets carry host elements 8, 9, 10 and 11.

Why does a copy-mode memcpy_h2d followed by launch never race, when a streaming one can?

In copy mode each PE frees the command stream only after memcpy's own task has written the data into memory. In streaming mode memcpy's part ends when it hands the wavelets to your queue; your data task finishes the job later, so you need a barrier.

You stream b, then x, but the device consumes all of x first. What happens and why?

Deadlock. b's wavelets are not consumed, back-pressure stops the b command from completing, and the host, still inside the blocking memcpy_h2d(b), never sends x. Even if it did, each PE would decode x only after finishing b.

Why does every course program use queues ≥ 2 and colors below 20 (in practice 0–3)?

memcpy owns colors 20–23 on both architectures, and input/output queue 0 (data) plus, on WSE-3, queue 1 (the command stream). Everything below those colors and from queue 2 up is free; the course simply starts at color 0 and queue 2.

One of program 01's copies moves 64 floats to the device. Roughly how long does that copy take on a real system, how long does the whole program's I/O take, and what would you change for a big workload?

About 200 µs, almost all of it TCP overhead; the 256 bytes themselves take under a microsecond at 7 Gb/s. Program 01 issues four commands (two H2D copies, one launch, one D2H), so if each pays the overhead its I/O costs about 0.8 ms. Batch data into few large copies (or nonblocking calls the runtime can aggregate), and keep data resident on the wafer.
