Host I/O and memcpy

The wafer has enormous internal bandwidth and a comparatively narrow door to the outside world. Every program in this course uses the SDK's memcpy runtime to get data on and off the wafer and to call device functions from Python. Knowing how it works explains several rules — and one bug we hit.

After this chapter you can

  • Explain the memcpy "halo" columns and why your rectangle needs --fabric-offsets.
  • Choose between copy mode and streaming mode.
  • Use the command stream correctly: every RPC must call unblock_cmd_stream(), and a streaming copy needs a barrier before you read results.

The SDK's bandwidth benchmark puts it plainly: "The maximum bandwidth of a single channel is around 7Gbps … the overhead of TCP is about 200 us" SDK 2.10.1. Sixteen channels give roughly 14 GB/s, so filling 44 GB of SRAM through this path would take over three seconds Derived — while the SRAM itself can be read at 21 PB/s. Conclusion: data that matters must stay on the wafer (inference), or arrive through dedicated hardware (MemoryX in training, Chapter 8). In this course's labs, host transfers dominate total runtime — Lab 3 measures this.

What --memcpy adds around your program

When you compile with --memcpy, cslc generates extra PE programs in columns to the west and east of your rectangle: command fan-out and host→device demultiplexing on the west, device→host multiplexing on the east. For our programs with --channels 1 the compiler emitted 3 west and 2 east columns Measured from out/.

memcpy also claims a fixed set of on-chip resources on every PE SDK 2.10.1:

Six calls on the host

course/programs/01-saxpy/run.py
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder

rt = SdkRuntime(args.name, cmaddr=args.cmaddr)     # cmaddr=None → simulator
xs, ys = rt.get_id('x'), rt.get_id('y')         # exported symbol IDs
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
rt.memcpy_h2d(xs, x, 0, 0, 1, 1, N, **kw)            # (x0, y0, width, height, elements per PE)
rt.memcpy_h2d(ys, y, 0, 0, 1, 1, N, **kw)
rt.launch('saxpy', a, nonblock=False)                # RPC with an f32 argument
rt.memcpy_d2h(out, ys, 0, 0, 1, 1, N, **kw)
rt.stop()

The four integers name a rectangle of PEs (x, y, width, height) and the last is the element count per PE. Splitting data across PEs is the host's job: for an array going to a row of P PEs, element block k lands on PE k (programs 03 and 04 lay out their arrays this way).

The command stream

Every host call becomes a command wavelet on color 22, decoded by memcpy's control tasks on the device. Commands are serialized. While an RPC runs, the stream is blocked; the device function must call sys_mod.unblock_cmd_stream() — directly or from a completion task — before the next command can run. "The user must call unblock_cmd_stream() at the end of a RPC" SDK 2.10.1, memcpy.csl. Forget it on even one PE and the host hangs on its next call.

Copy mode vs streaming mode

Copy mode (streaming=False) The host names an exported array; memcpy writes or reads it on a rectangle of PEs. Device code is not involved beyond exporting the symbol. Simple and safe. Programs 01, 03, 04, 05.
Streaming mode (streaming=True) The host passes a color ID instead of a symbol; each element arrives as a wavelet that your data task (or fabric DSD) must consume. No launch needed — arrival starts the computation. Program 02.

Command-stream timeline: the bug we found in program 02

Program 02 streams 100 values into a PE; a data task accumulates sum and sum of squares; then the host copies the statistics back. Toggle the barrier and press Play. Bar lengths are schematic; the values read are the real measured ones.

What actually happened Without the barrier the host read sum = 30.818; the correct total was 26.138. The value we got is exactly the running sum after 95 of the 100 values Measured. A streaming memcpy_h2d completes when the host has injected its wavelets, not when the device has processed them, so the following D2H copy raced the last few data tasks. The fix is an RPC that leaves the command stream blocked until the last data task runs: 
fn wait_done() void {
  if (count[0] == @as(u32, N)) { sys_mod.unblock_cmd_stream(); }  // already done
  else { host_waiting = true; }                                   // on_value() unblocks later
}

Ordering matters too

Because commands are serialized, streams must be sent in the order the device expects. The SDK's gemv-09 tutorial warns: "If the b values were streamed in before x, the program would hang" SDK 2.10.1. For bulk inputs that every PE in a row or column needs, memcpy_h2d_rowbcast/colbcast send one copy and let the fabric replicate it, saving host bandwidth (host→device only).

Check yourself

Your RPC starts an async send and returns. Where should unblock_cmd_stream() go?

In the task activated when the send completes (as in programs 03–05), not at the end of the RPC — otherwise the host could issue a D2H copy before the data has moved.

Why does every course program use queues ≥ 2 and colors ≤ 4?

memcpy owns queues 0–1 on WSE-3 and colors 20–23. Low colors and queues from 2 up are free.

Why can't you treat the wafer like a GPU and stream weights in for each request?

The SDK host path is ~7 Gb/s per channel, about 14 GB/s at most — orders of magnitude below on-wafer bandwidth. Data must stay resident or come through MemoryX.
