DSDs: loops as hardware

With no hardware caches and no DRAM (only a tiny software-managed cache, Chapter 3), the WSE needs a different way to make memory access cheap. The answer is the data structure descriptor (DSD): a description of a whole walk over memory, or over a stream of wavelets, which the PE's address generator executes so that one instruction processes an entire vector.

After this chapter you can

  • Write memory DSDs in both spellings (tensor_access and base/extent/stride), predict exactly which words they touch, and move a DSD at run time with @increment_dsd_offset and friends.
  • Estimate how long a DSD instruction takes from measured per-element rates, and lay out arrays so that operands do not collide in SRAM.
  • Declare fabric DSDs on queues, and explain why the direction of a transfer lives in the routes, not in the DSD.
  • Run DSD operations asynchronously, chain them through completion tasks, and avoid the two classic stalls: a blocking fabric op, and a data task competing with a fabric DSD.
  • Use a FIFO to absorb bursts or to work around WSE-3's one-fabric-input rule, and say what it costs.

One instruction, a whole loop

In C you would write for (i = 0; i < N; i++) y[i] += x[i] * a;. In CSL you describe x and y once and issue one instruction (Lab 1, program 01, run in Chapter 11):

course/programs/01-saxpy/pe_program.csl
const x_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> y[i] });

fn saxpy(a: f32) void {
  @fmacs(y_dsd, y_dsd, x_dsd, a);   // y[i] = y[i] + x[i] * a   for all N
  sys_mod.unblock_cmd_stream();     // tell the host this call is done (Chapter 7)
}

Reading CSL: @name is a builtin, .{ .a = 1 } is an anonymous struct literal, and |i|{N} -> x[i] reads "for i in 0..N, element x[i]". Chapter 10 covers the language.

The descriptor is loaded into a data-structure register (DSR); a WSE-3 core has 48 of them Vendor, WSE-3 (HC2024) (no WSE-2 count has been published). The datapath walks the descriptor, generating addresses and streaming operands through the arithmetic unit, with no per-element instruction fetch, loop counter or branch Derived from SDK and vendor descriptions. The tensor_access form names an induction variable, a bound and an affine index: |i|{M} -> A[i*N] means "M elements starting at A[0], stride N", which is a column of a row-major matrix.

If you know CUDA

A DSD is the whole loop, not one lane of it: @fmacs(y_dsd, y_dsd, x_dsd, a) replaces a grid-stride loop, and the descriptor's extent, stride and offset do the job of threadIdx. The CUDA habit of one element per thread becomes one long DSD per PE. Scalar code that moves a DSD around in a loop costs about 33–35 cycles per step Measured, simulator, so keep loops inside descriptors (below). Appendix B maps the rest: warps, loops and shared-memory bank conflicts (the placement rule below).

Two spellings, and moving a DSD

Every 1-D memory DSD is base address + extent + stride. tensor_access is a readable way to write the same thing; the SDK's gemv-02 tutorial shows both side by side SDK 2.10.1, gemv-02-memory-dsds. A DSD is also an ordinary run-time value: you can change it between instructions. That is how a 2-D algorithm is built from 1-D instructions. The scalar loop runs over columns, and the loop over the M elements of each column stays in hardware:

SDK tutorials/gemv-02-memory-dsds/pe_program.csl (condensed)
var A: [M*N]f32;                       // row-major M x N
var A_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{M} -> A[i*N] });
//  same as  @get_dsd(mem1d_dsd, .{ .base_address = &A, .extent = M, .stride = N });

for (@range(u16, N)) |i| {
  @fmacs(y_dsd, y_dsd, A_dsd, x[i]);             // y += A[:, i] * x[i]
  A_dsd = @increment_dsd_offset(A_dsd, 1, f32);  // slide to column i+1
}
@fadds(y_dsd, y_dsd, b_dsd);                     // y = A x + b

GEMV column sweep

The gemv-02 program exactly: M = 4, N = 6, A[idx] = idx, x = 1, b = 2. Each step runs one @fmacs over the column that A_dsd currently describes, then moves the DSD.

The same pattern, "a 1-D DSD times a scalar, move the DSD, repeat", is the inner loop of Lab 4's matrix multiply: program 06 runs @fmacs(C_dsd, C_dsd, A_dsd, Bp.*[j * Kt + k]) and then @increment_dsd_offset(A_dsd, Mt, f32) to step to the next column of its A tile (Chapter 14) course program 06-summa.

More than one dimension: mem4d_dsd

A DSD can nest several induction variables. Leaving an index out of one operand's access expression makes that operand repeat, which turns a nested loop with a reduction into one instruction. The 25-point stencil sums the data received from four directions this way SDK 2.10.1, benchmarks/25-pt-stencil/task.csl:

var buffer = @zeros([directionCount, pattern, chunkSize]f32);
const bufferDsd = @get_dsd(mem4d_dsd, .{
  .tensor_access = |i,j,k|{directionCount, pattern, chunkSize} -> buffer[i, j, k] });
const accumulatorDsd = @get_dsd(mem4d_dsd, .{
  .tensor_access = |i,j,k|{directionCount, pattern, chunkSize} -> accumulator[k] });  // ignores i, j
const dstDsd = @increment_dsd_offset(accumulatorDsd, offset, f32);
@fadds(dstDsd, dstDsd, bufferDsd);   // accumulator[k] += buffer[i, j, k] for every i, j, k

The destination walks accumulator[0..chunkSize) once for every (i, j), so every direction and pattern slice is folded onto the same few words. The same shape (a 3-D buffer reduced onto acc[k]) compiled for WSE-3 in our test Measured, cslc 2.10.1.

How fast is one instruction?

We timed single DSD instructions in the simulator: one op over 1,024 elements, memory to memory, on a 1 × 1 rectangle, bracketed by the PE's timestamp counter (TSC: a per-PE cycle counter that the <time> library module reads; Chapter 11 and Appendix C show how), using the SDK's single-tile-matvec harness. The three operands are separate arrays 1,025 words apart (4,100 bytes, which is 4 bytes apart within the 16-byte bank cycle: a slow placement for WSE-2 adds and f16, see the placement table). Three things follow.

  • A fixed start-up of about 15–17 cycles for an isolated op bracketed by timestamp reads, then a fixed rate per element. @fmacs over 1 / 16 / 64 / 256 / 1,024 elements took 18 / 33 / 81 / 273 / 1,041 cycles on WSE-3 Measured. Consecutive ops inside one task start faster, in about 6 cycles each on WSE-3 and 5 on WSE-2 (Chapter 13) Measured, Chapter 13. Either way, vectors of a few dozen elements or fewer spend a large share of their time starting.
  • f32 multiply-accumulate runs at one element per cycle on both chips (when its sources do not share a bank); WSE-3 doubled the rate of simple moves, but not of f32 FMAC Measured. Adds reach 2 per cycle on both chips when placed well, and WSE-2 drops to 1 per cycle otherwise (table). That is why Lab 3 (f32) is a wash between the chips (Chapter 13). We know the rate, not the hardware reason; do not read an f32 lane count into it.
  • Precision is where SIMD width pays off, if the operands are placed for it. In-place f16 FMAC runs at about 4 per cycle on WSE-3 in every placement tested (272 cycles for 1,024). On WSE-2 it runs at about 4 per cycle (270) when the two sources start 8 bytes apart in the 16-byte bank cycle, and about 2 (526) otherwise, including the layout of the table above Measured, Appendix E. The vendor SIMD widths for FP16 are 4 (WSE-2) and 8 (WSE-3) Vendor. In a full f16 matvec (the SDK benchmark, N = 64) we measured 2,165 cycles on WSE-2 and 1,335 on WSE-3, against 4,216 and 4,214 in f32 Measured, simulator. The SIMD width is a ceiling, not a rate. WSE-2 reaches its full 4-wide f16 rate only with the right placement; on WSE-3 we never saw more than about 4 f16 FMACs per cycle (about 7 for a plain move), half its 8-wide SIMD, and no source says why Derived.

Layout matters: operand collisions in SRAM

A PE's 48 KB is 8 single-ported banks Vendor, HC22. Academic papers describe them as 6 KB each, interleaved by 32-bit word Independent; the SDK numbers them differently (below), and Cerebras has not published the physical layout (Chapter 3, Appendix E). An FMAC needs two source words and writes one word every cycle, so if its streams keep landing on the same hardware, it slows down. The SDK's matvec benchmark shifts A by one word (A_array[i+1]) and pads each column to a multiple of 4 words, "to avoid bank conflicts" SDK 2.10.1, single-tile-matvec. We measured what that buys:

  • Matvec without the +1 shift: 2,134 instead of 1,110 cycles (N = 32), 8,310 instead of 4,214 (N = 64), almost exactly 2× Measured, WSE-3.
  • Unpadded columns: N = 31 with stride 31 took 1,294 cycles instead of 1,078 padded to 32 (+20%), because only some columns then collide Measured by the ch06 depth review, WSE-3.
  • Single @fmacs over 1,024 elements: the time doubles exactly when its two source streams start at word addresses that are equal modulo 4 Measured, WSE-2 and WSE-3. The next section explains why "mod 4", and the table gives the other ops.
  • Lab 1 hits this case. Program 01 as shipped declares x and y back to back, and N = 1,024 is a multiple of 4, so its @fmacs takes 2,063 cycles on WSE-3 (2,062 on WSE-2). One padding word between the arrays gives 1,039 (1,038) Measured, TSC, Chapter 11.

Which bank does an operand start in? The placement rule

The SDK's cs_readelf man page gives the rule: "The bank a memory access lies in is determined by bits [3:1] of the address … A 32-bit read of the same address is broken into two 16-bit reads … Bank conflicts where concurrent reads and writes target the same bank or the same bank modulo 4 may result in cycle delays" SDK 2.10.1, cs_readelf(1). Its --sym output prints the banks of every variable, and they follow that rule Measured, cslc 2.10.1 ELFs. So the SDK numbers banks in 16-bit units: bank = (byte address ÷ 2) mod 8. An f32 word covers banks 2k and 2k + 1, four words cover all eight, and the pattern repeats every 16 bytes SDK 2.10.1.

That is where "mod 4" comes from. Two streams whose start addresses are equal mod 4 words (16 bytes) start in the same bank, and because they step in lockstep they hit the same banks on every cycle: the man page's "same bank" case. The man page's second clause, "same bank modulo 4" (banks b and b + 4, 8 bytes apart), predicts a second slow case, but it does not slow f32 at all; on WSE-2 it is the fast placement Measured, Appendix E. The widget draws the streams on the 16-bit bank ruler.

One rule for placement Rates are layout-dependent. Peak needs the two source streams in opposite halves of the 16-byte bank cycle, that is, starting 8 bytes (2 f32 words, 4 f16 elements) apart mod 16; the same bank halves the rate Measured. The rule differs by chip: on WSE-3 only f32 FMAC is sensitive (to the same bank), while on WSE-2 adds and f16 also need the 8-byte placement. That explains Lab 3's fast add on both chips (u[i] and u[i+2] are 8 bytes apart, Chapter 13) and Lab 1's slow FMAC (x and y in the same bank). To place arrays, put a 2-word pad between them and check the start banks with cs_readelf --sym (Chapter 10). Short vectors can still surprise you (at N = 64 program 01's unpadded case clashes on WSE-3 but not WSE-2, Chapter 11), so pad and measure.

Where the descriptor lives: DSRs, @load_to_dsr and @map

Normally the compiler loads each DSD into a DSR before the instruction that uses it, and a DSD that is not known at compile time costs DSRs (cslc --dump-dsr-alloc-graph shows the allocation) SDK 2.10.1, topic-15 (Chapter 10). DSRs come in three roles, destination, source 0 and source 1, and you can load them yourself. With .save_address = true the register keeps its end address after an op, so the next op continues where the last one stopped. The SDK matvec uses this so that the whole outer loop becomes one @map over x:

SDK benchmarks/single-tile-matvec/src/pe_matvec.csl (condensed)
const y_dest_dsr = @get_dsr(dsr_dest, 0);
const y_src0_dsr = @get_dsr(dsr_src0, 0);
const A_src1_dsr = @get_dsr(dsr_src1, 0);
fn step(curX: f32) void { @fmacs(y_dest_dsr, y_src0_dsr, A_src1_dsr, curX); }

@load_to_dsr(y_dest_dsr, y_dsd, .{ .save_address = false });
@load_to_dsr(y_src0_dsr, y_dsd, .{ .save_address = false });
@load_to_dsr(A_src1_dsr, A_dsd, .{ .save_address = true });  // A keeps advancing
@map(step, x_dsd);                                         // one FMAC column per x[j]

What @map actually does. Its signature is @map(fn, inputs…, output): the inputs are DSDs or scalars, the last argument receives each result, and @map calls fn once per element of its DSDs SDK 2.10.1, topic-10-map-builtin. It is fast per element only when fn itself issues one vector op over many elements, as step does above. Lab 5's dot product uses the other kind, a scalar body:

Fabric DSDs: communication is an operand

What a fabric op does when the fabric is not ready. The fabric never drops a wavelet: a full queue pushes back on the sender (Chapter 4, back-pressure). A DSD op on the fabric inherits that. If its input queue is empty, or its output link is backed up, it waits, element by element, on its microthread; the CE and the other microthreads carry on SDK 2.10.1, pipeline-01 README. Three things on this page follow from that one fact: a synchronous fabric op can deadlock, because then the CE is the thing waiting (below); "completion" of a send means the data left this PE's output queue; and pipeline-01 stalls past 14 wavelets (FIFOs).

A fabric DSD is a DSD that names a queue (and through it a colour) instead of memory. A fabin_dsd describes "the next extent wavelets arriving on this input queue"; a fabout_dsd describes "send extent wavelets out of this output queue". Plug them into the same builtins and data is moved and computed on in one step. Here is how Lab 2's row reduction (program 03, Chapter 12) declares them:

course/programs/03-row-reduce/pe_program.csl
const oq: output_queue = @get_output_queue(2);
const iq: input_queue  = @get_input_queue(2);

const out_dsd = @get_dsd(fabout_dsd, if (@is_arch("wse3")) .{ .extent = M, .output_queue = oq }
                                     else .{ .extent = M, .output_queue = oq, .fabric_color = send_color });
const in_dsd  = @get_dsd(fabin_dsd, .{ .extent = M, .input_queue = iq });

comptime {   // bind the queues to colours (Chapter 5)
  @initialize_queue(oq, if (@is_arch("wse3")) .{ .color = send_color } else .{});
  @initialize_queue(iq, .{ .color = recv_color });
}

// middle PE: receive the running sum, add my own v, send the result on
@fadds(out_dsd, in_dsd, v_dsd, .{ .async = true, .activate = exit_id });

A fabric DSD has no base address and no stride. Its extent counts elements arriving or leaving, and it names a hardware queue; the queue is bound to a colour. On WSE-2 the outgoing colour is a field of the fabout DSD, on WSE-3 it is fixed when the queue is initialised SDK 2.10.1, program 03 and topic-05. Two details from the SDK:

  • 16-bit data packs two per wavelet. With 16-bit operands the extent counts operands, not wavelets: "Each operand is 16-bits while 'size' specifies the number of 32-bit wavelets. Each wavelet packs 2 16-bit operands", hence .extent = size * 2 SDK 2.10.1, sdklayout-04-h2d-d2h.
  • "Infinite" streams. Streaming kernels that never know their length use const INFINITE_DSD_LEN: u16 = 0x7fff; as the extent SDK 2.10.1, pipeline-02 and pipeline-03.
One consumer per queue If a data task is bound to the queue (WSE-3) or colour (WSE-2) that a fabin DSD reads, each arriving wavelet activates the task, and the task consumes the wavelet before the DSD can. Either bind no data task to that queue, as programs 03 and 04 do, or @block it while the DSD op runs SDK 2.10.1, pipeline-01. Chapter 5 shows the task side of this.
WSE-3 limit: one fabric input per operation "WSE3 does not allow multiple fabric inputs per DSD operation" SDK 2.10.1, sdklayout-03. To add two incoming streams, first drain one into a FIFO (explained below), then operate on FIFO + fabric. Lab 2's reduction only ever has one fabric input, so the same source runs on both chips (only the fabout DSD fields differ, via @is_arch) Measured, simulator, WSE-2 and WSE-3.

Data picks the address: wavelet_index_offset

A wavelet can carry an index as well as a value (Chapter 3's 16-bit value + 16-bit index payload SDK 2.10.1, topic-04). A memory DSD declared with .wavelet_index_offset = true accepts a per-call .index that shifts where it starts, so the arriving data chooses which column to work on:

SDK benchmarks/gemv-checkerboard-pattern/pe.csl (condensed)
var A = @zeros([A_local_dim_x, A_local_dim_y]f16);   // row-major
const dsd_A = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{A_local_dim_x} -> A[i, 0],
                                     .wavelet_index_offset = true });
task fmac_task(wlet_data: f16, idx: u16) void {   // one wavelet = (x_j, j)
  @fmach(dsd_mul_temp, dsd_mul_temp, dsd_A, wlet_data, .{ .index = idx });   // y += A[:, j] * x_j
  ...

The f32 version in the sdklayout-05-gemv tutorial passes .index = 2 * idx to reach column idx, so the offset appears to count 16-bit units Derived from the two SDK uses. This is how dataflow sparsity works at the instruction level: a sender that skips zero xj never sends them, and the receiver's DSD jumps straight to the right column for the ones that do arrive.

Async operations and completion tasks

Add .async = true and the operation runs on a microthread while the CE moves on. Two optional fields say what to do when it finishes: .activate = id (mark that local task ready) or .unblock = id (clear its blocked bit). Chapter 5 explains those two bits; here is what they look like in real code. Program 04 (Lab 3) uses both kinds of op:

course/programs/04-heat-stencil/pe_program.csl
// synchronous: the CE executes this to completion before the next line
@fadds(lap_dsd, left, right);
// asynchronous: started on a microthread; the CE continues; t_se runs when it finishes
@fmovs(to_e, last_cell, .{ .async = true, .activate = done_se });
  • What "finished" means. Completion is local to this PE's side of the transfer: for a send, the last element has left this PE's output queue. It says nothing about whether the neighbour has received it; only the receiver's own op completion tells the receiver Derived.
  • Why fabric ops should be async. A synchronous op on a fabin DSD keeps the CE inside that instruction while it waits for wavelets. If those wavelets depend on something the CE itself must do first, nothing can progress. SDK pipeline-01 shows the real case: a blocking @add16(outDsd, inDsd, 1) on a memcpy input stream (an H2D, host-to-device, copy; D2H is the reverse; Chapter 7) stalls, "the instruction trace shows @add16 repeatedly querying data from input queue 1, which is still empty … The CE has no resource to run the H2D command received by the router" SDK 2.10.1, pipeline-01. The reason is that memcpy is not a DMA engine: its receive handler runs as tasks on this PE's own CE (Chapter 7) SDK 2.10.1, memcpy, and a CE stuck inside @add16 cannot run them. Blocking sends of a couple of wavelets can work (topic-04 does it), but the SDK notes async "would be better".
  • .unblock as a throttle. A data task blocks itself, starts an async send from its buffer, and lets the send's completion unblock it, so only one send is ever in flight and later wavelets wait in the queue:
SDK tutorials/topic-09-fifos/buffer.csl
task process_task(element: f32) void {
  @block(process_task_id);                     // do not run again until the send is done
  elem[0] = element * element * element;
  @fmovs(out_dsd, elem_dsd, .{ .async = true, .unblock = process_task });
}

FIFOs extend the tiny hardware queues

Hardware queues hold only a handful of wavelets: the WSE-2 memcpy library's comments give input-queue depths of 6, 4 and 2 wavelets for queues 0–1, 2–3 and 4–7 SDK 2.10.1, csl-libs/memcpy/wse2/memcpy.csl. In SDK pipeline-01, where a single PE loops memcpy input straight back out, the program "stalls when size exceeds 14", and the capacity is architecture-dependent SDK 2.10.1, pipeline-01/02. The README gives the mechanism: H2D and D2H are serialized, so the host starts the D2H only after the H2D finishes, and the H2D finishes only once all its data has been pushed into the I/O path's internal queues. The output cannot drain until then; once those queues are full, back-pressure (Chapter 4) stops the input and the H2D stalls. So 14 is the total buffering along that I/O path, not the depth of one queue.

@allocate_fifo(buffer) turns an SRAM array into a FIFO. One async op pushes into it and another pops from it; each runs on its own microthread, so the producer never waits for the consumer as long as the buffer has room. "The FIFO requires two microthreads and a scratch buffer" SDK 2.10.1, pipeline-02. The ops can compute on the way through:

SDK tutorials/topic-09-fifos/buffer.csl
var fifo_buffer = @zeros([1024]f32);
const fifo = @allocate_fifo(fifo_buffer);
@fadds(fifo, in_dsd, ten_dsd, .{ .async = true });   // fabric -> FIFO, adding 10
@fnegs(loopback_dsd, fifo, .{ .async = true });     // FIFO -> fabric, negated

Lab 3's whole update, in three instructions

The stencil keeps ghost cells at both ends of its array so that three overlapping DSDs see the left neighbour, the cell itself, and the right neighbour of every cell (program 04, Chapter 13):

course/programs/04-heat-stencil/pe_program.csl
const left  = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i] });
const mid   = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i + 1] });
const right = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{n} -> u[i + 2] });

@fadds(lap_dsd, left, right);         // lap[i] = u[i] + u[i+2]   (left + right neighbour of cell i+1)
@fmacs(lap_dsd, lap_dsd, mid, -2.0);  // lap[i] += -2 * u[i+1]
@fmacs(mid, mid, lap_dsd, alpha);    // u[i+1] += alpha * lap[i]

Here i is the DSDs' induction variable, so cell i of the rod lives at u[i+1]. The update can be in place because the first two instructions finish lap for every cell before the third overwrites any u; a single fused pass would read left neighbours that were already updated. Pick the "Lab 3 stencil" preset in the visualizer to see the three overlapping windows; at 2.5 cycles per cell (above), the three instructions stream for 40 cycles at n = 16 on WSE-3 Derived, plus about 19 cycles of start-up (about 6 per instruction), ≈ 59 cycles in all, which is what Chapter 13 measures Measured, Chapter 13.

Check yourself

Write a DSD for the main diagonal of an 8 × 8 row-major matrix.

|i|{8} -> A[i * 9] (stride 9), or, if A is declared [8, 8]f32, |i|{8} -> A[i, i].

After A_dsd = @increment_dsd_offset(A_dsd, 1, f32) on |i|{6} -> A[i*8], which words does it visit?

1, 9, 17, 25, 33, 41: the next column.

What does a stride of 0 do?

It visits the same word every time: a broadcast of one memory value as a vector operand.

Estimate the WSE-3 cycles for @fadds over 512 f32 elements, and for @fmacs over the same.

About 17 + 512/2 ≈ 270 cycles for the add, and about 17 + 512 ≈ 530 for the FMAC (measured rates: 2 and 1 elements per cycle).

Lab 1's program 01 runs its @fmacs at 2 cycles per element, not 1. Why, and what fixes it?

x and y are declared back to back and N = 1,024 is a multiple of 4 words, so y starts 4,096 bytes after x: equal mod 16 bytes, the same SDK bank. The two source streams then hit the same banks on every cycle (2,063 cycles on WSE-3). A padding word between the arrays moves y to a different start bank and gives 1,039 cycles; a 2-word (8-byte) pad is the placement that is fast for every op in the table. The SDK matvec does the same with its one-word shift of A.

Why is @fadds(out_dsd, in_dsd, v_dsd) faster than receiving into memory and then adding?

It avoids writing the incoming vector to SRAM and reading it back, saves one instruction start-up, and overlaps receive, add and send in one pipelined operation.

Where in in_dsd is the direction "from the west" encoded?

Nowhere. The DSD names an input queue bound to a colour, and the layout's route for that colour makes it arrive from the west.

On WSE-3 you want out = in_west + in_east, both from the fabric. Why does @fadds(out, in_w, in_e) not work, and what do you write instead?

WSE-3 allows one fabric input per op. Drain one stream into a FIFO with an async @fmovs(fifo, in_w, .{.async = true}), then @fadds(out, in_e, fifo, .{.async = true}). That costs two microthreads and the buffer.

Your async send activates done, and done calls unblock_cmd_stream(). Does that guarantee the neighbour has received the data?

No. Completion is local to the sender's operation. The receiver's own op completion is what tells the receiver.

A data task is bound to input queue 2, and you also start @fmovs(buf, in_dsd) on a fabin DSD for queue 2. What goes wrong?

The data task fires for each arriving wavelet and consumes it first, so the DSD op starves (or the data are silently eaten by an empty task). Block the task, or do not bind one to that queue.
