CSL and the toolchain

CSL — the Cerebras Software Language — looks like Zig, but its real content is a type system for hardware resources: colors, queues, tasks and descriptors. This chapter covers the language, the three files every program has, and the toolchain that turns them into a running simulation.

After this chapter you can

  • Read every line of a complete CSL program and say what runs where and when.
  • Compile and simulate with cslc and cs_python, and find the outputs.
  • Set up the SDK in a fresh Linux environment.

The language in one screen

Ordinary parts

  • Types: bool, i16, i32, u16, u32, f16, f32, arrays [N]f32, pointers *[N]f32 and many-item [*]f32.
  • const / var, fn, if/else (with braces when used as statements), for (@range(i16, n)) |i|, while (c) : (i += 1).
  • Builtins start with @: @as, @zeros, @bitcast, @get_dsd...
  • No null pointers. Runtime functions take pointers, not arrays.

Hardware parts

  • param: compile-time constants from the layout or --params. Different params → different ELF.
  • comptime { }: bindings and exports evaluated at compile time.
  • Resource types: color, input_queue, output_queue, data_task_id, local_task_id, control_task_id, mem1d_dsd, fabin_dsd, fabout_dsd.
  • @is_arch("wse3") picks per-chip code in one source file.
Most bugs are resource bugs Every bug we hit while writing this course's programs was about a resource, not arithmetic: an export's mutability flag, a race on the command stream, two operations sharing a microthread. The scalar language is the easy part.

From source to simulation

course/programs/01-saxpy/commands.sh
cslc --arch=wse3 ./layout.csl --fabric-dims=8,3 --fabric-offsets=4,1 \
     --params=N:64 -o out --memcpy --channels 1
cs_python run.py --name out
FlagMeaning
--arch=wse2|wse3target chip (default wse2). All course programs build for both.
--fabric-dims=W,Hsize of the simulated fabric, including memcpy's columns
--fabric-offsets=X,Ywhere your rectangle's (0,0) sits in the fabric
--params=N:64,...values for the layout's params
--memcpy --channels 1add the host-I/O runtime with one channel (up to 16)
--out-routes, --fp16-formatdump per-PE routing; choose f16 / bf16 / cb16

A cheap trick we used for program 02's race: export an extra array, have the data task record each running sum into it, read it back, and compare with numpy.cumsum. On a deterministic simulator, recording state is often faster than stepping a debugger.

Setting up the SDK

The SDK ships as a tarball with wrapper scripts and a 3.4 GB Singularity image (.sif) containing the compiler, runtime and simulator. In the cloud container used for this course, two things were needed beyond unpacking it Measured:

  1. A container runtime. The wrappers call singularity; Ubuntu's own singularity-container package (SingularityCE 4.1.1) works.
  2. Dropping one capability. Running as root in a container without CAP_SYS_RESOURCE, every tool failed with "Requesting capability set … while permitted capability set is …". Setting SINGULARITY_DROP_CAPS=CAP_SYS_RESOURCE fixed it.

The repository's .claude/skills/cerebras-sdk/scripts/setup.sh does all of this idempotently and ends with a smoke test. Then:

source /home/user/cerebras-sdk/env.sh
cd course/programs && ARCH=wse3 bash run_all.sh

Check yourself

Which file decides that PE (3,0) talks to PE (4,0) on color 1?

layout.csl, through @set_color_config on both PEs. Device code only sees queues bound to that color.

You change a param from 8 to 16 PEs and compilation gets slower. Why?

Each unique combination of params is a separate PE program to compile. Using runtime coordinates from <layout> instead of per-PE params reduces unique programs.

Where do you look when a simulation hangs?

sim.log (with <simprint> output) to see which PEs reached which point; the stop cause in sim_stats.json; then csdb.
