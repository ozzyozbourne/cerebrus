Lab 2: reduce and broadcast

Now the PEs talk to each other. Program 03 sums vectors held by a row of PEs by letting the running total flow east through the row. Program 05 sends one vector down a whole column with one color and multicast routes. Together they cover the two collective shapes that most wafer algorithms are built from, and both programs time their own kernels, so you can see what the fabric costs apart from host I/O. Chapter 9 counted roughly 12 of these collectives per transformer layer (at least 8, ~12–14 in a real layer) and borrowed this lab's hop cost to price them. Here you measure what one costs.

After this lab you can

  • Write a multi-PE layout with per-PE roles and colors, and explain why each PE configures only the routes and queues it uses.
  • Use a fabric-in/memory/fabric-out DSD operation to build a streaming (systolic: each PE does its step on the data as it flows past, as in Chapter 6's fabric-DSD figure) reduction.
  • Use a multicast route to broadcast without any relay code.
  • Time a kernel with the PE's timestamp counter, apart from host I/O, and know which timestamp comparisons are valid.
  • Explain, with measured numbers, why streaming through PEs beats store-and-forward.
Run it yourself

source /home/user/cerebras-sdk/env.sh. Then, in course/programs/03-row-reduce, run bash commands.sh. Every program reads its knobs from the environment:

  • Program 03: P (PEs in the row, default 8, at least 2) and M (vector length, default 32), e.g. P=16 M=64 bash commands.sh.
  • Program 05 (course/programs/05-column-broadcast): R (rows, default 6) and M.
  • Both: ARCH=wse2 or ARCH=wse3 (default).

commands.sh sizes the fabric to your rectangle plus memcpy's frame: --fabric-dims=$((P+7)),3 with offsets 4,1 (Chapter 7). run.py prints the kernel cycles measured on the PEs. The whole-run simulated cycle count is in sim_stats.json: python3 -c "import json;print(json.load(open('sim_stats.json'))['cycle_count'])".

Program 03 · Row reduction

P PEs in a row each hold a vector v[M]. PE 0 sends its vector east. Each middle PE receives the running sum from the west, adds its own vector while the data passes through, and sends the result east. The last PE adds into memory. Each PE runs one instruction.

course/programs/03-row-reduce/layout.csl
// 03-row-reduce: P PEs in a row each hold a vector v[M]. The sum of all
// vectors flows west -> east: every PE adds its own v to the stream as it
// passes through (fabric-in + memory -> fabric-out in ONE DSD operation).
// Teaches: colors, static routes (rx/tx), checkerboard color alternation.
param P: i16;   // number of PEs in the row
param M: i16;   // vector length per PE

// Two colors alternate by column parity. A middle PE receives on one color
// and sends on the other; with a single color its router could not tell
// "incoming from WEST, deliver to me" from "outgoing from me, go EAST".
const c0: color = @get_color(0);
const c1: color = @get_color(1);

const memcpy = @import_module("<memcpy/get_params>", .{ .width = P, .height = 1 });

layout {
  @set_rectangle(P, 1);
  for (@range(i16, P)) |x| {
    const send_c = if (x % 2 == 0) c0 else c1;   // color this PE transmits on
    const recv_c = if (x % 2 == 0) c1 else c0;   // color its west neighbour used
    const role: i16 = if (x == 0) 0 else if (x == P - 1) 2 else 1; // first/middle/last

    @set_tile_code(x, 0, "pe_program.csl", .{
      .memcpy_params = memcpy.get_params(x), .M = M, .role = role,
      .send_color = send_c, .recv_color = recv_c });

    if (role != 2) // everyone but the last PE: CE -> RAMP -> router -> EAST
      @set_color_config(x, 0, send_c, .{ .routes = .{ .rx = .{RAMP}, .tx = .{EAST} } });
    if (role != 0) // everyone but the first PE: WEST -> router -> RAMP -> CE
      @set_color_config(x, 0, recv_c, .{ .routes = .{ .rx = .{WEST}, .tx = .{RAMP} } });
  }
  @export_name("v", [*]f32, true);
  @export_name("reduce", fn()void);
  @export_name("start_timer", fn()void);
  @export_name("t_start", [*]u16, true);   // 3 x u16 = one 48-bit timestamp
  @export_name("t_end", [*]u16, true);
}
course/programs/03-row-reduce/pe_program.csl
param memcpy_params;
param M: i16;
param role: i16;          // 0 = first, 1 = middle, 2 = last
param send_color: color;
param recv_color: color;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// Kernel timer: the <time> library reads the PE's 48-bit timestamp counter
// (TSC) as three u16 words. We stamp when reduce() starts and when exit_task
// runs, so the host can see kernel cycles separately from host I/O.
const tsc = @import_module("<time>");
var t_start = @zeros([tsc.tsc_size_words]u16);
var t_end   = @zeros([tsc.tsc_size_words]u16);
var t_start_ptr: [*]u16 = &t_start;
var t_end_ptr:   [*]u16 = &t_end;

var v: [M]f32;
var v_ptr: [*]f32 = &v;
const v_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{M} -> v[i] });

// WSE-3: every fabric transfer goes through a hardware queue bound to a color.
// Queues 0 and 1 belong to memcpy, so user queues start at 2. A middle PE runs
// ONE op that uses both oq 2 and iq 2, so sharing microthread 2 is safe here.
const oq: output_queue = @get_output_queue(2);
const iq: input_queue  = @get_input_queue(2);

const out_dsd = @get_dsd(fabout_dsd, if (@is_arch("wse3")) .{ .extent = M, .output_queue = oq }
                                     else .{ .extent = M, .output_queue = oq, .fabric_color = send_color });
const in_dsd  = @get_dsd(fabin_dsd, .{ .extent = M, .input_queue = iq });

const exit_id: local_task_id = @get_local_task_id(9);
task exit_task() void {
  tsc.get_timestamp(&t_end);       // this PE's op has finished
  sys_mod.unblock_cmd_stream();
}

fn start_timer() void {            // launched once, on every PE, before reduce()
  tsc.enable_tsc();                // resets and starts the counter
  sys_mod.unblock_cmd_stream();
}

fn reduce() void {
  tsc.get_timestamp(&t_start);
  // All ops are async: they run on a microthread and activate exit_task when
  // the last of the M wavelets has gone through.
  if (role == 0) {
    @fmovs(out_dsd, v_dsd, .{ .async = true, .activate = exit_id });          // send v
  } else if (role == 1) {
    @fadds(out_dsd, in_dsd, v_dsd, .{ .async = true, .activate = exit_id });  // fwd (in + v)
  } else {
    @fadds(v_dsd, in_dsd, v_dsd, .{ .async = true, .activate = exit_id });    // v = in + v
  }
}

comptime {
  @bind_local_task(exit_task, exit_id);
  if (role != 2) @initialize_queue(oq, if (@is_arch("wse3")) .{ .color = send_color } else .{});
  if (role != 0) @initialize_queue(iq, .{ .color = recv_color });
  @export_symbol(v_ptr, "v");
  @export_symbol(reduce);
  @export_symbol(start_timer);
  @export_symbol(t_start_ptr, "t_start");
  @export_symbol(t_end_ptr, "t_end");
}

#!/usr/bin/env cs_python
import argparse, json
import numpy as np
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder  # pylint: disable=no-name-in-module

p = argparse.ArgumentParser(); p.add_argument('--name'); p.add_argument('--cmaddr')
args = p.parse_args()
prm = json.load(open(f"{args.name}/out.json"))['params']
P, M = int(prm['P']), int(prm['M'])

V = np.random.default_rng(2).standard_normal((P, M)).astype(np.float32)   # row x = PE x
rt = SdkRuntime(args.name, cmaddr=args.cmaddr)
vs = rt.get_id('v')
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
rt.memcpy_h2d(vs, V.ravel(), 0, 0, P, 1, M, **kw)   # PE x receives V[x, :]
rt.launch('start_timer', nonblock=False)           # every PE: reset its TSC
rt.launch('reduce', nonblock=False)                # every PE: start its one DSD op
out = np.zeros(M, dtype=np.float32)
rt.memcpy_d2h(out, vs, P - 1, 0, 1, 1, M, **kw)    # result lives on the last PE

def read_tsc(name):    # P timestamps; 16-bit words arrive in u32 slots
  w = np.zeros(3 * P, dtype=np.uint32)
  rt.memcpy_d2h(w, rt.get_id(name), 0, 0, P, 1, 3, **dict(kw, data_type=MemcpyDataType.MEMCPY_16BIT))
  w = (w & 0xffff).astype(np.int64).reshape(P, 3)
  return w[:, 0] + (w[:, 1] << 16) + (w[:, 2] << 32)
t0, t1 = read_tsc('t_start'), read_tsc('t_end')
rt.stop()

np.testing.assert_allclose(out, V.sum(axis=0), rtol=1e-5, atol=1e-5)
print(f"summed {P} vectors of length {M} across the row; first 4:", out[:4])
# Both stamps of a pair come from the SAME PE's clock; never subtract across PEs.
print("reduce() start -> op done, per PE (own TSC):", (t1 - t0).tolist())
print(f"kernel on the last PE: {t1[-1] - t0[-1]} cycles (host I/O excluded)")
print("SUCCESS!")

Reading the code: roles are compile-time params

The layout loop runs at compile time. For each column x it computes three values and passes them to @set_tile_code: role (0 first, 1 middle, 2 last), send_color and recv_color. Inside pe_program.csl they are params, so the compiler knows their values. if (role == 0) in reduce() is folded away, and each PE's binary holds only its own branch. The compiler builds one binary per unique set of params (Chapter 10). For P = 8 that is 4 binaries: first, last, and two middle ones with the colors swapped.

The guards follow one rule: configure only what this PE uses. Every PE except the last sends, so it gets a send_c route (RAMP → EAST) and an output queue bound to send_c. Every PE except the first receives, so it gets a recv_c route (WEST → RAMP) and an input queue bound to recv_c. A middle PE has both, on two different colors: that is the checkerboard from Chapter 4, and the stepper below shows why it needs two colors.

Two chips, one source. On WSE-3, @initialize_queue binds an output queue to one color, and the DSD names only the queue. On WSE-2 the color goes on the fabout_dsd (.fabric_color), and the queue is initialized without one. Input queues are bound to a color on both chips. The @is_arch expressions select the right form at compile time (Chapter 5, WSE-2 vs WSE-3 table).

Why output queue 2 and input queue 2 are safe here, but were not in Lab 3's first version (Chapter 5) On WSE-3 queues 0 and 1 belong to memcpy, so user queues start at 2. Chapter 5's rule is that two concurrent operations must not share a microthread, and on WSE-3 a queue's microthread defaults to its queue ID. A middle PE runs one operation, @fadds(out, in, v). That op uses both queues on one microthread, so nothing clashes. Lab 3 (Chapter 13) runs four ops at once, which is why its first version, with shared queue numbers, failed and why it now uses distinct input queues. Program 05 uses input queue 4 only out of habit: no PE there uses both queues.

What happens inside, in order

  1. memcpy_h2d(vs, V.ravel(), 0, 0, P, 1, M) writes a P × 1 rectangle with M floats per PE, so PE x gets row x of V. This is the only host copy into the row.
  2. launch('start_timer') runs on every PE in the rectangle. Each PE resets its own timestamp counter (TSC) and unblocks.
  3. launch('reduce') also reaches every PE. Each PE stamps t_start, starts one async DSD op and returns at once. That PE's command stream stays blocked until it calls unblock_cmd_stream(). Each PE works through its own queue of host commands, one at a time, and takes the next only after the current one unblocks. The host does not wait for any of this: launch() returns at once. That one model explains both why launch-then-read is safe (step 6) and the timing skew in program 05 below.
  4. The PEs do not start at exactly the same moment, and they don't need to. A middle PE's @fadds takes in_dsd as an operand, so it waits for each wavelet to arrive. If a PE downstream has not started yet, its input queue fills and back-pressure stalls the PE upstream. Nothing is lost (Chapter 4). Arrival orders the computation, not the host.
  5. Each PE's op ends after its M-th wavelet, which activates exit_task: stamp t_end, unblock. PE 0 finishes first, once its M wavelets have left the CE. They may still be sitting in queues and routers: PE 1 normally starts consuming about one hop later, but PE 0 can finish even if PE 1 has consumed nothing, because up to ~18 wavelets fit in one hop (see back-pressure below). PE P−1 finishes last, when the total is in its v.
  6. launch has long since returned on the host. The host's next command, memcpy_d2h, waits on each PE until that PE has unblocked (Chapter 7; which call waits for what). It reads v from PE P−1 alone, plus the two 48-bit timestamps from every PE.

Why two colors? Step through the routers

Router stepper: checkerboard vs one color

Four PEs. Each router has one route per color: every input in rx goes to every output in tx. Step through to watch the running sum travel. Then switch to one color: a middle router would need rx {WEST, RAMP} → tx {RAMP, EAST}, and the sum breaks. On WSE-3 such a route does not even compile (two rx directions, Chapter 4) Measured, cslc 2.10.1; on WSE-2 it compiles, but the run gives a wrong answer or stalls (a P = 4, M = 8 test had not finished after 6 minutes) Unverified which, in general.

Why it is fast: streaming, not store-and-forward

A middle PE does not wait for the whole vector before forwarding. @fadds(out_dsd, in_dsd, v_dsd) processes element i as soon as wavelet i arrives and emits it immediately. The vector moves through the row as a wavefront. The reduction takes about M + c·(P − 1) cycles, plus a fixed few tens, not P × M. Here c is the cost of one CE-forwarded hop: the router hop, ramp up, the CE's @fadds pipeline and ramp down. It is measured below at ≈ 9.2 cycles on WSE-3 and ≈ 6.0 on WSE-2 Derived from measurements. Of that, the router hop is 2.0 / 1.0 Measured, and the remaining ≈ 7.2 / 5.0 is ramp up, the CE pipeline and ramp down together Derived; we did not separate those three further. Throughput stays one wavelet per cycle per link, so c only shifts the wavefront.

The SDK's gemv-08 tutorial reduces the same way: its middle columns run @fadds(out_dsd, y_dsd, in_dsd, …), fabric in plus memory to fabric out, with a first column that only sends and a last that adds into memory SDK 2.10.1, gemv-08-routes-3/pe_program.csl. (gemv-06 and gemv-07 are only 2 PEs wide, so they have no middle PE to forward through.) The alternative, store-and-forward, receives the whole vector into memory, adds, and only then sends. That is a fine choice when the PE has other work to do on the data. For a pure chain, the measured cost differs a lot. This is the whole change to a middle PE, and it reproduces the 348 cycles in the table below Measured, P = 8, M = 32:

Two ops in a row, each with its own startup, is where the widget's M + 2c per store-and-forward hop comes from.

Race: streaming vs store-and-forward, on one clock

Each cell is one element of the vector at one PE. Both grids advance on the same clock (30 ms per cycle), so the slower one really takes longer. The model uses the measured hop cost c for the chosen chip: a streaming hop costs c, and a store-and-forward hop costs M + 2c, because each PE runs two ops and each op pays its own startup Derived. The fixed ~20 cycles per run are left out. At M = 32 the chart adds simulator measurements on the last PE's own clock Measured. Those readings run about one router hop per PE low (see "Only subtract timestamps from the same PE" below).

Measuring the kernel, not the host

The simulator's cycle_count counts the whole run: loading, every host copy, every launch. For this program that total says almost nothing about the reduction. A copy of program 03 whose reduce() does nothing gives identical totals Measured. So program 03 times itself. The <time> library reads the PE's 48-bit timestamp counter (the pattern from the SDK's tutorials/topic-02-libraries SDK 2.10.1, first used in Chapter 11's timed SAXPY). The counter comes back as three 16-bit words, each in its own u32 slot of the D2H copy, and run.py joins them into one 48-bit number (Appendix C walks through this). It then subtracts the start stamp from the end stamp on the same PE. The pattern: stamp the start in the function that arms the receive, stamp the end in the task that sees the last wavelet. One caveat for short spans such as the 50 and 58 below: an empty pair of stamps already reads about 10 cycles on WSE-3 (glossary) Measured, so only differences between such numbers are clean.

Only subtract timestamps from the same PE

Each PE's counter starts when start_timer reaches that PE, so the counters are not synchronized. The launch also reaches PEs at different times, and that offset cancels out of any one PE's stamps. Comparing PE 3's end against PE 0's start would mix two clocks. That is why run.py prints t_end − t_start per PE. The SDK's benchmarks/bandwidth-test builds an explicit fabric sync for the same reason ("the tsc counters of all PEs are not synchronized").

So the per-PE list in the output (50, 58, 65, 73, …) is not a wavefront measured on one clock. Its step of ~7.2 cycles per PE (5.0 on WSE-2) is the hop cost minus however much later each PE's clock started. To get the hop cost itself, time a round trip on one PE.

The hop cost, on one clock: a round trip

A variant of program 03 (not shipped with the course; the change is small enough to make yourself) makes the last PE send its sum back west on a third color, routed WEST through every middle router and up the RAMP only at PE 0. That path is pure router hops. PE 0 then times "send v → receive the sum back" on its own counter. A CE-forwarded hop (route up to the CE, @fadds, route back out) costs 11.15 − 2.0 ≈ 9.2 cycles on WSE-3 and 7.0 − 1.0 = 6.0 on WSE-2 Derived. That is the c in the model. The per-PE "own clock" step (7.2 / 5.0) is exactly one router hop less than this, which fits each PE's clock starting one hop later than its west neighbour's Derived. At small P the WSE-2 round trips have a ~90-cycle floor that hides the slope, so fit it only from P ≥ 12. The router-only row is also irregular below that: 105 at P = 8 but 94 at P = 16. A floor alone cannot explain a decrease, and we did not track down the cause, so treat the WSE-2 points below P = 12 as noise Unverified.

With c ≈ 9, the P term equals the M term once P ≈ M / 9: around 30 PEs at M = 256. Past that point the hops, not the words, dominate a chain. That is not where a tree starts to win, because each level of a tree resends the whole vector. Chapter 14 models a tree as log₂P · (15 + M) + 2(P − 1) against the chain's 9P + M and finds the tree wins from P ≈ 27 at M = 32. The same model at M = 256 puts the crossover at P ≈ 280 (chain 2,776 vs tree 2,761 cycles) Derived. Short vectors want a tree, long vectors a chain.

When a PE is late: back-pressure

We delayed only the last PE (a busy loop before its @fadds), at P = 8. A delay shorter than the wavefront's arrival time (about 50 cycles there) changes nothing. With M = 128 and a ~590-cycle delay, PE 0 still finished on schedule: the 7 hops between it and the stalled PE held all 128 wavelets, about 18 per hop. With M = 512 every PE waited, and as the chain drained, adjacent PEs finished about 16 cycles apart on their own clocks Measured. Those clocks start one router hop (2 cycles) apart (see the round trip above), so the true spacing is about 18 Derived, which agrees with 128 / 7 ≈ 18. So each hop (output queue + router + input queue) holds roughly 18 wavelets. Where they sit: program 03's input queue 2 holds 4 wavelets and output queue 2 holds 6 SDK 2.10.1, memcpy.csl queue comments, so about 10 are in the queues and the remaining ~8 in the router and ramp buffers between them Derived; not split further. It is the same kind of total I/O-path buffering (queues plus router) as behind Chapter 5's "one SDK example stalls past 14", and the reason Chapter 4 can say nothing is dropped: a full buffer stops the sender. Rule of thumb: a chain of P PEs buffers ≈ 18·(P − 1) wavelets. If M fits, upstream PEs finish even while the consumer is stalled. If not, everyone waits for the slowest PE.

Program 05 · Column broadcast by multicast

The root PE of a column sends its vector once. Every middle router delivers each wavelet to its own CE and forwards it south in the same hop (a multicast, Chapter 4): .tx = .{RAMP, SOUTH}. The bottom router only delivers (.tx = .{RAMP}). Forwarding SOUTH there would push wavelets out of your rectangle into memcpy's frame. No PE runs relay code: the router does the copying, at router-hop cost.

// 05-column-broadcast: the top PE of a column multicasts a vector x down the
// column. Each router hands every wavelet to its own CE *and* forwards it
// SOUTH in the same hop (tx = {RAMP, SOUTH}), so one send reaches R PEs.
// Every PE then computes y = s * x with its own scale s.
// Teaches: multicast routes, a single color shared by a whole column, fabin->mem ops.
param R: i16;     // rows (PEs in the column)
param M: i16;     // vector length

const bcast: color = @get_color(0);
const memcpy = @import_module("<memcpy/get_params>", .{ .width = 1, .height = R });

layout {
  @set_rectangle(1, R);
  for (@range(i16, R)) |y| {
    @set_tile_code(0, y, "pe_program.csl", .{ .memcpy_params = memcpy.get_params(0),
                                             .M = M, .is_root = (y == 0), .bcast = bcast });
    if (y == 0) {             // root: CE -> router -> SOUTH
      @set_color_config(0, y, bcast, .{ .routes = .{ .rx = .{RAMP},  .tx = .{SOUTH} } });
    } else if (y == R - 1) {  // bottom: NORTH -> CE only
      @set_color_config(0, y, bcast, .{ .routes = .{ .rx = .{NORTH}, .tx = .{RAMP} } });
    } else {                  // middle: NORTH -> CE and onward SOUTH (multicast)
      @set_color_config(0, y, bcast, .{ .routes = .{ .rx = .{NORTH}, .tx = .{RAMP, SOUTH} } });
    }
  }
  @export_name("x", [*]f32, true);
  @export_name("y", [*]f32, true);
  @export_name("s", [*]f32, true);
  @export_name("go", fn()void);
  @export_name("start_timer", fn()void);
  @export_name("t_start", [*]u16, true);
  @export_name("t_end", [*]u16, true);
}

param is_root: bool;
param bcast: color;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// Kernel timer, as in program 03: 48-bit TSC stamps at go() and at completion.
const tsc = @import_module("<time>");
var t_start = @zeros([tsc.tsc_size_words]u16);
var t_end   = @zeros([tsc.tsc_size_words]u16);
var t_start_ptr: [*]u16 = &t_start;
var t_end_ptr:   [*]u16 = &t_end;

var x: [M]f32;      // root: source vector; others: received copy
var y: [M]f32;      // result y = s * x
var s = [1]f32 { 0.0 };
var x_ptr: [*]f32 = &x;
var y_ptr: [*]f32 = &y;
var s_ptr: [*]f32 = &s;

const x_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{M} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{M} -> y[i] });

const oq: output_queue = @get_output_queue(2);
const iq: input_queue  = @get_input_queue(4);
const out_dsd = @get_dsd(fabout_dsd, if (@is_arch("wse3")) .{ .extent = M, .output_queue = oq }
                                     else .{ .extent = M, .output_queue = oq, .fabric_color = bcast });
const in_dsd  = @get_dsd(fabin_dsd, .{ .extent = M, .input_queue = iq });

const recv_done: local_task_id = @get_local_task_id(10);
const send_done: local_task_id = @get_local_task_id(11);

task t_recv() void {               // x has fully arrived
  tsc.get_timestamp(&t_end);
  @fmuls(y_dsd, x_dsd, s[0]);      // y = x * s
  sys_mod.unblock_cmd_stream();
}
task t_send() void {               // root: broadcast is out
  tsc.get_timestamp(&t_end);
  @fmuls(y_dsd, x_dsd, s[0]);
  sys_mod.unblock_cmd_stream();
}

fn start_timer() void {            // launched first, so every PE resets together
  tsc.enable_tsc();
  sys_mod.unblock_cmd_stream();
}

fn go() void {
  tsc.get_timestamp(&t_start);
  if (is_root) {
    @fmovs(out_dsd, x_dsd, .{ .async = true, .activate = send_done });
  } else {
    @fmovs(x_dsd, in_dsd, .{ .async = true, .activate = recv_done });
  }
}

comptime {
  @bind_local_task(t_recv, recv_done);
  @bind_local_task(t_send, send_done);
  if (is_root) {
    @initialize_queue(oq, if (@is_arch("wse3")) .{ .color = bcast } else .{});
  } else {
    @initialize_queue(iq, .{ .color = bcast });
  }
  @export_symbol(x_ptr, "x");
  @export_symbol(y_ptr, "y");
  @export_symbol(s_ptr, "s");
  @export_symbol(go);
  @export_symbol(start_timer);
  @export_symbol(t_start_ptr, "t_start");
  @export_symbol(t_end_ptr, "t_end");
}

rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
rt.launch('start_timer', nonblock=False)          # first command: all TSCs reset together
rt.memcpy_h2d(xs, x, 0, 0, 1, 1, M, **kw)          # only the root gets x from the host
rt.memcpy_h2d(ss, s, 0, 0, 1, R, 1, **kw)          # one scale per PE
rt.launch('go', nonblock=False)
y = np.zeros(R * M, dtype=np.float32)
rt.memcpy_d2h(y, ys, 0, 0, 1, R, M, **kw)

def read_tsc(name):    # R timestamps; 16-bit words arrive in u32 slots
  w = np.zeros(3 * R, dtype=np.uint32)
  rt.memcpy_d2h(w, rt.get_id(name), 0, 0, 1, R, 3, **dict(kw, data_type=MemcpyDataType.MEMCPY_16BIT))
  w = (w & 0xffff).astype(np.int64).reshape(R, 3)
  return w[:, 0] + (w[:, 1] << 16) + (w[:, 2] << 32)
t0, t1 = read_tsc('t_start'), read_tsc('t_end')
rt.stop()

Look at the host side. x is copied to the root only (a 1 × 1 rectangle), and the fabric fills every other PE's x. s goes to all R PEs, one float each. So the broadcast replaces R − 1 host copies. On the device, the non-root PEs run @fmovs(x_dsd, in_dsd): fabric in, memory out. That is the opposite of program 03, where the incoming stream never touches memory. The receivers need x stored before @fmuls can read it. t_send and t_recv do the same work. They are separate only to show that the root's completion means "sent" and a receiver's means "received". Exercise 4 merges them.

What happens inside, in order

  1. launch('start_timer') is the first command, so every PE resets its counter at the same point in its command stream.
  2. memcpy_h2d(xs, x, 0, 0, 1, 1, M) sends x to the root only. memcpy_h2d(ss, s, 0, 0, 1, R, 1) sends one scale to each of the R PEs.
  3. launch('go') runs everywhere. The root's @fmovs(out_dsd, x_dsd) pushes M wavelets SOUTH. Each receiver's @fmovs(x_dsd, in_dsd) fills its x as the multicast passes.
  4. When its op completes, each PE runs t_send (root) or t_recv (others): stamp, y = s · x, unblock. Then the host reads the R × M block of y from all PEs.
Timing the broadcast, and a trap: command-stream skew

Each PE's memcpy commands form its own queue (step 3 of program 03, Chapter 7). The receivers skip the x copy, so they reach go() earlier than the root: 2,248 cycles after their timer reset, against 2,610 for the root. That gap of about 362 cycles is the root's extra host copy Measured. A receiver's own go() → x received span is therefore 431–439 cycles (±1 cycle run to run, because the skew depends on host timing), and almost all of it is idle waiting for the root. The root itself finishes sending in 50.

Subtracting the skew, the last receiver has x about 69–78 cycles after the root starts. That is about 2 cycles per row on top of M + ~37 Derived, consistent with a pure router hop (2.0 cycles on WSE-3). Roughly half of the ~37 is the root's own send: its @fmovs takes 50 = M + 18 on its clock. The rest is the first hop off the root's ramp, the receiver's @fmovs start-up and its completion; we did not separate those Derived. Multicast forwarding never involves the CE, so each row costs a router hop, not program 03's ~9-cycle CE hop. The flip side: a multicast moves at the pace of its slowest receiver, because a wavelet goes down no branch until every branch has room (Chapter 4, measured). On WSE-2 the skew is 348 cycles and the arrivals come 85–89 cycles after the root starts.

Lesson: "kernel time" on one PE can be another PE's host I/O. If you time kernels, give every PE the same command history (for example, copy x to all PEs while timing), or synchronize clocks over the fabric as bandwidth-test does.

CSL detail learned the hard way A lone statement if without braces is fine (program 03: if (role != 2) @set_color_config(...);). Add an else, and braces become mandatory: if (a) stmt; else stmt; fails with "Unexpected character". That is why program 05's three-way route choice and its queue setup use { }. Expression-form if chains need no braces: const role = if (x == 0) 0 else if (x == P - 1) 2 else 1;.

The library version: <collectives_2d>

The SDK packages both shapes as a library, used in tutorials/topic-11 and benchmarks/gemv-collectives_2d SDK 2.10.1. Its broadcast and reduce_fadds are programs 05 and 03 in library form. Each dimension gets 2 colors and 2 entrypoints, and the reduce network is the same alternating C0/C1 checkerboard as program 03. Unlike our static routes, it rewrites routes at runtime (switches, filters, reset_routes), sends teardown wavelets after every op, and lets the root sit anywhere (Chapter 14 takes the library apart). When it goes wrong
  • The simulator never finishes, or cs_python aborts after a few seconds with "received length (0 bytes) is not expected … could be a kernel stall" (glossary, Chapter 10's hang procedure). A wavelet has nowhere to go, or nothing consumes it, or some PE never unblocks. Check that every sender has a matching receiver route on the same color (mind the parity!). Check that the last PE has no EAST route and the bottom PE no SOUTH route. P must be at least 2: with P = 1, PE 0 is both first and last.
  • It hangs only after you add a second async op. Two concurrent ops share a microthread (Chapter 5). Renumber the queues, or give the ops distinct .ut_ids.
  • The result is all zeros or just your own input. You read the wrong PE: the sum lives on PE P−1, not PE 0.
  • Compile error about a color or queue on one PE. A guard is missing: a PE initialized a queue for a color it has no route for, or the other way round.
  • Bisect like Lab 1. Set P = 2 (first + last, no middle), then P = 3. Read v back from every PE with one memcpy_d2h(..., 0, 0, P, 1, M) to see how far the sum got.

Composing the two: a distributed GEMV

Put program 05 and program 03 together and you have the SDK's gemv-08 pattern: multicast the x slices down the columns, let each PE multiply its block of A, then reduce the partial results along the rows with alternating colors. The SDK tutorials gemv-06 to gemv-08 build up to exactly this SDK 2.10.1. gemv-08 is the full pattern, with 3 colors. Its row reduction is program 03's streaming pattern: first column @fmovs, middle columns @fadds(out, y, in), last column adds into memory. Only its x path differs: a data task recv_x runs once per arriving wavelet and does one @fmacs per scalar, instead of a bulk fabric copy.
