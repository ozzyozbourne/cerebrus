Lab 4: 2-D GEMM with SUMMA

Every lab so far ran on a row or a column. This one uses a P × P grid of PEs to multiply two matrices with SUMMA, the textbook distributed GEMM. Each step broadcasts one block column of A along the rows and one block row of B down the columns, and then every PE multiplies the two tiles it received. The SDK's <collectives_2d> library does the broadcasts, rewriting the routes at run time and tearing them down after each step. We time each step on the tile's own counter. At realistic tile sizes the kernel spends almost all its time computing, which is the opposite of Lab 3's result. It still reaches only a third of the multiply-add rate, and the measurements show where the rest goes.

After this lab you can

  • Explain SUMMA as "P outer products of block columns and block rows", and map it onto a P × P grid with 2-D host I/O.
  • Read <collectives_2d>: two colors per axis, routes rewritten per broadcast, a teardown wavelet, and a lock task that fires the callback.
  • Build a task that waits for two independent networks (block + activate), and re-arm it every step.
  • Time broadcast and compute separately with the TSC, compare them with a compute-bound estimate, and find the instruction and bank-clash overheads.
  • Budget a kernel before writing it: memory, colors, task IDs, queues and microthreads, and a cycle model.
Run it yourself

Knobs: P (grid side, default 4), T (tile size, default 8; or set Mt, Kt, Nt separately), KERNEL (0 = the SDK's column loop, 1 = the outer-product variant from the measurement section) and ARCH (wse3 default, or wse2). Example: P=6 T=16 KERNEL=1 ARCH=wse2 bash commands.sh. Larger tiles take minutes: T = 32 at P = 4 took about 4 minutes of wall time.

From GEMV to SUMMA

Chapter 12 composed a distributed GEMV from two collectives: broadcast slices of x down the columns, multiply locally, and reduce partial y along the rows. A GEMM, C = A·B, is many GEMVs at once (one per column of B), so you could run that pattern N times. SUMMA (Scalable Universal Matrix Multiplication Algorithm, van de Geijn and Watts, 1997) organises the same work so that no reduction is needed at all.

Cut A (M × K), B (K × N) and C (M × N) into a P × P grid of blocks. PE (px, py) owns block row py and block column px of all three: A(py, px), B(py, px) and C(py, px). The owner of a block of C computes it:

C(py, px) = Σ_s  A(py, s) · B(s, px)        s = 0 … P−1

The term for step s needs block column s of A and block row s of B. So at step s the PEs in grid column s broadcast their A block along their row, the PEs in grid row s broadcast their B block down their column, and every PE adds one tile product into its C. After P steps each C block is complete, and it never moved. In matrix terms each step adds one rank-K/P update, an outer product of a block column and a block row.

The GEMV warm-up. Set Nt=1 and the same program computes a matrix times P vectors at once (B is K × P): a batched GEMV. Each step still broadcasts an A tile along the rows, but the B "tile" is a column segment of only Kt words, and each PE does Kt multiply-adds per output element. Compared with Chapter 12's GEMV, the vector is broadcast and the result stays put, instead of the vector staying put and the result being reduced. The warm-up exercise runs it.

Green fill is how much of each C tile is done. Right: the same step on the whole matrices. Click a PE to follow it. The cycle estimate uses the measured WSE-3 fits from this chapter (kernel 0, P = 4).

Why it suits the wafer. Each step moves Mt·Kt + Kt·Nt words into every PE and does Mt·Kt·Nt multiply-adds there. For square tiles of side T that is 2T² words for T³ multiply-adds: the compute grows faster than the traffic, so large tiles are compute-bound. The broadcasts are multicasts (one send reaches the whole row, Chapter 12's program 05), so their cost barely depends on P. And C never moves, so the only data in flight is A and B.

Data layout and host I/O on a 2-D grid

The host copies each matrix in a single memcpy_h2d over the whole P × P rectangle (Chapter 7). With MemcpyOrder.ROW_MAJOR, the flat host array is consumed PE by PE in row-major order over the grid (py outer, px inner), Mt·Kt words per PE. So the host must arrange A so that each PE's tile is contiguous, and in the order the PE wants. This program stores every tile column-major, so that a column of the A tile, which is what the inner multiply-add streams over, is contiguous.

Reading C back is the inverse: the device returns (py, px, column, row), and transpose(0, 3, 1, 2) brings it back to (block row, row, block column, column). Getting one axis wrong does not crash anything: the program just multiplies the wrong numbers, and the numpy check catches it. That check is the first line of defence in any 2-D program.

Inside <collectives_2d>

Chapter 12 used the library in one dimension and measured its fixed cost at about 700 cycles Measured, Ch. 12. Here we need it in both dimensions, so it is worth opening up. The source is csl-libs/collectives_2d/pe.csl in the SDK image (1,312 lines) SDK 2.10.1; the broadcast path is short.

What one instance owns

Each axis is a separate instance of the module (row and col in our program). Each one owns two colors (DATA_COLOR_0, DATA_COLOR_1), two local task IDs (an FSM task and a "lock" task), two input/output queue pairs and one DSD-register set. Broadcast uses only color 0; color 1 is for reduce_fadds, which needs the alternating checkerboard of Chapter 12's program 03. The layout calls c2d.get_params(px, py, ids), which records only whether the PE sits at either end of its row and column. The PE reads its own coordinate at run time (init()), so the compiler builds a handful of ELF files instead of P². At load time color 0 is a broadcast network rooted at PE 0, in teardown mode.

Why the routes change at run time

A static route has a fixed input direction, and on WSE-3 a route accepts at most one input direction (Chapter 4). In SUMMA the root of the row broadcast moves one column east every step: at step 0 every PE receives from the west side, at step P−1 from the east side, and in between the PEs left of the root receive from the east and the PEs right of it from the west. With static routes you would need a color per root, P colors per axis. The library uses one color and rewrites it before each broadcast:

collectives_2d/pe.csl, configure_broadcast_network() (abridged)
if (pe_id == root) {                    // the root's CE feeds the router
  // ends of the line send one way, everyone else both ways
  color_config.reset_routes(addr, .{.tx = [2]direction{POS_DIR, NEG_DIR}, .rx = RAMP});
} else if (pe_id < root) {               // left of / above the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, NEG_DIR}, .rx = POS_DIR});
} else {                                 // right of / below the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, POS_DIR}, .rx = NEG_DIR});
}
tile_config.teardown.exit(DATA_COLOR_0);  // leave teardown: traffic may flow

POS_DIR is EAST for the row instance and SOUTH for the column instance. Every non-root router passes the wavelet both to its own CE (RAMP) and onward, which is program 05's multicast with a run-time root.

One broadcast, end to end

  1. broadcast(root, buf, count, callback) blocks the lock task, records the root and the buffer, clears the filter and switch state left by any earlier gather or scatter, rewrites the routes as above, and leaves teardown mode.
  2. Transfer. It activates its FSM task, which starts one asynchronous 32-bit move of count words: memory → fabric at the root, fabric → memory everywhere else. The move runs on the microthread of its queue (2 for the row instance, 3 for the column instance) and activates the FSM task again when it finishes.
  3. Teardown. On that second run the FSM calls initiate_teardowns(). Only the root sends anything: one control wavelet with the TEARDOWN command and the CE-ignore bit set, on color 0. It follows the same routes as the data, so it reaches every router in the line after the last data wavelet, and each router puts color 0 back into teardown mode.
  4. Lock. Entering teardown runs the CE's teardown handler, task 29 (Chapter 4), which activates the lock task. The FSM unblocks the lock when its own transfer is done. So the lock runs only when both have happened: the data is in my memory, and the network is torn down and ready to be rewritten. The lock task then activates the user's callback (our x_done or y_done).

The teardown is what makes the next step's rewrite safe: no PE can reconfigure color 0 while wavelets of the previous broadcast are still in its router. What happens to a root that starts step s+1 while a slower neighbour is still computing step s? Its data waits behind the neighbour's router, which is still in teardown mode, and the lossless fabric back-pressures the sender until the neighbour calls broadcast and leaves teardown. The library's comments describe this ordering ("if we clear TIP bit before routing is reconfigured, it stalls"); we did not isolate it in a separate experiment Derived from the library source.

Chain or tree?

Both the library's broadcast and Chapter 12's program 05 are chains: the wavelets stream through every router of the line, one hop after another, and each router copies them to its CE on the way. A chain broadcast costs about (hops × hop cost) + words, and the hop cost is tiny (2.0 cycles on WSE-3, 1.0 on WSE-2 Measured, Ch. 4), so for a row of a few hundred PEs the word count dominates. Reductions are different, because each PE must add before forwarding. A chain reduce still streams (≈ 9.2 cycles per hop through a PE's compute on WSE-3, 6.0 on WSE-2, plus the words Measured, Ch. 12). A binary tree would need only log₂P levels but each level is a separate message, and Chapter 12 measured store-and-forward at more than 3× the streaming chain (348 vs 101 cycles at P = 8, M = 32) Measured, Ch. 12. With c ≈ 9 per hop and ≈ 15 cycles per store-and-forward message (Lab 3 measured ≈ 14.6 per transfer with its completion task, Chapter 13), a chain over P PEs beats a tree until roughly 9·P > log₂P · (15 + M) + 2·P (the last term is the tree's wire): about P ≈ 8 for a single word and P ≈ 35 for M = 32 Derived. So a whole-wafer scalar allreduce wants a tree, and a short row of long vectors wants a chain. SUMMA itself needs no reduction; Chapter 15's solver does.

The task that waits on two networks

Each step needs both tiles before it can compute: the A tile from the row broadcast and the B tile from the column broadcast. They finish in either order. Chapter 5's join does this with two bits: the compute task starts blocked; y_done unblocks it and x_done activates it. A task runs only when it is both activated and unblocked, so compute runs exactly once, after the later of the two callbacks. At the end of compute, @block(COMPUTE) re-arms the join for the next step before start_step() issues the next pair of broadcasts.

Why not count, as Lab 3 did with pending? That works too, but it needs a counter, a decrement in each callback and a test. The join is free: the hardware task picker evaluates it.

Walking through the code

The layout file is short. Two calls per PE: the library parameters with our colors and entrypoint task IDs, and the PE program with the tile sizes. The resource map at the top is the budget sheet the design section below fills in.

course/programs/06-summa/layout.csl
// 06-summa: C = A·B on a P x P grid of PEs with the SUMMA algorithm.
// Adapted from Cerebras SDK 2.10.1 benchmarks/gemm-collectives_2d (layout.csl,
// pe.csl, run.py), rewritten in the course's style, with per-step TSC stamps.
//
// Each PE (px, py) owns one tile of each matrix: A is Mt x Kt, B is Kt x Nt,
// C is Mt x Nt, all column-major. In step s, the PEs of column s broadcast
// their A tile along their row, and the PEs of row s broadcast their B tile
// down their column; then every PE does C_tile += A_s · B_s.
// Teaches: a 2-D decomposition, <collectives_2d> (routes rewritten at run
// time, teardown), a task that waits on two networks, the compute-bound regime.
//
// Resource map (every PE)
//   colors        0, 1  row (x) broadcast         2, 3  column (y) broadcast
//                 (20-23 belong to memcpy and the runtime, Chapter 4)
//   local tasks   8, 9  x library (FSM, lock)     10, 11  y library (FSM, lock)
//                 12 exit   13 compute   14 x_done   15 y_done
//                 (the teardown handler, task 29, is installed by the library)
//   queues        0, 1  memcpy    2, 4  x library    3, 5  y library
//   microthreads  = queue IDs: a broadcast uses 2 (x) and 3 (y) at the same time
param P: u16;              // grid is P x P PEs
param Mt: u16;             // tile sizes on one PE
param Kt: u16;
param Nt: u16;
param kernel: u16 = 0;     // 0 = column @fmacs (SDK), 1 = outer product (pe_program.csl)

const memcpy = @import_module("<memcpy/get_params>", .{ .width = P, .height = P });
const c2d = @import_module("<collectives_2d/params>");

layout {
  @set_rectangle(P, P);
  for (@range(u16, P)) |px| {
    const memcpy_params = memcpy.get_params(px);
    for (@range(u16, P)) |py| {
      // get_params only records which end of its row/column a PE sits at;
      // the PE reads its own coordinates at run time (fewer distinct ELFs).
      const c2d_params = c2d.get_params(px, py, .{
        .x_colors      = .{ @get_color(0),          @get_color(1) },
        .x_entrypoints = .{ @get_local_task_id(8),  @get_local_task_id(9) },
        .y_colors      = .{ @get_color(2),          @get_color(3) },
        .y_entrypoints = .{ @get_local_task_id(10), @get_local_task_id(11) },
      });
      @set_tile_code(px, py, "pe_program.csl", .{
        .memcpy_params = memcpy_params, .c2d_params = c2d_params,
        .Mt = Mt, .Kt = Kt, .Nt = Nt, .kernel = kernel });
    }
  }
  @export_name("A", [*]f32, true);
  @export_name("B", [*]f32, true);
  @export_name("C", [*]f32, true);
  @export_name("tsc", [*]u16, true);   // 3P + 2 timestamps of 3 x u16 per PE
  @export_name("main", fn()void);
}

The PE program. The library instances come first, each with its own queues and DSD registers. main() is the RPC; it returns immediately and the rest is a chain of tasks: start_step → two broadcasts → x_done/y_done → compute → start_step … → exit, which unblocks the host. Kernel 0 is the SDK's loop; kernel 1 is explained in the measurement section.

course/programs/06-summa/pe_program.csl
// 06-summa PE program (see layout.csl for the algorithm and the resource map).
param memcpy_params;
param c2d_params;
param Mt: i16;
param Kt: i16;
param Nt: i16;
param kernel: u16;         // 0 = column @fmacs (as in the SDK), 1 = outer product

const P = @get_rectangle().width;

const EXIT:       local_task_id = @get_local_task_id(12);
const COMPUTE:    local_task_id = @get_local_task_id(13);
const X_DONE:     local_task_id = @get_local_task_id(14);
const Y_DONE:     local_task_id = @get_local_task_id(15);

// One library instance per axis. Each owns two colors, two queues, two task IDs
// and one set of DSD registers. x and y must not share any of them.
const row = @import_module("<collectives_2d/pe>", .{
  .dim_params = c2d_params.x, .queues = [2]u16{2, 4},
  .dest_dsr_ids = [1]u16{1}, .src0_dsr_ids = [1]u16{1}, .src1_dsr_ids = [1]u16{1} });
const col = @import_module("<collectives_2d/pe>", .{
  .dim_params = c2d_params.y, .queues = [2]u16{3, 5},
  .dest_dsr_ids = [1]u16{2}, .src0_dsr_ids = [1]u16{2}, .src1_dsr_ids = [1]u16{2} });

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// Home tiles (filled by the host) and receive buffers, all column-major.
var A_tile = @zeros([Mt * Kt]f32);
var B_tile = @zeros([Kt * Nt]f32);
var C_tile = @zeros([Mt * Nt]f32);
var A_buf  = @zeros([Mt * Kt]f32);
var T_tile = @zeros([if (kernel == 1) Mt * Nt else 1]f32);   // kernel 1 only
var B_buf  = @zeros([Kt * Nt]f32);
var A_ptr: [*]f32 = &A_tile;
var B_ptr: [*]f32 = &B_tile;
var C_ptr: [*]f32 = &C_tile;

// Kernel timing on this PE's own TSC: stamp[0] at main(), then per step s
// stamp[1+3s] = broadcasts issued, [2+3s] = compute starts, [3+3s] = compute
// ends, and stamp[3P+1] just before the host is released. Only compare stamps
// from the same PE (each counter starts when the launch reaches that PE).
const timestamp = @import_module("<time>");
var stamp = @zeros([3 * (3 * P + 2)]u16);
var tsc_ptr: [*]u16 = &stamp;
fn stamp_now(k: u16) void {
  timestamp.get_timestamp(@ptrcast(*[3]u16, &stamp[3 * k]));
}

var px: u16 = 0;
var py: u16 = 0;
var step: u16 = 0;

// main() is the host's RPC. It returns at once; the step chain continues in tasks.
fn main() void {
  timestamp.enable_tsc();
  stamp_now(0);
  row.init();
  col.init();
  px = row.pe_id;          // my column index (x coordinate)
  py = col.pe_id;          // my row index (y coordinate)
  start_step();
}

fn start_step() void {
  stamp_now(1 + 3 * step);
  // Root of the row broadcast is the PE in column `step`; it sends its home
  // tile, everyone else receives into A_buf. Same for B down the columns.
  const Ap = if (px == step) &A_tile else &A_buf;
  const Bp = if (py == step) &B_tile else &B_buf;
  row.broadcast(step, @ptrcast([*]u32, Ap), @as(u16, Mt * Kt), X_DONE);
  col.broadcast(step, @ptrcast([*]u32, Bp), @as(u16, Kt * Nt), Y_DONE);
}

// The join: COMPUTE starts blocked. y_done unblocks it, x_done activates it;
// it runs only when both have happened, in either order (Chapter 5).
task x_done() void { @activate(COMPUTE); }
task y_done() void { @unblock(COMPUTE); }

task compute() void {
  stamp_now(2 + 3 * step);
  const Ap = if (px == step) &A_tile else &A_buf;
  const Bp = if (py == step) &B_tile else &B_buf;

  if (kernel == 0) {
    // C[:, j] += A[:, k] * B[k, j]: one @fmacs of length Mt per (k, j) pair,
    // Kt * Nt instructions per step. The scalar B[k, j] is read from memory.
    var A_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{Mt} -> A_tile[i] });
    A_dsd = @set_dsd_base_addr(A_dsd, Ap);
    for (@range(i16, Kt)) |k| {
      var C_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{Mt} -> C_tile[i] });
      for (@range(i16, Nt)) |j| {
        @fmacs(C_dsd, C_dsd, A_dsd, Bp.*[j * Kt + k]);
        C_dsd = @increment_dsd_offset(C_dsd, Mt, f32);
      }
      A_dsd = @increment_dsd_offset(A_dsd, Mt, f32);
    }
  } else {
    // C += A[:, k] (outer) B[k, :]: two instructions of length Mt * Nt per k,
    // Kt * 2 instructions per step. 2-D DSDs with a zero stride repeat column
    // k of A across j and row k of B across i; T_tile holds the product.
    var A2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> A_tile[i] });
    var B2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> B_tile[j * Kt] });
    const T2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> T_tile[j * Mt + i] });
    const C2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> C_tile[j * Mt + i] });
    A2 = @set_dsd_base_addr(A2, Ap);
    B2 = @set_dsd_base_addr(B2, Bp);
    for (@range(i16, Kt)) |k| {
      @fmuls(T2, A2, B2);
      @fadds(C2, C2, T2);
      A2 = @increment_dsd_offset(A2, Mt, f32);
      B2 = @increment_dsd_offset(B2, 1, f32);
    }
  }
  stamp_now(3 + 3 * step);

  step += 1;
  @block(COMPUTE);                     // re-arm the join for the next step
  if (step < P) start_step() else @activate(EXIT);
}

task exit() void {
  stamp_now(3 * P + 1);
  sys_mod.unblock_cmd_stream();        // only now does the host's launch() return
}

comptime {
  @bind_local_task(exit, EXIT);
  @bind_local_task(compute, COMPUTE);
  @bind_local_task(x_done, X_DONE);
  @bind_local_task(y_done, Y_DONE);
  @block(COMPUTE);
  @export_symbol(A_ptr, "A");
  @export_symbol(B_ptr, "B");
  @export_symbol(C_ptr, "C");
  @export_symbol(tsc_ptr, "tsc");
  @export_symbol(main);
}

Notes on the details:

  • Home tile or buffer. At step s the root of the row broadcast is the PE whose px == s. It sends from its own A_tile; everyone else receives into A_buf. compute makes the same choice, so a PE multiplies its own tile when it is the root. The two buffers cost 2 extra tiles of memory, the price of not overwriting home tiles that later steps still need to send.
  • Kernel 0's loop. For each k and j it reads the scalar B[k, j] and issues one @fmacs of length Mt: C[:, j] += A[:, k] · B[k, j]. That is Kt·Nt vector instructions per step, each moving a DSD with @increment_dsd_offset (Chapter 6).
  • Timestamps. stamp_now(k) writes the 48-bit TSC into slot k of an exported array: once at main(), three times per step (broadcasts issued, compute starts, compute ends) and once in exit. The host reads them with a 16-bit memcpy, as in Lab 3. All differences are taken on one PE, because counters on different PEs start at different times (Chapter 12).

The host script: tile, copy, launch, read C and the stamps, check against numpy, then report one PE's split.

course/programs/06-summa/run.py
#!/usr/bin/env cs_python
# Host side of 06-summa (adapted from Cerebras SDK 2.10.1 benchmarks/gemm-collectives_2d/run.py).
import argparse, json
import numpy as np
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder  # pylint: disable=no-name-in-module

p = argparse.ArgumentParser(); p.add_argument('--name'); p.add_argument('--cmaddr')
args = p.parse_args()
cfg = json.load(open(f"{args.name}/out.json"))
prm = cfg['params']
P, Mt, Kt, Nt, kern = (int(prm[k]) for k in ('P', 'Mt', 'Kt', 'Nt', 'kernel'))
M, K, N = Mt * P, Kt * P, Nt * P                    # A is M x K, B is K x N

np.random.seed(7)
A = np.random.rand(M, K).astype(np.float32)
B = np.random.rand(K, N).astype(np.float32)

# Host layout: PE (px, py) gets block row py, block column px, flattened
# column-major. reshape(rows, tile_rows, cols, tile_cols) -> (py, px, col, row).
def to_tiles(X, tr, tc):
  return X.reshape(P, tr, P, tc).transpose(0, 2, 3, 1).ravel()
def from_tiles(flat, tr, tc):
  return flat.reshape(P, P, tc, tr).transpose(0, 3, 1, 2).reshape(P * tr, P * tc)

# suppress_simfab_trace: large tiles would otherwise write gigabytes of simulator traces.
rt = SdkRuntime(args.name, cmaddr=args.cmaddr, suppress_simfab_trace=True)
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
# One memcpy per matrix covers the whole P x P rectangle: the wire order is
# row-major over PEs (py outer, px inner), Mt*Kt words per PE.
rt.memcpy_h2d(rt.get_id('A'), to_tiles(A, Mt, Kt), 0, 0, P, P, Mt * Kt, **kw)
rt.memcpy_h2d(rt.get_id('B'), to_tiles(B, Kt, Nt), 0, 0, P, P, Kt * Nt, **kw)
rt.launch('main', nonblock=False)
Cf = np.zeros(M * N, dtype=np.float32)
rt.memcpy_d2h(Cf, rt.get_id('C'), 0, 0, P, P, Mt * Nt, **kw)
S = 3 * P + 2                                         # timestamps per PE
w = np.zeros(P * P * S * 3, dtype=np.uint32)
rt.memcpy_d2h(w, rt.get_id('tsc'), 0, 0, P, P, S * 3,
              **dict(kw, data_type=MemcpyDataType.MEMCPY_16BIT))
rt.stop()

C = from_tiles(Cf, Mt, Nt)
np.testing.assert_allclose(C, A @ B, rtol=1e-5, atol=1e-6)

w = (w & 0xffff).astype(np.int64).reshape(P, P, S, 3)  # (py, px, stamp, word)
t = w[..., 0] | (w[..., 1] << 16) | (w[..., 2] << 32)
total = t[:, :, -1] - t[:, :, 0]                      # same-PE differences only
issue, cbeg, cend = t[:, :, 1:-1:3], t[:, :, 2:-1:3], t[:, :, 3:-1:3]
comp = (cend - cbeg).sum(-1)                          # compute, all steps
comm = (cbeg - issue).sum(-1)                         # issue -> both broadcasts done
py, px = P - 1, P - 1                                  # report the far corner PE
print(f"C = A·B with A {M}x{K}, B {K}x{N} on {P}x{P} PEs, tiles {Mt}x{Kt} · {Kt}x{Nt}; C[:2, :4] =")
print(np.array2string(C[:2, :4], precision=4))
print(f"kernel time (TSC, per PE, cycles): min {total.min()}, max {total.max()}")
print(f"PE ({px},{py}) over {P} steps: total {total[py, px]} = broadcast wait {comm[py, px]}"
      f" + compute {comp[py, px]} + other {total[py, px] - comm[py, px] - comp[py, px]}")
shape = f"{Kt * Nt} @fmacs of length {Mt}" if kern == 0 else f"{Kt} x (@fmuls + @fadds) of length {Mt * Nt}"
print(f"compute per step {comp[py, px] / P:.0f} cycles for {Mt * Kt * Nt} multiply-adds ({shape})")
print("SUCCESS!")

What the numbers say

  • Compute takes over quickly. At T = 4 the two phases are about equal (broadcast 2,310 vs compute 2,492 cycles on WSE-3). At the default T = 8 compute is 80% of the kernel, at T = 16 it is 94%, and at T = 32 it is 97.5% (10,277 vs 414,896) Measured. This is the opposite of Lab 3, where a 16-cell step was 70% messages, tasks and instruction start-up: GEMM does T³ work for 2T² words, so the fabric falls out of the picture once tiles are more than a few words across.
  • A broadcast step costs a fixed ≈ 520 cycles plus about 1 cycle per word received on WSE-3, counting both tiles: 650, 1,033, 1,673 and 2,569 cycles per step for T = 8, 16, 24, 32, against 520 + 2T² = 648, 1,032, 1,672 and 2,568 Measured → Derived fit. On WSE-2 the same fit is ≈ 429 + 2T² (558 and 941 cycles at T = 8 and 16; 2,476 at T = 32). Two broadcasts run at once, each on its own microthread and network, yet the time grows with the sum of the two tiles, so at this size the two transfers do not overlap fully. With non-square tiles (P = 2, Kt = Nt = 8) growing only the A tile from 32 to 256 words added 0.5–0.8 cycles per word, so they overlap partly; we have not isolated where the PE serialises them. The fixed part is the library's per-operation work (route rewrite, FSM tasks, teardown, the lock task, the callback), the same order as the ≈ 700 cycles Chapter 12 measured for the library in one dimension.
  • The step time does not depend on P. At T = 8 on WSE-3, a broadcast step costs 626, 650, 653 and 654 cycles for P = 2, 4, 6, 8, and compute is 2,903 cycles at every P; on WSE-2, 563, 558 and 557 cycles for P = 2, 4, 8 Measured. The multicast streams through the routers at 1–2 cycles per hop, so the extra hops of a wider grid are lost in the noise. The kernel therefore grows exactly with the number of steps: 7,188, 14,422, 21,624 and 28,828 cycles for P = 2, 4, 6, 8 (WSE-3), close to 3,600·P. Weak scaling is flat per step; the total grows with P because a P-times-larger matrix needs P steps.
  • But compute reaches only a fraction of the ideal. A PE can do one f32 multiply-add per cycle (Chapter 6), so a step's ideal is T³ cycles. Kernel 0 needs 2,903 cycles for 512 multiply-adds at T = 8 (18% of ideal) and 103,724 for 32,768 at T = 32 (32%) on WSE-3; on WSE-2, 2,768 (18%) and 96,630 at T = 32 (34%) Measured. Two separate costs, both from Chapter 6, explain it; the next callout takes them apart.
  • Kernel 1: fewer, longer instructions. Replacing the Kt·Nt short @fmacs with Kt pairs of @fmuls + @fadds of length Mt·Nt (2-D DSDs with a zero stride broadcast column k of A and row k of B over the tile) cuts the step to 1,594 cycles at T = 8 and 63,890 at T = 32 on WSE-3: 51% of ideal, 1.6× faster than the SDK loop Measured. Per k it costs 1.87 cycles per element + 77, fitted over T = 8–32 Derived fit. On WSE-2, where @fadds moves 1 element per cycle instead of 2, it costs 2.0 per element + 112: 1,921 cycles at T = 8 and 69,026 at T = 32 (47% of ideal) Measured. It needs one more Mt × Nt tile of memory, which lowers the largest tile that fits (below).
  • Host I/O is still a large share of the whole run. At the defaults the simulator counts 36,959 cycles in total, of which the kernel is 14,422 (39%); at T = 32 it is 425,382 of 635,409 (67%) Measured. As in Labs 1–3, time the kernel with the TSC.
Where the other two-thirds go: start-up and a bank clash

Kernel 0 issues Kt·Nt instructions of length Mt per step. Each one costs a fixed part plus a per-element part, and both are larger than the ideal 0 + 1:

  • A fixed ≈ 29–38 cycles per instruction. Reading the scalar B[k, j] (with its index arithmetic), @increment_dsd_offset and starting the op. Chapter 6 measured about 33–35 cycles per step for this kind of scalar loop around a DSD op. With Mt = 8 that alone is about 80% of the instruction. Removing the multiply-adds entirely leaves 27 cycles per step (WSE-3) for the timestamps and the empty task, so the loop really is the cost Measured. The fixed part grows a little with the tile size (≈ 29 at Kt = Nt = 8, ≈ 37–38 at 16–32); we have not isolated why.
  • 2 cycles per element instead of 1. Chapter 6's operand-collision rule: @fmacs runs at half speed when its two source streams start at addresses that are equal mod 4 words. Here the sources are column j of C (C_tile + j·Mt) and column k of A (A + k·Mt). When Mt is a multiple of 4 every (j, k) pair has the same alignment as the two array bases, so either all instructions clash or none do. In the course's runs they all did. With an odd Mt the alignment cycles through the four residues and about a quarter clash. A Mt sweep at P = 2, Kt = Nt = 8 on WSE-3 shows exactly that: 45.4, 60.9 and 92.4 cycles per @fmacs for Mt = 8, 16, 32 (2·Mt + 29), but 49.9, 52.4 and 72.4 for Mt = 15, 17, 33 (≈ 1.25·Mt + 31) Measured.

The test. Shift C by one word and the clash should go. It does, but only halfway at first: with C padded, each PE ran its compute in 13,739 cycles on the step where it multiplies its own A tile and still 17,835 on the step where it uses A_buf (P = 2, T = 16, WSE-3), because the two A arrays sit at different alignments. The PEs then waited for each other, so the kernel was no faster: the grid moves at the pace of its slowest PE. Putting both A arrays in one array (home tile, then buffer: same alignment) and padding C by 1, 2 or 3 words gives 13,739 on every step and every PE; padding by 0 gives 17,835 again. The difference is 4,096 cycles, exactly one cycle per multiply-add Measured. With the fix, kernel 0 takes 2,391 / 13,739 / 70,956 cycles per step at T = 8 / 16 / 32 on WSE-3 (46% of ideal at T = 32, up from 32%) and 12,004 instead of 16,086 at T = 16 on WSE-2 Measured, P = 2. Exercise 4 walks through it.

The same two costs appear in kernel 1, in a different mix. It issues only 2·Kt instructions, so the fixed part almost vanishes, but its @fmuls on two zero-stride 2-D DSDs costs about 1.6 cycles per element on WSE-3 and 1.35 on WSE-2 (16 @fmuls alone take 6,774 and 5,808 cycles per step at T = 16), while @fadds alone takes 0.5 and 1.0 cycles per element, as Chapter 6 found Measured, ablation. We have not isolated why the @fmuls is slower than 1 per cycle; the zero-stride operand reads one word repeatedly, and the collision rule is empirical. Applying the C-padding fix to kernel 1 saves only 6% (8,418 vs 8,914 cycles per step at T = 16, WSE-3).

The lesson for the roofline. "Compute-bound" on the wafer does not mean "at peak". The fabric is out of the way, but every instruction pays start-up and every pair of operands must avoid a bank clash. The levers are the same as in Lab 3: fewer, longer instructions, and pad and measure.

Put the fits on the largest square grid the SDK-visible WSE-2 fabric allows: 750 × 994 minus memcpy's frame gives at most 743 PEs across, so P = 743, about 552k PEs (Chapter 13). Take the largest tiles that linked on WSE-2 and the 1.1 GHz WSE-2 clock Vendor, HC22:

  • Kernel 1, T = 39. ≈ 3,470 + 123,000 cycles per step, ≈ 85 ms for 28,977², ≈ 0.57 PFLOP/s, 47% of that peak.

Use the budget calculator above to try other points. Caveats: simulator cycles and models fitted at P ≤ 8, extrapolated to P = 743 on the strength of the flat per-step cost (a 743-hop multicast adds ≈ 750–1,500 cycles of latency per step at 1–2 cycles per hop, under 1% here); f32 only, while the wafer's headline numbers are 16-bit (Chapter 6 measured f16 @fmach at 2–4 elements per cycle, so a tuned f16 kernel could be several times faster, unmeasured here); and loading the three matrices from the host (≈ 13 GB at T = 45) is left out. The real lesson is the ratio: at this scale the fabric costs about 2% of each step, and the per-PE instruction stream is the whole game. It is the same lesson as a GPU's tiled matmul and Tenstorrent's: once the tiles are in place, the inner loop decides how close you get to peak.

Check yourself

Why does SUMMA need no reduction, while Chapter 12's GEMV did?

The owner of a C block accumulates every term of its own sum: at step s it receives the A and B blocks it needs. In the GEMV the A blocks stayed put and each PE produced a partial sum of a y block that lived on several PEs, so the partials had to be added along the row.

Why does the library rewrite routes before every broadcast instead of declaring them in the layout?

The root moves every step, so the direction each router receives from changes. A static route has one input direction (on WSE-3 at most one is allowed), so static routes would need one color per possible root. Rewriting one color at run time keeps it to two colors per axis.

What does the teardown wavelet protect against?

Rewriting a router while wavelets of the previous broadcast are still passing through it. The root sends the teardown after its last data wavelet, on the same route, so each router enters teardown only after the data has gone by, and the next broadcast() may then reconfigure it.

x_done runs, then y_done. How many times does compute run, and what if the order is reversed?

Once, either way. compute starts blocked; one callback activates it and the other unblocks it, and the task picker runs it only when both bits are set. compute blocks itself again before starting the next step.

Kernel 0 at T = 32 needs 101 cycles per @fmacs of 32 elements. Where do they go?

About 2 cycles per element (64), because the two source streams collide in the same memory bank so @fmacs runs at half speed, plus about 37 cycles per instruction for the loop: reading the scalar, moving the DSD and starting the op.

Doubling P at fixed tile size: what happens to the time per step and to the total?

The time per step stays almost constant (the multicast's hop cost is tiny), so the kernel takes twice as long in total, for a matrix twice as large in each dimension: 8× the work in 2× the time, on 4× the PEs.

Kernel 1 runs the tile as @fmuls + @fadds. Why does it gain less over kernel 0 on WSE-2 than on WSE-3?

@fadds streams 2 f32 elements per cycle on WSE-3 but 1 on WSE-2 (Chapter 6), so the pair costs about 1.9 cycles per element on WSE-3 and 2.0 on WSE-2, while kernel 0's loop is a little cheaper on WSE-2 (about 27 vs 30 cycles of per-instruction overhead).
