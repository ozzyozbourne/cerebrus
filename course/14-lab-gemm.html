Lab 4: 2-D GEMM with SUMMA

Every lab so far ran on a row or a column. This one uses a P × P grid of PEs to multiply two matrices with SUMMA, the textbook distributed GEMM. Each step broadcasts one block column of A along the rows and one block row of B down the columns, and then every PE multiplies the two tiles it received. The SDK's <collectives_2d> library does the broadcasts, rewriting the routes at run time and tearing them down after each step. We time each step on each PE's own timestamp counter (TSC). At realistic tile sizes the kernel spends almost all its time computing, which is the opposite of Lab 3's result. Yet the SDK's multiply loop reaches only 18% of the multiply-add rate at the default tile and about a third at T = 32. The measurements show where the rest goes, and a rewrite with @map and one word of padding, taken from Chapter 6, gets to 94%.

After this lab you can

  • Explain SUMMA as "P outer products of block columns and block rows", and map it onto a P × P grid with 2-D host I/O.
  • Read <collectives_2d>: two colors per axis, routes rewritten per broadcast, a teardown wavelet, and a lock task that fires the callback.
  • Build a task that waits for two independent networks (block + activate), and re-arm it every step.
  • Time broadcast and compute separately with the TSC, compare them with a compute-bound estimate, and find the instruction and bank-clash overheads.
  • Budget a kernel before writing it: memory, colors, task IDs, queues and microthreads, and a cycle model.

From GEMV to SUMMA

Chapter 12 composed a distributed GEMV from two collectives: broadcast slices of x down the columns, multiply locally, and reduce partial y along the rows. A GEMM, C = A·B, is many GEMVs at once (one per column of B), so you could run that pattern N times. SUMMA (Scalable Universal Matrix Multiplication Algorithm, van de Geijn and Watts, 1997) organises the same work so that no reduction is needed at all.

Cut A (M × K), B (K × N) and C (M × N) into a P × P grid of blocks. PE (px, py) owns block row py and block column px of all three: A(py, px), B(py, px) and C(py, px). The owner of a block of C computes it:

Mind the index order.

PE coordinates are (x, y) = (column, row), but matrix blocks are indexed (row, column). So PE (px, py) owns block (py, px): PE (2, 0) holds the block in block row 0, block column 2. Swapping the two is the most common way to get a wrong C in a 2-D program, and nothing crashes when you do.

C(py, px) = Σ_s  A(py, s) · B(s, px)        s = 0 … P−1

The term for step s needs block column s of A and block row s of B. So at step s the PEs in grid column s broadcast their A block along their row, the PEs in grid row s broadcast their B block down their column, and every PE adds one tile product into its C. After P steps each C block is complete, and it never moved. In matrix terms each step adds one rank-K/P update, an outer product of a block column and a block row.

The GEMV warm-up. Set Nt=1 and the same program computes a matrix times P vectors at once (B is K × P): a batched GEMV. Each step still broadcasts an A tile along the rows, but the B "tile" is a column segment of only Kt words, and each PE does Kt multiply-adds per output element. Compared with Chapter 12's GEMV, the vector is broadcast and the result stays put, instead of the vector staying put and the result being reduced. The warm-up exercise runs it.

Why it suits the wafer. Each step moves Mt·Kt + Kt·Nt words into every PE and does Mt·Kt·Nt multiply-adds there. For square tiles of side T that is 2T² words for T³ multiply-adds: the compute grows faster than the traffic, so large tiles are compute-bound. The broadcasts are multicasts (one send reaches the whole row, Chapter 12's program 05), so their cost barely depends on P. And C never moves, so the only data in flight is A and B.

Data layout and host I/O on a 2-D grid

The host copies each matrix in a single memcpy_h2d over the whole P × P rectangle (Chapter 7). With MemcpyOrder.ROW_MAJOR, the flat host array is consumed PE by PE in row-major order over the grid (py outer, px inner), Mt·Kt words per PE. So the host must arrange A so that each PE's tile is contiguous, and in the order the PE wants. This program stores every tile column-major, so that a column of the A tile, which is what the inner multiply-add streams over, is contiguous.

Reading C back is the inverse: the device returns (py, px, column, row), and transpose(0, 3, 1, 2) brings it back to (block row, row, block column, column). Getting one axis wrong does not crash anything: the program just multiplies the wrong numbers, and the numpy check catches it. That check is the first line of defence in any 2-D program.

Inside <collectives_2d>

Chapter 12 used the library in one dimension and measured its fixed cost at about 700 cycles Measured, Ch. 12. Here we need it in both dimensions, so it is worth opening up. The source is csl-libs/collectives_2d/pe.csl in the SDK image (1,312 lines) SDK 2.10.1; the broadcast path is short.

What one instance owns

Each axis is a separate instance of the module (row and col in our program). Each one owns two colors (DATA_COLOR_0, DATA_COLOR_1), two local task IDs, two input/output queue pairs and one set of DSD registers. The two tasks are an FSM task (a small finite-state-machine task that runs once per stage of a collective and decides what to do next) and a lock task (below). The DSD registers (DSRs) are the hardware registers that hold a descriptor while an operation runs (Chapter 6); the two instances must use different ones, which is what dest_dsr_ids and its siblings choose in pe_program.csl. Broadcast uses only color 0; color 1 is for reduce_fadds, which needs the alternating checkerboard of Chapter 12's program 03. The layout calls c2d.get_params(px, py, ids), which records only whether the PE sits at either end of its row and column. The PE reads its own coordinate at run time (init()), so the compiler builds a handful of ELF files instead of P². At load time color 0 is a broadcast network rooted at PE 0, in teardown mode.

Why the routes change at run time

A static route has a fixed input direction, and on WSE-3 a route accepts at most one input direction (Chapter 4). In SUMMA the root of the row broadcast moves one column east every step: at step 0 every PE receives from the west side, at step P−1 from the east side, and in between the PEs left of the root receive from the east and the PEs right of it from the west. With static routes you would need a color per root, P colors per axis. The library uses one color and rewrites it before each broadcast:

collectives_2d/pe.csl, configure_broadcast_network() (abridged)
if (pe_id == root) {                    // the root's CE feeds the router
  // ends of the line send one way, everyone else both ways
  color_config.reset_routes(addr, .{.tx = [2]direction{POS_DIR, NEG_DIR}, .rx = RAMP});
} else if (pe_id < root) {               // left of / above the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, NEG_DIR}, .rx = POS_DIR});
} else {                                 // right of / below the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, POS_DIR}, .rx = NEG_DIR});
}
tile_config.teardown.exit(DATA_COLOR_0);  // leave teardown: traffic may flow

POS_DIR is EAST for the row instance and SOUTH for the column instance. Every non-root router in the middle of the line passes the wavelet both to its own CE (RAMP) and onward; the PEs at the two ends of the line have nobody to pass it to, so their routes only take it to their CE (.tx = RAMP, a branch the abridged listing leaves out). This is program 05's multicast with a run-time root.

One broadcast, end to end

  1. broadcast(root, buf, count, callback) blocks the lock task, records the root and the buffer, clears the filter and switch state left by any earlier gather or scatter, rewrites the routes as above, and leaves teardown mode.
  2. Transfer. It activates its FSM task, which starts one asynchronous 32-bit move of count words: memory → fabric at the root, fabric → memory everywhere else. The move runs on the microthread of its queue (2 for the row instance, 3 for the column instance) and activates the FSM task again when it finishes.
  3. Teardown. On that second run the FSM calls initiate_teardowns(). Only the root sends anything: one control wavelet with the TEARDOWN command and the CE-ignore bit set, on color 0. (A control wavelet carries commands for the routers it passes; with CE-ignore set, the routers act on it but no PE's CE receives it as data, Chapter 4.) It follows the same routes as the data, so it reaches every router in the line after the last data wavelet, and each router puts color 0 back into teardown mode.
  4. Lock. Entering teardown runs the CE's teardown handler, task 29 (Chapter 4, Chapter 5), which activates the lock task. The FSM unblocks the lock when its own transfer is done. So the lock runs only when both have happened: the data is in my memory, and the network is torn down and ready to be rewritten. The lock task then activates the user's callback (our x_done or y_done).

The teardown is what makes the next step's rewrite safe: no PE can reconfigure color 0 while wavelets of the previous broadcast are still in its router. What happens to a root that starts step s+1 while a slower neighbour is still computing step s? Its data waits behind the neighbour's router, which is still in teardown mode, and the lossless fabric back-pressures the sender until the neighbour calls broadcast and leaves teardown. The library's comments describe this ordering ("if we clear TIP bit before routing is reconfigured, it stalls"; TIP is the router's teardown-in-progress flag for that color, and clearing it is what teardown.exit() does); we did not isolate it in a separate experiment Derived from the library source.

Both this broadcast and Chapter 12's program 05 are chains: the wavelets stream through every router of the line and each router copies them to its CE on the way. Whether a tree would be better is a question for reductions, not broadcasts; the aside after "Scaling up" works it out.

The task that waits on two networks

Each step needs both tiles before it can compute: the A tile from the row broadcast and the B tile from the column broadcast. They finish in either order. Chapter 5's join does this with two bits: the compute task starts blocked; y_done unblocks it and x_done activates it. A task runs only when it is both activated and unblocked, so compute runs exactly once, after the later of the two callbacks. At the end of compute, @block(COMPUTE) re-arms the join for the next step before start_step() issues the next pair of broadcasts.

Why not count, as Lab 3 did with pending? That works too, but it needs a counter, a decrement in each callback and a test. The join is free: the hardware task picker evaluates it.

Walking through the code

The layout file is short. Two calls per PE: the library parameters with our colors and entrypoint task IDs, and the PE program with the tile sizes. The resource map at the top is the budget sheet the design section below fills in.

// 06-summa: C = A·B on a P x P grid of PEs with the SUMMA algorithm.
// Adapted from Cerebras SDK 2.10.1 benchmarks/gemm-collectives_2d (layout.csl,
// pe.csl, run.py), rewritten in the course's style, with per-step TSC stamps.
//
// Each PE (px, py) owns one tile of each matrix: A is Mt x Kt, B is Kt x Nt,
// C is Mt x Nt, all column-major. In step s, the PEs of column s broadcast
// their A tile along their row, and the PEs of row s broadcast their B tile
// down their column; then every PE does C_tile += A_s · B_s.
// Teaches: a 2-D decomposition, <collectives_2d> (routes rewritten at run
// time, teardown), a task that waits on two networks, the compute-bound regime.
//
// Resource map (every PE)
//   colors        0, 1  row (x) broadcast         2, 3  column (y) broadcast
//                 (20-23 belong to memcpy and the runtime, Chapter 10)
//   local tasks   8, 9  x library (FSM, lock)     10, 11  y library (FSM, lock)
//                 12 exit   13 compute   14 x_done   15 y_done
//                 (the teardown handler, task 29, is installed by the library)
//   queues        0, 1  memcpy    2, 4  x library    3, 5  y library
//   microthreads  = queue IDs: a broadcast uses 2 (x) and 3 (y) at the same time
param P: u16;              // grid is P x P PEs
param Mt: u16;             // tile sizes on one PE
param Kt: u16;
param Nt: u16;
param kernel: u16 = 0;     // 0 = column @fmacs (SDK), 1 = outer product (pe_program.csl)

const memcpy = @import_module("<memcpy/get_params>", .{ .width = P, .height = P });
const c2d = @import_module("<collectives_2d/params>");

layout {
  @set_rectangle(P, P);
  for (@range(u16, P)) |px| {
    const memcpy_params = memcpy.get_params(px);
    for (@range(u16, P)) |py| {
      // get_params only records which end of its row/column a PE sits at;
      // the PE reads its own coordinates at run time (fewer distinct ELFs).
      const c2d_params = c2d.get_params(px, py, .{
        .x_colors      = .{ @get_color(0),          @get_color(1) },
        .x_entrypoints = .{ @get_local_task_id(8),  @get_local_task_id(9) },
        .y_colors      = .{ @get_color(2),          @get_color(3) },
        .y_entrypoints = .{ @get_local_task_id(10), @get_local_task_id(11) },
      });
      @set_tile_code(px, py, "pe_program.csl", .{
        .memcpy_params = memcpy_params, .c2d_params = c2d_params,
        .Mt = Mt, .Kt = Kt, .Nt = Nt, .kernel = kernel });
    }
  }
  @export_name("A", [*]f32, true);
  @export_name("B", [*]f32, true);
  @export_name("C", [*]f32, true);
  @export_name("tsc", [*]u16, true);   // 3P + 2 timestamps of 3 x u16 per PE
  @export_name("main", fn()void);
}

The PE program. The library instances come first, each with its own queues and DSD registers. main() is the RPC; it returns immediately and the rest is a chain of tasks: start_step → two broadcasts → x_done/y_done → compute → start_step … → exit, which unblocks the host's command stream. The host's launch() call returned long before: it returns at once, and it is the host's next command (the memcpy_d2h of C) that waits until exit runs (Chapter 7). Kernel 0 is the SDK's loop; kernel 1 is explained in the measurement section.

course/programs/06-summa/pe_program.csl
// 06-summa PE program (see layout.csl for the algorithm and the resource map).
param memcpy_params;
param c2d_params;
param Mt: i16;
param Kt: i16;
param Nt: i16;
param kernel: u16;         // 0 = column @fmacs (as in the SDK), 1 = outer product

const P = @get_rectangle().width;

const EXIT:       local_task_id = @get_local_task_id(12);
const COMPUTE:    local_task_id = @get_local_task_id(13);
const X_DONE:     local_task_id = @get_local_task_id(14);
const Y_DONE:     local_task_id = @get_local_task_id(15);

// One library instance per axis. Each owns two colors, two queues, two task IDs
// and one set of DSD registers. x and y must not share any of them.
const row = @import_module("<collectives_2d/pe>", .{
  .dim_params = c2d_params.x, .queues = [2]u16{2, 4},
  .dest_dsr_ids = [1]u16{1}, .src0_dsr_ids = [1]u16{1}, .src1_dsr_ids = [1]u16{1} });
const col = @import_module("<collectives_2d/pe>", .{
  .dim_params = c2d_params.y, .queues = [2]u16{3, 5},
  .dest_dsr_ids = [1]u16{2}, .src0_dsr_ids = [1]u16{2}, .src1_dsr_ids = [1]u16{2} });

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// Home tiles (filled by the host) and receive buffers, all column-major.
var A_tile = @zeros([Mt * Kt]f32);
var B_tile = @zeros([Kt * Nt]f32);
var C_tile = @zeros([Mt * Nt]f32);
var A_buf  = @zeros([Mt * Kt]f32);
var T_tile = @zeros([if (kernel == 1) Mt * Nt else 1]f32);   // kernel 1 only
var B_buf  = @zeros([Kt * Nt]f32);
var A_ptr: [*]f32 = &A_tile;
var B_ptr: [*]f32 = &B_tile;
var C_ptr: [*]f32 = &C_tile;

// Kernel timing on this PE's own TSC: stamp[0] at main(), then per step s
// stamp[1+3s] = broadcasts issued, [2+3s] = compute starts, [3+3s] = compute
// ends, and stamp[3P+1] just before the host is released. Only compare stamps
// from the same PE (each counter starts when the launch reaches that PE).
const timestamp = @import_module("<time>");
var stamp = @zeros([3 * (3 * P + 2)]u16);
var tsc_ptr: [*]u16 = &stamp;
fn stamp_now(k: u16) void {
  timestamp.get_timestamp(@ptrcast(*[3]u16, &stamp[3 * k]));
}

var px: u16 = 0;
var py: u16 = 0;
var step: u16 = 0;

// main() is the host's RPC. It returns at once; the step chain continues in tasks.
fn main() void {
  timestamp.enable_tsc();
  stamp_now(0);
  row.init();
  col.init();
  px = row.pe_id;          // my column index (x coordinate)
  py = col.pe_id;          // my row index (y coordinate)
  start_step();
}

fn start_step() void {
  stamp_now(1 + 3 * step);
  // Root of the row broadcast is the PE in column `step`; it sends its home
  // tile, everyone else receives into A_buf. Same for B down the columns.
  const Ap = if (px == step) &A_tile else &A_buf;
  const Bp = if (py == step) &B_tile else &B_buf;
  row.broadcast(step, @ptrcast([*]u32, Ap), @as(u16, Mt * Kt), X_DONE);
  col.broadcast(step, @ptrcast([*]u32, Bp), @as(u16, Kt * Nt), Y_DONE);
}

// The join: COMPUTE starts blocked. y_done unblocks it, x_done activates it;
// it runs only when both have happened, in either order (Chapter 5).
task x_done() void { @activate(COMPUTE); }
task y_done() void { @unblock(COMPUTE); }

task compute() void {
  stamp_now(2 + 3 * step);
  const Ap = if (px == step) &A_tile else &A_buf;
  const Bp = if (py == step) &B_tile else &B_buf;

  if (kernel == 0) {
    // C[:, j] += A[:, k] * B[k, j]: one @fmacs of length Mt per (k, j) pair,
    // Kt * Nt instructions per step. The scalar B[k, j] is read from memory.
    var A_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{Mt} -> A_tile[i] });
    A_dsd = @set_dsd_base_addr(A_dsd, Ap);
    for (@range(i16, Kt)) |k| {
      var C_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{Mt} -> C_tile[i] });
      for (@range(i16, Nt)) |j| {
        @fmacs(C_dsd, C_dsd, A_dsd, Bp.*[j * Kt + k]);
        C_dsd = @increment_dsd_offset(C_dsd, Mt, f32);
      }
      A_dsd = @increment_dsd_offset(A_dsd, Mt, f32);
    }
  } else {
    // C += A[:, k] (outer) B[k, :]: two instructions of length Mt * Nt per k,
    // Kt * 2 instructions per step. 2-D DSDs with a zero stride repeat column
    // k of A across j and row k of B across i; T_tile holds the product.
    var A2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> A_tile[i] });
    var B2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> B_tile[j * Kt] });
    const T2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> T_tile[j * Mt + i] });
    const C2 = @get_dsd(mem4d_dsd, .{ .tensor_access = |j, i|{Nt, Mt} -> C_tile[j * Mt + i] });
    A2 = @set_dsd_base_addr(A2, Ap);
    B2 = @set_dsd_base_addr(B2, Bp);
    for (@range(i16, Kt)) |k| {
      @fmuls(T2, A2, B2);
      @fadds(C2, C2, T2);
      A2 = @increment_dsd_offset(A2, Mt, f32);
      B2 = @increment_dsd_offset(B2, 1, f32);
    }
  }
  stamp_now(3 + 3 * step);

  step += 1;
  @block(COMPUTE);                     // re-arm the join for the next step
  if (step < P) start_step() else @activate(EXIT);
}

task exit() void {
  stamp_now(3 * P + 1);
  sys_mod.unblock_cmd_stream();        // the host's next command (memcpy_d2h of C) can now run;
                                       // launch() itself returned at once
}

comptime {
  @bind_local_task(exit, EXIT);
  @bind_local_task(compute, COMPUTE);
  @bind_local_task(x_done, X_DONE);
  @bind_local_task(y_done, Y_DONE);
  @block(COMPUTE);
  @export_symbol(A_ptr, "A");
  @export_symbol(B_ptr, "B");
  @export_symbol(C_ptr, "C");
  @export_symbol(tsc_ptr, "tsc");
  @export_symbol(main);
}

Notes on the details:

  • Home tile or buffer. At step s the root of the row broadcast is the PE whose px == s. It sends from its own A_tile; everyone else receives into A_buf. compute makes the same choice, so a PE multiplies its own tile when it is the root. The two buffers cost 2 extra tiles of memory, the price of not overwriting home tiles that later steps still need to send.
  • Kernel 0's loop. For each k and j it reads the scalar B[k, j] and issues one @fmacs of length Mt: C[:, j] += A[:, k] · B[k, j]. That is Kt·Nt vector instructions per step, each moving a DSD with @increment_dsd_offset. It is the same "1-D DSD × scalar, move, repeat" pattern as Chapter 6's GEMV column sweep, and "Kernel 0's fixed cost" below measures what that pattern costs and how Chapter 6's @map removes it.
  • Timestamps. stamp_now(k) writes the 48-bit TSC into slot k of an exported array: once at main(), three times per step (broadcasts issued, compute starts, compute ends) and once in exit. The host reads them with a 16-bit memcpy, as in Lab 3. All differences are taken on one PE, because each PE's counter is zeroed when the launch reaches that PE (Chapter 12).

#!/usr/bin/env cs_python
# Host side of 06-summa (adapted from Cerebras SDK 2.10.1 benchmarks/gemm-collectives_2d/run.py).
import argparse, json
import numpy as np
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder  # pylint: disable=no-name-in-module

p = argparse.ArgumentParser(); p.add_argument('--name'); p.add_argument('--cmaddr')
args = p.parse_args()
cfg = json.load(open(f"{args.name}/out.json"))
prm = cfg['params']
P, Mt, Kt, Nt, kern = (int(prm[k]) for k in ('P', 'Mt', 'Kt', 'Nt', 'kernel'))
M, K, N = Mt * P, Kt * P, Nt * P                    # A is M x K, B is K x N

np.random.seed(7)
A = np.random.rand(M, K).astype(np.float32)
B = np.random.rand(K, N).astype(np.float32)

# Host layout: PE (px, py) gets block row py, block column px, flattened
# column-major. reshape(rows, tile_rows, cols, tile_cols) -> (py, px, col, row).
def to_tiles(X, tr, tc):
  return X.reshape(P, tr, P, tc).transpose(0, 2, 3, 1).ravel()
def from_tiles(flat, tr, tc):
  return flat.reshape(P, P, tc, tr).transpose(0, 3, 1, 2).reshape(P * tr, P * tc)

# suppress_simfab_trace: large tiles would otherwise write gigabytes of simulator traces.
rt = SdkRuntime(args.name, cmaddr=args.cmaddr, suppress_simfab_trace=True)
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
# One memcpy per matrix covers the whole P x P rectangle: the wire order is
# row-major over PEs (py outer, px inner), Mt*Kt words per PE.
rt.memcpy_h2d(rt.get_id('A'), to_tiles(A, Mt, Kt), 0, 0, P, P, Mt * Kt, **kw)
rt.memcpy_h2d(rt.get_id('B'), to_tiles(B, Kt, Nt), 0, 0, P, P, Kt * Nt, **kw)
rt.launch('main', nonblock=False)
Cf = np.zeros(M * N, dtype=np.float32)
rt.memcpy_d2h(Cf, rt.get_id('C'), 0, 0, P, P, Mt * Nt, **kw)
S = 3 * P + 2                                         # timestamps per PE
w = np.zeros(P * P * S * 3, dtype=np.uint32)
rt.memcpy_d2h(w, rt.get_id('tsc'), 0, 0, P, P, S * 3,

Where the other two-thirds go: start-up and a bank clash

Kernel 0 issues Kt·Nt instructions of length Mt per step. Each one costs a fixed part plus a per-element part, and both are larger than the ideal 0 + 1:

  • A fixed ≈ 29–38 cycles per instruction. Reading the scalar B[k, j] (with its index arithmetic), @increment_dsd_offset and starting the op. Chapter 6 measured about 33–35 cycles per step for this kind of scalar loop around a DSD op, and removed almost all of it in its matvec with @map over DSRs (N + 2 instead of N + 35 cycles per column). The same rewrite here cuts the fixed part from ≈ 29–37 to ≈ 2–6 cycles per instruction (measured below). With Mt = 8 an instruction costs 2,903 / 64 = 45.4 cycles, so the fixed part is about two-thirds of it (29 of 45 cycles) Derived. Removing the multiply-adds entirely leaves 27 cycles per step (WSE-3) for the timestamps and the empty task, so the loop really is the cost Measured. The fixed part grows a little with the tile size (≈ 29 at Kt = Nt = 8, ≈ 37–38 at 16–32); we have not isolated why.
  • 2 cycles per element instead of 1. Chapter 6's placement rule: DSD op rates depend on where the operands sit; peak needs the two source streams in opposite halves of the 16-byte bank cycle (8 B apart), and the same bank halves the rate; f32 @fmacs is the lenient case, running at half speed only when its two sources start at addresses equal mod 16 bytes (4 words, the same bank). Chapter 6's matvec avoids it by shifting one array by a word, which is exactly exercise 4's fix. Here the sources are column j of C (C_tile + j·Mt) and column k of A (A + k·Mt). When Mt is a multiple of 4 every (j, k) pair has the same alignment as the two array bases, so either all instructions clash or none do. In the square-tile runs they all did (exercise 1's WSE-2 Nt = 1 build is an exception: its arrays landed clash-free): 45.4, 60.9 and 92.4 cycles per @fmacs for Mt = 8, 16, 32 is 2·Mt + 29 Measured, P = 2, Kt = Nt = 8, WSE-3. With any other Mt the alignment changes from instruction to instruction, so only some of them clash; exercise 5 measures how many.

The test. If the clash is real, moving C by one word relative to the A arrays should remove one cycle per multiply-add and nothing else. Exercise 4 makes that change and checks the prediction; the hollow points in the chart above are its result. Two consequences are worth knowing now. First, a fix that helps only some PEs or some steps does not help at all, because the grid moves at the pace of its slowest PE. No barrier enforces that. A PE that finishes early issues its next broadcast and waits, because the root that must send it the next tile may still be computing; and a fast root's data waits behind any slow neighbour's router that is still in teardown (back-pressure, above). Exercise 4's half-fix shows it in the per-step stamps (P = 2, T = 16, WSE-3): PE (0,0) computes step 0 in 13,739 cycles instead of 17,835, then waits 4,822 cycles for step 1's tiles instead of about 1,000. Almost all of the 4,096 cycles it saved (about 3,800) reappear as waiting, and its kernel takes 37,539 cycles against 37,814 unfixed (0.7% faster) Measured → Derived. Second, the result depends on where the linker put each array, so you need to see the addresses: cs_readelf --syms out/bin/out_0_0.elf lists every array with its byte address (Chapter 10 introduces cs_readelf). In the shipped build at T = 16, A_tile, B_tile, C_tile, A_buf and B_buf sit at 0x1708, 0x1b08, 0x1f08, 0x2308 and 0x2708, in declaration order, all equal mod 16 bytes (4 words) Measured, cs_readelf 2.10.1.

The same two costs appear in kernel 1, in a different mix. It issues only 2·Kt instructions, so the fixed part almost vanishes, but its @fmuls on two zero-stride 2-D DSDs costs about 1.65 cycles per element on WSE-3 and 1.4 on WSE-2 at T = 16, start-up included (16 @fmuls of 256 elements alone take 6,774 and 5,808 cycles per step, for 4,096 elements), while @fadds alone takes 0.5 and 1.0 cycles per element Measured, ablation. Its sources, C and the product tile, start in the same bank, the placement where Chapter 6 found WSE-2's add drops to 1 per cycle; WSE-3 keeps 2. On WSE-3 the two ablations add up to about 2.1 cycles per element at T = 16, which matches the measured kernel-1 step at that size (8,914 cycles for 4,096 multiply-adds, 2.18 including start-up). The fitted 1.87 is lower only because it leaves out the start-up. The fit is 1.87·Mt·Nt + 77 cycles per k, so the all-in cost is 1.87 + 77/(Mt·Nt) per multiply-add: 2.17 at T = 16 and 1.95 at T = 32, against 2.18 and 1.95 measured (and 1,574 vs 1,594 cycles per step at T = 8) Derived. The fit matches the data; the 77 cycles per k are spread over more elements as T grows. We have not isolated why the @fmuls is slower than 1 per cycle; the zero-stride operand reads one word repeatedly, and the collision rule is empirical. Kernel 1 is alignment-sensitive too: on WSE-2 at T = 39 the pair costs 1.63 cycles per element instead of 2.0 Measured, P = 2 (depth review). Padding C (exercise 4's fix) saves only 6% in kernel 1 (8,418 vs 8,914 cycles per step at T = 16, WSE-3).

The lesson for the roofline. "Compute-bound" on the wafer does not mean "at peak". The fabric is out of the way, but every instruction pays start-up and every pair of operands must avoid a bank clash. The levers are the same as in Lab 3: fewer, longer instructions, and pad and measure. Here they work: @map over DSRs plus one word of padding takes kernel 0 from 32% to 94% of the f32 ideal at T = 32 (below). And the ceiling used here is the f32 one, 1 multiply-add per cycle. The wafer's headline numbers are 16-bit, where f16 @fmach streams about 4 elements per cycle on WSE-3 in every placement Chapter 6 tested (on WSE-2, 4 or 2 depending on placement). So kernel 1's 51% of the f32 ceiling is about 13% of what a WSE-3 PE could do in 16-bit, and even the 94% rewrite is about 24% Derived.

How kernel 1's 2-D DSDs walk the tile

Kernel 1 builds an outer product from two 2-D DSDs that each leave one induction variable out of their index: A2 = |j, i|{Nt, Mt} -> A_tile[i] has no j, and B2 = |j, i|{Nt, Mt} -> B_tile[j * Kt] has no i. A variable missing from the index expression gives that dimension stride 0, the 2-D version of the "broadcast one value" preset (|i|{16} -> v[0], stride 0) in Chapter 6's DSD explorer. So as the op runs through (j, i), j outer and i inner, A2 repeats the same column of A for every j and B2 repeats the same element of B for every i. The increments follow from the layout. Column k + 1 of a column-major A tile starts Mt words later, so A2 moves by Mt per k. The product needs two instructions and a scratch tile because @fmacs multiplies a vector by a scalar (Chapter 6's builtins table): it cannot take two vector multiplicands and an accumulator at once. The table also shows something about the slow @fmuls: one of its operands rereads the same word, B2 for Mt elements in a row and A2's column every Nt; whether that is why it runs below 1 element per cycle, we have not isolated.

Host I/O is the same order as the kernel. The program loads A and B and reads C back: 11–14 GB at these sizes. Through the system's 1.2 Tb/s I/O (150 GB/s, Chapter 8) that is at least 74–93 ms, as long as the kernel itself; through the SDK host path of Chapter 7 (at most about 14 GB/s) it is 0.8–1.0 s, ten times the kernel Derived. So end to end, a single resident GEMM of this size runs at half the rate above at best. The budget calculator prints both times.

This is not how Cerebras runs big matmuls. A ~30k² f32 GEMM is about the largest that fits resident in SRAM, with all three matrices on the wafer. Production training streams the weights instead: they live in MemoryX and arrive one layer at a time while the activations stay on the wafer (Chapter 8, Chapter 9). Resident SUMMA is a teaching kernel for the 2-D mechanics.

Caveats: simulator cycles; f32 only, while the wafer's headline numbers are 16-bit (f16 @fmach streams about 4 elements per cycle on WSE-3, and 2–4 on WSE-2 depending on placement (Chapter 6), so a tuned 16-bit kernel could be several times faster, unmeasured here). The lesson is the ratio: at this scale the fabric costs about 1.5–4.5% of each step, and the per-PE instruction stream (and where the linker put the arrays) is the whole game. It is the same lesson as a GPU's tiled matmul and Tenstorrent's: once the tiles are in place, the inner loop decides how close you get to peak.

What this program leaves on the table

The program runs broadcast and compute strictly one after the other: start_step() is called only after compute finishes. Three designs an expert would try next:

  • Double-buffered SUMMA (overlap communication with compute). Receive the tiles of step s+1 into a second pair of buffers while step s computes. Ideally the kernel becomes about P · max(broadcast, compute) + one broadcast: at the default T = 8 on WSE-3, 4 × 2,903 + 650 + 209 ≈ 12,500 cycles instead of 14,422 (−14%). The 209 is what the run output calls "other": main()'s set-up before the first broadcast, the short gaps between steps and the exit task, none of which overlapping removes Measured, expected_output.txt; at T = 32 only −2%, and on the wafer under −3%, because there compute is already 97–99% of the step Derived, unmeasured. The costs: two more tiles (7 · 4T² bytes for kernel 0, so the largest tile drops from 45–46 to about 38; kernel 1 from 41–42 to 35–36), and a third join condition, because a buffer may only be overwritten once the compute that reads it is done. And a catch specific to this library: tasks do not preempt each other (Chapter 5), and broadcast() only activates the library's FSM task, which starts the move and later sends the teardown. While a long compute task runs, the FSM cannot run, so issuing the next broadcast at the top of compute starts nothing until it returns. Real overlap needs compute split into several shorter tasks, or moves you start yourself with .async = true (Chapter 6). Even then, the receive moves and the @fmacs compete for the same memory Unverified. Exercise 7 builds it.
  • Cannon's algorithm. It skews A and B once, then every step shifts each A tile one PE west and each B tile one PE north. That is nearest-neighbour traffic on static routes, with no route rewrite and no teardown, which suits a mesh with cheap hops. The catch is the wrap-around: the shift is cyclic, and the wafer is a mesh, not a torus, so the tile leaving column 0 must travel P − 1 hops back east (or the grid must be folded into a ring), plus the initial skew. SUMMA needs neither, and also works on non-square grids. That is the usual reason to choose it on a mesh Derived.
  • Computing straight from the fabric. The Cerebras idiom is a fabric input DSD as an operand (fabin_dsd, Chapter 6, Chapter 12): operate on wavelets as they arrive, without landing them first. Kernel 0 reuses each A column Nt times, so it would still need one column of buffer (Mt words) instead of a whole A tile, saving most of a tile of memory. <collectives_2d> always lands data in memory, so this needs your own routes and moves.
  • Kernel 0's fixed cost. About 29–37 cycles per instruction is two-thirds of the time at T = 8. The lever the course has already measured is Chapter 6's @map over DSRs, and we measured it here too. Swap the loops so that j is outer. Aside: chain or tree?

Both the library's broadcast and Chapter 12's program 05 are chains. A chain broadcast costs about (hops × hop cost) + words, and the hop cost is tiny (2.0 cycles on WSE-3, 1.0 on WSE-2 Measured, Ch. 4), so for a row of a few hundred PEs the word count dominates. Reductions are different, because each PE must add before forwarding. A chain reduce still streams (≈ 9.2 cycles per hop through a PE's compute on WSE-3, 6.0 on WSE-2, plus the words Derived from measurements, Ch. 12). A binary tree needs only log₂P levels, but each level is a separate message, and Chapter 12 measured store-and-forward at more than 3× the streaming chain (348 vs 101 cycles at P = 8, M = 32) Measured, Ch. 12. With c ≈ 9 per hop and ≈ 15 cycles per store-and-forward message (Lab 3 measured ≈ 14.6 per transfer with its completion task, Chapter 13), one dimension costs about 9·P + M as a chain and log₂P · (15 + M) + 2·(P − 1) as a tree (the last term is the tree's wire: the levels' hop distances add up to about P − 1 hops at 2 cycles each). The tree wins once the chain is longer: from about P ≈ 5–6 for a single word (the exact crossover moves with how the constants are rounded), and from P ≈ 27 for M = 32 Derived. So a whole-wafer scalar allreduce wants a tree, and a short row of long vectors wants a chain. SUMMA needs no reduction; Chapter 15's solver does, and exercise 6 works the numbers.

Check yourself

Why does SUMMA need no reduction, while Chapter 12's GEMV did?

The owner of a C block accumulates every term of its own sum: at step s it receives the A and B blocks it needs. In the GEMV the A blocks stayed put and each PE produced a partial sum of a y block that lived on several PEs, so the partials had to be added along the row.

Why does the library rewrite routes before every broadcast instead of declaring them in the layout?

The root moves every step, so the direction each router receives from changes. A static route has one input direction (on WSE-3 at most one is allowed), so static routes would need one color per possible root. Rewriting one color at run time keeps the broadcast to one color per axis (the library reserves a second color per axis for its reduce).

What does the teardown wavelet protect against?

Rewriting a router while wavelets of the previous broadcast are still passing through it. The root sends the teardown after its last data wavelet, on the same route, so each router enters teardown only after the data has gone by, and the next broadcast() may then reconfigure it.

x_done runs, then y_done. How many times does compute run, and what if the order is reversed?

Once, either way. compute starts blocked; one callback activates it and the other unblocks it, and the task picker runs it only when both bits are set. compute blocks itself again before starting the next step.

Kernel 0 at T = 32 needs 101 cycles per @fmacs of 32 elements. Where do they go?

About 2 cycles per element (64), because the two source streams collide in the same memory bank so @fmacs runs at half speed, plus about 37 cycles per instruction for the loop: reading the scalar, moving the DSD and starting the op.

Doubling P at fixed tile size: what happens to the time per step and to the total?

The time per step stays almost constant (the multicast's hop cost is tiny), so the kernel takes twice as long in total, for a matrix twice as large in each dimension: 8× the work in 2× the time, on 4× the PEs.

Kernel 1 runs the tile as @fmuls + @fadds. Why does it gain less over kernel 0 on WSE-2 than on WSE-3?

In this program the @fadds's two sources (C and the product tile) start in the same bank. In that placement it streams 2 f32 elements per cycle on WSE-3 but 1 on WSE-2 (Chapter 6; with the sources 8 bytes apart, WSE-2 would also reach 2), which makes the pair dearer on WSE-2. Its zero-stride @fmuls is actually a little faster there (about 1.4 vs 1.65 cycles per element at T = 16, start-up included), which offsets part of that. The bigger reason is the baseline: kernel 0 is already cheaper on WSE-2 (96,630 vs 103,724 cycles per step at T = 32: 94.4 vs 101.3 cycles per instruction, so about 30 vs 37 cycles of fixed cost on top of the 64 for the clash), so there is less to gain.

With MemcpyOrder.ROW_MAJOR on a 2 × 2 grid, which PE's tile is the third block of the flat host array, and why must each tile be column-major in this program?

The wire order is row-major over PEs, py outer and px inner: PE (0,0), (1,0), (0,1), (1,1). The third block goes to PE (0,1), which owns block row 1, block column 0. Column-major tiles make a column of A contiguous, and a column of A is exactly what each @fmacs streams over (and a column of C is what it accumulates into).

Why does the color count stay at 4 for any P, and which task ID must you never bind?

Each axis uses one library instance with two colors, and the routes are rewritten at run time for each root, so no color per root is needed: 2 axes × 2 colors = 4, whatever P is. Never bind your own task to 29: it is the teardown handler, which the library installs. (Colors 20–23 and memcpy's task IDs and queues are taken as well.)
