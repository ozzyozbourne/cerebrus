SDK example index

SDK 2.10.1 ships 34 tutorials, 21 benchmarks and two reusable benchmark libraries in its extras, and two "kernel" libraries inside the compiler image. This page lists every one of them: what it teaches, which chip it has a run script for, and where this course explains the idea. Use it to pick your next example after each chapter.

After this appendix you can

  • Find the SDK example that exercises a concept from any chapter, and check before you start whether it runs on your target chip.
  • Follow a suggested order of SDK examples after each course chapter.
  • Build the solver benchmarks that import benchmark-libs, which fail out of the box.

How this index was made

The list is every directory under extras/csl-extras-202604101435-6-d2f7d96e/examples/{tutorials,benchmarks} of the installed SDK, plus benchmarks/benchmark-libs/* and csl-libs/kernels/* from the SDK image SDK 2.10.1. The chip column comes from the run scripts each example ships (commands_wse2.sh, commands_wse3.sh); we checked that each script's --arch matches its name. A missing script means the SDK provides no tested command line for that chip, not necessarily that the code cannot be ported. The "Where in the course" column uses the current chapter numbers (Chapter 14 is the SUMMA lab built on gemm-collectives_2d, Chapter 15 the CG lab). It extends the Phase 3 SDK coverage audit. Two corrections to that audit: fft-3d and topic-15 are WSE-3 only, and gemv-00 has no run script for either chip (it is a syntax tour, not a program).

Running an SDK example, and the one import fix you will need

Copy the example directory into your home directory (never under /tmp), source /home/user/cerebras-sdk/env.sh, and run bash commands_wse3.sh (or _wse2). Most examples print SUCCESS!.

The four solver benchmarks (conjugate-gradient, preconditioned-conjugate-gradient, bicgstab, power-method) import "../../benchmark-libs/…" by a relative path. They fail with error: Unable to open ./src/../../benchmark-libs/stencil_3d_7pts/layout.csl, even in place in the extras tree, because the SDK wrappers run the compiler in a container that sees only the current directory Measured. The fix: keep benchmark-libs/ as a sibling of the example directory (copy both), and let the container see it:

cp -r …/benchmarks/conjugate-gradient …/benchmarks/benchmark-libs ~/sdk/
cd ~/sdk/conjugate-gradient
export CSL_IMPORT_PATH=$(realpath ../benchmark-libs)   # wrapper bind-mounts this path
bash commands_wse3.sh                                   # SUCCESS!, |xf_ref - xf_wse| = 3.05e-05

CSL_IMPORT_PATH takes colon-separated realpaths and is read by the host wrapper. The compiler flag cslc --import-path DIR adds a search directory for <…> imports, which is what the library's own comment asks for, but on its own it did not fix this failure in our tests: the relative path still has to be visible inside the container Measured, WSE-3, 5 × 5 PEs, 2 iterations.

Notes on particular examples

  • WSE-2 only: topic-14-color-swap (its README: "CSL currently does not support color swap on WSE-3"), histogram-torus, spmv-hypersparse and 25-pt-stencil ship only commands_wse2.sh SDK 2.10.1.
  • WSE-3 only: topic-15-wse3-microthreads (explicit microthread IDs exist only on WSE-3) and fft-3d, which is built on csl-libs/kernels/fft and uses input queues 2 and 4 and microthreads 2 and 3 by default SDK 2.10.1, kernels/fft/fft3d.csl.
  • Timing idiom. Every solver and stencil benchmark times itself with the TSC plus an allreduce-based sync and a reference stamp, and converts at 850 MHz. Appendix C explains the method and its 1-cycle-per-hop correction ("Synchronise, then correct").
  • device_run.py. The CG family ships a second host script that moves the iteration loop onto the device "to remove I/O pressure" SDK 2.10.1. Chapter 15 compares the two.
  • Libraries you can reuse. benchmark-libs/allreduce (row reduce, column reduce, broadcast back) and benchmark-libs/stencil_3d_7pts (with separate wse2/ and wse3/ implementations) are ordinary CSL modules that take colors and queues as parameters. kernels/tally is a two-phase completion counter ("every PE must signal completion at least once") used by histogram-torus SDK 2.10.1, kernels/tally/layout.csl.
