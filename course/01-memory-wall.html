Chapter 1 · Part I · Why wafer-scale

The memory wall

Modern AI chips can do far more arithmetic than their memory can feed. Every architecture in this course — the Cerebras wafer, Tenstorrent's Tensix grid, NVIDIA's GPUs — is a different answer to that one problem. Start here.

After this chapter you can

  • Compute a chip's ridge point for a given memory level, and say whether a kernel is compute-bound or bandwidth-bound there.
  • Derive why LLM decode at small batch needs only ~1 FLOP per byte, why batching helps until the KV cache catches up, and why prefill is compute-bound.
  • Turn a bandwidth and a model size into an upper bound on tokens per second, and decide how many chips a model needs.
  • Spot the "SRAM vs HBM" comparison trap, and say what Cerebras trades for its bandwidth: capacity, and moving data between PEs.
Terms used here
Decode / prefill: generating one new token per step / processing the whole prompt in one pass.
Dense FLOP/s: peak with no assumed zero-skipping. Vendors often quote "sparse" figures that are 2× (NVIDIA 2:4) or 8× (Cerebras, analyst reading) higher — Chapter 2. See also dense / sparse FLOPs.
BF16 / FP16, FP8, FP4, BlockFP8: number formats of 2, 1 and ½ bytes. BlockFP8 is Tenstorrent's 8-bit format with one exponent shared by a block of values.
SM, RF, smem: an NVIDIA streaming multiprocessor (the GPU's core, 132 on an H100 SXM), its register file, and its shared memory.
HBM / GDDR6: DRAM stacked next to the GPU die inside its package / ordinary graphics DRAM soldered on the board.
Tensix: one Tenstorrent core (Chapter 16).
PE (processing element): one of the ~900,000 tiny cores on a Cerebras WSE-3, each with its own 48 KB of SRAM (Chapter 3).
Fabric: the on-wafer network linking each PE to its four neighbours (Chapter 4).
Tensor-parallel / pipeline split: two ways to spread a model over chips: every chip holds a slice of every layer and all read at once, or each chip (or region of PEs) holds whole layers and a token visits them in order (TP / PP).
Region / layer-pipelined: on Cerebras inference, the block of PEs that holds one layer; a token passes through the regions in sequence (figure below, Chapter 8, glossary).
KV cache: the keys and values of every earlier token, which attention re-reads on every decode step.

Two numbers describe every accelerator

Strip an accelerator down and you get two numbers: how fast it can compute (peak FLOP/s) and how fast it can move data from where the data lives to where the math happens (bytes/s). The ratio between them is the ridge point:

ridge point  =  peak FLOP/s  ÷  memory bandwidth (bytes/s)      // units: FLOP per byte

A kernel has its own ratio, its arithmetic intensity: how many floating-point operations it performs for each byte it moves between the math units and the memory in question, reads plus writes. (For LLM decode that is essentially the weight bytes it reads.) If the kernel's intensity is below the ridge point, the arithmetic units sit idle waiting for memory — the kernel is bandwidth-bound. Above it, memory keeps up and the kernel is compute-bound. Plotting attainable performance against intensity gives the roofline: a slanted line (bandwidth × intensity) that meets a flat ceiling (peak compute) at the ridge.

For an H100 SXM running dense BF16: 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOP/byte Vendor inputs Derived. A kernel streaming from HBM must do almost 300 operations on every byte before the GPU's tensor cores become the bottleneck. A float vector add c = a + b does 1 FLOP for 12 bytes (read 8, write 4), about 0.083 FLOP/byte Derived: 3,500× short.

A roofline is always drawn for one level of memory. A GPU has several — registers, shared memory/L1, L2, HBM — each with its own bandwidth and so its own ridge point. The roofline that matters is the one for the level where your working set actually lives. For a 140 GB model on a GPU that is HBM. The Cerebras bet, which this course examines, is to make the working set live in a level that is one cycle from the math. Use the Memory level menu below to see each chip's other levels.

Why LLM decode lives on the slanted part

When a language model generates a token, every weight of the model is read once and used for one multiply-add per sequence in the batch. Rule of thumb: one token costs FLOPs ≈ 2 × parameters (one multiply-add per weight), so a 70B model needs ≈ 140 GFLOP per token Derived. Worked example: a multiply-add is 2 FLOPs and an FP16 weight is 2 bytes, so batch-1 decode does 2 FLOP ÷ 2 B = about 1 FLOP per byte of weights Derived. That is 300× below the H100's HBM ridge, so the tensor cores are busy about 0.3% of the time.

Because each token must stream every weight once, single-stream speed has a hard cap: tokens/s ≤ bandwidth ÷ model bytes. An 8B model in FP16 (16 GB) on one H100 gives 3.35 TB/s ÷ 16 GB ≈ 210 tokens/s at most Derived, however many FLOPs the chip has. Prefill is different: it reuses each weight across every prompt token, so a 2,000-token prompt reaches about 1,300 FLOP/byte and is compute-bound Derived.

Why batching helps, and why it stops helping

Derivation: intensity of a linear layer, plus the KV cache

A linear layer multiplies a d × d weight matrix by B input vectors (one per sequence). FLOPs = 2·B·d². Bytes moved at FP16 = 2·d² (weights) + 2·2·B·d (inputs in, outputs out). So intensity = B·d² ÷ (d² + 2·B·d) ≈ B while B ≪ d. For d = 8,192: B = 1 gives 1.0, B = 64 gives 63, and B = 2,000 (a prefill) gives about 1,300 Derived. It can never exceed d/2 ≈ 4,100.

Attention adds the KV cache, which every sequence reads in full on every step and which batching does not share. For a Llama-3-70B-shaped model (80 layers, 8 KV heads of width 128: Llama-3 shares 8 K/V heads among its 64 query heads, called grouped-query attention, which shrinks the cache 8×) it is 80 × 8 × 128 × 2 (K and V) × 2 B ≈ 0.33 MB per token per sequence Derived, assumes Llama-3 shapes. At a 2,000-token context that is ≈ 0.65 GB per sequence, or ≈ 42 GB for batch 64. Step intensity ≈ (64 × 140 GFLOP) ÷ (140 GB + 42 GB) ≈ 49 FLOP/byte; at 8,000 tokens it falls to ≈ 30 Derived. That is why sources quote "about 50–100 FLOP/byte" for batch 64 on a 70B model Indep, research notes, still far under the H100's ridge. Batching helps until the KV cache is as large as the weights; after that, extra batch buys little intensity. The limit is easy to compute: as B grows, intensity tends to 2P ÷ (context × KV bytes per token) = 140 GFLOP ÷ 0.65 GB ≈ 213 FLOP/byte at 2k context, and ≈ 53 at 8k Derived. So for a 70B model at 2k context, no batch size reaches the H100's HBM ridge of 295. And batching raises throughput, not per-user speed.

On Tenstorrent the bound lands within about 2× of the real speed, so bandwidth really is the limit there, as Tenstorrent itself says. On the wafer the single-user bound needs care. The 600,000 figure adds up all four wafers' bandwidth, but in a layer-pipelined deployment one user's token sits in one layer's region at a time, so that user only ever sees about 1/80 of it: roughly 7,500 tok/s at the headline bandwidth (which also counts writes), and about 2,000–4,000 at real kernel read rates and the SDK's assumed 850 MHz, a range the measured speed sits inside Derived (about 3,300–6,600 at the ~1.4 GHz press estimate Unverified; Chapter 9 shows both). The per-region argument applies to the arithmetic too. One user's token is in 1/80 of the PEs, so it sees 4 × 15.6 PF ÷ 80 ≈ 780 TF, which caps one user at 140 GFLOP ÷ 780 TF ≈ 5,600 tok/s Analyst peak Derived. At the f16 rate real kernels reach in the simulator (about 4 multiply-adds per cycle per PE, half the vendor SIMD width, set by operand placement; Chapter 6), that is ≈ 6 PF per wafer at 850 MHz and a cap of ≈ 2,200 tok/s Measured rate Derived. So on the wafer compute is, if anything, the tighter limit: decode's ≈ 1 FLOP/B sits just above the WSE-3 ridge of 0.74, where the read limit and the math limit nearly coincide (Chapter 9's "7.5 B per cycle" GEMV rate is itself a multiply-accumulate limit). With the weights in SRAM, single-stream decode is limited by something the roofline does not model: each token must pass through 80 layers in sequence, spread over four wafers joined by Ethernet, and each layer's partial sums must be reduced across many PEs over the fabric. On the wafer, single-user decode is set by each layer region's multiply-accumulate rate (at ≈ 1 FLOP/B, about the same as its SRAM read rate) plus latency and communication, and the extra bandwidth and FLOPs go to serving many users at once. The sources do not break down Cerebras's per-token latency, so this explanation is our inference Derived; Chapters 4, 5 and 9 show what that time is made of.

A per-token budget makes this concrete. 2,314 tok/s is ≈ 432 µs per token, or ≈ 5.4 µs per layer over 80 layers: ≈ 4,600 cycles at the SDK's assumed 850 MHz SDK 2.10.1, or ≈ 7,600 at the ~1.4 GHz that CS-4 press coverage estimates for WSE-3 Analyst Unverified Derived. Chapter 9 measures the f16 matrix-vector product over one PE's 38.9 KB of weights at ~5,200 cycles, or ~2,600 for a not-demonstrated 8-wide kernel Measured Derived. What is left goes to reducing partial sums across the region, fabric hops and three wafer-to-wafer crossings. At 850 MHz the measured kernel alone would overrun the budget, one hint that the production clock is higher than the SDK assumes. Chapter 9's latency budget builds this up term by term.

Prefill is the other half. On the flat part of the roofline every chip runs at its peak, so the comparison becomes FLOPs per dollar and per watt. Dense WSE-3 is estimated at about 16× an H100 (15.6 PF ÷ 989 TF) Analyst Derived, but a CS-3 system draws about 23 kW Vendor, and fast decode does not shorten time to first token. That is why the independently measured Cerebras advantage is tokens per second for one user, not cost per token at high batch ($0.60 per million tokens versus ~$0.10–0.25 on H100 at large batch Vendor Analyst; Chapter 18).

The wall is getting taller

From H100 to Rubin, HBM bandwidth grows about 5.7× (3.35 → 19.2 TB/s; 19.2 is Rubin's revised spec, the launch spec was 22) Derived from vendor figures. Rubin is rated at 50 PF NVFP4 for inference, a figure that relies on Transformer Engine compression, and 35 PF NVFP4 dense (the training figure) Vendor, roughly 35× the H100's 989 TF BF16 (Chapter 17). On the dense figure the ridge rises from ~295 to ~1,800 FLOP/byte Derived. Most of that growth is the number format: at the same precision the ridge is roughly flat (B200 BF16: 2.25 PF ÷ 8 TB/s ≈ 281), and an FP4 weight is a quarter of the bytes of a BF16 one, so decode intensity also rises 4×. Three answers to the same wall

  • GPU: raise intensity (batching, fused kernels) and buy more HBM bandwidth every generation. Since 2026 NVIDIA also pairs its GPUs with an SRAM decode chip (Groq 3 LPX, Chapter 17), a partial move toward the on-chip-memory answer.
  • Tenstorrent: keep tiles in a large per-core SRAM, stream from cheap GDDR6, and spread models over Ethernet built into every chip.
  • Cerebras: make on-chip SRAM big enough to hold the working set, so decode runs on the SRAM roofline — then pay for it in capacity and in moving data between PEs.

Why not just add SRAM to a GPU? Because SRAM is big. A bit of fast on-chip SRAM takes six transistors, and on TSMC's 5 nm process the densest cell is 0.021 µm² Indep. 44 GB is 3.5 × 1011 bits, so the cells alone cover ≈ 7,400 mm², and ≈ 10,500 mm² once each array's decoders and sense amplifiers are counted Derived. That is about 12 times the largest die a lithography reticle can print (858 mm²), and the H100 spends its ~814 mm² on 50 MB of L2. Holding the weights in SRAM needs a chip far larger than one reticle, which is why Chapter 2 starts by asking how a whole wafer can be one chip.

Latency is not bandwidth. The GPU's thousands of threads hide the wait for each HBM access, but they cannot raise the rate at which HBM delivers bytes; a bandwidth-bound kernel stays bandwidth-bound however many threads it has. Little's law says how much work must be in flight: bytes in flight = bandwidth × latency. To keep 3.35 TB/s busy at an HBM latency of roughly 500 ns Unverified ballpark; we found no published H100 measurement, an H100 needs about 1.7 MB of requests outstanding Derived, which is why it keeps thousands of threads resident (Chapter 17 uses the same figure). A PE's SRAM answers in one cycle, so a PE needs only 23 GB/s × one cycle (≈ 1.2 ns at 850 MHz) ≈ 27 bytes in flight, about seven f32 words, against the H100's 1.7 MB Derived: no threads needed. The latency it must hide is the fabric's: about one cycle per hop on the hardware (the WSE-3 simulator models 2) plus about two cycles on and off the ramp (Chapter 4).

The comparison trap Cerebras markets "7,000×" the memory bandwidth of an H100 Vendor. That compares on-wafer SRAM (21 PB/s) to the GPU's off-chip HBM (3.35 TB/s). (Those two figures actually give about 6,300× Derived; the marketing figure appears to use a slightly lower GPU baseline.) But 21 PB/s is the sum of 900,000 private 48 KB memories, each reachable only by its own core. The fair GPU counterpart is the GPU's aggregate register-file + shared-memory bandwidth, which is also tens to hundreds of TB/s Derived: shared memory alone is 132 SMs × 32 banks × 4 B per clock × 1.98 GHz ≈ 33 TB/s Vendor inputs, and the register file is faster again. So the like-for-like bandwidth gap is somewhere around 50–650×, not 6,300×. The real difference is capacity at that speed: 44 GB on a wafer Vendor versus ≈ 67 MB of registers and L1 on an H100 (132 SMs × 512 KB) Derived, about 650×.

Capacity cuts both ways. A 70B model in FP16 is ~140 GB of weights Derived: more than one H100 (80 GB) and more than three times one WSE-3 (44 GB). To hold it you need 2 H100s, 1 B200, 5 Blackhole p150s (in GDDR6), or 4 CS-3s with the weights in SRAM Derived; four wafers give 176 GB, leaving about 36 GB on paper for the KV cache and activations, and ≈ 20 GB once each PE's ~4.2 KB of program code and task table is set aside (≈ 3.8 GB per wafer; Chapter 3) Measured overhead Derived. GPUs split the model across devices and still read it from HBM. Cerebras either spreads the weights across several wafers so they stay in SRAM (inference), or keeps the weights off the wafer in MemoryX and streams them in layer by layer (training, Chapter 8). "No DRAM" means no DRAM on the wafer, not none in the system. And weights must stay resident: loading one wafer's 44 GB through the SDK host path at ~14 GB/s takes about 3 seconds Derived.

Keep this trade-off in mind for the rest of Part II. Cerebras turns a memory-bandwidth problem into a data-placement and communication problem, and Chapters 3–6 are mostly about how the wafer makes placement and neighbour-to-neighbour movement cheap.

Check yourself

A kernel moves 4 bytes to or from HBM for every 2 FLOPs it does. Is it bandwidth- or compute-bound on an H100?

Intensity = 0.5 FLOP/byte, far below the ~295 ridge. It is bandwidth-bound and can reach at most 0.5 × 3.35 TB/s ≈ 1.7 TFLOP/s, under 0.2% of peak.

Compute the ridge point of a Tenstorrent Blackhole p150 (664 TFLOP/s BlockFP8, 512 GB/s GDDR6). Is batch-64 decode (~60 FLOP/B) compute-bound there?

664e12 ÷ 512e9 ≈ 1,300 FLOP/byte. No: 60 is far below it, so decode is even more bandwidth-bound than on an H100 (ridge ≈ 295). This is why Tenstorrent leans on keeping data in its 1.5 MiB (1,536 KiB)-per-core SRAM and on small weight formats.

What is the most tokens per second one H100 can generate for a single user on a 16 GB model, and what sets the limit?

≈ 3.35 TB/s ÷ 16 GB ≈ 210 tokens/s. HBM bandwidth sets it, because every weight is streamed once per token; more FLOPs would not help.

Batch 64 should give about 64 FLOP/byte. Why does a 70B model at a 2,000-token context land nearer 50?

Each sequence also reads its own KV cache on every step (~0.65 GB per sequence for a Llama-3-70B shape, ~42 GB for 64 sequences), and batching does not share it. The bytes grow while the weight FLOPs do not, so intensity ≈ 9 TFLOP ÷ 182 GB ≈ 49. Longer contexts push it lower still.

Your kernel's working set is 20 MB on an H100. Which roofline applies, and what changes?

It can live in L2 (50 MB) or, tiled, in shared memory (~30 MB across all SMs). The ridge falls from ~295 (HBM) to ~260 (L2) or roughly 30 (shared memory), But intensity is not one fixed number: it is measured against the traffic at each level. Tiling into shared memory cuts the HBM traffic, which raises the kernel's HBM intensity and can lift it past 295. The kernel then also has to clear the shared-memory ridge (~30) on its shared-memory traffic, a different count of bytes.

The roofline widget shows WSE-3 decode at 100% of peak. What three assumptions make that true?

(1) The whole model fits in on-wafer SRAM: 44 GB per wafer, so a 70B FP16 model needs four wafers. (2) Each weight sits in the 48 KB of the PE that uses it, so no fabric transfer is needed. (3) The analyst 15.6 PF dense peak is reachable; real f16 kernels in the simulator reach about half the vendor SIMD width (the dashed "measured f16 kernel" roof, ≈ 6 PF). Break either of the first two assumptions and you move to another roofline: the fabric's, or the wafer edge's, whose ridge is near 100,000 FLOP/byte.

Why is "21 PB/s vs 3.35 TB/s" not apples to apples, and what is the bigger difference?

It compares on-chip SRAM to off-chip DRAM. Each PE can only reach its own 48 KB at that speed; moving data between PEs uses the fabric (Chapter 4). Compared with the GPU's own on-chip SRAM the bandwidth gap is perhaps 50–650×; the bigger difference is capacity at that speed, 44 GB versus ≈ 67 MB.
