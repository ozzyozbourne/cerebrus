The memory wall

Modern AI chips can do far more arithmetic than their memory can feed. Every architecture in this course — the Cerebras wafer, Tenstorrent's Tensix grid, NVIDIA's GPUs — is a different answer to that one problem. Start here.

After this chapter you can

  • Compute a chip's ridge point and say whether a kernel is compute-bound or bandwidth-bound.
  • Explain why LLM decode at small batch is starved for bandwidth, while prefill is not.
  • Recognise the "SRAM vs HBM" comparison trap in vendor marketing.

Two numbers describe every accelerator

Strip an accelerator down and you get two numbers: how fast it can compute (peak FLOP/s) and how fast it can move data from where the data lives to where the math happens (bytes/s). The ratio between them is the ridge point:

ridge point  =  peak FLOP/s  ÷  memory bandwidth (bytes/s)      // units: FLOP per byte

A kernel has its own ratio, its arithmetic intensity: how many floating-point operations it performs for each byte it reads. If the kernel's intensity is below the ridge point, the arithmetic units sit idle waiting for memory — the kernel is bandwidth-bound. Above it, memory keeps up and the kernel is compute-bound. Plotting attainable performance against intensity gives the famous roofline: a slanted line (bandwidth × intensity) that meets a flat ceiling (peak compute) at the ridge.

For an H100 SXM running dense BF16: 989 TFLOP/s ÷ 3.35 TB/s ≈ 295 FLOP/byte Vendor inputs Derived. A kernel needs to do almost 300 operations on every byte it fetches from HBM before the GPU's tensor cores are the bottleneck.

Why LLM decode lives on the slanted part

When a language model generates a token, every weight of the model is read once and used for roughly one multiply-add per sequence in the batch. At batch 1 that is about 1 FLOP per byte of weights. Batching raises intensity roughly in proportion to the batch size, yet a 70B model at batch 64 only reaches about 50–100 FLOP/byte — still well under the H100's ridge. Prefill (processing the prompt) reuses each weight across thousands of tokens, reaching thousands of FLOP/byte: compute-bound.

And the wall is getting taller. From H100 to Rubin, HBM bandwidth grows about 5.7× (3.35 → 19.2 TB/s) while low-precision FLOPs grow much faster, partly because the number format shrinks from BF16 to FP4 Derived from vendor figures. Each generation, a GPU has more arithmetic per byte it can fetch.

Three answers to the same wall

The comparison trap Cerebras markets "7,000×" the memory bandwidth of an H100 Vendor. That compares on-wafer SRAM (21 PB/s) to the GPU's off-chip HBM (3.35 TB/s). But 21 PB/s is the sum of 900,000 private 48 KB memories, each reachable only by its own core. The fair GPU counterpart is the GPU's aggregate register-file + shared-memory bandwidth, which is also tens to hundreds of TB/s Derived. The real difference is capacity at that speed: 44 GB on a wafer versus ~66 MB of registers and L1 on an H100.

Check yourself

A kernel does 2 FLOPs per 4-byte float it reads. Is it bandwidth- or compute-bound on an H100?

Intensity = 0.5 FLOP/byte, far below the ~295 ridge. It is bandwidth-bound and can reach at most 0.5 × 3.35 TB/s ≈ 1.7 TFLOP/s, under 0.2% of peak.

Why does batching help decode on a GPU?

Each weight read from HBM is reused for every sequence in the batch, so FLOPs per byte rise roughly linearly with batch size. Throughput rises; per-user latency does not improve.

Why is "21 PB/s vs 3.35 TB/s" not apples to apples?

It compares on-chip SRAM to off-chip DRAM. Each PE can only reach its own 48 KB at that speed; moving data between PEs uses the fabric (Chapter 4).
