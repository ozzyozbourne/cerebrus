Lab 5: a conjugate-gradient solver

Lab 3's stencil marched a rod forward in time. Most stencils on a supercomputer do something else: they are the matrix inside an iterative solver. This lab solves a 3-D Poisson problem with conjugate gradient (CG) on a grid of PEs. The program combines three modules, memcpy plus two SDK libraries, so its main lesson is composition: how modules share one PE's colors, tasks and queues. Then we measure where an iteration's cycles go, and why every iteration waits for one global sum.

After this lab you can

  • Write CG and sort its steps into local, neighbour and global work, and say which one limits a wafer-sized solve.
  • Combine library modules on one PE: give each its colors, task IDs, queues and DSRs, and check the budget.
  • Explain how the SDK's allreduce reroutes one color three times per call, and why it acts as a barrier.
  • Compare a host-driven loop with an on-device loop in simulated cycles, and estimate the gap on a real system.
  • Measure a per-iteration cost split with the TSC and predict how it scales with the grid and the column height.

The problem and the CG algorithm

Take the Poisson equation −∇²u = f on a box, with u = 0 on the boundary. The 7-point finite-difference stencil turns it into a linear system A u = b. Each row of A has 6 on the diagonal and −1 for each of the six neighbours (west, east, south, north, below, above); neighbours outside the box drop out. A is symmetric and positive definite, so conjugate gradient applies. With 125 unknowns you could invert A; with a billion you cannot even store it. CG never forms A. It only needs to apply it, and applying A is exactly a stencil.

Here is CG in numpy. It is the reference that run.py checks the device against, and it follows Golub and Van Loan's Algorithm 10.2.1, as the SDK benchmark does:

def cg_numpy(max_ite):
    x = x0.copy(); r = b - A(x); rho = np.vdot(r, r); k = 0
    while rho > tol * tol and k < max_ite:
        k += 1
        p = r.copy() if k == 1 else r + (rho / rho_old) * p   # axpy           local
        w = A(p)                                             # stencil SpMV   neighbours
        alpha = rho / np.vdot(p, w)                          # dot product    GLOBAL
        x = x + alpha * p;  r = r - alpha * w                # 2 axpy         local
        rho_old, rho = rho, np.vdot(r, r)                    # dot product    GLOBAL
    return x

Here A(v) applies the stencil, x0 is the starting guess (zero), and tol = EPS·|b|, so the loop stops when |r| ≤ EPS·|b|. The denominator of α, ⟨p, w⟩ = ⟨p, A p⟩, is called η (eta) in the device code. The device splits each iteration into four phases, which the profile below times separately:

The last row is new. In Lab 3 every PE waited only for its two neighbours. Here every iteration contains two global sums. No PE can compute α until every PE has contributed to ⟨p, w⟩, and no PE can decide whether to stop until the global ⟨r, r⟩ is back.

How many iterations? CG's error shrinks at least as fast as 2·((√κ − 1)/(√κ + 1))k, where κ = λmax/λmin is A's condition number (Golub and Van Loan, Theorem 10.2.6). For this A on an N × N × N box, λ = 6 ∓ 6·cos(π/(N+1)), so κ = cot²(π/(2N+2)): 13.9 at N = 5, 32.2 at N = 8, 67.8 at N = 12 Derived. The SDK benchmark prints the same 0.80 and 11.20 extreme eigenvalues for its 5 × 5 × 5 case SDK 2.10.1. √κ grows like N, so on a cube the iteration count grows in proportion to the side. That holds only when all three sides grow. For a W × H × Z box, λmin = Σ 2(1 − cos(π/(n+1))) over the three sides, and the z term never shrinks if Z stays fixed: with Z = 5, κ can never exceed about 44, however wide the grid Derived. Keep both cases in mind for the scaling section.

Mapping onto the wafer

The SDK's 3-D stencils, and this lab, use the pencil decomposition from Lab 3's last table. The box is W × H × Z cells. PE (px, py) owns the whole z-column at (x = px, y = py), Z cells long, of every vector. A PE stores five vectors (b, x, p, w, r), so 20·Z bytes, plus 7 stencil coefficients.

  • SpMV, w = A p. The z-neighbours are in local memory, so the z part of the stencil is three @fmacs over shifted DSDs. The x/y part needs the four neighbouring columns. The library sends p to the east, west, north and south in blocks of BLOCK_SIZE wavelets, receives the four neighbours' blocks, and adds them in with four more @fmacs.
  • Dot products. Each PE sums over its own column (@map, as in the SDK's blas.csl), then the allreduce adds the W·H partial sums and returns the total to every PE. A single wavelet travels.
  • axpys. Purely local @fmacs. α and β are scalars that every PE computes from the same allreduced values, so every PE takes the same decision without any extra message.

Composing modules

Labs 1–3 wrote every line on the PE themselves, apart from memcpy. This program writes about 300 lines of CSL and imports about 2,200 (2,900 counting both chips' variants of the stencil): the SDK's benchmark-libs/stencil_3d_7pts (the SpMV) and benchmark-libs/allreduce (the global sums), each with a layout half and a PE half. The libraries live in course/programs/07-cg/lib/, copied from SDK 2.10.1 with an attribution header.

Three rules make composition work.

  1. The top level owns every hardware ID. A library takes the colors, local task IDs, queues and DSR numbers it uses as parameters (on WSE-3 the stencil also takes its microthread), and never picks its own. The layout comment in layout.csl is the ledger: stencil colors 0–7 and tasks 14–16; allreduce color 8 and tasks 17–20; the program's own state-machine task 12; queues 0–1 for memcpy, 2 for allreduce, 4–7 for the stencil.
  2. Two halves, two kinds of parameter. A layout half runs at compile time for each (px, py) and returns a struct (for the stencil, the color parity of each direction, as in Lab 3's figure). The PE half takes that struct plus everything that is a property of the PE program, such as queue numbers.
  3. Libraries hand control back through a callback. Neither library knows about the host. When spmv() or allreduce() finishes, it calls the function it was given. The SDK's host-driven kernel passes sys_mod.unblock_cmd_stream; its device-driven kernel passes a function that activates the next state. This program passes phase_done(), which does either. That one indirection is the whole difference between the two loops below.

Microthreads are only partly in the ledger: the stencil takes its microthread as a parameter, but the allreduce takes none, so the compiler picks one for its asynchronous sends, and moving the stencil’s from 3 to 2 changed nothing we could see. The shipped program keeps every slot separate on both chips; the WSE-2 experiment makes one genuinely shared. That shared queue works here only because the program never runs the stencil and the allreduce at the same time. This matters for the pipelined CG variants in the scaling section, which overlap the allreduce with the SpMV on purpose.

The import path trap

Copied out of the SDK on its own, the CG benchmark does not compile: Unable to open ./src/../../benchmark-libs/stencil_3d_7pts/layout.csl Measured (phase-3 review run). Its imports climb two directories to a sibling benchmark-libs/ folder. Two more facts matter when you fix it. First, cslc resolves an import path relative to the directory of the top-level layout.csl, not the importing file: the stencil's dispatch file asked for "wse3/pe.csl" and got Unable to open ./wse3/pe.csl Measured. Second, cslc and cs_python run inside a container that only mounts the current directory, so a library elsewhere on disk needs CSL_IMPORT_PATH (or --import-path) SDK 2.10.1. This lab avoids both by copying the libraries into lib/ and changing the two dispatch paths to "lib/stencil_3d_7pts/wse3/pe.csl" and …/wse2/pe.csl, the only edit to the SDK files.

The allreduce every iteration waits on

A global sum over a 2-D grid needs a route for every partial sum to reach one PE and a route for the result to reach everyone. Lab 2 built a row reduce on two alternating colors and a broadcast on a multicast route, each with static routes. The SDK's allreduce does all three stages with one color, and rewrites that color's routes between stages:

  1. Row reduce. Routes: every PE forwards from west to east (switch position 0), and the last PE in the row delivers to its CE. Every PE except the last sends its value, then a switch-advance control wavelet. The control wavelet flips the next router's switch from "forward from the west" (position 0) to "take from my own CE" (position 1), so values arrive at the last PE one at a time, nearest last. The last PE adds them as they arrive with an asynchronous @fadds from the fabric, W − 1 times. The first PE then sends a teardown wavelet.
  2. Column reduce. The same, north to south, on the last column only: H − 1 values reach the bottom-right PE.
  3. Broadcast. The bottom-right PE sends the sum north up the last column, and every PE in that column sends it west along its row, by multicast routes (Lab 2's mechanism). Then a teardown.

Between stages each PE calls reset_routes, clears its switch position and exits teardown mode on that color (tile_config). The teardown wavelet is how the PEs agree that a stage is over: each PE's teardown handler activates the task that moves the library's state machine on. That is why it needs only one color, one queue and four task IDs. The cost is that a stage can only start once the previous one has drained, so the three stages run strictly one after another, and every message is a single wavelet whose cost is almost all latency.

Why the allreduce is a barrier

No PE gets the sum back until the broadcast reaches it, and the broadcast cannot start until the bottom-right PE has every row's partial sum. So no PE leaves an allreduce before the last PE has entered it. A PE that reaches the allreduce early just waits inside it. You can see this in the profile. Every PE spending the same 4,574 cycles per iteration on the default 5 × 5 grid is what any loop with a global barrier shows in steady state, so it is not the evidence. The evidence is the spread: the share spent inside the allreduce varies from PE to PE by 228 cycles (1,898 to 2,126) Measured, although every PE does the same allreduce work. The PEs that finished their own phases early absorb the difference as waiting inside the call.

The SDK also ships a general-purpose 2-D library, <collectives_2d>, introduced in Chapter 12. It uses two colors per dimension and also rewrites routes at runtime; Chapter 14 uses it for SUMMA's row and column broadcasts and goes into its parameters. Chapter 12 measured its fixed overhead at about 700 cycles per operation Measured, the same order as the allreduce here.

Two loops, one program

The only difference between the loops is what phase_done() does next.

  • Host-driven. The host calls f_update_p, f_spmv_Ap, f_eta and f_update_x_r_rho one after another with launch(…, nonblock=False), then copies rho back and decides whether to go on. phase_done() calls unblock_cmd_stream(), so each launch returns only when its phase has finished on every PE. This is the SDK's run.py with kernel.csl, and it is how you would first port a CG written in numpy: the loop stays in Python.
  • Device-driven. The host makes one call, f_cg. Now phase_done() activates task STATE (next_phase), which looks at the phase that just finished and starts the next one. After the ⟨r, r⟩ allreduce it tests the stopping rule itself. That is the SDK's device_run.py with kernel_cg.csl.

The device loop decides when to stop without any extra message because the allreduce leaves the same ρ on every PE, so every PE takes the same branch at the same iteration. run.py checks that all W·H copies of the ρ history are identical. Unlike Lab 3's step chain, the iteration here is gated by the allreduce, a global barrier, rather than by neighbours. That is why a single counter of finished operations is enough and no PE can run an iteration ahead.

Four things stand out.

  1. The SpMV is not the arithmetic. 7 multiply-adds on 5 cells is 35 flops, yet the stencil phase takes 1,866 cycles. Almost all of it is the library's message protocol: four directions, each a send and a receive of 2-wavelet blocks, each with its own task. Lab 3 measured the same thing on a smaller scale: a 90-cycle floor per step for four transfers with their completion tasks (≈ 15 cycles each), bookkeeping, and ≈ 6 cycles to start each vector instruction inside a task (≈ 17 for an isolated op, Chapter 6).
  2. The allreduce costs as much as the SpMV, for two single-float sums. As the scaling section shows, that cost grows with the grid's side while the SpMV's does not.
  3. Every PE takes the same time per iteration. All 25 PEs measured exactly 4,574 cycles per iteration, but their allreduce share ranged from 1,898 to 2,126 Measured. The allreduce is a barrier: PEs that finish their own work early wait inside it.
  4. Profiling is not free. With PROFILE=0 the device loop takes 4,261 cycles per iteration on WSE-3 (3,782 on WSE-2), so the eleven mark() calls per iteration (seven in the phases, one in each of the four phase_done() calls) cost about 310–400 cycles, roughly 30–35 cycles each, 7–10% Measured. (record()'s timestamp stays in with PROFILE=0.) Use the profile to see the split, and the PROFILE=0 number for the speed.

Host loop or device loop

In the simulator the host loop costs 1,224 extra cycles per iteration on WSE-3 and about 1,140–1,150 on WSE-2 (run to run), essentially all of it in the control bucket: control rises by 1,262 cycles on WSE-3 while the axpy and allreduce buckets fall slightly Measured. The simulator charges only the device side of each launch: memcpy's command task decoding the RPC and the unblock_cmd_stream() at the end, five times per iteration (four launches and one copy of ρ). The host side costs nothing in simulated time, because the simulator has no network. With 15 host iterations instead of 3 the per-iteration figure is 5,783 instead of 5,798, and repeated 3-iteration runs gave 5,790–5,798, so it is stable to about 0.3% Measured; the device-loop figure repeated exactly.

On a real system each of those five commands crosses the network. Chapter 7 uses the SDK's figure of about 200 µs of overhead per transfer SDK 2.10.1. Five per iteration is about 1 ms, against 4,261 cycles ≈ 5 µs for the iteration itself at the SDK's 850 MHz, so a host-driven CG would spend about 99.5% of its time waiting for the host Derived. The simulator's 27% gap understates the real one by two orders of magnitude.

That model assumes every command is a full, synchronous round trip, which is how run.py drives it (nonblock=False). The obvious first improvement is to queue the four launches with nonblock=True and block only on the copy of ρ, which the host needs before it can decide whether to go on. If the 200 µs is mostly latency that overlaps, that leaves about one round trip per iteration; if it is per-command work, nothing is saved. So a non-blocking host loop costs somewhere between about 200 µs and 1 ms per iteration Derived, still 40 to 200 times the 5 µs iteration. For any iterative solver, put the loop on the device, and copy results back once at the end.

How it scales

Two knobs change the cost of an iteration: the grid of PEs (W × H) and the column on each PE (Z). They act on different phases.

Grid size. With Z = 5 fixed, the stencil, axpy and dot phases take the same cycles on every grid from 3 × 3 to 16 × 16: each PE does the same local work and talks to the same four neighbours. Only the allreduce grows Measured, WSE-3, 6 iterations each:

A plane fits all seven grids to within 30 cycles: allreduce ≈ 958 + 100·W + 88·H cycles for the two calls in an iteration on WSE-3 Derived. On WSE-2 the allreduce grows from 1,561 cycles at 5 × 5 to 2,705 at 12 × 12, about 82 cycles per PE of W + H against 94 on WSE-3 Measured. Halving the coefficients (two calls per iteration), each call costs about 50 cycles per PE along a row and 44 along a column Derived. A router hop costs 2 cycles on WSE-3 (Chapter 4), so distance is not what costs. In the row and column reduce stages each PE's message reaches the last PE separately, with its own send, switch-advance wavelet and fabric add, so the cost is per contributing PE, not per hop. That makes this allreduce linear in the grid's side, and serial.

Column length. With the grid fixed at 5 × 5, the allreduce stays at 1,898 cycles whatever Z is, and the stencil grows (Z is cells per PE; the last three columns are the stencil SpMV, the two local dots and the three axpys, in cycles per iteration) Measured, WSE-3:

ZBLOCKcycles / iter.SpMVdotaxpy

With 2-wavelet blocks the stencil costs about 276 cycles per extra cell, about 40 times its 7 multiply-adds per cell (≈ 7 cycles at one f32 multiply-add per cycle, Chapter 6). Bigger blocks remove almost all of it: at Z = 100 the stencil drops from 27,782 cycles (50 blocks per direction) to 6,483 (10 blocks) and 1,957 (one block) Measured. Each block saved is worth about 500–530 cycles, one send and one receive in each of four directions, so roughly 65 cycles per message Derived.

What BLOCK costs, and how long a column can be. BLOCK_SIZE sizes the library's four receive buffers, one per direction (west_buf … north_buf in wse3/pe.csl), so they take 16·BLOCK bytes: 1.6 KB at BLOCK = 100 Derived. That 1.6 KB buys a 4.9× faster iteration at Z = 100 (32,004 → 6,573 cycles). We measured the cap by compiling ever-longer columns on a 5 × 5 grid: the program links up to Z ≈ 1,835 cells per PE on WSE-3 with BLOCK = 2 (≈ 1,757 with BLOCK = 100, the 1.6 KB difference) and ≈ 1,978 on WSE-2, and fails above with ran out of PE memory Measured. Five vectors at 4 bytes take 20 bytes per cell, so that is ≈ 37 KB of vectors after the code of three modules. BLOCK is therefore a latency knob that is nearly free in memory. The SDK ships BLOCK_SIZE:2 SDK 2.10.1, and this program keeps that default as BLOCK; we have no measurement showing what the small block buys (it may let sends overlap the @fmacs on long columns). At ≈ 1,800 cells per PE a whole wafer of about 900,000 PEs holds about 1.6 × 10⁹ unknowns Derived, the billion the problem section said you could not store as a matrix.

The two local dots are scalar @map loops, together about 10 cycles per cell, so at Z = 100 they cost 1,115 cycles: more than half the whole one-block stencil (1,957) and more than the three axpys (898) Measured. A DSD-based dot would probably cost far less per cell; we did not try one. At BLOCK=100 the centre PE's allreduce also rose from 1,898 to 2,292 cycles. Over all 25 PEs it ranged from 1,951 to 2,438, against 1,898–2,236 at BLOCK = 2 Measured: the fastest PE's allreduce barely moved, so the extra cycles on the centre PE are mostly waiting at the barrier for PEs whose stencil phase finished later.

How far from peak. One iteration does about 23 flops per cell: 13 in the stencil, 2 × 2 in the dots, 3 × 2 in the axpys. The default run does 5 × 23 = 115 flops per PE in 4,574 cycles, about 0.025 flops per cycle, or 1.3% of the 2 flops per cycle of one f32 multiply-add per cycle Derived. At Z = 100 with BLOCK = 100 it is about 2,300 flops in 6,573 cycles, about 17% Derived. The default lab sits deep in the latency-bound regime; real stencil codes put hundreds to thousands of cells on each PE.

CG usually beats its bound because the bound uses only κ, the ratio of the extreme eigenvalues. CG adapts to the whole distribution of eigenvalues (and to which eigenvectors b contains): once it has resolved the extreme ones, it speeds up.

f32 at scale

The bounds and the stopping rule assume exact arithmetic. CG updates r by recurrence (r −= α w), and in f32 that recursive residual drifts away from the true one, b − A x, as κ grows. In the same numpy f32 recurrence the recursive residual reaches 1e-5 on every cube, but the true residual |b − A x|/|b| is 5.7e-6 at 5³, 2.0e-5 at 24³ and 8.9e-5 at 48³ Derived. On this lab's sizes the two agree (the run prints both). At wafer scale (κ ≈ 12,000 for 950 × 950 × 100) expect worse: check the true residual, recompute r = b − A x every so often (residual replacement), and consider accumulating the dot products in higher precision. The order of the allreduce's sum also changes the rounding, so a different grid shape gives slightly different iterates.

The scaling law of this solver

Two cases, both driven by the allreduce.

  • Wider grid, fixed column (weak scaling: W = H = N, Z fixed). The SpMV, dots and axpys cost the same on every grid; the allreduce grows like N. The iteration count rises at first and then levels off (about 40 at Z = 5, table above). So the time per solve grows linearly with the side, all of it through the allreduce. At 16 × 16 PEs the two allreduces already take 60% of an iteration (3,966 of 6,650 cycles) Measured.
  • Growing cube (W = H = Z = N). Now the iterations grow like N too, and so does the stencil (Z = N cells per PE). Time per solve grows like N², asymptotically, once the allreduce dominates; at the sizes we ran, the other phases still matter.

Extrapolated to a whole wafer (about 900,000 PEs, say 950 × 950) the fit gives roughly 180,000 cycles of allreduce per iteration, against about 2,700 cycles of other work at Z = 5 and about 30,000 at Z = 100 Derived. That is an extrapolation sixty times beyond the largest grid we simulated, and it describes this library, not the fabric. The library reduces one PE's value at a time, about 50 cycles per PE per call. The course's own measurements give lower costs per PE for one 950-PE row stage Derived:

So algorithms for big wafers attack the global sums: faster reductions (streaming chains, trees whose cost grows with hops rather than with PEs), more cells per PE so the local work outweighs the sum, CG variants that merge the two dot products into one reduction per iteration (Chronopoulos–Gear, exercise 3), and pipelined CG (Ghysels–Vanroose), which overlaps the reduction with the next SpMV. Overlap needs every slot of the two libraries disjoint on both chips (the WSE-2 shared-queue experiment above would then break) and a phase_done() that waits for both. Preconditioning is no shortcut here: the SDK's preconditioned CG uses Jacobi SDK 2.10.1, and with a constant diagonal of 6 Jacobi only rescales A, leaving κ and the iteration count unchanged. Stronger preconditioners (multigrid, incomplete factorisations) need more global or recursive communication, which meets the same cost.

Check yourself

Which CG steps need data from more than one PE, and what kind?

The stencil (w = A p) needs the four neighbouring PEs' columns. The two dot products need every PE: a local sum, then an allreduce. The axpys are local.

Why does no library in this program choose its own colors or task IDs?

Several modules share one PE. Only the top level sees all of them, so it hands each its slots as parameters and keeps the ledger. A clash on a color, task ID or initialized queue is then a compile error at a single place.

How does each PE know when to stop the device loop without asking the host?

The allreduce leaves the same ρ = ⟨r, r⟩ on every PE, so every PE evaluates the same test with the same values and stops at the same iteration.

All 25 PEs take exactly 4,574 cycles per iteration, but their allreduce times differ by 228 cycles. Why?

The allreduce is a barrier: no PE gets the sum back until all have contributed. A PE that reaches it early waits inside it, so the waiting shows up in its allreduce bucket and the iteration time comes out the same everywhere.

The simulator says the host loop costs 27% more per iteration. Why is that misleading for a real system?

The simulator only charges the device's part of each launch. On a real system each of the five host commands per iteration (four launches and one copy of ρ) has about 200 µs of overhead: 5 × 200 µs ≈ 1 ms, against 4,261 cycles / 850 MHz ≈ 5 µs for the iteration itself. So the host loop is roughly 200 times slower, not 27%. Non-blocking launches can cut that to about one round trip, still ~40×.

You double both W and H, keeping Z = 5. What happens to the time per iteration, and to the time per solve?

Per iteration only the allreduce grows, by about 100·W + 88·H more cycles. The iteration count rises only a little and then levels off: with Z fixed, κ is capped (about 44 for Z = 5), so going from 5 × 5 to 10 × 10 takes CG from 15 to 24 iterations, and no grid needs more than about 40. So the time per solve grows roughly linearly with the side, through the allreduce. Only if Z grows too (a growing cube) do the iterations grow like the side as well, giving roughly the square.

You copy the SDK's stencil library into lib/ and cslc fails with Unable to open ./wse3/pe.csl. Why, and what is the fix?

cslc resolves an import path relative to the directory of the top-level layout.csl, not the importing file, so the dispatch file's "wse3/pe.csl" is looked for next to the layout. Change the path to "lib/stencil_3d_7pts/wse3/pe.csl" (or pass --import-path; the container only mounts the current directory).

At Z = 100, what does BLOCK = 100 instead of 2 save, and what does it cost?

It saves about 26,000 stencil cycles per iteration (27,782 → 1,957), because each PE sends one message per direction instead of 50. It costs four receive buffers of BLOCK floats, 16·BLOCK bytes ≈ 1.6 KB, which lowers the longest column that fits by about 80 cells.
