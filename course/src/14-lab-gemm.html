Lab 4: 2-D GEMM with SUMMA

Every lab so far ran on a row or a column. This one uses a P × P grid of PEs to multiply two matrices with SUMMA, the textbook distributed GEMM. Each step broadcasts one block column of A along the rows and one block row of B down the columns, and then every PE multiplies the two tiles it received. The SDK's <collectives_2d> library does the broadcasts, rewriting the routes at run time and tearing them down after each step. We time each step on the tile's own counter. At realistic tile sizes the kernel spends almost all its time computing, which is the opposite of Lab 3's result. It still reaches only a third of the multiply-add rate, and the measurements show where the rest goes.

After this lab you can

  • Explain SUMMA as "P outer products of block columns and block rows", and map it onto a P × P grid with 2-D host I/O.
  • Read <collectives_2d>: two colors per axis, routes rewritten per broadcast, a teardown wavelet, and a lock task that fires the callback.
  • Build a task that waits for two independent networks (block + activate), and re-arm it every step.
  • Time broadcast and compute separately with the TSC, compare them with a compute-bound estimate, and find the instruction and bank-clash overheads.
  • Budget a kernel before writing it: memory, colors, task IDs, queues and microthreads, and a cycle model.

From GEMV to SUMMA

Chapter 12 composed a distributed GEMV from two collectives: broadcast slices of x down the columns, multiply locally, and reduce partial y along the rows. A GEMM, C = A·B, is many GEMVs at once (one per column of B), so you could run that pattern N times. SUMMA (Scalable Universal Matrix Multiplication Algorithm, van de Geijn and Watts, 1997) organises the same work so that no reduction is needed at all.

Cut A (M × K), B (K × N) and C (M × N) into a P × P grid of blocks. PE (px, py) owns block row py and block column px of all three: A(py, px), B(py, px) and C(py, px). The owner of a block of C computes it:

Mind the index order.

PE coordinates are (x, y) = (column, row), but matrix blocks are indexed (row, column). So PE (px, py) owns block (py, px): PE (2, 0) holds the block in block row 0, block column 2. Swapping the two is the most common way to get a wrong C in a 2-D program, and nothing crashes when you do.

C(py, px) = Σ_s  A(py, s) · B(s, px)        s = 0 … P−1

The term for step s needs block column s of A and block row s of B. So at step s the PEs in grid column s broadcast their A block along their row, the PEs in grid row s broadcast their B block down their column, and every PE adds one tile product into its C. After P steps each C block is complete, and it never moved. In matrix terms each step adds one rank-K/P update, an outer product of a block column and a block row.

The GEMV warm-up. Set Nt=1 and the same program computes a matrix times P vectors at once (B is K × P): a batched GEMV. Each step still broadcasts an A tile along the rows, but the B "tile" is a column segment of only Kt words, and each PE does Kt multiply-adds per output element. Compared with Chapter 12's GEMV, the vector is broadcast and the result stays put, instead of the vector staying put and the result being reduced. The warm-up exercise runs it.

SUMMA, one step at a time

Green fill is how much of each C tile is done. Right: the same step on the whole matrices. Click a PE to follow it. Why it suits the wafer. Each step moves Mt·Kt + Kt·Nt words into every PE and does Mt·Kt·Nt multiply-adds there. For square tiles of side T that is 2T² words for T³ multiply-adds: the compute grows faster than the traffic, so large tiles are compute-bound. The broadcasts are multicasts (one send reaches the whole row, Chapter 12's program 05), so their cost barely depends on P. And C never moves, so the only data in flight is A and B.

Data layout and host I/O on a 2-D grid

The host copies each matrix in a single memcpy_h2d over the whole P × P rectangle (Chapter 7). With MemcpyOrder.ROW_MAJOR, the flat host array is consumed PE by PE in row-major order over the grid (py outer, px inner), Mt·Kt words per PE. So the host must arrange A so that each PE's tile is contiguous, and in the order the PE wants. This program stores every tile column-major, so that a column of the A tile, which is what the inner multiply-add streams over, is contiguous.

Reading C back is the inverse: the device returns (py, px, column, row), and transpose(0, 3, 1, 2) brings it back to (block row, row, block column, column). Getting one axis wrong does not crash anything: the program just multiplies the wrong numbers, and the numpy check catches it. That check is the first line of defence in any 2-D program.

Inside <collectives_2d>

Chapter 12 used the library in one dimension and measured its fixed cost at about 700 cycles Measured, Ch. 12. Here we need it in both dimensions, so it is worth opening up. The source is csl-libs/collectives_2d/pe.csl in the SDK image (1,312 lines) SDK 2.10.1; the broadcast path is short.

What one instance owns

Each axis is a separate instance of the module (row and col in our program). Each one owns two colors (DATA_COLOR_0, DATA_COLOR_1), two local task IDs, two input/output queue pairs and one set of DSD registers. The two tasks are an FSM task (a small finite-state-machine task that runs once per stage of a collective and decides what to do next) and a lock task (below). The DSD registers (DSRs) are the hardware registers that hold a descriptor while an operation runs (Chapter 6); the two instances must use different ones, which is what dest_dsr_ids and its siblings choose in pe_program.csl. Broadcast uses only color 0; color 1 is for reduce_fadds, which needs the alternating checkerboard of Chapter 12's program 03. The layout calls c2d.get_params(px, py, ids), which records only whether the PE sits at either end of its row and column. The PE reads its own coordinate at run time (init()), so the compiler builds a handful of ELF files instead of P². At load time color 0 is a broadcast network rooted at PE 0, in teardown mode.

Why the routes change at run time

A static route has a fixed input direction, and on WSE-3 a route accepts at most one input direction (Chapter 4). In SUMMA the root of the row broadcast moves one column east every step: at step 0 every PE receives from the west side, at step P−1 from the east side, and in between the PEs left of the root receive from the east and the PEs right of it from the west. With static routes you would need a color per root, P colors per axis. The library uses one color and rewrites it before each broadcast:

collectives_2d/pe.csl, configure_broadcast_network() (abridged)
if (pe_id == root) {                    // the root's CE feeds the router
  // ends of the line send one way, everyone else both ways
  color_config.reset_routes(addr, .{.tx = [2]direction{POS_DIR, NEG_DIR}, .rx = RAMP});
} else if (pe_id < root) {               // left of / above the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, NEG_DIR}, .rx = POS_DIR});
} else {                                 // right of / below the root
  color_config.reset_routes(addr, .{.tx = [2]direction{RAMP, POS_DIR}, .rx = NEG_DIR});
}
tile_config.teardown.exit(DATA_COLOR_0);  // leave teardown: traffic may flow

POS_DIR is EAST for the row instance and SOUTH for the column instance. Every non-root router in the middle of the line passes the wavelet both to its own CE (RAMP) and onward; the PEs at the two ends of the line have nobody to pass it to, so their routes only take it to their CE (.tx = RAMP, a branch the abridged listing leaves out). This is program 05's multicast with a run-time root.

One broadcast, end to end

  1. broadcast(root, buf, count, callback) blocks the lock task, records the root and the buffer, clears the filter and switch state left by any earlier gather or scatter, rewrites the routes as above, and leaves teardown mode.
  2. Transfer. It activates its FSM task, which starts one asynchronous 32-bit move of count words: memory → fabric at the root, fabric → memory everywhere else. The move runs on the microthread of its queue (2 for the row instance, 3 for the column instance) and activates the FSM task again when it finishes.
  3. Teardown. On that second run the FSM calls initiate_teardowns(). Only the root sends anything: one control wavelet with the TEARDOWN command and the CE-ignore bit set, on color 0. (A control wavelet carries commands for the routers it passes; with CE-ignore set, the routers act on it but no PE's CE receives it as data, Chapter 4.) It follows the same routes as the data, so it reaches every router in the line after the last data wavelet, and each router puts color 0 back into teardown mode.
  4. Lock. Entering teardown runs the CE's teardown handler, task 29 (Chapter 4, Chapter 5), which activates the lock task. The FSM unblocks the lock when its own transfer is done. So the lock runs only when both have happened: the data is in my memory, and the network is torn down and ready to be rewritten. The lock task then activates the user's callback (our x_done or y_done).

The teardown is what makes the next step's rewrite safe: no PE can reconfigure color 0 while wavelets of the previous broadcast are still in its router. What happens to a root that starts step s+1 while a slower neighbour is still computing step s? Its data waits behind the neighbour's router, which is still in teardown mode, and the lossless fabric back-pressures the sender until the neighbour calls broadcast and leaves teardown. The library's comments describe this ordering ("if we clear TIP bit before routing is reconfigured, it stalls"; TIP is the router's teardown-in-progress flag for that color, and clearing it is what teardown.exit() does); we did not isolate it in a separate experiment Derived from the library source.

Both this broadcast and Chapter 12's program 05 are chains: the wavelets stream through every router of the line and each router copies them to its CE on the way. Whether a tree would be better is a question for reductions, not broadcasts; the aside after "Scaling up" works it out.

The task that waits on two networks

Each step needs both tiles before it can compute: the A tile from the row broadcast and the B tile from the column broadcast. They finish in either order. Chapter 5's join does this with two bits: the compute task starts blocked; y_done unblocks it and x_done activates it. A task runs only when it is both activated and unblocked, so compute runs exactly once, after the later of the two callbacks. At the end of compute, @block(COMPUTE) re-arms the join for the next step before start_step() issues the next pair of broadcasts.

Why not count, as Lab 3 did with pending? That works too, but it needs a counter, a decrement in each callback and a test. The join is free: the hardware task picker evaluates it.

Notes on the details:

  • Home tile or buffer. At step s the root of the row broadcast is the PE whose px == s. It sends from its own A_tile; everyone else receives into A_buf. compute makes the same choice, so a PE multiplies its own tile when it is the root. The two buffers cost 2 extra tiles of memory, the price of not overwriting home tiles that later steps still need to send.
  • Kernel 0's loop. For each k and j it reads the scalar B[k, j] and issues one @fmacs of length Mt: C[:, j] += A[:, k] · B[k, j]. That is Kt·Nt vector instructions per step, each moving a DSD with @increment_dsd_offset (Chapter 6).
  • Timestamps. stamp_now(k) writes the 48-bit TSC into slot k of an exported array: once at main(), three times per step (broadcasts issued, compute starts, compute ends) and once in exit. The host reads them with a 16-bit memcpy, as in Lab 3. All differences are taken on one PE, because counters on different PEs start at different times (Chapter 12).

What the numbers say

  • Compute takes over quickly. At T = 4 the two phases are about equal (broadcast 2,310 vs compute 2,492 cycles on WSE-3). At the default T = 8 compute is 80% of the kernel, at T = 16 it is 94%, and at T = 32 it is 97.5% (10,277 vs 414,896) Measured. This is the opposite of Lab 3, where a 16-cell step was 70% messages, tasks and instruction start-up: GEMM does T³ work for 2T² words, so the fabric falls out of the picture once tiles are more than a few words across.
  • A broadcast step costs a fixed ≈ 520 cycles plus about 1 cycle per word received on WSE-3, counting both tiles: 650, 1,033, 1,673 and 2,569 cycles per step for T = 8, 16, 24, 32, against 520 + 2T² = 648, 1,032, 1,672 and 2,568 Measured → Derived fit. On WSE-2 the same fit is ≈ 429 + 2T² (558 and 941 cycles at T = 8 and 16; 2,476 at T = 32). Two broadcasts run at once, each on its own microthread and network, yet the time grows with the sum of the two tiles, so at this size the two transfers do not overlap fully. With non-square tiles (P = 2, Kt = Nt = 8) growing only the A tile from 32 to 256 words added 0.5–0.8 cycles per word, so they overlap partly; we have not isolated where the PE serialises them. The fixed part is the library's per-operation work (route rewrite, FSM tasks, teardown, the lock task, the callback), the same order as the ≈ 700 cycles Chapter 12 measured for the library in one dimension. One explanation for the "sum of words" fits the numbers: both fabric → memory moves go through the same receive path into the PE (the ramp or the memory write port), which would then accept about 1 word per cycle in total. That is a hypothesis, not a measurement Unverified; the test is to time one broadcast alone against both together at the same total word count. If it holds, it is the per-PE communication ceiling for a real roofline: a square tile does T/2 multiply-adds per word received.
  • The step time does not depend on P. At T = 8 on WSE-3, a broadcast step costs 626, 650, 653 and 654 cycles for P = 2, 4, 6, 8, and compute is 2,903 cycles at every P; on WSE-2, 563, 558 and 557 cycles for P = 2, 4, 8 Measured. The multicast streams through the routers at 1–2 cycles per hop, so the extra hops of a wider grid are lost in the noise. The kernel therefore grows exactly with the number of steps: 7,188, 14,422, 21,624 and 28,828 cycles for P = 2, 4, 6, 8 (WSE-3), close to 3,600·P. Weak scaling is flat per step; the total grows with P because a P-times-larger matrix needs P steps.
  • Strong scaling is a different story. Fix the matrix instead: N = 256 can run as P = 8 with T = 32 or as P = 32 with T = 8. From the per-step costs in the table, P = 8 takes 8 × (2,569 + 103,724) ≈ 850,000 cycles and P = 32 takes 32 × (650 + 2,903) ≈ 114,000: 7.5× faster on 16× the PEs, about 47% parallel efficiency Derived from the P = 4 measurements; P = 32 not run. As T shrinks, the fixed costs (≈ 520 cycles per broadcast, ≈ 30 per instruction) take over. Try it in the budget calculator below.
  • But compute reaches only a fraction of the ideal. A PE can do one f32 multiply-add per cycle (Chapter 6), so a step's ideal is T³ cycles. Kernel 0 needs 2,903 cycles for 512 multiply-adds at T = 8 (18% of ideal) and 103,724 for 32,768 at T = 32 (32%) on WSE-3; on WSE-2, 2,768 (18%) and 96,630 at T = 32 (34%) Measured. Two separate costs, both from Chapter 6, explain it; the next callout takes them apart.
  • Kernel 1: fewer, longer instructions. Replacing the Kt·Nt short @fmacs with Kt pairs of @fmuls + @fadds of length Mt·Nt (2-D DSDs with a zero stride broadcast column k of A and row k of B over the tile) cuts the step to 1,594 cycles at T = 8 and 63,890 at T = 32 on WSE-3: 51% of ideal, 1.6× faster than the SDK loop Measured. Per k it costs about 1.87 cycles per element + 77, fitted over T = 8–32 Derived fit; the callout below explains why this fit is only approximate. On WSE-2, where @fadds moves 1 element per cycle instead of 2, it costs 2.0 per element + 112: 1,921 cycles at T = 8 and 69,026 at T = 32 (47% of ideal) Measured. It needs one more Mt × Nt tile of memory, which lowers the largest tile that fits (below).
  • The compute fits hold only for tile heights that are multiples of 4. Every square tile in the P = 4 runs (4, 8, 16, 24, 32) is a multiple of 4, so every @fmacs clashed (the callout explains why). Other heights land somewhere else, and not in the same direction on both chips. At T = 45, kernel 0 takes 189,224 cycles per step on WSE-3, 30% less than the fit's 271,000, but 276,575 on WSE-2, 11% more than its fit; at T = 46 WSE-2 takes 315,978, 20% more than the fit (149 cycles per @fmacs of 46). Kernel 1 on WSE-2 takes 97,004 per step at T = 39, 21% under its fit, but 152,872 at T = 42, on the fit Measured, P = 2. So the lines in the chart and the calculator are trustworthy only when Mt is a multiple of 4; anywhere else, measure.
  • Host I/O is still a large share of the whole run. At the defaults the simulator counts 36,959 cycles in total, of which the kernel is 14,422 (39%); at T = 32 it is 425,382 of 635,409 (67%) Measured. As in Labs 1–3, time the kernel with the TSC.
Where the other two-thirds go: start-up and a bank clash

Kernel 0 issues Kt·Nt instructions of length Mt per step. Each one costs a fixed part plus a per-element part, and both are larger than the ideal 0 + 1:

  • A fixed ≈ 29–38 cycles per instruction. Reading the scalar B[k, j] (with its index arithmetic), @increment_dsd_offset and starting the op. Chapter 6 measured about 33–35 cycles per step for this kind of scalar loop around a DSD op. With Mt = 8 an instruction costs 2,903 / 64 = 45.4 cycles, so the fixed part is about two-thirds of it (29 of 45 cycles) Derived. Removing the multiply-adds entirely leaves 27 cycles per step (WSE-3) for the timestamps and the empty task, so the loop really is the cost Measured. The fixed part grows a little with the tile size (≈ 29 at Kt = Nt = 8, ≈ 37–38 at 16–32); we have not isolated why.
  • 2 cycles per element instead of 1. Chapter 6's operand-collision rule: @fmacs runs at half speed when its two source streams start at addresses that are equal mod 4 words. Here the sources are column j of C (C_tile + j·Mt) and column k of A (A + k·Mt). When Mt is a multiple of 4 every (j, k) pair has the same alignment as the two array bases, so either all instructions clash or none do. In the course's runs they all did: 45.4, 60.9 and 92.4 cycles per @fmacs for Mt = 8, 16, 32 is 2·Mt + 29 Measured, P = 2, Kt = Nt = 8, WSE-3. With any other Mt the alignment changes from instruction to instruction, so only some of them clash; exercise 5 measures how many.

The test. If the clash is real, moving C by one word relative to the A arrays should remove one cycle per multiply-add and nothing else. Exercise 4 makes that change and checks the prediction; the hollow points in the chart above are its result. Two consequences are worth knowing now. First, a fix that helps only some PEs or some steps does not help at all, because the grid moves at the pace of its slowest PE. Second, the result depends on where the linker put each array, so you need to see the addresses: cs_readelf --syms out/bin/out_0_0.elf lists every array with its byte address (Chapter 10 introduces cs_readelf). In the shipped build at T = 16, A_tile, B_tile, C_tile, A_buf and B_buf sit at 0x1708, 0x1b08, 0x1f08, 0x2308 and 0x2708, in declaration order, all equal mod 16 bytes (4 words) Measured, cs_readelf 2.10.1.

The same two costs appear in kernel 1, in a different mix. It issues only 2·Kt instructions, so the fixed part almost vanishes, but its @fmuls on two zero-stride 2-D DSDs costs about 1.6 cycles per element on WSE-3 and 1.35 on WSE-2 (16 @fmuls alone take 6,774 and 5,808 cycles per step at T = 16), while @fadds alone takes 0.5 and 1.0 cycles per element, as Chapter 6 found Measured, ablation. On WSE-3 the two ablations add up to about 2.1 cycles per element at T = 16, which matches the measured kernel-1 step at that size (8,914 cycles for 4,096 multiply-adds, 2.18 including start-up). The fitted 1.87 is lower because the per-element cost falls as T grows (1.95 at T = 32): the fit averages over T = 8–32 and is only approximate Derived. We have not isolated why the @fmuls is slower than 1 per cycle; the zero-stride operand reads one word repeatedly, and the collision rule is empirical. Kernel 1 is alignment-sensitive too: on WSE-2 at T = 39 the pair costs 1.63 cycles per element instead of 2.0 Measured, P = 2 (depth review). Padding C (exercise 4's fix) saves only 6% in kernel 1 (8,418 vs 8,914 cycles per step at T = 16, WSE-3).

The lesson for the roofline. "Compute-bound" on the wafer does not mean "at peak". The fabric is out of the way, but every instruction pays start-up and every pair of operands must avoid a bank clash. The levers are the same as in Lab 3: fewer, longer instructions, and pad and measure. And the ceiling used here is the f32 one, 1 multiply-add per cycle. The wafer's headline numbers are 16-bit, where a PE does about 3.2–4 multiply-adds per cycle on WSE-3 (Chapter 6), so kernel 1's 51% of the f32 ceiling is only about 13–16% of what the PE could do in 16-bit Derived.

Caveats: simulator cycles and models fitted at P ≤ 8, extrapolated to P = 743 on the strength of the flat per-step cost (a 743-hop multicast adds ≈ 750–1,500 cycles of latency per step at 1–2 cycles per hop, under 1% here); f32 only, while the wafer's headline numbers are 16-bit (Chapter 6 measured f16 @fmach at 2–4 elements per cycle, so a tuned f16 kernel could be several times faster, unmeasured here); and loading the three matrices from the host (≈ 13 GB at T = 45) is left out. The real lesson is the ratio: at this scale the fabric costs about 2% of each step, and the per-PE instruction stream is the whole game. It is the same lesson as a GPU's tiled matmul and Tenstorrent's: once the tiles are in place, the inner loop decides how close you get to peak.

  4. Remove the bank clash. Change the program so that no @fmacs has its two sources at addresses equal mod 4 words. Predict the compute per step at P=2 T=16 before and after, from the callout's mechanism alone.

    Hints

    Start with cs_readelf --syms out/bin/out_0_0.elf and write down the address of every tile. Then: a comptime pointer cast is not allowed, so you cannot export &C_mem[1] directly. Declare C_mem one word longer, point the DSDs at C_mem[i + 1], export all of C_mem, and drop the first word of each PE's block on the host. Look at the per-step stamps (add print(cend - cbeg) to run.py), not just the sum: the PE multiplies A_tile on one step and A_buf on the other, and arrays declared after C move when C grows.

    Expected result

    Prediction. Before: 17,835 cycles per step (69.7 per instruction = 2·16 + 38). After: one cycle less per multiply-add, 17,835 − 16³ = 13,739.

    Padding C alone is a half-fix. It gives 13,739 on the step where a PE multiplies its own A_tile but still 17,835 on the step where it uses A_buf (P = 2, T = 16, WSE-3) Measured. The symbol table says why: A_buf is declared after C_tile, so making C one word longer moves A_buf by the same word and it stays aligned with C's data, while A_tile, declared before C, does not move. The kernel gets no faster, because the PEs wait for each other.

    The full fix keeps both A arrays in one array, so they share an alignment, and pads C. Every edit:

    1. Declarations: replace A_tile and A_buf by var A_both = @zeros([2 * Mt * Kt]f32); (home tile in the first half, receive buffer in the second), and C_tile by var C_mem = @zeros([Mt * Nt + 1]f32);.
    2. Exports: var A_ptr: [*]f32 = &A_both; (the host's memcpy_h2d fills the first half) and var C_ptr: [*]f32 = &C_mem;.
    3. In both start_step (the broadcast source or destination) and compute: const Ap: [*]f32 = if (px == step) @ptrcast([*]f32, &A_both) else @ptrcast([*]f32, &A_both[Mt * Kt]); (a run-time cast is allowed). If you change only compute, the broadcasts still use the old arrays and C is wrong.
    4. DSD templates: A_tile[i] becomes A_both[i], and C_tile[…] becomes C_mem[… + 1] (in kernel 0, and in kernel 1's A2 and C2 if you keep it).
    5. run.py: read Mt * Nt + 1 words per PE and drop the first: Cf = np.zeros(P * P * (Mt * Nt + 1), dtype=np.float32), pass Mt * Nt + 1 to memcpy_d2h, then Cf = Cf.reshape(P * P, Mt * Nt + 1)[:, 1:].ravel().

    Result: 13,739 cycles on every step and every PE, exactly as predicted: 1 cycle per multiply-add saved, 23% Measured. Padding by 1, 2 or 3 words works; padding by 0 gives 17,835 again. At T = 32 the fix brings kernel 0 from 103,724 to 70,956 cycles per step (46% of ideal, up from 32%), at T = 8 to 2,391, and on WSE-2 at T = 16 from 16,086 to 12,004 Measured, P = 2.

Check yourself

Why does SUMMA need no reduction, while Chapter 12's GEMV did?

The owner of a C block accumulates every term of its own sum: at step s it receives the A and B blocks it needs. In the GEMV the A blocks stayed put and each PE produced a partial sum of a y block that lived on several PEs, so the partials had to be added along the row.

Why does the library rewrite routes before every broadcast instead of declaring them in the layout?

The root moves every step, so the direction each router receives from changes. A static route has one input direction (on WSE-3 at most one is allowed), so static routes would need one color per possible root. Rewriting one color at run time keeps the broadcast to one color per axis (the library reserves a second color per axis for its reduce).

What does the teardown wavelet protect against?

Rewriting a router while wavelets of the previous broadcast are still passing through it. The root sends the teardown after its last data wavelet, on the same route, so each router enters teardown only after the data has gone by, and the next broadcast() may then reconfigure it.

x_done runs, then y_done. How many times does compute run, and what if the order is reversed?

Once, either way. compute starts blocked; one callback activates it and the other unblocks it, and the task picker runs it only when both bits are set. compute blocks itself again before starting the next step.

Kernel 0 at T = 32 needs 101 cycles per @fmacs of 32 elements. Where do they go?

About 2 cycles per element (64), because the two source streams collide in the same memory bank so @fmacs runs at half speed, plus about 37 cycles per instruction for the loop: reading the scalar, moving the DSD and starting the op.

Doubling P at fixed tile size: what happens to the time per step and to the total?

The time per step stays almost constant (the multicast's hop cost is tiny), so the kernel takes twice as long in total, for a matrix twice as large in each dimension: 8× the work in 2× the time, on 4× the PEs.

Kernel 1 runs the tile as @fmuls + @fadds. Why does it gain less over kernel 0 on WSE-2 than on WSE-3?

@fadds streams 2 f32 elements per cycle on WSE-3 but 1 on WSE-2 (Chapter 6), which makes the pair dearer on WSE-2; its zero-stride @fmuls is actually a little faster there (1.35 vs 1.6 cycles per element), which offsets part of that. The bigger reason is the baseline: kernel 0 is already cheaper on WSE-2 (96,630 vs 103,724 cycles per step at T = 32, about 27 vs 30 cycles of per-instruction overhead), so there is less to gain.

With MemcpyOrder.ROW_MAJOR on a 2 × 2 grid, which PE's tile is the third block of the flat host array, and why must each tile be column-major in this program?

The wire order is row-major over PEs, py outer and px inner: PE (0,0), (1,0), (0,1), (1,1). The third block goes to PE (0,1), which owns block row 1, block column 0. Column-major tiles make a column of A contiguous, and a column of A is exactly what each @fmacs streams over (and a column of C is what it accumulates into).

Why does the color count stay at 4 for any P, and which task ID must you never bind?

Each axis uses one library instance with two colors, and the routes are rewritten at run time for each root, so no color per root is needed: 2 axes × 2 colors = 4, whatever P is. Never bind your own task to 29: it is the teardown handler, which the library installs. (Colors 20–23 and memcpy's task IDs and queues are taken as well.)
