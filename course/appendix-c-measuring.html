Appendix C · Reference

Measuring and observing

The simulator gives you three instruments: one number for the whole run, a cycle counter on each PE, and a trace of every instruction. They answer different questions, and confusing them is the most common way to publish a wrong cycle count. This page puts them side by side, runs all three on one @fmacs, and ends with the profilers you would use on the other two machines in this course. Terms such as TSC, RPC, H2D/D2H and DSD are defined in Appendix A.

After this appendix you can

  • Pick the right instrument for a question: whole-run cycles, on-tile TSC, or the instruction trace.
  • Time a kernel with <time>, read the 48-bit result on the host, and say why two PEs' counters cannot be subtracted.
  • Turn on the instruction trace, read one line, and find a kernel's first and last element in it.
  • Name the equivalent tools on Tenstorrent (device profiler, Tracy) and NVIDIA (Nsight Systems, Nsight Compute).

1 · Whole-run cycles: sim_stats.json

The simulator writes sim_stats.json into the directory you ran cs_python from. cycle_count is the simulated clock when the simulator stopped, and the simulator stops only after the fabric has been idle for 50 cycles once the host is done ("sunsetCount": 50 in simconfig.json) Measured. Chapter 10's "Simulator outputs" shows a whole file.

Two facts make it a poor kernel timer. First, it is dominated by host I/O. In program 01 at N = 64 on WSE-3 (7,740 cycles in all; the examples further down use N = 256), the two H2D copies cost about 1,355 and 1,291 cycles, the D2H about 4,440 and the @fmacs about 130 Measured, Ch 11 (Chapter 11, "What happens inside, in order"). In Lab 2 the kernel is 1–3 % of the total (Chapter 12). Second, it is noisy: the simulator keeps counting while it waits for host commands, so a loaded container inflates it (Chapter 11, "Cycle totals are approximate"). Here are eight runs of the same timed SAXPY build:

Same program, eight runs

Program 01's timed variant, N = 256, f32, PAD 1 (one padding word between x and y), WSE-3. What it is good for: the end-to-end cost of a host program, run one simulation at a time on a quiet machine. It is not good for differences. For a per-step cost, take the slope of the TSC between two step counts: Lab 3 runs 10 and 100 steps and divides the TSC difference by 90, which cancels the fixed start-up (Chapter 13, "Time it inside the kernel"). Differencing two cycle_count totals inherits their noise: the same Lab 3 build reported 5,260 and 8,905 cycles on a quiet and a loaded machine, with the same TSC Measured, Ch 13. Two more warnings. "Stopped due to idleness" ends both a success and a deadlock, so only your host-side check tells them apart. A fatal stop writes no sim_stats.json at all Measured, Ch 10.

2 · On-tile cycles: the TSC and <time>

Each PE has a 48-bit timestamp counter (TSC). The <time> library reads it as three 16-bit words. The library source in the SDK image shows what the calls do SDK 2.10.1, csl-libs/time/internal.csl:

  • enable_tsc() writes 7 to the performance-counter control register and then calls reset_tsc_counter(), because "timestamp counters on hardware begin execution as a random 48-bit number". So enabling also zeroes the counter: call it before your first stamp, never between the two stamps of one measurement. Calling it again at the start of each launched function is fine, as long as both stamps of a measurement come after that call: program 03 enables in its own launched start_timer(), and Lab 5 re-enables in f_init before each solve.
  • get_timestamp(&t) copies the three counter words into t[0..2], least significant first.
  • The module also exports disable_tsc(), reset_tsc_counter() and get_perf_cntr(&t, id), which reads hardware performance counter 0 or 1 into the same three-word format SDK 2.10.1, csl-libs/time.csl. What those two counters count is not documented in the library; the course does not use them.
  • A second library, <timer>, wraps the TSC in numbered timers: start(id) and stop(id) stamp into per-timer buffers, and elapsed(id, &r) subtracts them on the device with a 48-bit borrow (subtract_timestamps), so the host reads one duration instead of two stamps SDK 2.10.1, csl-libs/timer.csl. No SDK example uses it; Lab 5 hand-rolls the same idea.
device: course/programs/01-saxpy/timed/pe_program.csl (excerpt)
const tsc = @import_module("<time>");
var t0 = @zeros([3]u16);
var t1 = @zeros([3]u16);

fn saxpy(a: f32) void {
  tsc.enable_tsc();             // control = 7, counter reset to 0
  tsc.get_timestamp(&t0);
  @fmacs(y_dsd, y_dsd, x_dsd, a);
  tsc.get_timestamp(&t1);
  for (@range(i16, 3)) |i| { ts[i] = t0[i]; ts[3 + i] = t1[i]; }   // exported as [*]u16
  sys_mod.unblock_cmd_stream();
}
host: course/programs/01-saxpy/timed/run.py (excerpt)
t = np.zeros(6, np.uint32)                       # 16-bit copy mode: one u16 per u32 slot
rt.memcpy_d2h(t, tss, 0, 0, 1, 1, 6, streaming=False, order=MemcpyOrder.ROW_MAJOR,
              data_type=MemcpyDataType.MEMCPY_16BIT, nonblock=False)
w = memcpy_view(t, np.dtype(np.uint16)).astype(np.int64)
stamp = lambda k: w[k] | (w[k + 1] << 16) | (w[k + 2] << 32)   # the SDK calls this make_u48
print(stamp(3) - stamp(0), "cycles")

The SDK recommends the same idiom over host-side timers: "the runtime may not send the command right after the user issues it" SDK 2.10.1, bandwidth-test README. Use the course's 01-saxpy/timed program as a template; Chapter 11 ("Measure the kernel itself") has its full table. For a kernel with several phases, Lab 5 reads the TSC at every phase boundary and accumulates each phase into its own bucket, compiled out with PROFILE=0 (Chapter 15, "Where an iteration's cycles go"). Its eleven mark() calls per iteration cost 7–10 % of the iteration, about 30–35 cycles each Measured, Ch 15. That does not contradict the 10-cycle empty region below: a bare get_timestamp pair is cheap, but each mark() also joins the words into a 32-bit time, subtracts the previous stamp and adds the difference into a bucket in memory. Reading the counter is cheap; arithmetic on stamps on the device is not.

Kernels made of tasks. SAXPY's kernel is one function, so two stamps can bracket it. Most kernels from Chapter 5 on are tasks that wavelets or finished async ops activate, so there is no single function to wrap. Stamp the start in the function that starts the work (the one that issues the async op or arms the receive), stamp the end in the task that runs once the last wavelet has been handled, and export both from that same PE. Program 03 does exactly this: a launched start_timer() calls enable_tsc(), reduce() stamps t_start as it issues its async @fadds, and exit_task, which the op activates after the last of its M wavelets, stamps t_end (Chapter 12, "Measuring the kernel, not the host").

The same-PE rule

Subtract only stamps taken on the same PE. Each PE's counter is zeroed when that PE calls enable_tsc() (before that, on hardware, it runs from a random value). PEs reach that call at different cycles, so their counters are offset by an unknown amount, on the simulator and on hardware alike; that is why the SDK benchmarks need a reference stamp at all. A "time from PE A sending to PE B receiving" computed by subtracting A's stamp from B's is meaningless. Chapters 12 and 13 apply the rule.

Two ways around it, for anything that spans PEs:

  • Round trip. Send from a PE and time until the answer comes back to the same PE. Chapter 12 ("The hop cost, on one clock: a round trip") measures a pure router hop this way: 2.0 cycles/hop on WSE-3 and 1.0 on WSE-2 Measured. A hop through a PE's compute (receive, add, send) costs about 9.2 and 6.0 Measured.
  • Synchronise, then correct. Several SDK benchmarks (7pt-stencil-spmv and the CG-family solvers, among others; Appendix D lists which) put every PE on one time base in four steps SDK 2.10.1, 7pt-stencil-spmv/run.py conjugate-gradient/run.py:
    1. Synchronise all PEs, for example with an allreduce.
    2. The bottom-right PE sends a signal; each PE stamps time_ref when the signal reaches it.
    3. The host corrects each time_ref for the signal's travel: it subtracts (width + height − 2) − (px + py), which is the Manhattan hop count from the bottom-right PE (width − 1, height − 1) to PE (px, py), at 1 cycle per hop. It then subtracts the corrected time_ref from that PE's start and end stamps.
    4. It reports max(time_end) − min(time_start) over all PEs.
    Worked line, 3 × 3 grid: PE (0,0) is (3 + 3 − 2) − 0 = 4 hops from PE (2,2), so its time_ref is stamped 4 cycles after the sender's, and the host takes 4 off it so both references name the same instant; PE (2,2) itself gets 0 Derived. That correction assumes 1 cycle per hop. On WSE-3 we measured 2, so PE (0,0) really stamped 8 cycles late and is left 4 off; in general the start/end alignment can be off by up to about width + height cycles Derived; harmless for a long solve, visible for a short kernel.

3 · The instruction trace

You first met the instruction trace in Chapter 11, "Look inside: the instruction trace"; this section is the reference. Set one environment variable for the run. The wrapper passes SINGULARITYENV_* variables into the SDK container, and the simulator then writes every executed instruction into sim.log Measured:

SINGULARITYENV_SIMFABRIC_DEBUG=inst_trace cs_python run.py --name out
grep "P4.1: .*EX OP.*FMACS" sim.log | head -2          # your PE at fabric (4,1)
python3 trace_tasks.py sim.log P4.1                    # group into runs of one task

PEs are named by fabric coordinates, not by your rectangle's. With the course's --fabric-offsets=4,1 (3 memcpy columns and 1 halo column on the west, 1 halo row on the north; Chapter 7), your PE (px, py) prints as P(px+4).(py+1): PE (0,0) is P4.1, and in Lab 2 the last PE of a 4-PE row, (3,0), is P7.1 Derived.

It is big. Every PE prints at least one line per cycle, IDLE cycles included, so the size grows with the total simulated cycles times the PEs, not with your kernel: our one-PE, N = 256 runs wrote between 230,000 and 345,000 lines (17–21 MB) on either chip, depending on how long that run's host I/O took Measured. Use it on small sizes and few PEs, and grep for your PE.

Each instruction appears at least twice. An [IS OP] line is printed when it issues (Pipe: 3 on WSE-3, 2 on WSE-2) and an [EX OP] line when it executes (Pipe: 6 and 4), three cycles later on WSE-3 and two on WSE-2; the same Instr number ties them together. A DSD operation prints one [EX OP] line per element, and a DSD load prints two (one per descriptor word). So grep for EX OP: a plain grep FMACS finds 257 lines for 256 elements Measured. The course's helper course/programs/01-saxpy/trace_tasks.py groups the [EX OP] instructions of one task on one PE into runs: it starts a new run whenever the task changes or the gap since that task's previous instruction is 40 cycles or more. Gaps under 40 cycles, IDLE cycles included, are merged, so a run can contain idle stretches, and two back-to-back pieces of work by one task can merge into one run (the worked example shows a case). It prints the task, its first and last cycle, how many instructions it executed, and the notable opcodes, which is the quickest way to see a timeline. The task numbers are memcpy's, and they differ by chip: in our runs your RPC ran inside memcpy's T01 on WSE-3 but T22 on WSE-2 Measured. Chapter 11's task table describes the WSE-3 IDs.

Three readings of the same run:

  • TSC: 271 cycles on WSE-3 and 270 on WSE-2 with padding, identical in every rerun. Without padding, 527 and 526: a bank clash doubles the op. Why one word matters: cs_readelf --symbols on the PAD 0 build places x at byte 0x0c20 and y at 0x1020, 1,024 B apart, and 1,024 ≡ 0 (mod 16 B), so both source streams start in the same bank and stay in step; with PAD 1, y moves to 0x1024, 4 B off, and the clash is gone Measured, cs_readelf, WSE-3, N = 256. The rule (Chapter 6, "Layout matters"): DSD op rates depend on where the two source streams start in SRAM's 16-byte cycle of 8 banks, and two streams that start in the same bank run at half rate SDK 2.10.1, cs_readelf man page Measured, Ch 6.
  • Trace: 256 FMACS [EX OP] lines, one per element, one cycle apart: exactly 1 element/cycle. The other 15 TSC cycles are, in order: the rest of the first stamp interleaved with three stores that save it (5), the two DSD loads (2), three idle cycles while the FMACS travels from issue to execute (3), four NOPs the compiler placed after it (4) and the second stamp's first read (1).
  • cycle_count: the padded WSE-3 build was slower than the unpadded one in the first pair (22,844 vs 22,126), although its kernel was 256 cycles faster. Host-load noise is larger than the effect you are trying to see.

How much of the 15 is the instrument? Deleting the @fmacs and timing the two stamps alone gives 10 cycles on WSE-3, with or without padding Measured. Set against the itemised 15, that splits them as: instrument ≈ rest of stamp t0 (5) + the four NOPs (4) + t1's first read (1) = 10; op ≈ the two DSD loads (2) + the issue-to-execute fill (3) = 5 Derived. Counting the NOPs as instrument is inferred from the 10-cycle total, not seen directly (we did not trace the empty region). So "time an empty region and subtract" turns 271 into 261 = 256 + 5, and those 5 belong to the op itself: you would pay them every time you ran it Derived.

On WSE-2 the same code reads the counter from config addresses 0x318–0x31a (control at 0x31e) inside task T22: the first stamp is 4, the second 0x0112 = 274, and 274 − 4 = 270, again exactly the TSC result. The trace and the TSC agree to the cycle on both chips. Absolute stamps are not quite fixed, though: in one WSE-2 rerun every line of the kernel came one cycle later (FMACS @4157 → @4412), with the same differences. Grouped by trace_tasks.py, the WSE-3 kernel RPC sits inside one run:

T01    3353-4113   (  761 cyc,  510 instr) BLK FMACS OQFLUSH UBLK

That 761-cycle run is not exactly the RPC. It starts at @3353 while memcpy pushes the RPC's arguments (an earlier push is a separate run, T01 3285-3305), contains your function (enable_tsc at @3608 to UBLK at @3902), and continues 211 cycles past UBLK: the same task, now unblocked, is already taking in the next command, the D2H of y, whose own tasks (T29, then T21/T30) follow from @4119 Measured. trace_tasks.py merges the two because the gap between them is under 40 cycles. The 271 is the part between your two stamps. The whole program is the outer span, and it is the one that moves: two traced WSE-3 runs executed this stretch at exactly the same cycles (3353–4113), yet ended at 21,515 and 29,368. All of the difference arose after the kernel, during the D2H copies and the waits for the host around them. Untraced runs of the same build ended between 21,631 and 24,763.

Common pitfalls

  1. Reporting cycle_count as kernel time. In the worked example the kernel was 1.1–1.3 % of it. Time the kernel with the TSC; for a per-step cost, take the TSC slope between two step counts.
  2. Comparing or differencing totals. Eight runs of one build gave 21,515 to 29,368 cycles, and two runs of an unpadded build 22,126 and 31,193 Measured. Run one simulation at a time, rerun alone before you chase a difference, and never read a kernel cost off the difference of two totals.
  3. Subtracting TSC values from two PEs. Use a round trip on one PE, or the SDK's sync and time_ref method with its 1-cycle-per-hop correction (2 on WSE-3).
  4. Calling enable_tsc() between stamps. It resets the counter to zero. Enable before the first stamp of a measurement; re-enabling at the start of each launched function is fine.
  5. Decoding the stamp wrongly. Three u16 words, least significant first. In 16-bit copy mode each u16 arrives in its own u32 slot, so view the buffer as u16 before joining (memcpy_view).
  6. Forgetting the overhead. The 271 includes 15 cycles that are not the 256 FMACS elements. An empty region costs 10 of them, so subtract that for short regions; the other 5 are the op's own start-up (DSD loads, pipeline fill) and belong to the op.
  7. Measuring an accidental layout. The same op took 527 or 271 cycles depending on one padding word. Pad and measure, and say which layout you timed.
  8. Tracing a big run. 230,000–345,000 lines for one PE and 256 elements, and the size grows with total simulated cycles × PEs, IDLE lines included. Shrink the problem first. Grep EX OP so you do not count issue lines, and remember that task numbers differ by chip (T01 vs T22).
  9. Trusting "Stopped due to idleness". A deadlock ends the same way. A FATAL stop writes no sim_stats.json, and launch() returns at once, whether or not the device ever unblocks; the next memcpy is what waits, and it aborts with "could be a kernel stall" (Chapter 10, "Simulator outputs" and "When it hangs").
  10. Converting cycles to seconds without saying the clock. 850 MHz is the SDK's assumption, 1.1 GHz is the vendor's WSE-2 figure, and there is no official WSE-3 clock (a press estimate of about 1.4 GHz is unverified).

Your change makes cycle_count drop from 22,800 to 21,700. Did your kernel get faster?

You cannot tell. Reruns of an unchanged program moved by more than that, in both directions. Read the TSC around the kernel in both versions and compare those (stable to the cycle). If you only have totals, run each version alone several times and expect the spread to swamp a 5 % change.

PE (0,0) stamps 1,200 when it sends; PE (3,0) stamps 1,180 when it receives. What was the latency?

Unknown, and the negative value shows why: the two counters started at different times. Time a round trip on PE (0,0), or synchronise and subtract each PE's reference stamp as the SDK benchmarks do.

In the trace, consecutive FMACS Seq values are two cycles apart. What do you suspect, and how do you confirm it?

A bank clash: x and y start in the same bank and the op runs at half speed. Add one padding word between the arrays and look again; in our runs the spacing became one cycle and the TSC fell from 527 to 271.

Your host prints a kernel time of 1,163,936,137,216 cycles for the SAXPY whose trace shows 256 FMACS lines one cycle apart. What went wrong?

The number is exactly 271 × 232: the right count, shifted 32 bits. The three words were joined most significant first (w2 | w1<<16 | w0<<32), so the low word, which holds the whole small count, landed at the top. Join least significant first, w0 | w1<<16 | w2<<32, after viewing the 16-bit copy's u32 slots as u16 with memcpy_view Derived.
