Appendix C · Reference

Measuring and observing

The simulator gives you three instruments: one number for the whole run, a cycle counter on each PE, and a trace of every instruction. They answer different questions, and confusing them is the most common way to publish a wrong cycle count. This page puts them side by side, runs all three on one @fmacs, and ends with the profilers you would use on the other two machines in this course.

After this appendix you can

  • Pick the right instrument for a question: whole-run cycles, on-tile TSC, or the instruction trace.
  • Time a kernel with <time>, read the 48-bit result on the host, and say why two PEs' counters cannot be subtracted.
  • Turn on the instruction trace, read one line, and find a kernel's first and last element in it.
  • Name the equivalent tools on Tenstorrent (device profiler, Tracy) and NVIDIA (Nsight Systems, Nsight Compute).

1 · Whole-run cycles: sim_stats.json

The simulator writes sim_stats.json into the directory you ran cs_python from. cycle_count is the simulated clock when the simulator stopped, and the simulator stops only after the fabric has been idle for 50 cycles once the host is done ("sunsetCount": 50 in simconfig.json) Measured. Chapter 10's "Simulator outputs" shows a whole file.

Two facts make it a poor kernel timer. First, it is dominated by host I/O. In program 01 each H2D costs about 1,360 cycles and the D2H about 4,400 of 7,740, against about 130 for the @fmacs (Chapter 11). In Lab 2 the kernel is 1–3 % of the total (Chapter 12). Second, it is noisy: the simulator keeps counting while it waits for host commands, so a loaded container inflates it. Here are five runs of the same timed SAXPY from this session:

Same program, five runs

Program 01's timed variant, N = 256, f32, PAD 1, WSE-3, run five times in this session. The fifth run had the instruction trace on. Each run is drawn relative to the first.

What it is good for: the end-to-end cost of a host program, and differences. Lab 3 times a timestep by running 100 and 200 steps and dividing the difference by 100, which cancels the fixed I/O (Chapter 13). Run the two simulations one at a time on a quiet machine. Two more warnings. "Stopped due to idleness" ends both a success and a deadlock, so only your host-side check tells them apart. A fatal stop writes no sim_stats.json at all Measured, Ch 10.

2 · On-tile cycles: the TSC and <time>

Each PE has a 48-bit timestamp counter. The <time> library reads it as three 16-bit words. The library source in the SDK image shows what the calls do SDK 2.10.1, csl-libs/time/internal.csl:

  • enable_tsc() writes 7 to the performance-counter control register and then calls reset_tsc_counter(), because "timestamp counters on hardware begin execution as a random 48-bit number". So enabling also zeroes the counter: call it once, before your first stamp, not between two stamps.
  • get_timestamp(&t) copies the three counter words into t[0..2], least significant first.
device: course/programs/01-saxpy/timed/pe_program.csl (excerpt)
const tsc = @import_module("<time>");
var t0 = @zeros([3]u16);
var t1 = @zeros([3]u16);

fn saxpy(a: f32) void {
  tsc.enable_tsc();             // control = 7, counter reset to 0
  tsc.get_timestamp(&t0);
  @fmacs(y_dsd, y_dsd, x_dsd, a);
  tsc.get_timestamp(&t1);
  for (@range(i16, 3)) |i| { ts[i] = t0[i]; ts[3 + i] = t1[i]; }   // exported as [*]u16
  sys_mod.unblock_cmd_stream();
}
host: course/programs/01-saxpy/timed/run.py (excerpt)
t = np.zeros(6, np.uint32)                       # 16-bit copy mode: one u16 per u32 slot
rt.memcpy_d2h(t, tss, 0, 0, 1, 1, 6, streaming=False, order=MemcpyOrder.ROW_MAJOR,
              data_type=MemcpyDataType.MEMCPY_16BIT, nonblock=False)
w = memcpy_view(t, np.dtype(np.uint16)).astype(np.int64)
stamp = lambda k: w[k] | (w[k + 1] << 16) | (w[k + 2] << 32)   # the SDK calls this make_u48
print(stamp(3) - stamp(0), "cycles")

The SDK recommends the same idiom over host-side timers: "the runtime may not send the command right after the user issues it" SDK 2.10.1, bandwidth-test README. Use the course's 01-saxpy/timed program as a template; Chapter 11 ("Measure the kernel itself") has its full table.

The same-PE rule

Subtract only stamps taken on the same PE. In the simulator each PE's counter starts when the launch reaches that PE, so counters on different PEs are offset by an unknown amount (cross-chapter note 19). On hardware they start as random numbers. A "time from PE A sending to PE B receiving" computed by subtracting A's stamp from B's is meaningless.

Two ways around it, for anything that spans PEs:

  • Round trip. Send from a PE and time until the answer comes back to the same PE. Chapter 12 ("The hop cost, on one clock: a round trip") measures a pure router hop this way: 2.0 cycles/hop on WSE-3 and 1.0 on WSE-2 Measured. A hop through a PE's compute (receive, add, send) costs about 9.2 and 6.0 Measured.
  • Synchronise, then correct. The SDK's solver and stencil benchmarks run an allreduce to synchronise all PEs, then the bottom-right PE sends a signal and every PE samples a reference stamp, time_ref. The host subtracts time_ref from each PE's start and end, corrects for the signal's travel with (width + height − 2) − (px + py) cycles, and reports max(time_end) − min(time_start) SDK 2.10.1, 7pt-stencil-spmv/run.py. That correction assumes 1 cycle per hop. On WSE-3 we measured 2, so the start/end alignment can be off by up to about width + height cycles Derived; harmless for a long solve, visible for a short kernel.

3 · The instruction trace

Set one environment variable for the run. The wrapper passes SINGULARITYENV_* variables into the SDK container, and the simulator then writes every executed instruction into sim.log Measured:

SINGULARITYENV_SIMFABRIC_DEBUG=inst_trace cs_python run.py --name out
grep "P4.1: .*EX OP.*FMACS" sim.log | head -2          # your PE at fabric (4,1)
python3 trace_tasks.py sim.log P4.1                    # group into runs of one task

It is big: our one-PE, N = 256 run wrote 318,240 lines (20.7 MB) on WSE-3 and 230,747 lines (17.1 MB) on WSE-2 Measured. Use it on small sizes and few PEs, and grep for your PE. Click the parts of one real line:

On WSE-2 the same code reads the counter from config addresses 0x318–0x31a (control at 0x31e) inside task T22: the first stamp is 4, the second 0x0112 = 274, and 274 − 4 = 270, again exactly the TSC result. The trace and the TSC agree to the cycle on both chips. Grouped by trace_tasks.py, the WSE-3 kernel RPC is one run:

T01    3353-4113   (  761 cyc,  510 instr) BLK FMACS OQFLUSH UBLK

That 761-cycle run is the whole RPC as memcpy's command task executes it (argument handling, your function, unblock). The 271 is the part between your two stamps. And the whole program took about 21,700 cycles.

Profiling on the other machines

The same three needs (whole run, one kernel, what each core does) exist everywhere; the tools differ because the other machines are real hardware with clocks that drift and caches that warm up. Sources: tt-metalium Device Program Profiler, tt-metalium Tracy Profiler, Nsight Systems User Guide, Nsight Compute Profiling Guide. One difference matters most. A GPU or Tensix profiler measures real silicon with run-to-run variance from clocks, caches and scheduling, so you take medians over many runs. The Cerebras simulator is deterministic inside the kernel (the TSC never moved), but it is slow and small: the course simulated at most 16 PEs per run (Chapter 18).

Common pitfalls

  1. Reporting cycle_count as kernel time. In the worked example the kernel was 1.2 % of it. Time the kernel with the TSC, or difference two runs.
  2. Comparing totals from parallel or first runs. Five runs of one program gave 21,631 to 29,368 cycles Measured. Run one simulation at a time, and rerun alone before you chase a difference.
  3. Subtracting TSC values from two PEs. Use a round trip on one PE, or the SDK's sync and time_ref method with its 1-cycle-per-hop correction (2 on WSE-3).
  4. Calling enable_tsc() between stamps. It resets the counter to zero. Enable once, early.
  5. Decoding the stamp wrongly. Three u16 words, least significant first. In 16-bit copy mode each u16 arrives in its own u32 slot, so view the buffer as u16 before joining (memcpy_view).
  6. Forgetting the overhead. The 271 includes about 15 cycles that are not the 256 FMACS elements. For short regions, time an empty region and subtract it.
  7. Measuring an accidental layout. The same op took 527 or 271 cycles depending on one padding word. Pad and measure, and say which layout you timed.
  8. Tracing a big run. 318,240 lines for one PE and 256 elements. Shrink the problem first. Remember that task numbers differ by chip (T01 vs T22).
  9. Trusting "Stopped due to idleness". A deadlock ends the same way. A FATAL stop writes no sim_stats.json, and launch() returns even if the device never unblocks; the next memcpy then aborts with "could be a kernel stall" (notes 7, 21).
  10. Converting cycles to seconds without saying the clock. 850 MHz is the SDK's assumption, 1.1 GHz is the vendor's WSE-2 figure, and there is no published WSE-3 clock.

Check yourself

Your change makes cycle_count drop from 22,800 to 21,700. Did your kernel get faster?

You cannot tell. Reruns of an unchanged program moved by more than that. Read the TSC around the kernel (stable to the cycle), or run both versions alone and compare differences between two problem sizes.

PE (0,0) stamps 1,200 when it sends; PE (3,0) stamps 1,180 when it receives. What was the latency?

Unknown, and the negative value shows why: the two counters started at different times. Time a round trip on PE (0,0), or synchronise and subtract each PE's reference stamp as the SDK benchmarks do.

In the trace, consecutive FMACS Seq values are two cycles apart. What do you suspect, and how do you confirm it?

An operand bank collision: the op runs at half speed. Add one padding word between the arrays and look again; in our runs the spacing became one cycle and the TSC fell from 527 to 271.
