Systems: CS-3, MemoryX, SwarmX, CS-4

A WSE-3 wafer has 44 GB of on-chip SRAM Vendor. Frontier models need hundreds of gigabytes to terabytes. Cerebras crosses that gap in two opposite ways. For training it streams the weights through the wafer, one layer at a time. For inference it pins the weights onto several wafers and passes each token through them. (Neither has anything to do with the SDK's "streaming mode" from Chapter 7.)

  • Place CS-1 to CS-4, and the CS-5/CS-6 roadmap, on a timeline with the right numbers.

The system around the wafer

A CS-n is the system (power, cooling, I/O) built around one WSE-n wafer. CS-4 breaks the pattern: it is a rack holding three WSE-3T wafers, the higher-clocked WSE-3 variant from Chapter 2. Three execution modes run on these systems. Each one is a different answer to the 44 GB limit.

Training: weight streaming

A training step in one paragraph (for readers from HPC rather than ML) In the forward pass a batch of inputs goes through the layers in order; each layer multiplies its input activations by its weight matrix, and its output activations are the next layer's input. The last layer's output is compared with the right answer to give one number, the loss. The backward pass runs the layers in reverse and uses the chain rule to get the gradient of the loss with respect to every weight (and, on the way, with respect to every layer's input activations). Each backward layer needs the activations its forward pass produced, which is why they are stored. Finally an optimizer step nudges every weight against its gradient. Repeat for the next batch.

From 2021, Cerebras trains large models by weight streaming. The activations stay on the wafer. The weights live off the wafer in MemoryX, a DRAM-plus-flash service that also performs the weight update. The whole wafer computes one layer at a time. SwarmX "handles the broadcast of weights from MemoryX to the entire cluster and effectively reduces (sums) gradients in the opposite direction" Vendor. The training docs put it in one line: "The compiler maps one kernel (layer) at a time onto the entire WSE, first for the forward pass and then for the backward pass" Vendor.

Systems

One training step on a weight-streaming cluster Vendor (white paper and training docs):

  1. The batch is cut into equal shards, one per system. "This technique is known as data parallelism." The shard is layer 1's input.
  2. Forward pass. MemoryX streams layer 1's weights, and SwarmX broadcasts one copy to every wafer. Each wafer computes layer 1's activations and keeps them in SRAM. Then layer 2's weights arrive, and so on. MemoryX starts sending layer k+1 before layer k has finished, so the latency of the off-wafer trip is hidden.
  3. At the loss layer each wafer computes the loss delta, the gradient of the loss with respect to the last layer's output, which seeds the backward pass. SwarmX also sums the loss values and sends them to the user node, the host CPU server that runs the training script.
  4. Backward pass, last layer first. Each layer's weights are streamed again, now in transposed order (MemoryX keeps both views of one copy). Transposed because the forward pass computed Y = X·W, and the backward pass computes the input gradient dX = dY·Wᵀ; the weight gradient is dW = Xᵀ·dY, which needs the stored X. The wafer uses its stored activations to compute activation gradients and weight gradients. The weight gradients stream out in FP32, SwarmX sums them across wafers, and MemoryX applies the optimizer update as they arrive. The last layer's weights "can be retained to save time": the last layer of the forward pass is the first layer of the backward pass, so its weights are already on the wafer when the backward pass starts.
  5. The critical path is layer 1: its weights get their gradients last and are needed first in the next step. The wafer emits each layer's gradients in the same order the weights were sent, so updated weights can start streaming before layer 1's gradients are complete. The round trip "can be completely hidden when the compute time of the first layer is greater than the round-trip latency".
  6. At intervals, all weights are pulled from MemoryX to the user node as a checkpoint.

Per step, each parameter crosses the link twice inward as FP16 (forward and backward) and once outward as an FP32 gradient: "32 bits of data are sent in each direction per parameter" Vendor. The activations of every layer must stay on the wafer until the backward pass uses them, so wafer SRAM still limits the batch per wafer. It no longer limits the size of the model.

Do the stored activations fit? The sources do not say how. Take GPT-3 XL (hidden size H = 2,048, 24 layers; the Andromeda workload below) and a shard of 250,000 tokens, the "hundreds of thousands" the white paper describes in the next section. One layer's output alone is 2,048 × 2 B × 250,000 ≈ 1 GB, so 24 layer outputs are ≈ 25 GB of the 44 GB Derived. A transformer layer also produces wider intermediates (the feed-forward block is 4H wide, and attention adds Q, K, V and scores), so keeping every intermediate would need several times that and could not fit Derived. The usual ML answers are to store only layer-boundary tensors and recompute the rest in the backward pass, or to use smaller shards for wider models. The weight-streaming white paper and Hot Chips decks the course draws on do not say which Cerebras uses Unverified. Treat "hundreds of thousands of tokens per shard" and "every layer's activations stay on the wafer" as two vendor statements whose reconciliation is not published.

Why streaming does not starve the wafer

Chapter 7 left a puzzle: off-wafer data is slow, so keep the data that matters on the wafer (inference), or bring it in through dedicated hardware (MemoryX in training). Here is the dedicated hardware. The white paper says "The WSE-2's 1.2Tb/s of I/O bandwidth is used for receiving weights from and transmitting gradients back to the MemoryX service" Vendor, and HC2024 gives the same 1.2 Tb/s for CS-3 Vendor. That is 150 GB/s, about 10× the SDK host path of Chapter 7, but still about 140,000× less than the wafer's 21 PB/s of SRAM bandwidth Derived. It works because of Chapter 1's arithmetic intensity: in training, every weight that arrives is used once for every token in the wafer's shard. That reuse is physical, not a caching trick: as the next section shows, each weight packet is multicast down a column of cores that together hold every token's activations, so one arrival does one multiply-add per token.

Worked example: tokens per weight
  • Link: 1.2 Tb/s = 150 GB/s. At 2 bytes per FP16 weight, that is 75 billion weights per second into the wafer Derived.
  • Each arriving weight does one multiply-add (2 FLOP) per token in the shard. With T tokens per shard, that is 2T FLOP per weight, or about T FLOP per byte.
  • To keep a WSE-2 busy at its 7.5 PF FP16 dense peak (Hot Chips 2022 Vendor): 7.5×10¹⁵ ÷ (2 × 75×10⁹) ≈ 50,000 tokens per shard Derived, about 25 sequences of 2,048 tokens per wafer Derived. Below that the link is the bottleneck; above it, compute is.
  • This knee is Chapter 1's ridge point for the off-wafer link, in new units. Because a weight does about T FLOP per byte, "tokens per shard" is the arithmetic intensity, and the knee sits where it equals peak ÷ link bandwidth. Chapter 1's table gives the CS-3 off-wafer ridge as ≈ 100,000 FLOP/B; the widget below puts the WSE-3 knee at ≈ 104,000 tokens, the same number Derived.
  • The white paper says "batch shards typically contain hundreds of thousands of tokens" Vendor, comfortably past that knee.
  • Decode has T = 1 per sequence. The same link would then feed only 150 GFLOP/s, about 0.002% of the wafer Derived. That is why inference does the opposite.

Link-bound or compute-bound?

Weights arrive over the 1.2 Tb/s link; each one is reused for every token in the shard. The curve is utilisation = min(1, 2 × T × 75 G weights/s ÷ dense peak). It ignores the backward pass, which does twice the compute per weight and so is easier to feed. All outputs Derived.

A layer on the wafer

What does "the whole wafer computes one layer" mean at the level of the PEs from Chapters 3–6? Hot Chips 2022 and the white paper describe it Vendor. The activation tensor [B][S][H] is spread over the whole wafer, each core holding a tile: features H across the x axis, batch and sequence positions down y. Weights never get a home on the wafer: "No memory used for weights, not even stored temporarily." Instead each weight travels as a 32-bit fabric packet, "weight (16b) + index (16b)". It is multicast down the column of cores that holds the matching features, and its arrival triggers an FMAC against each core's local activations. That is one AXPY per weight, and exactly the data-triggered task of Chapter 5 and the DSD FMAC of Chapter 6. Then a PSUM command (a control wavelet) makes each row of cores ring-reduce its partial sums, and an FSUM command sends the final sum to the column that owns that output feature. Reductions overlap with the next weights. Zero weights are simply never sent, which is where Cerebras's "native unstructured sparsity" comes from (glossary).

Why a row reduction? Write the layer as Y = X·W, with X[j][k] the activation of token j, input feature k, and W[k][i] the weight from input feature k to output feature i. Weight W[k][i] goes to the column that holds input feature k; every core there adds W[k][i]·X[j][k] for each of its tokens j into a partial sum for output i. Output i needs the sum over all k, and the k's live in different columns, so its partial sums are spread across the whole row. That is why each row must ring-reduce (PSUM), and why FSUM must then deposit the total in output i's column: Y ends up laid out exactly like X, ready to be the next layer's input. In CSL terms, each piece is something Part II already showed, although Cerebras's own training kernels are not written by course readers and their code is not public: the column multicast is a color whose route has several outputs (Chapter 4); the FMAC on arrival is a data task, or an @fmach with a fabric-input DSD (Chapter 5, Chapter 6); PSUM and FSUM are control wavelets that change what the cores do next (Chapter 4). Lab 4 builds a 2-D GEMM from the same parts.

Which bytes cross the link? Three formats appear on this page. The vendor's "32 bits in each direction per parameter" counts 2 B per weight per crossing, twice: the dense case Vendor. On the wafer each weight travels as a 32-bit packet, 16-bit value plus 16-bit index; the index is the weight's position in its matrix row (MemoryX's table below calls it a "column index"), which tells the receiving cores which partial sum it feeds. For a sparse model, MemoryX keeps exactly that pair (FP16 value + 2-byte index) for each non-zero, which suggests each non-zero crosses the link as 4 B. If so, sparsity cuts link bytes only when more than half the weights are zero Derived. The sources do not say where the index is attached for dense weights, at MemoryX or at the wafer edge Unverified.

MemoryX: what it stores, and what it computes

The table needs one piece of ML vocabulary: mixed-precision training. The math on the wafer uses 16-bit copies of the weights, which halves traffic and doubles speed, but tiny updates would round away in 16 bits, so an FP32 master copy of every weight is kept and updated instead. The Adam optimizer, the common default, also keeps two running averages per weight (the "moments": a running mean of the gradient and of its square) and uses them to scale each update. Each of these is one more FP32 number per parameter.

Table Vendor. GPT-3 at 175B × 20 B = 3.5 TB, which is why the white paper sets a 4 TB minimum, and 120T × 20 B = 2.4 PB, the top of its range Derived. The CS-3 blog's 1,200 TB for "24 trillion parameters" implies 50 B per parameter, so the assumptions changed between eras Derived.

MemoryX uses "DRAM and flash storage in a hybrid fashion", and its storage and I/O "match or exceed the I/O bandwidth of a CS-2". It runs any optimizer, with a FLOP/s rate "three orders of magnitude greater than its I/O bandwidth" Vendor. Its compute never becomes the bottleneck, because the update costs O(P) work for P parameters, while the wafer's work grows as O(B·S·P) with batch and sequence. For the same reason one MemoryX can serve a cluster of any size Vendor.

SwarmX: a broadcast–reduce tree

SwarmX is built from broadcast–reduce nodes, each "containing a set of 100Gb/s network interfaces" and able to do one 1:4 or two 1:2 broadcast–reduce operations, with "enough compute to perform the floating-point gradient reductions at line-rate" Vendor. The nodes form a bidirectional tree. Node count grows linearly with the number of systems N, and latency grows as log N. Because gradients are summed on the way up, one copy of the gradient tensor crosses each link, the same as the weights going down. The white paper's summary: "From the perspective of the MemoryX service, the SwarmX fabric looks just like a single CS-2 and from the perspective of the CS-2, the SwarmX looks just like the MemoryX service" Vendor. So "the same mapping is used for every layer across all systems", and adding systems is pure data parallelism. No system ever holds part of the model, because only one layer has to fit at a time and any layer fits on any wafer. Cerebras chose this deliberately: mixing streaming with tensor parallelism (splitting one layer's matrices across devices) or pipeline parallelism (splitting the layers across devices) adds activation traffic, so it sets both to 1 (glossary: TP / PP / DP; GPUs need both, Chapter 17). It calls the result "linear scaling". The published evidence is Andromeda: 16 CS-2s gave 15.87× one CS-2's throughput on a GPT-3 XL genomics workload Vendor. That is one vendor workload at 16 systems, not a general proof.

Before weight streaming: layer-pipelined mode

CS-1 and the original CS-2 installation used layer-pipelined execution, for models "below 1 billion parameters, which can fit entirely in the on-chip memory" Vendor. All the layers are loaded onto the wafer at once. The compiler "maps each kernel/layer of the network onto a region (a rectangle)", connects the regions with on-wafer data paths, and sizes and places them "to optimize the throughput". Activations flow forward from region to region, and activation gradients flow back. Weights stay in their region and are updated on the wafer at the end of each backward step. After an initial fill latency, "all the layers of the network enter a steady state of active execution" Vendor. Keep this picture in mind: 2024 inference brings back the same spatial idea.

Inference: pin the weights, pass the tokens

Inference flips the trade. Decode uses each weight once per token per sequence (the T = 1 end of the widget above), so streaming weights in would leave the wafer idle. Instead the weights stay on the wafers (pinned-weight inference). Llama 3.1-70B (~140 GB at 16-bit Derived) went onto four CS-3s in August 2024, 20 layers each. Each layer gets a region of PEs holding its weights and its share of the KV cache, and only one 16 KB activation vector per token crosses each wafer boundary Vendor (Hot Chips 2024). This is the layer-pipelined idea of the previous section, brought back for decode.

CS-4 and the roadmap

CS-4 keeps the WSE-3 silicon but rebuilds everything around it. The mechanism behind its "2× faster" claim is mostly power: conversion moved next to the wafer allows "twice as much power to the WSE-3 Turbo, enabling higher operating frequencies and faster token generation" Vendor. "WSE-3 Turbo" is the vendor's name for the WSE-3T of Chapter 2, so Cerebras itself attributes the speed-up to clock. It publishes no clock figure; press estimates are ~1.4 GHz for WSE-3 and ~2.8 GHz for WSE-3T Analyst Unverified (The Next Platform), against the 850 MHz the SDK benchmarks assume SDK.

CS-5, targeted for 2027, pairs Nexus with a next-generation WSE. Cerebras targets up to 10,000 output tok/s per user on gpt-oss-120b and Gemma 4 31B, up to 5,000 tok/s per user and 3 million tok/s per megawatt on multi-trillion-parameter models, and support for "models with more than 50 trillion parameters" Vendor. CS-6 integrates "wafer-scale SRAM and compute with 3D-stacked DRAM through ultra-high-bandwidth connections" Vendor. As ServeTheHome puts it, "Cerebras will be employing DRAM for the first time" Press. That is a direct attack on the capacity limit this whole chapter works around.

Where this sits for a CSL programmer Weight streaming and multi-wafer inference are run by Cerebras's machine-learning stack, not by programs you write with the SDK. That stack extracts the model graph (TensorFlow via XLA in the 2020 slides, PyTorch today), lowers it to LAIR, matches it to a library of hand-written kernels, sizes and places each kernel as a rectangle of PEs, routes them and links an executable (ISPD 2020 slides Vendor). For weight streaming it maps one layer at a time onto the whole wafer and runs the same mapping on every system. Chapter 9 walks through that compile path and the inference side. The CSL SDK that Part III teaches is a separate, lower-level path for custom kernels on one wafer (or the simulator), where you place the rectangles yourself, and its host path is the memcpy runtime of Chapter 7. The labs in Chapters 11–15 build the pieces such a mapping needs: data-triggered FMACs, broadcast along rows and columns, reductions and a 2-D GEMM.

Check yourself

Why does weight streaming suit training but not low-latency inference?

In training, each weight arriving over the 1.2 Tb/s link is reused for every token in the shard; past about 50,000 tokens per shard a WSE-2 is compute-bound Derived. Decode uses each weight for only one token per sequence, so every token would wait on weights arriving over the off-wafer links (~150 GB/s per CS-3 wafer, about 1/20 of one H100's 3.35 TB/s HBM) Derived. Pinning weights in 21 PB/s SRAM avoids that.

How many times does each weight cross the MemoryX link in one training step, and in what format?

Twice inward as FP16 (forward pass, then backward pass in transposed order) and once outward as an FP32 gradient, which SwarmX sums across systems before MemoryX applies the update. That is 32 bits in each direction per parameter Vendor.

Inference keeps weights pinned, and training streams them. Which one is limited by how many wafers you own, and why?

Inference: all weights (plus KV cache) must fit in the SRAM of the wafers serving the model, so Llama 70B at 16-bit needs four CS-3s. Training only needs one layer to fit at a time; MemoryX holds the rest, so adding systems adds data parallelism, not capacity.

A CS-4 rack has three 44 GB wafers. Can it hold Llama 70B at 16-bit with weights pinned?

No: 3 × 44 = 132 GB < 140 GB before any KV cache. At 8-bit (70 GB) it fits, with about 62 GB to spare Derived.
