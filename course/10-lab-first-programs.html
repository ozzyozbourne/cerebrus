Lab 1: SAXPY and wavelet tasks

Two single-PE programs. The first uses the host-driven style: copy data in, call a function, copy results out. The second uses the dataflow style: the host streams values, and each arriving wavelet runs a task. Both were compiled and run on the SDK 2.10.1 simulator for WSE-3 and WSE-2 Measured; the code below is the exact validated source. Then we look inside both runs, cycle by cycle.

After this lab you can

  • Write, compile and validate a complete single-PE program, and read its output.
  • Say where the simulated cycles of a run go, and time a kernel on the PE itself.
  • Bind a data task to a streaming input on both WSE-2 and WSE-3.
  • Produce, spot and fix the race between streaming input and result readback.

Program 01 · SAXPY: y ← a·x + y

The layout places one PE, exports two arrays and one function. Because the function takes an argument, its exported type is fn(f32)void. Chapter 9 walks through these three files line by line; here we build them, run them and look inside.

First the build-and-run script. The flags were explained in Chapter 9: an 8 × 3 fabric leaves room for memcpy's columns west and east of your code, and your 1 × 1 rectangle sits at offset (4,1), so your PE appears as P4.1 in traces. --params=N:64 sets the compile-time vector length; --memcpy --channels 1 adds the host-transfer framework (Chapter 7).

course/programs/01-saxpy/commands.sh
#!/usr/bin/env bash
set -e
cslc --arch=${ARCH:-wse3} ./layout.csl --fabric-dims=8,3 --fabric-offsets=4,1 --params=N:64 -o out --memcpy --channels 1
cs_python run.py --name out
course/programs/01-saxpy/layout.csl
// 01-saxpy: y = a*x + y on a single PE.
// Teaches: layout block, memcpy params, exported symbols, host-callable RPC.
param N: i16;      // vector length (compile-time)

const memcpy = @import_module("<memcpy/get_params>", .{ .width = 1, .height = 1 });

layout {
  @set_rectangle(1, 1);                         // 1 column x 1 row of PEs
  @set_tile_code(0, 0, "pe_program.csl", .{ .memcpy_params = memcpy.get_params(0), .N = N });

  @export_name("x", [*]f32, true);              // host may write and read
  @export_name("y", [*]f32, true);
  @export_name("saxpy", fn(f32)void);           // RPC taking the scalar a
}
course/programs/01-saxpy/pe_program.csl
param memcpy_params;
param N: i16;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// Both vectors live in this PE's 48 KB SRAM. There is no other memory.
var x: [N]f32;
var y: [N]f32;
var x_ptr: [*]f32 = &x;
var y_ptr: [*]f32 = &y;

// A DSD is a hardware loop descriptor: base address + length (+ stride).
const x_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> y[i] });

fn saxpy(a: f32) void {
  // One instruction walks all N elements: y[i] = y[i] + x[i] * a
  @fmacs(y_dsd, y_dsd, x_dsd, a);
  // Tell memcpy this RPC is finished so the host's next command can run.
  sys_mod.unblock_cmd_stream();
}

comptime {
  @export_symbol(x_ptr, "x");
  @export_symbol(y_ptr, "y");
  @export_symbol(saxpy);
}
course/programs/01-saxpy/run.py
#!/usr/bin/env cs_python
import argparse, json
import numpy as np
from cerebras.sdk.runtime.sdkruntimepybind import SdkRuntime, MemcpyDataType, MemcpyOrder  # pylint: disable=no-name-in-module

p = argparse.ArgumentParser(); p.add_argument('--name'); p.add_argument('--cmaddr')
args = p.parse_args()
N = int(json.load(open(f"{args.name}/out.json"))['params']['N'])

rng = np.random.default_rng(0)
x = rng.standard_normal(N).astype(np.float32)
y = rng.standard_normal(N).astype(np.float32)
a = np.float32(2.5)

rt = SdkRuntime(args.name, cmaddr=args.cmaddr)
xs, ys = rt.get_id('x'), rt.get_id('y')
rt.load(); rt.run()
kw = dict(streaming=False, order=MemcpyOrder.ROW_MAJOR, data_type=MemcpyDataType.MEMCPY_32BIT, nonblock=False)
rt.memcpy_h2d(xs, x, 0, 0, 1, 1, N, **kw)        # (x0, y0, width, height, elems per PE)
rt.memcpy_h2d(ys, y, 0, 0, 1, 1, N, **kw)
rt.launch('saxpy', a, nonblock=False)
out = np.zeros(N, dtype=np.float32)
rt.memcpy_d2h(out, ys, 0, 0, 1, 1, N, **kw)
rt.stop()

np.testing.assert_allclose(out, a * x + y, rtol=1e-6, atol=1e-6)
print("first 4:", out[:4], " expected:", (a * x + y)[:4])
print("SUCCESS!")

The device computes y + x·a with a fused multiply-add: one rounding at the end. numpy rounds the product first, then the sum. Over all 64 elements, 17 differ from numpy in the last bit and all 64 match a one-rounding FMA (float32(float64(x)*2.5 + float64(y))) exactly Measured. The test tolerates this with assert_allclose(…, rtol=1e-6, atol=1e-6): relative plus absolute tolerance, so elements near 0 are judged by the absolute term.

What happens inside, in order

Every host call becomes a command on color 22, memcpy's command color SDK 2.10.1, memcpy/sys_params.csl. The memcpy module compiled into your PE (sys_mod) decodes it: write SRAM, run your RPC, or read SRAM. The cycle stamps below come from the simulator's instruction trace of this exact run (WSE-3, N = 64) Measured; how to get that trace is shown further down.

Three things the trace shows that the code alone does not:

  • "Blocked" is literal. When the RPC command arrives, memcpy's f_rpc executes a BLK instruction on its own command task (cycle 3,089); later command wavelets wait in input queue 1 until your unblock_cmd_stream() executes UBLK (cycle 3,251) SDK 2.10.1, memcpy/wse3/sys.csl Measured. launch() itself returns to Python without waiting for that; it is the next command that cannot run until the unblock.
  • The scalar travels as two 16-bit pushes. The RPC command carries a wavelet count, a split into two u16 halves, and the function id 3 from out_rpc.json. memcpy pushes them onto a small u16 stack and dispatches on the id SDK 2.10.1, memcpy/wse3/memcpy.csl.
  • D2H is the slow part. In copy mode each PE sends one element, then a control wavelet that advances a switch so the PEs of a row take turns SDK 2.10.1, memcpy/wse3/memcpyd2h.csl. That is a 35-cycle data task (T21) and a 21-cycle control task (T30) per element: about 60 cycles per element out, against a few per element in.

So the @fmacs is about 130 cycles of 7,740, under 2% Measured, and copying y back costs more than everything else together. Lab 3 separates kernel time from host I/O a different way: run the same program with 0 and 100 kernel iterations and subtract, so the host transfers cancel.

Fit: WSE-3 ≈ 3,640 + 64·N, WSE-2 ≈ 3,060 + 59·N Derived. The slope is the cost of moving one element in, in, and out (about 2 + 2 + 60 cycles); the compute is 2 of those 64 cycles. WSE-3 is not faster here: these runs are bound by memcpy and by f32, and WSE-3's gains are in f16 (next section). At the 850 MHz the SDK's benchmarks assume SDK 2.10.1, bandwidth-test, 7,740 cycles is about 9.1 µs of device time Derived; the simulator needs 10–30 s of wall time for it.

Cycle totals are approximate

cycle_count includes time the device spent waiting for the host, so it depends on how busy your machine is. Program 01 reran at 7,738–7,740 on an idle machine, but gave 16,940 once while other simulations were running; program 02 varies by a few hundred cycles even when idle (7,021–7,543) Measured. On a heavily loaded machine a correct program can even abort with "could be a kernel stall"; we saw this in 3 of 28 runs made two or three at a time. Run one simulation at a time when you compare totals, rerun alone before debugging a stall, and time device code with the timestamp counter instead: its numbers did not change between runs.

Measure the kernel itself: f32 vs f16, WSE-2 vs WSE-3

The standard SDK idiom (topic-02, bandwidth-test) reads the PE's 48-bit timestamp counter just before and after the code you care about. The SDK explains why this beats host-side timing: "the runtime may not send the command right after the user issues it" SDK 2.10.1, bandwidth-test README. The variant in 01-saxpy/timed/ does this around the single DSD op, and can switch to f16 (@fmach) and insert padding between x and y:

course/programs/01-saxpy/timed/pe_program.csl
param memcpy_params;
param N: i16;
param HALF: i16;
param PAD: i16;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);
const tsc = @import_module("<time>");          // the PE's 48-bit timestamp counter
const T: type = if (HALF != 0) f16 else f32;

// x and y are contiguous; PAD extra words at the end of x shift where y starts.
var x: [N + PAD]T;
var y: [N]T;
var x_ptr: [*]T = &x;
var y_ptr: [*]T = &y;
const x_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd, .{ .tensor_access = |i|{N} -> y[i] });

var ts = @zeros([6]u16);                       // [t0 (3 x u16), t1 (3 x u16)]
const ts_ptr: [*]u16 = &ts;
var t0 = @zeros([3]u16);
var t1 = @zeros([3]u16);

fn saxpy(a: f32) void {
  tsc.enable_tsc();
  tsc.get_timestamp(&t0);
  if (HALF != 0) { @fmach(y_dsd, y_dsd, x_dsd, @as(f16, a)); }
  else           { @fmacs(y_dsd, y_dsd, x_dsd, a); }
  tsc.get_timestamp(&t1);
  for (@range(i16, 3)) |i| { ts[i] = t0[i]; ts[3 + i] = t1[i]; }
  sys_mod.unblock_cmd_stream();
}

comptime {
  @export_symbol(x_ptr, "x");
  @export_symbol(y_ptr, "y");
  @export_symbol(ts_ptr, "ts");
  @export_symbol(saxpy);
}

  • f32: one element per cycle on both chips, unless the operands collide. As shipped, program 01's @fmacs runs at 2 cycles per element on WSE-3 (and on WSE-2 from N = 1,024). One padding word between x and y (PAD 1) brings it to 1 cycle per element everywhere. SRAM is split into single-ported banks interleaved by word Vendor; an in-place FMAC needs a y word and an x word every cycle, and at some address offsets both fall in the same bank. Chapter 6 measures the same doubling. The exact rule is not documented: treat "pad and measure" as the method Measured.
  • f16: 4 per cycle on WSE-3, 2 on WSE-2 for this op Measured. WSE-3 doubles f16 throughput and leaves f32 unchanged, which agrees with the vendor's "FP16 SIMD doubled" Vendor. It is half the quoted 8-wide f16 SIMD, because each element of an in-place op needs two reads and a write; the width is a ceiling, not a rate.
  • About 15 cycles of start-up per op; at N = 64 that dominates the f16 numbers.

A small helper groups the trace into runs of one task. It is how every cycle stamp on this page was produced:

course/programs/01-saxpy/trace_tasks.py
#!/usr/bin/env python3
"""Group the simulator's instruction trace into runs of one task on one PE.

Run the program with the trace on:
    SINGULARITYENV_SIMFABRIC_DEBUG=inst_trace cs_python run.py --name out
then:
    python3 trace_tasks.py sim.log P4.1        # P4.1 = your PE at fabric offset (4,1)
Each output line is one run of consecutive instructions from one task:
    task  first-last cycle  (length, instructions)  notable opcodes
"""
import re, sys

NOTABLE = ("FMAC", "FMUL", "FADD", "FMOV", "MOV32", "BLK", "UBLK", "ACTVT", "OQ")
log, pe = sys.argv[1], sys.argv[2]
pat = re.compile(r"^@(\d+) " + re.escape(pe) + r": .*\[EX OP\] . 0x[0-9a-f]+: (T\d+)\s+(?:\S+\?\s+)?(\S+)")
runs = []                                   # [task, first, last, count, opcodes]
for line in open(log, errors="replace"):
    m = pat.match(line)
    if not m:
        continue
    cyc, task, op = int(m.group(1)), m.group(2), m.group(3)
    if runs and runs[-1][0] == task and cyc - runs[-1][2] < 40:
        r = runs[-1]; r[2] = cyc; r[3] += 1; r[4].add(op)
    else:
        runs.append([task, cyc, cyc, 1, {op}])
for task, a, b, n, ops in runs:
    key = " ".join(sorted(o for o in ops if o.startswith(NOTABLE)))
    print(f"{task:4} {a:6}-{b:<6} ({b - a + 1:5} cyc, {n:4} instr) {key}")
task id in the tracewhat it is SDK 2.10.1, memcpy/sys_params.csl Measured
T01memcpy's command task (input queue 1, color 22); your RPC runs inside it
T02your data task in program 02 (WSE-3: bound to input queue 2)
T21 / T30D2H data send / control wavelet that advances the switch
T27H2D finished: unblock the command stream

Exercises

Do these in ~/lab1/01-saxpy, not in course/programs.

  1. Change N:64 to N:4096 in commands.sh. Does it still fit in the PE's 48 KB SDK 2.10.1? Then try N:6000. Predict first: two arrays of 4·N bytes, plus memcpy's code and tables.
    Check

    N = 4096 (32 KB of arrays) compiles and passes in about 266,000 cycles: 64× the elements for 34× the cycles, because the fixed I/O cost is amortized. N = 6000 needs 48,000 bytes for the arrays alone; the linker stops with ld.lld: error: ran out of PE memory for data (section .bss) (and "for task table"). The largest N that links is 5,615 on WSE-3 (44,920 bytes of arrays) and 5,784 on WSE-2 Measured, matching the course's estimate of about 44 KB usable for user arrays on WSE-3 after memcpy's fixed overhead.

  2. Add a second RPC scale(b: f32) that computes y ← b·y with @fmuls, and call it from the host after saxpy.
    Hint and check

    Layout: @export_name("scale", fn(f32)void);. Device: fn scale(b: f32) void { @fmuls(y_dsd, y_dsd, b); sys_mod.unblock_cmd_stream(); } and @export_symbol(scale); in the comptime block. Host: rt.launch('scale', np.float32(0.5), nonblock=False) before the D2H, and assert against 0.5 * (a*x + y). This passes on both chips Measured. Look in out/bin/out_rpc.json: what id did scale get?

  3. Remove sys_mod.unblock_cmd_stream() and run again. Predict first: what does launch() do, and what does the next call (memcpy_d2h) do?
    What we saw

    launch() returns normally. The memcpy_d2h command then waits behind the blocked stream; the simulator stops when the fabric goes idle, and about 4 s later cs_python aborts (exit code 134) with terminate called after throwing an instance of 'std::runtime_error' what(): the received length (0 bytes) is not expected (256 bytes), could be a kernel stall. No sim_stats.json is written Measured. Memorise that message: it almost always means some RPC never unblocked the command stream (Chapter 7), or a barrier never released. On hardware, expect a hang instead. Put the line back.

  4. Time the kernel yourself: in a copy of 01-saxpy/timed, predict the f16 TSC count at N = 2048 on WSE-3 and on WSE-2, then run bash commands.sh 2048 1 0 with each ARCH.
    Check

    From the table: about 15 + 0.25·2048 ≈ 530 cycles on WSE-3 and 15 + 0.5·2048 ≈ 1,040 on WSE-2 Derived. If yours is far off, check that you really built with HALF:1 (the output line says f16 @fmach).

  5. With the instruction trace on, find the cycles at which your @fmacs starts and ends (Seq: 0 and Seq: 63). How many cycles per element? Now set PAD:1 in the timed variant and look again.
    Check

    Unpadded on WSE-3: 3,124 to 3,250, so 2 cycles per element (the Seq numbers advance every second cycle). With one pad word, consecutive Seq values are one cycle apart Measured.

Program 02 · A task per wavelet

Now the host does not write into an array. It streams: each of the N values becomes one 32-bit wavelet sent on a memcpy color. On the PE, that color is bound to input queue 2 and the queue is bound to a data task, so each arriving value runs on_value() once, with the value as its argument.

The script has one extra parameter: --params=MEMCPYH2D_DATA_1_ID:0 picks color 0 for the stream. run.py reads the same value back from out/out.json, so host and device agree.

course/programs/02-wavelet-tasks/commands.sh
#!/usr/bin/env bash
set -e
cslc --arch=${ARCH:-wse3} ./layout.csl --fabric-dims=8,3 --fabric-offsets=4,1 \
  --params=N:100 --params=MEMCPYH2D_DATA_1_ID:0 -o out --memcpy --channels 1
cs_python run.py --name out
course/programs/02-wavelet-tasks/layout.csl
// 02-wavelet-tasks: the host streams N numbers into one PE. Every arriving
// 32-bit wavelet triggers a *data task* that updates running statistics.
// Teaches: streaming memcpy, input queues, data tasks (wavelet-triggered tasks).
param N: i16;
param MEMCPYH2D_DATA_1_ID: i16;    // which color memcpy uses for our stream

const memcpy = @import_module("<memcpy/get_params>", .{
  .width = 1, .height = 1, .MEMCPYH2D_1 = MEMCPYH2D_DATA_1_ID });

layout {
  @set_rectangle(1, 1);
  @set_tile_code(0, 0, "pe_program.csl", .{ .memcpy_params = memcpy.get_params(0), .N = N });
  @export_name("stats", [*]f32, false);      // false = host may read but not write
  @export_name("count", [*]u32, false);
  @export_name("wait_done", fn()void);   // barrier RPC
}
course/programs/02-wavelet-tasks/pe_program.csl
param memcpy_params;
param N: i16;

const sys_mod = @import_module("<memcpy/memcpy>", memcpy_params);

// stats = [sum, sum of squares, max, min]
var stats = [4]f32 { 0.0, 0.0, -1.0e30, 1.0e30 };
var count = [1]u32 { 0 };
const stats_ptr: [*]f32 = &stats;
const count_ptr: [*]u32 = &count;
var host_waiting: bool = false;   // set by wait_done() if it runs before the last task

// The color memcpy streams on is chosen by the host side (a param).
const h2d_color: color = @get_color(@bitcast(u16, sys_mod.MEMCPYH2D_1));
// On WSE-3 a wavelet lands in an *input queue*; the data task is bound to the queue.
// (Queues 0 and 1 are reserved by memcpy on WSE-3, so we use 2.)
const h2d_iq: input_queue = @get_input_queue(2);
const recv_task_id: data_task_id =
  if (@is_arch("wse2")) @get_data_task_id(h2d_color)   // WSE-2: task ID == color
  else @get_data_task_id(h2d_iq);                      // WSE-3: task ID == input queue

// Runs once per wavelet; the 32-bit payload arrives as the argument.
task on_value(v: f32) void {
  stats[0] += v;
  stats[1] += v * v;
  if (v > stats[2]) stats[2] = v;
  if (v < stats[3]) stats[3] = v;
  count[0] += 1;
  // Last value processed: if the host is waiting in wait_done(), release it.
  if (count[0] == @as(u32, N) and host_waiting) sys_mod.unblock_cmd_stream();
}

// RPC the host calls after streaming. A streaming memcpy_h2d "completes" as
// soon as all wavelets are injected -- NOT when the data tasks have consumed
// them. Without this barrier the host reads half-finished statistics.
fn wait_done() void {
  if (count[0] == @as(u32, N)) {
    sys_mod.unblock_cmd_stream();     // all done already
  } else {
    host_waiting = true;              // leave the command stream blocked;
  }                                   // on_value() unblocks it later
}

comptime {
  @bind_data_task(on_value, recv_task_id);
  // WSE-3 only: connect the color to input queue 2 (WSE-2 binds the color directly).
  if (@is_arch("wse3")) @initialize_queue(h2d_iq, .{ .color = h2d_color });
  @export_symbol(stats_ptr, "stats");
  @export_symbol(count_ptr, "count");
  @export_symbol(wait_done);
}

Reading program 02

  • Color. memcpy owns the stream's color; the host chose its number (0) with a compile parameter, and @get_color(@bitcast(u16, sys_mod.MEMCPYH2D_1)) turns it into a color value.
  • Queue. On WSE-3 a color reaches the core only through an input queue; @initialize_queue(h2d_iq, .{ .color = h2d_color }) connects them. Queue 2, because memcpy uses queues 0 and 1 on WSE-3 (Chapter 7). On WSE-2 the call is skipped (if (@is_arch("wse3")), as in SDK topic-03) because there the task binds to the color directly.
  • Task ID. A task is a hardware entry point, not a function you call. @bind_data_task attaches it to an ID: the color on WSE-2, the input queue on WSE-3 (Chapter 5). @is_arch is evaluated at compile time, so each binary contains only one branch. If you add your own local tasks, use IDs 8–20; never bind task 29, which memcpy uses for teardown.
  • Exports. stats and count are exported with mutability false: the host may read but not write them ("immutable": 1 in out_rpc.json). Program 01's arrays use true because the host writes them. Here the device-side pointers are also declared const. Chapter 9 tells how we got this wrong once.
  • The barrier flag. host_waiting records that wait_done() ran before the last task, so that task knows it must release the host.
  • Initial values. max starts at −1e30 and min at +1e30, so the first value replaces both.

The bug, and the debugging method

Chapter 7's widget animates this race; here is how it was found. The first version had no wait_done. All 100 tasks fired and max/min were right, but the sum was 30.818 instead of 26.138 Measured. Steps taken:

  1. Copied the program to a scratch directory, added an exported seen[N] array, and recorded each received value: all 100 matched the input exactly, so the transport was fine.
  2. Recorded the running sum after each task instead: every partial sum matched numpy.cumsum. So the device computed the right answer.
  3. Searched the host-side cumulative sums for 30.818176: it is exactly the sum after 95 values.

Conclusion: the host read stats before the last five tasks ran. A streaming H2D completes when all wavelets have been sent, not when they have been consumed. wait_done() keeps the command stream blocked until on_value() sees the last value. Validated afterwards at N = 100 and N = 500, on WSE-3 and WSE-2 Measured.

The instruction trace shows exactly where the host got ahead. Scrub through both runs below; the task start times are the measured ones from sim.log (WSE-3, N = 100).

Wavelets in, tasks run, host reads

Drag the cycle slider or press Play. Toggle the barrier to compare the two measured runs. Every tick on the middle track is one on_value() starting.

  • Tasks start at cycle 1,329 and take about 40 cycles each (about 21 instructions; the rest is task entry and exit) Measured. memcpy delivers faster than that, so a backlog builds in the queues: the core runs one task at a time.
  • The streaming H2D is "done" at cycle 4,709, when memcpy's T27 unblocks the command stream. Only 84 of 100 tasks have run; 16 values are still queued Measured.
  • Without the barrier, the D2H of stats needs about 830 cycles of command handling, so its first element (the sum) leaves at cycle 5,539, after 95 tasks. The D2H then sends one element at a time while tasks keep running: the sum of squares leaves after 96 tasks, which is why the failing row reads 3207.2998, the sum of 96 squares. One memcpy_d2h sampled four values at four different moments. count is read last, at cycle 7,777, so it shows 100: a correct-looking counter does not prove the result was read at the right time.
  • With the barrier, wait_done arrives at cycle 4,987 with 89 done and blocks; the 100th on_value starts at 5,421 and unblocks at 5,460; only then does the D2H start.

Why the barrier itself is race-free

The RPC wait_done() runs inside memcpy's command task; on_value() is another task. The core runs one task at a time, each to completion (Chapter 5), so the two can never interleave. Either all 100 values have been handled before wait_done runs (count is N: unblock at once), or wait_done finishes first and sets host_waiting, and the 100th on_value sees the flag and unblocks. There is no moment in between where a wavelet could slip past both checks. The two D2H commands queue behind the still-blocked command stream. The same argument is what you will use for the barriers in Labs 2 and 3.

Aside: receive the whole stream with one instruction (WSE-3, measured)

Instead of a task per wavelet, a fabric DSD can receive all N wavelets into SRAM with one asynchronous instruction: a local task runs @fmovs(buf_dsd, in_dsd, .{ .async = true, .activate = done_id }) with in_dsd a fabin_dsd of extent N on input queue 2, and the completion task done computes the statistics in a loop and unblocks the host as before. In a WSE-3 variant (by the depth reviewer), all 100 values were in SRAM by cycle ~1,500 (about 1.7 cycles per wavelet, against 40 for a task each), and total cycles fell from 7,020 to 6,289 at N = 100, from 24,960 to 19,148 at N = 500 and from 85,290 to 67,317 at N = 2,000 Measured. The trace also shows the cost of run-to-completion: the scalar loop in done() ran for ~3,000 cycles, and memcpy's H2D-complete unblock could not run until it finished. A WSE-2 port of this variant stalled and is not shown. Fabric DSDs and async operations are covered in Chapter 6 and used in Labs 2 and 3.

  2. With the barrier removed (as in "Produce the bug yourself"), try N = 100, 500 and 2000. Use numpy.cumsum to find how many values made it into stats[0]. Does the number of missing values change with N? Why might stats[1] include one more value than stats[0]?
    Check

    At every N the host's sum equals the partial sum after N − 5 values (95, 495, 1995), and stats[1] includes N − 4 Measured. The shortfall is set by how long the D2H command takes to start (fixed), not by N, so the fraction of missing values (5/N) shrinks as N grows: that is why this bug is easy to miss at large N. (The relative error of the sum itself jumps around, because the sum of uniform(−10, 10) values is close to zero.) stats[1] includes one more value because the D2H sends one element at a time while tasks keep running.

  3. Stream f16 pairs: change the task to task on_value(lo: f16, hi: f16) void and accumulate both halves (convert with @as(f32, lo)). On the host, pack two f16 into one u32 per wavelet, packed = data16.view(np.uint32) where data16 is an np.float16 array, and stream packed with MEMCPY_32BIT and N // 2 elements. Remember to wait for N/2 tasks, not N.
    Why not MEMCPY_16BIT, and check

    In streaming mode MEMCPY_16BIT puts one 16-bit value in each wavelet, with the upper half zero or an index (SDK topic-03), so a two-argument task would receive (value, 0) SDK 2.10.1. Packing on the host is what puts two halves in one wavelet, as SDK topic-04 does with (idx << 16) + val. Element 2k lands in lo, element 2k+1 in hi. With N = 100 our version fired 50 tasks and its statistics matched data16.astype(np.float32) within rtol=1e-4 (sum 26.157837) on both chips Measured.

  4. Stretch: add a delay loop (say 200 iterations) to on_value and rerun with the instruction trace on. Does the streaming H2D still complete at cycle ~4,709? How many tasks have run when it does?
    Hint

    The hardware queues hold only a few wavelets ("the program stalls when size exceeds 14", SDK pipeline-01) SDK 2.10.1. When they are full, memcpy cannot inject more, so H2D completion should move later. Use trace_tasks.py to find the T27 line. We have not measured this one: it is yours to find.

If it fails

Common failures and what they mean
  • cslc: command not found: run source /home/user/cerebras-sdk/env.sh in this shell.
  • cs_python errors in a directory under /tmp: work under your home directory instead.
  • ld.lld: error: ran out of PE memory for data (or "for task table"): your arrays plus memcpy's code and tables exceed the PE's memory; reduce N (exercise 1).
  • the received length (0 bytes) is not expected … could be a kernel stall: an RPC never called unblock_cmd_stream(), or a barrier never released. On a busy machine it can also be a host-side timeout; rerun alone before debugging.
  • AssertionError: Not equal to tolerance: compare with the expected output above; for streaming programs, suspect reading results too early.
  • Cycle counts that disagree with this page: see Cycle totals are approximate.
  • Under run_all.sh, read <program>/run.log. For a hang or stall, look at the end of sim.log and at sim_stop_cause in sim_stats.json (Chapter 9's debugging table).
  • Clutter: each run leaves out/, sim.log, sim_stats.json, simfab_traces/ and wio_flows_tmpdir.* behind. Delete them freely; commands.sh rebuilds everything.
