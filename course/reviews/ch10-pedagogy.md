# ch10 · pedagogy review

Summary: The chapter has two strong parts: the SAXPY sequence diagram, and the "bug and debugging method" callout, which shows real debugging step by step. The validated-source mechanism ({{code}}/{{out}}) is a good idea. But the lab is mostly "read code, run script". It never explains program 02's code and does not refer back to the line-by-line walkthrough of program 01 in ch09. Exercises have no expected answers, and two of them have problems: the f16 exercise is wrong as written, and the remove-unblock exercise describes behaviour that does not match what happens. The run instructions miss program 02, tell learners to edit the validated sources in place, and give no help when something fails. I ran every exercise in a scratch copy (SDK 2.10.1, WSE-3). The measured answers below can go straight into the page.

## Findings

### P3 [major] Program 02's code is shown but not explained, and nothing links to ch09's walkthrough of program 01
Location: Program 02, between `{{code:programs/02-wavelet-tasks/pe_program.csl}}` and the figure; program 01 intro paragraph.
Problem: Program 01 gets one sentence (on `fn(f32)void`). That is acceptable only because ch09 annotates it line by line, but ch10 never says so. Program 02 brings in at least seven new constructs that get no explanation here: `@get_color(@bitcast(u16, sys_mod.MEMCPYH2D_1))`; `input_queue`/`@get_input_queue(2)`; the `@is_arch` conditional for `data_task_id`; `task` vs `fn`; `@bind_data_task`/`@initialize_queue` in `comptime`; `@export_name(..., false)` vs `true` (ch09 says "we got this wrong once in program 02", but this chapter does not mention it); and `host_waiting`, which is used in `on_value` before its declaration.
Why it matters: The objective "Bind a data task to a streaming input on both WSE-2 and WSE-3" is met only if the learner understands the binding chain, not just copies it.
Concrete fix: (a) Change the program 01 intro to: "The layout places one PE, exports two arrays and one function. Because the function takes an argument, its exported type is <code>fn(f32)void</code>. Chapter 9 walks through these three files line by line; here we run them and look inside." (b) After program 02's pe_program block, insert:
> <h3>Reading program 02</h3><ul><li><b>Color.</b> memcpy owns the stream's color; the host chose its number (0) with a compile parameter, and <code>@get_color(@bitcast(u16, sys_mod.MEMCPYH2D_1))</code> turns it into a <code>color</code> value.</li><li><b>Queue.</b> On WSE-3 a color reaches the CE only through an input queue; <code>@initialize_queue(h2d_iq, .{ .color = h2d_color })</code> connects them. Queue 2 because memcpy owns 0 and 1 (Chapter 7).</li><li><b>Task ID.</b> A <code>task</code> is a hardware entry point, not a function you call. <code>@bind_data_task</code> attaches it to an ID: the color on WSE-2, the queue on WSE-3 (Chapter 5). <code>@is_arch</code> is evaluated at compile time, so each binary contains only one branch.</li><li><b>Exports.</b> <code>stats</code> and <code>count</code> are declared <code>const</code> pointers on the device, so the layout must export them with mutability <code>false</code>. A mismatch is a compile error.</li><li><b>Order.</b> <code>host_waiting</code> is declared after <code>on_value</code>; CSL resolves globals regardless of order.</li><li><b>Initial values.</b> max starts at −1e30 and min at +1e30 so the first value replaces both.</li></ul>

### P4 [major] Missing "what happens inside" for program 02: why wait_done and on_value cannot race
Location: After the bug callout's conclusion paragraph.
Problem: `wait_done()` reads `count[0]` and then sets `host_waiting`. `on_value()` reads `host_waiting`. A learner trained on CPUs will ask what happens if a wavelet arrives between those two lines. The answer is that tasks run to completion on the single CE, and the RPC itself runs inside memcpy's command task, so nothing can interleave. The page never says this. That is the core of why the barrier is correct. Program 02 also has no sequence diagram like program 01's, although its timing is the whole lesson.
Why it matters: Without it the fix looks like a lucky pattern, and learners cannot design their own barriers in Labs 2 and 3.
Concrete fix: Add after the callout:
> <h3>Why the barrier itself is race-free</h3><p>The RPC <code>wait_done()</code> runs inside memcpy's command task; <code>on_value()</code> is another task. The CE runs one task at a time, each to completion (Chapter 5). So either all 100 values have been handled before <code>wait_done</code> runs (count is N: unblock now), or <code>wait_done</code> finishes first and sets <code>host_waiting</code>, and the 100th <code>on_value</code> sees the flag and unblocks. There is no moment in between. The two D2H copies queue behind the still-blocked command stream.</p>
Optionally reuse the `#seq1` drawing code for a second sequence (`memcpy_h2d(stream)` → "100 wavelets injected · H2D done" → `launch('wait_done')` → "stream blocked" → `on_value ×100` → "100th: unblock" → `memcpy_d2h(stats)`).

### P5 [major] Exercise "Stream f16 pairs … send MEMCPY_16BIT data" is wrong as written
Location: Program 02 exercise 3.
Problem: In streaming mode with `MEMCPY_16BIT`, each wavelet carries **one** 16-bit value in its low half. The high half is zero or an index (see SDK `tutorials/topic-03-streaming-wavelet-data/run.py`, which uses `input_array_to_u32` and then reads only the low 16 bits). A two-argument data task therefore receives (value, 0-or-index), not a pair. To get pairs, pack two f16 into each u32 on the host and send `MEMCPY_32BIT`. The exercise also has no hint on host packing and no expected result.
Why it matters: A learner who follows the instructions gets wrong statistics and will think their binding is broken. The exercise cannot be tested.
Concrete fix: Replace with:
> <li>Stream f16 pairs: change the task to <code>task on_pair(lo: f16, hi: f16) void</code> and accumulate both. On the host, pack two f16 into one u32 per wavelet — <code>packed = np.frombuffer(data16.astype(np.float16).tobytes(), dtype=np.uint32)</code> — and stream <code>packed</code> with <code>MEMCPY_32BIT</code> (N/2 wavelets). <em>Do not</em> use <code>MEMCPY_16BIT</code> here: in streaming mode it puts one 16-bit value per wavelet, with the upper half zero or an index (SDK topic-03). Check: your sum should match <code>data16.astype(np.float16).astype(np.float32).sum()</code> within ~1e-2 relative; remember to wait for N/2 tasks, not N.</li>

### P6 [major] Exercise "Remove unblock_cmd_stream()" has no expected result, and the real behaviour differs from what ch07 leads learners to expect
Location: Program 01 exercise 3.
Problem: Ch07 says "the host hangs on its next call". In SDK 2.10.1 the simulator does not hang. About 4 s after start, `cs_python` aborts with `terminate called after throwing an instance of 'std::runtime_error'  what(): the received length (0 bytes) is not expected (256 bytes), could be a kernel stall`, and `sim.log` ends in `Caught signal 11` (measured, WSE-3). The learner is told to "note what the host does" but has nothing to compare against, and will meet this cryptic message again later in real bugs.
Why it matters: This is the most useful message to learn to recognise. The exercise should name it.
Concrete fix: Replace with:
> <li>Remove <code>sys_mod.unblock_cmd_stream()</code> and run again. Predict first: what should the host's next call (<code>memcpy_d2h</code>) do? <details><summary>What we saw</summary>On the simulator the host does not wait forever: after a few seconds <code>cs_python</code> aborts with <code>the received length (0 bytes) is not expected (256 bytes), could be a kernel stall</code>. Memorise that message — it almost always means some RPC never unblocked the command stream (Chapter 7). On hardware, expect a hang instead. Put the line back.</details></li>

### P7 [major] No expected answers or hints for the remaining exercises
Location: Program 01 exercises 1, 2; program 02 exercises 1, 2.
Problem: None of the exercises shows a result or a check. Exercise 1's parenthetical hints at the answer but is not one. The histogram exercise leaves out the f32→index conversion, the clamping, and how to verify. Exercise 2 ("Does the error grow or shrink?") has a clear measured answer the learner cannot confirm. Measured, WSE-3:
- N:4096 compiles and passes, 266,295 cycles. N:5500 still compiles. N:6000 fails at link: `ld.lld: error: ran out of PE memory for data (section .bss)` / `… for task table`.
- Without the barrier, at N = 100, 500 and 2000 the host's sum is **always the partial sum after N − 5 values** (95, 495, 1995). The absolute shortfall stays about the same while the relative error shrinks. `count` still reads N, because it is copied after `stats`, by which time the last tasks have run.
- The histogram works with `var hist = @zeros([10]u32);`, `var b: i16 = @as(i16, (v + 10.0) * 0.5);`, clamped to 0..9. It matches `np.histogram(data, bins=10, range=(-10,10))[0]` exactly (`[8 11 11 7 10 10 10 10 15 8]` at N = 100).
Why it matters: Without checks, "teach by doing" turns into "do and hope". A learner who gets a different result cannot tell a mistake from expected behaviour.
Concrete fix: Add a `<details><summary>Check</summary>…</details>` to each item, for example:
> Ex 1: "N:4096 still fits (32 KB of data) and passes in ~266k cycles — 34× the work for 34× the cycles, because host I/O dominates. N:6000 needs 48 000 bytes of arrays alone; the linker stops with <code>ran out of PE memory for data (section .bss)</code>. The largest N that links is between 5500 and 6000 — find it."
> Ex 2 (scale): "Add <code>@export_name("scale", fn(f32)void);</code> to the layout, <code>fn scale(b: f32) void { @fmuls(y_dsd, y_dsd, b); sys_mod.unblock_cmd_stream(); }</code> plus <code>@export_symbol(scale);</code>, call <code>rt.launch('scale', np.float32(b), nonblock=False)</code> before the D2H, and assert against <code>b*(a*x+y)</code>."
> Histogram: "Index with <code>var b: i16 = @as(i16, (v + 10.0) * 0.5);</code>, clamp to 0..9, export <code>hist</code> like <code>count</code>, read it back with one more <code>memcpy_d2h</code>, and compare with <code>np.histogram(data, bins=10, range=(-10, 10))[0]</code>; it must match exactly."
> Barrier removal: "At every N the host sum equals <code>np.cumsum(data)[N-6]</code>: exactly five values are always still in flight, so the absolute error stays bounded while the relative error shrinks — which is why the bug is easy to miss at large N. Note that <code>count</code> still reads N: it is copied after <code>stats</code>. A correct-looking counter does not prove the result was read at the right time."

### P10 [minor] Tolerance and rounding difference in program 02 not explained
Location: After `{{out:programs/02-wavelet-tasks/expected_output.txt}}`.
Problem: Program 01 explains its last-digit mismatch (FMA). Program 02 shows sum of squares 3302.5337 vs 3302.5327 and uses `rtol=1e-4` instead of 1e-6, with no reason given.
Why it matters: A learner adapting the test may tighten it and get confusing failures, or not realise that summation order matters.
Concrete fix: Add: `<p>The sum of squares differs in the 4th decimal: the device adds 100 values one after another in arrival order, while numpy sums pairwise, so the f32 rounding differs. That is why this test uses <code>rtol=1e-4</code>.</p>`
