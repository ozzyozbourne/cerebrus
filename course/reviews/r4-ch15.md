## Errors

**E1 (low). #allreduce, column-reduce item and the `#ar-svg` caption.** Quoted text: "Column reduce. The same, north to south, on the last column only" and "(2) the last column reduces north to south".
- In `lib/allreduce/pe.csl`, `f_state_entry` runs STATE_COL_REDUCE on every PE. `colReduce_configure()` (l. 860–877) sets the N→S routes by `first_py`/`last_py` only, never by `last_px`.
- So all W columns reduce in parallel. Only the last column's result is meaningful; the other bottom PEs sum stale values, and the broadcast then overwrites them.
- The cost is unchanged, because the columns run in parallel. Fix: "every column reduces north to south at once; only the last column's sum is used."

**E2 (low–med). #scaling, "What BLOCK costs".** Quoted text: "we have no measurement showing what the small block buys (it may let sends overlap the @fmacs on long columns)".
- The library code rules this out. In `wse3/pe.csl`, `compute_and_next_send_recv()` runs `laplacian_xy()` (synchronous @fmacs) only after the block's sends and receives have all finished (`count_send_recv ≥ 2`). `f_comm` starts the next block only after that.
- So no send overlaps an @fmacs. This matches Ch 13's table ("no overlap with compute") and the library's own TODO.
- Fix: delete the guess. Optionally add a better hypothesis, still unmeasured: small blocks keep each transfer within the queue depth (Ch 7: input queue 4 wavelets, output queue 2 on WSE-3).

**E3 (low). Profile, first bullet.** Quoted text: "7 multiply-adds on 5 cells is 35 flops".
- That is 35 multiply-adds, which is 70 flops (65 at the page's own 13 flops per cell, given in "How far from peak").
- Fix: "35 multiply-adds (about 70 flops)".

**E4 (low). Scaling-law callout.** Quoted text: "With four such crossings per call … a streaming chain would take roughly 40,000 cycles per iteration".
- Four streaming crossings at 8,700 each, times 2 calls, gives about 70,000. The figure of 40,000 only follows if the two broadcast crossings run at the hop floor: (2×8,700 + 2×1,900) × 2 ≈ 42,400.
- That assumption is defensible, because Ch 12 shows multicast forwarding is a pure router hop, but the page never states it.
- Fix: state the assumption, or give about 70,000 and "2.6–12×".

**E5 (low). Exercise 4 hint.** Quoted text: "Tasks 21–24 are out on every count … 24 is memcpy's SYS_EN_MAIN".
- Ch 5's own table says 24 is "probably needed only in some memcpy modes", and notes the WSE-2 25-point stencil binds task 24.
- Fix: soften to "21–23 are reserved, and 24 is SYS_EN_MAIN; avoid it (Ch 5)".

**E6 (low). Still open (from r2-ch15-fixlog).** The `pe_program.csl` header shown on the page says "One CG iteration is five phases". The prose says four phases plus a check.

## Explanation problems

**X1. #allreduce, row-reduce item: the switch mechanics are half told.**
- The page says the control wavelet flips "the next router" from position 0 to 1. In the source, `switch_cmd_11` carries two commands, and the routes use `ring_mode`. One command moves the sender's own router from pos1 (RAMP) back to pos0 (from the west); the other moves the next router to pos1.
- The page also never says that every PE's value is already waiting in its output queue, held back until its router's switch points at the RAMP. That is the mechanism behind "farthest first".
- Fix: add one sentence: "all PEs push at once; each value waits in its output queue until the control wavelet ahead of it turns its router to the RAMP, and the same wavelet sets the sender's router back to forwarding."

**X2. "Two loops, one program", last paragraph.** Quoted text: "That is why a single counter of finished operations is enough".
- The program has no such counter. It uses the `phase` variable, and each phase ends in exactly one callback. The phrase only makes sense against Lab 3's `pending` counter, which the paragraph does not name.
- Fix: "So one `phase` variable is enough, where Lab 3 needed a `pending` count of four transfers."

**X3. #profile, "Host loop or device loop".**
- The measured +1,224 cycles is spread over five commands, about 245 device cycles per command. The page never gives that figure. Without it the learner cannot connect the simulated gap to what one command costs on the device.
- Fix: add the figure, and link Ch 7's experiment box.

**X4. Convergence figure caption.** The caption says the bound limits the A-norm error, not the residual, but not how the two relate.
- Fix: one line: ‖r‖/‖b‖ ≤ κ·‖e‖_A/‖e₀‖_A in the worst case. So the residual curve can sit above the bound by up to a factor of κ, which is about 14 here.

## Connecting gaps

**G1 (high, effort S). Lab 4's composition → Lab 5's "Composing modules".**
- The page opens with "Labs 1–3 wrote every line … apart from memcpy", so composition looks new.
- But Ch 14 (Lab 4, the page just before) already:
  - composed memcpy with two `<collectives_2d>` instances;
  - kept a resource-map comment as "the budget sheet";
  - ran a five-step budget procedure (#budget);
  - explained teardown → task 29 → lock task → callback (Ch 14, "Inside <collectives_2d>").
- The allreduce here uses the same pattern: an FSM, `C_LOCK` blocked by the operation, activated by T29, then `f_callback`. Ch 15 re-explains it without linking back.
- Bridge: "Lab 4 shared one PE between memcpy and one library; here two libraries compete for the same slots." Link the allreduce's teardown/lock paragraph to Ch 14's six-step sequence, and say what is new here: one color reused across three stages, and an FSM that chains them.

**G2 (med, effort S). Lab 3's ≈14.6 cycles per message → this page's ≈65 cycles per stencil message (and 276 cycles per extra cell).**
- The page cites Lab 3's per-transfer cost and then measures a cost about 4× higher, with no reason given.
- The reason is in `wse3/pe.csl` (`f_send`/`f_recv`/`f_comm`): Lab 3 issued its four transfers concurrently, but the library does everything one step at a time:
  - the four sends run strictly one after another, on one microthread, each waiting for the previous to complete before a task issues the next;
  - the four receives are also taken one direction at a time, in fixed order;
  - each block adds about 11 task runs, 4 synchronous @fmacs starts, and a COMM task.
- Ch 13 also measured this library (Z = 200: 4,206 vs 8,078 cycles for 1 vs 10 blocks). Ch 15 never cites that result.
- Bridge: a short "anatomy of one block" list or timeline, a link to Ch 13's "How the SDK's stencils differ", and the note that the library serialises its sends for microthread safety, which Lab 3's hang taught (cross-chapter notes 1 and 11).

**G3 (med, effort S). Ch 6 operand-collision rule → the axpy costs in the Z table.**
- From the page's own table, three axpys cost about 5.9 cycles per extra cell at Z = 20 and about 5.7 at Z = 100, but about 3.6 at Z = 50. Mine: 441 at Z = 20, 408 at Z = 22.
- The arrays are `[MAX_ZDIM]f32`. When MAX_ZDIM is a multiple of 4, the vectors start at addresses equal mod 4, which is the condition that runs @fmacs at half speed (cross-chapter notes 22, 23, 29; Ch 6).
- The page passes over the axpy column silently. It even compares dots with "the three axpys (898)" at Z = 100, which is the slow, aligned case.
- Bridge: a sentence plus a pointer to Ch 6: "at Z = 100 the axpys run at about 2 cycles per element because the arrays line up mod 4; pad MAX_ZDIM to ≡ 2 mod 4 and they halve." This is Derived, plus my Z = 20/22 measurement.

**G4 (med, effort M). The CG algorithm → why it has two global sync points, and how Chronopoulos–Gear removes one.**
- The page states the recurrence but not the data dependence:
  - α needs ⟨p, Ap⟩, which exists only after the SpMV;
  - β needs ⟨r, r⟩ of the *updated* r, which exists only after α.
- So the two reductions cannot merge without rewriting. Exercise 3 and the pipelined-CG paragraph assume the learner sees this.
- Bridge: a three-line dependency chain (SpMV → η → α → r → ρ → β), and one sentence on how C-G gets η from a recurrence using w = A r.

**G5 (med, effort S). Library callback → why phase_done() activates a task instead of calling the next phase.**
- `f_callback` runs inside the library's own task (the allreduce's `f_state_entry` at STATE_DONE; the stencil's `f_comm`). Calling `update_p()` directly would start the next library operation, or recurse, from inside that task.
- `@activate(STATE)` returns first and lets the task picker start the next phase cleanly. This is the SDK's `kernel_cg.csl` pattern, but the page shows it without the reason.
- Bridge: one sentence. Also point pipelined CG's "phase_done() that waits for both" at Ch 14's two-bit join (`@block`/activate), which is exactly that mechanism.

**G6 (low, effort S). Allreduce "≈50 cycles per PE per call" → which work makes up the 50.**
- In the source, each contribution is a chain: the sender's async `@mov32` completes, the `f_send_ctrl` task runs, the control `@mov32` goes out, the next switch flips, and the last PE's async `@fadds` re-activates `f_send_data`.
- That is two or three task launches plus async-op starts. At Lab 3's ≈15 cycles per transfer plus task, it lands near 50.
- Bridge: annotate the `#ar-svg` bottom strip with this chain. Say it is an estimate, not a measurement.

**G7 (low, effort S). Ch 3 / cross-chapter note 13 memory budget → "≈37 KB of vectors after the code of three modules".**
- The page could close the loop: a minimal program leaves about 44.5 KB for arrays on WSE-3 (note 13). So the three modules' code, buffers and task table cost about 7–8 KB.
- That is a useful worked number for the "budget" outcome.

**G8 (low). Glossary links.** The page uses pencil, DSR, microthread, teardown, SpMV, RPC and `@map` but has no links to Appendix A. Ch 11–14 have none either, so this is course-wide.
