## Errors

**E1 (med): the f16 WSE-2 rate is a layout artefact, not a chip limit.** Location: `#kernel-time`, the table column "f16 WSE-2" and the bullet "f16: 4 per cycle on WSE-3, 2 on WSE-2 … WSE-3 doubles f16 throughput and leaves f32 unchanged, which agrees with the vendor's 'FP16 SIMD doubled'". The cycles-vs-N paragraph says the same: "WSE-3's gains are in f16 (next section)".
- **What is right:** with PAD = 0, x and y start in the same bank, and WSE-2's `@fmach` runs at 0.5 cycles per element. With PAD = 4 (sources 4 banks apart), WSE-2 takes 270 cycles at N = 1,024, against 272 on WSE-3. So both chips do about 4 elements per cycle on this op.
- **Evidence:** my rerun (270 vs 526 above). Appendix E issue 2 (`#iss-clash`) and CROSS_CHAPTER_NOTES 29 report the same numbers, so the page also contradicts Appendix E.
- **Fix:**
  - Add an "f16 WSE-2, PAD 4" column (4 elements per cycle).
  - Reword the bullet: "f16 runs at 4 per cycle on WSE-3 at every offset we tried; WSE-2 reaches the same 4 per cycle only when the sources start 4 banks apart, and 2 per cycle otherwise."
  - Drop "agrees with FP16 SIMD doubled" for this op. Ch 6's `@fmovh`/`@faddh` rows are the better evidence for a WSE-3 f16 gain.
  - Exercise 4 is fine as written, because it uses PAD 0. Add "(unpadded)" to it.

**E2 (low): the slope breakdown does not add up.** Location: the "Cycles versus N" paragraph: "The slope is the cost of moving one element in, in, and out (about 2 + 2 + 60 cycles); the compute is 2 of those 64 cycles."
- **The problem:** 2 + 2 + 60 already makes 64, so the 2 cycles of compute do not fit inside it. The same page also measures H2D at about 5 cycles per element (widget step 4: 1,128–1,469 for 64 values) and D2H at 35 + 21 = 56 cycles per element.
- **Fix:** "≈ 3 + 3 in, ≈ 56 out (T21 35 + T30 21), 2 compute ≈ 64 [Derived]". Alternatively, say the in-cost is ~5 per element at N = 64 and falls as N grows.

**E3 (low): start-up and timestamp overhead are counted twice.** Location: `#kernel-time`.
- **The problem:** the page says the TSC cycles include "about 10 cycles for the two timestamp reads". It then lists "About 15 cycles of start-up per op". The padded f32 run takes 1,039 cycles for 1,024 elements, so there are only ~15 extra cycles in total, timestamps included. Ch 6 measures 18 cycles for a 1-element `@fmacs`, also timestamps included.
- **Fix:** "about 15 cycles of fixed cost per measurement (op start-up plus the timestamp reads)". Exercise 4's "15 +" formula is then consistent.

**E4 (low): a provenance tag goes further than its source.** Location: the `#kernel-time` bullet "SRAM is split into single-ported banks interleaved by word [Vendor]".
- **The problem:** the vendor (HC22) says only "8 single-ported banks". The interleave granularity is not vendor-documented. Ch 6 says "interleaved by 32-bit word [Vendor]", while App E reads 16-bit banks from the cs_readelf man page.
- **Fix:** "8 single-ported banks [Vendor]; how addresses map to banks is undocumented (Appendix E, issue 2)". Ch 6 has the same mis-tag (cross-page item).

**E5 (low): the 48 KB tag.** Location: Exercise 1, "the PE's 48 KB [SDK 2.10.1]". Ch 3 and Ch 10 tag 48 KB as Vendor (HC24). Use Vendor.

## Connecting gaps

**G1 (med): "H2D done" and the constant N − 5 shortfall are not connected (effort S).**
- **What fails to connect:** the page says "16 values are still queued" when the H2D is done. Exercise 2's answer explains the constant N − 5 shortfall only by "how long the D2H command takes to start". The stretch hint quotes "queues hold only a few wavelets" as an unrelated idea.
- **What is missing:** the link is queue capacity. A streaming H2D completes when its last wavelet is pushed into memcpy's internal queues (pipeline-01 README: "H2D finishes when it pushes all data into the dedicated queues … stalls when size exceeds 14"). On WSE-3, `memcpy/wse3/memcpy.csl` gives the depths: input queues 0–1 hold 6 wavelets and 2–3 hold 4 [SDK].
- **Bridge:** "about 16 values can be in flight (IQ0 relay + IQ2 + router buffers). That number is fixed by hardware, and so is the ~830-cycle D2H decode, which lets ~11 of them drain. Fixed buffering minus fixed drain = a constant 5 missing at any N." Then make the stretch exercise the test of this model.

**G2 (med): "the core runs one task at a time" does not reach the measured task spacing (effort S).**
- **What fails to connect:** the page states "tasks take about 40 cycles each". In the widget's own data, the spacing grows to ~59 cycles after the H2D is done (4,712 → 4,771 → …). Without the barrier it grows to ~96 cycles during the D2H (5,502, 5,598, 5,694 …). The page never says why. A learner who uses 40 cycles per task predicts that all 100 tasks finish by ~5,300, before the 5,539 read, and so cannot reproduce the bug from the model.
- **What is missing:** memcpy's own command and D2H tasks (T01, T21 35 cycles, T30 21 cycles) run on the same CE and alternate with `on_value`. One element out (≈56 cycles) plus one task (≈40) is the ~96-cycle step. This is also why the single `memcpy_d2h` sampled `stats[0]` and `stats[1]` one task apart.
- **Bridge:** one bullet under the widget, plus a "memcpy task" tick colour on the middle track.

**G3 (med): the f16 result is not tied to the bank rule (effort S).**
- **What fails to connect:** the page teaches "pad and measure" for f32 but presents the f16 numbers as chip properties. That is the E1 issue seen as a gap.
- **Bridge:** state that the same placement rule applies to f16 and can reverse the chip comparison, and point to App E `#iss-clash`.

**G4 (low): the BLK instruction is not linked to Ch 5's task-state model (effort S).**
- **What fails to connect:** the page says "memcpy's f_rpc executes BLK on its own command task", and that later commands "wait in input queue 1". It never maps this onto Ch 5's two bits per task (activated, blocked).
- **Bridge:** "BLK sets the blocked bit of task 1 (the data task on IQ1, color 22). Command wavelets keep arriving but the picker skips T01; your UBLK clears the bit. This is Ch 5's `@block`/`@unblock`, done by memcpy."

**G5 (low): the cost of copying out has no "why" (effort S).**
- **What fails to connect:** "D2H is the slow part" (~56 cycles per element, 57% of the run) has no stated reason.
- **What is missing:** `memcpy/sys_params.csl` says "chunk: chunk size of round-robin, only support/test chunk = 1". The PEs of a row take turns one element at a time, so even a 1-PE copy pays a control wavelet per element.
- **Bridge:** cite that line. It also tells the learner why Lab 2's D2H cost scales the way it does.

**G6 (low): timestamp rules needed for Lab 2 are left out (effort S).**
- **What fails to connect:** the page introduces `tsc.enable_tsc()` and `get_timestamp` but does not say what `enable_tsc` does. CROSS_CHAPTER_NOTES 26 says it zeroes the counter.
- **What is missing:** the page also never says that stamps may only be subtracted on the same PE (CROSS_CHAPTER_NOTES 19/26). Lab 2 needs exactly this rule.
- **Bridge:** one sentence, plus a forward link to Ch 12.

**G7 (low): the WSE-3 relay path is not linked to Ch 4 routing (effort S).**
- **What fails to connect:** the figcaption says memcpy's microthread "re-emits each wavelet on MEMCPYH2D_1 into your queue" on the same PE. A learner fresh from Ch 4 will ask how a color sent by a PE reaches that same PE's input queue.
- **Bridge:** "memcpy configures this color's route to go back to the core (RAMP in → RAMP out) on your PE", with a link to Ch 4. Tag it SDK if the route can be confirmed in `memcpy/wse3/memcpy.csl`; otherwise tag it Derived.
