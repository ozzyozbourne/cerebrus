# R4 audit · ch07 Host I/O and memcpy (07-host-io.html)

**Verdict: Mostly correct. Explanation quality: good.** Almost every SDK claim checks out against the libraries and examples. The page has one stale cross-reference to Ch 13. Its correct `launch()` claim is contradicted by three later labs; I re-measured it. The main gaps are the D2H path, the CSL code the page uses before Ch 10 teaches it, and two device-side mechanisms that are stated but never shown.

## Errors

**E1 (med) · `#door`, warn callout "The simulator does not model this door".** Quoted text: "Lab 3 (Chapter 13) separates them from the kernel by running 0 and 100 timesteps and subtracting." This is stale. Ch 13 (src/13-lab-stencil.html, "Why not difference the simulator's total cycles?") now times the kernel with the TSC, using the slope between 10 and 100 steps. It explicitly rejects the 0-step baseline: "A 0-step baseline is worse still … varied by hundreds of cycles". CROSS_CHAPTER_NOTES 4 and 17 say the same. Fix: "Lab 3 (Chapter 13) times the kernel with each PE's timestamp counter instead, because whole-run totals include memcpy and host idle time."

**E2 (high, cross-page; the wrong text is on other pages) · what `launch(..., nonblock=False)` waits for.** Ch07's call table is right: "`launch()` itself returns to Python without waiting for the device". Three later pages say the opposite:
- Ch 13 (src) step card: "returns without unblocking the command stream, so the host's launch(..., nonblock=False) keeps waiting".
- Ch 13 quiz: "Why does the host's launch('run', …) return only after the last step? … nonblock=False waits for that".
- programs/06-summa/pe_program.csl:123 (shown in Ch 14): "only now does the host's launch() return".
- programs/07-cg/pe_program.csl:115 and :217, plus the Ch 15 prose: "each launch returns only when its phase has finished".

I measured it again: program 01 with `saxpy` looping `@fmacs` 400 times (63,498 cycles, WSE-3, SDK 2.10.1). `launch()` took 0.00 s of wall time, and the next `memcpy_d2h` took 5.06 s (the whole simulated run). This matches CROSS_CHAPTER_NOTES 21 and Ch 10. The labs' programs still give correct results, because the next command is what waits. Fix the wording in Ch 13, 14 and 15 and in the two program comments ("the host's next command can now run"). Ch07 should state the rule once, prominently (see G1).

**E3 (low) · `#frame`.** Quoted text: "The bandwidth benchmark computes exactly this: `core_offset_x = 1 + 3 + width_west_buf`, `min_width = …`, `min_height = 1 + height + 1`". ## Explanation problems

**X1 · `#copy-path` step 1 and quiz Q3: the counter's direction is never stated.** The page says the counter "ticks on every wavelet and lets one through only when it reads 0". A reader who assumes it counts down gets the wrong answer from `init_count = (w − pid) % w`: PE 1 would start at 3 and keep wavelet 3, not wavelet 1. The library's table (memcpy/wse3/memcpyh2d.csl:57–62) shows it counting up and wrapping (P1: 3 0 1 2 3 0 …). Ch 04 phrases it a third way ("passes one wavelet … each time its counter wraps"). Fix: "counts up 0…limit and wraps; passes the wavelet when it reads 0". Add the 4-row table from the library, and link Ch 04 `#filters`.

**X2 · Bug callout: abbreviations used before they are defined.** The library quote "When UT0 is done, all data in IQ0 is drained, but OQ0 may not be empty" uses UT0, IQ0 and OQ0, which the page never defines. Gloss them inline (microthread 0, input queue 0, output queue 0).

**X3 · `#ordering`: one step is loose.** Quoted text: "the x command is never sent". Say why: the host is still inside the blocking `memcpy_h2d(b)` call, and b's stalled wavelets also sit in the same demux and row path that x would need. As written, "serialized" could be read as a device-side rule only.

**X4 · `#reserves` table: the Local tasks cell is too dense.** It packs the WSE-3 rules, the WSE-2 rules, the topic-09 map and the task-29 rule into one cell. Fix: split it into WSE-3 and WSE-2 rows, or draw a 0–31 number line per architecture marking memcpy, data-task and safe IDs. Ch 05 already has a budget figure, so link it.

**X5 · Cross-chapter mentions are plain text, not links.** Chapters 5, 8, 10 (one link only), 12 and 13 are mentioned without links, and nothing links the glossary. The glossary already has entries for memcpy frame, command stream, filter, launch/RPC, kernel stall, halo and channel, so link those terms on first use.

## Connecting gaps

**G1 (high, S) · Ch 07 call table → Labs 3–5 host loops: what "blocking" means for `launch()`.** The table states the fact, but a learner must also know three consequences:
1. `nonblock=False` on `launch()` waits only for the command to be sent.
2. The wait happens inside the next command.
3. A host wall-clock timer around `launch()` measures nothing.

Without these, the labs' comments read as more plausible than Ch 07 (E2). Bridge: a short "What blocks, and where" box with a two-row timeline: `launch` returns at t ≈ 0, and the next `memcpy` waits for the unblock. Include my measurement (0.00 s vs 5.06 s). The CG lab's host-driven loop can then be described correctly: each phase's wait sits in the following launch or copy.

**G2 (med, S–M) · Ch 05–06 (tasks, DSDs) → Ch 07 code: export, layout and params are used before they are taught.**
- Ch 07 uses `@export_symbol`/`@export_name`, `layout.csl` vs `pe_program.csl`, `param`, `@import_module("<memcpy/get_params>")`, `sys_mod` and `get_id`. Pages 01–06 contain no "export"/"@export_symbol" and no `param`. CSL structure arrives only in Ch 10.
- "Exported array", "exported device function" and the four-file streaming snippet therefore assume knowledge the reader does not have.
- Bridge: a 6-line box "How the host finds your arrays". It would show `@export_name` in the layout (name, type, writable), `@export_symbol` in the PE program and `get_id` on the host, with the memcpy params import as the one other line. Link it forward to Ch 10.

**G3 (med, M) · H2D path → D2H measurements: the reverse path is never explained.** The page gives a full section and a widget for H2D, but D2H gets only "mux merges per-row results". The experiment then reports D2H as 8× slower and not scaling with channels, with only a hypothesis attached. Missing mechanism, all from memcpy.csl:391–399 and sys_params WARNING 4:
- memcpy's microthread on each PE reads your array and sends {data, ctrl} pairs on color 21, which needs a switch-capable color, east along the row.
- Rows are merged in the mux column and leave through the mux adaptor.
- For streaming D2H, your output queue sends on your D2H color R→R into IQ0, and memcpy forwards it.

Bridge: a mirror-image paragraph plus a small diagram. The 8× result would then follow from a mechanism rather than appear as a puzzle.

**G4 (med, S) · Host call arguments → demux and filter settings.** The page shows the host's `(x0, y0, w, h, elements)` and the device's counter filters, but not what links them. The link is the demux adaptor's header `{enable_receiver[N], pes_per_receiver, pe_length}` (runtime/demux_adaptor.csl). The adaptor sends a teardown, then the config, then a teardown, before each tensor. Commands enter the command fan on their own path (FABRIC_CMD in layout_west_demux_cmdfan_multi.csl), not through the demux. Bridge: one numbered sequence: host call → header to adaptor → demux reconfigured → row filters set by the command on color 22 → data.

**G5 (med, S) · Ch 04 routing → the "do not route the streaming color" rule.** The page says memcpy "moves each wavelet from color 23 through queue 0 into your color, where your data task picks it up from your own input queue". It skips the hop that explains the rule: the wavelet leaves the CE through OQ0, goes to the router, comes back up the ramp on your color and lands in your IQ. memcpy sets that RAMP→RAMP route itself, so a user route would conflict. This hop is also why the color comes out of your 0–19 budget. Bridge: the library's own ASCII flow (memcpy.csl:372–380), drawn as a small figure.

**G6 (med, S) · "Streaming H2D completes early" (host) → "D2H read 95 values" (device).** Ch 05 says tasks run one at a time to completion. So why did memcpy's D2H work run while 5 `on_value` tasks were still queued? The page explains the host side and the queue depths, but never the device-side ordering: the D2H command's control task becomes runnable when its wavelet arrives on color 22, and the task picker is not obliged to drain IQ2 first. Also relevant: the library's note that a D2H after an H2D "cannot guarantee OQ0 is empty, so D2H command must call QFLUSH(OQ0)" (memcpy.csl:402–404). Bridge: one paragraph tagged Derived, plus a "picker chooses" tick in the race widget.

**G7 (low, S) · "Serialized per PE" vs "the whole row takes part" and inactive rows.** Rows with no active PE skip a command immediately, so different PEs can be at different commands. The page never says what the host-level "one at a time" guarantees across PEs. Add one sentence: each PE decodes in order, and a later command reaches a PE only after that PE has finished the earlier ones.
