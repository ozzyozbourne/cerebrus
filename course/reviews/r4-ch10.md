## Errors

**E1 (med) · #builds, "What cslc actually builds", step 1 and the "Stage order Derived…" legend.** The page lists "Wrapper checks and the frame" as the first stage, before "Evaluate the layout". In the wrapper source (`/cb/.../bin/cslc`, `main()`), the order is the other way round. `status = subprocess.call(cmd)` runs cslc-driver on your program first, and returns if that fails. Only then does `_generate_memcpy(...)` run. That function starts with `elf_list = dirname.glob("bin/*elf")` and reads the fabric and kernel dimensions *from the ELFs it just compiled*. Only after that does it apply the offset, channel and fabric-size checks and build `west/` and `east/`. **Fix:** move the wrapper checks and frame generation to the last stage. Say that a fabric-size RuntimeError arrives only after your own program has compiled (about 24 s) and that `out/bin/` already holds your ELFs. The error-decoder rows marked "compile (wrapper)" are fine.

**E2 (med) · #three-files, contract callout: "Breaking rule 1 or 4 is a compile error. Breaking rule 2's @export_symbol or rule 3 compiles cleanly…"** This is wrong for rule 1. Measured:
- (A) Deleting `@export_symbol(x_ptr, "x")` gives "Compilation successful", and `out_rpc.json` lists only saxpy, a and y. At run time `rt.get_id('x')` does not fail. The first `memcpy_h2d` then dies with `TypeError: memcpy_h2d(): incompatible function arguments`. That message is more misleading than the saxpy one.
- (B) An `@export_symbol` name that the layout never declares *is* a compile error: `error: name 'xx' was not declared during layout evaluation · note: use @export_name to declare 'xx'`.
- A typo in `rt.get_id('…')` is a Python-side run-time failure.

**Fix:** "A mismatched name or mutability flag is a compile error. A *missing* `@export_symbol`, for an array or a function, and a missing unblock compile cleanly and fail only at run time." Add row (A) to the error decoder and to "Break it on purpose".

**E3 (low–med) · #source-to-sim, #fabric-size, the flags table, the wrapper widget's CS-2 mode, and Q3: "--fabric-dims set to that system's fabric (750,994 on a CS-2) SDK 2.10.1, single-tile-matvec" and "the rectangle can be at most 743 × 992".** The cited source does not say this. `single-tile-matvec/README.rst` says "Dims here refers to the dimensions of the program rectangle … 750*994 matvecs, with one matvec occurring on each PE". Its `sweep.py` turns `--dims 750,994` into `--fabric-dims={width+7},{height+2}`, which is 757,996. So the SDK's only CS-2 example treats 750 × 994 as the *user rectangle*, which implies a fabric of at least 757 × 996. Web searches found neither number confirmed. **Fix:** tag the CS-2 fabric size Unverified, quote the README's own wording, and fix the 743 × 992 bound (or drop it). The same claim appears in Ch 2 (lines ~190, 219) and Ch 7 (line ~106 and its calculator). Tell the coordinator.

**E4 (low) · #memory widget and the "even an empty program" sentence.** The bar uses a fixed 4,240 B plus 8·N, so N = 5,615 shows red ("ran out of PE memory"). Cross-note 13 says N = 5,615 *links* on WSE-3. Also, "even an empty program uses about 4.2 KB" was measured as SAXPY without its arrays (it still has saxpy's code). Say "SAXPY minus its two arrays".

**E5 (low) · contract rule 4: "every param declared in layout.csl must be given with --params".** Params with defaults need no value, and the page's own reference card shows `param enable: bool = true;`. Color params can also come from `--colors`. **Fix:** "every param without a default".
