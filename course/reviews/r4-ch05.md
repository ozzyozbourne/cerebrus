# R4 audit: ch05, 05-tasks.html ("Tasks: computing on arrival")

**Verdict: Mostly correct. Explanation quality: good.** The SDK quotes, the ID maps, the priority register and the measured hang all check out. The real problems are two overstated mechanics (queue depth and the "must block" rule) and a few missing bridges around the join, the sentinel and the Lab 3 example.

## Errors

**E1 (med): queue depth is misattributed and called unpublished.** Location: #rules "Blocking", the buffered-vs-collapsed widget hint, and Check-yourself Q1.
- Quoted text: "Queues are small: one SDK example 'stalls when size exceeds 14' wavelets"; "The queue is drawn with 6 slots for illustration; the real depth is not published"; "holds only a handful (one SDK example stalls past 14)".
- What is right: the SDK does publish depths. memcpy/wse3/memcpy.csl lines 205–211 (the same in wse2/memcpy.csl) give input depth 6 for queues 0–1, 4 for queues 2–3 and 2 for queues 4–7. Output depths are 2, 6 and 2. Chapter 7 already tables these. pipeline-01's "14" is not one queue's depth: its README says "the hardware has some internal queues to hold the data for I/O" while H2D and D2H are serialized. So 14 is total buffering along the I/O path.
- Fix: say "input queue 2, which program 02 uses, holds 4 wavelets [SDK, memcpy.csl]". Set the widget's CAP to 4 or label it as queue 2. Keep the "14" only as an example of path buffering.

**E2 (med): the "must block" rule is stated without its condition.** Location: #rules "Blocking", plus the comment in the #entry-points sketch.
- Quoted text: "If a fabric DSD is to read a queue, you must block that queue's data task; otherwise the task fires on each wavelet and consumes it first [pipeline-01]".
- What is right: blocking is needed only when a data task is bound to that color (WSE-2) or queue (WSE-3). The course's own Lab 3 (programs/04, fabin DSDs on iq 4/5) has no `@block` and passes on both chips. So does pipeline-01's own code (it binds no data task to queue 2). Its README warning is about the WSE-2 color's task.
- Fix: "If a data task is bound to the color/queue a fabric DSD reads, block it…". Add one line: "Lab 3 binds no data task to its receive queues, so it has nothing to block."

**E3 (low): stale fixed cost.** Location: #priority, last paragraph.
- Quoted text: "Lab 3's measured ~88 fixed cycles per step (Chapter 13)".
- What is right: Chapter 13 uses 90 + 2.5·n, and CROSS_CHAPTER_NOTES 23 says "under the 90 + 2.5·n model (not 88)". Change it to ~90.

**E4 (low): the excerpt drops the arch guard it is meant to teach.** Location: #budget, "pe_program.csl (Lab 1, program 02), excerpt, simplified".
- The excerpt shows `@initialize_queue(h2d_iq, .{ .color = h2d_color });` with no condition.
- The real file has `if (@is_arch("wse3")) @initialize_queue(...)`.
- The excerpt is introduced as "the idiom that makes one source file serve both chips", so it should keep the guard.

**E5 (low): the collision explorer labels a queue memcpy does not use on WSE-2.** Location: #portability, the explorer widget.
- The queue selectors mark queue 1 "(memcpy)" on both chips.
- Choosing queue 1 on WSE-2 prints "uses queue 1, which memcpy owns (queue 0 on WSE-2)", which contradicts itself.
- WSE-2 memcpy uses only queue 0 (memcpy/wse2/memcpyh2d.csl `input_queue_id`), as the page's own budget table says.
- Fix: in `fillQueues` and the message, use `i < (arch==="wse3" ? 2 : 1)`.

## Explanation problems

**X1 (#path): the opener is now stale.** It says "Chapter 4 said that the color picks the task at the receiver. That is exactly true on WSE-2…". Chapter 4 now says it already: "WSE-2 picks the task by color; WSE-3 puts it in an input queue… (Ch. 5)". Fix: "Chapter 4 previewed the WSE-3 extra step; here it is in detail."

**X2 (#sentinels): the sentinel snippet mixes in a switch.**
- It uses `SWITCH_ADV` for a plain sentinel, and `tx_ctrl_dsd` is never defined.
- Fix: use `ctrl.encode_control_task_payload(done_id)` (control.csl: "activates a control task with no argument"), or opcode `NOP`.
- Show the fabout DSD with `.control = true` (Chapter 4), and keep `SWITCH_ADV` for the switch sentence.

**X3 (#budget): three different "safe" counts.** The page moves between 13 (8–20), 15 (8–20 + 25, 26) and 18 IDs.
- The 25-pt squeeze compares its 18 tasks with "13 IDs, 8–20", but the table says 15 are safe.
- Use one number, 15, in both places. Also note that 25-pt's IDs 2 and 3 would have to move to ≥ 8 on WSE-3.

**X4 (intro vs #budget): "context switch" means two things.** The intro says there is "no context-switch machinery for user code". The budget section says 24 is SYS_EN_MAIN, the "first task after context switch". Add half a sentence: memcpy's "context switch" swaps whole kernels, while tasks are never preempted.

**X5 (#rules to #join-rule): the bit rules are scattered.** The rules for which event sets or clears which bit are spread over four sections. Add one mapping table:
- wavelet in queue: activated = 1
- `@activate` / `.activate`: activated = 1
- `@block`: blocked = 1
- `@unblock` / `.unblock`: blocked = 0
- task starts: activated = 0 (assumed, as in the widget)

This is the hardware-to-code mapping the learning objectives promise.

**X6 (#priority): "The picker is not purely first-come"** implies a documented FIFO baseline. The page itself later says the equal-priority order is undocumented. Say "Readiness is not the only input to the picker".

## Connecting gaps

**G1 (med, S): Lab 3 is used as the running example but never introduced.** Ideas that fail to connect: "four async transfers per step" → why there are four, and what `update()` computes.
- Lab 3 is Chapter 13, eight chapters later. The page uses ghost cells, "send east / receive from west" and `pending` with no picture of the problem.
- Bridge: a 3-line box with a small figure. A rod split over P PEs, each holding n cells plus 2 ghost cells. Each step sends its edge cells to both neighbours, receives theirs, then applies u += α·(left + right − 2u).

**G2 (med, S): the join is never re-armed.** Ideas that fail to connect: "block + activate = join" → using that join in a loop.
- After L runs, both bits are 0, so the next iteration's join is gone unless the code calls `@block(L)` again.
- programs/06-summa does exactly this (`@block(COMPUTE); // re-arm the join for the next step`).
- Bridge: add step 5, "L re-blocks itself before starting the next round", and a forward link: "Lab 4 (Chapter 14) uses this join every SUMMA step". Right now the page says only that Lab 3 uses the other tool.

**G3 (med, S): why four tasks are safe is never stated.** Ideas that fail to connect: "one shared task loses completions" → "four tasks fix it".
- The invariant is missing: each per-op task can be activated at most once before it runs, because the next step's ops start only after `pending == 0`, that is, after all four tasks have run.
- Bridge: one sentence that states the invariant, plus the general rule: "one task per event source, and no source fires twice before its task runs".

**G4 (med, S): why the sentinel arrives last is never explained.** Ideas that fail to connect: "the sender streams N data wavelets then a control wavelet" → "the receiver knows the stream is complete".
- The missing step is ordering. The control wavelet travels on the same color, through the same lossless in-order route and, on WSE-3, the same input queue. So it cannot overtake the data wavelets.
- Bridge: one sentence tagged Derived, with a short sequence diagram. This was N6, still open (from ch05-fixlog).

**G5 (low-med, S): the common `.unblock` idiom is not shown.** Ideas that fail to connect: the `.unblock` paragraph → its most common real use.
- In that idiom a data task blocks itself, forwards the wavelet asynchronously and unblocks on completion, so its one-word buffer is never overwritten.
- It appears in SDK gemv-09 (`@block(memcpy_recv_x_task_id); … .unblock = memcpy_recv_x_task_id`) and topic-14.
- Bridge: a 4-line snippet. It also shows a data task and the blocked bit working together.

**G6 (low, S): the two ID ranges are never explained.** Ideas that fail to connect: "control IDs 0–63" (Measured) and "activatable IDs < 31" (5-bit field).
- The page gives a reason for only the second range. The first follows from the 6-bit entrypoint field, bits 16–21 (control.csl: `ENTRYPOINT_BIT_POSN = 16`, opcode at bit 22). Chapter 4's control-wavelet figure already draws that field.
- Bridge: one sentence pointing to Chapter 4's figure.

**G7 (low, M): there is no timeline of the CE and microthreads together.** Ideas that fail to connect: "a task runs to completion" ↔ "async ops progress meanwhile", and main-thread priority.
- There is no timeline showing the CE running tasks while microthreads stream. Without one, "main thread ranks against microthreads" has no visible meaning. What they share is Chapter 3's single datapath and fabric ports.
- Bridge: a two-lane Gantt chart of one Lab 3 step (N4, still open from ch05-fixlog), and a sentence that names the shared resource.

**G8 (low, S): chapters and terms are not linked.** Chapters 3, 4, 6, 7, 10 and 13 are named in plain text, and no term links to the glossary. The page has no `href` to another page at all. Add links on first mention, for example glossary entries `#g-microthread` and `#g-fabric-dsd`.
