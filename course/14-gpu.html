NVIDIA GPUs, the incumbent

A GPU solves the memory wall the opposite way from the wafer. It keeps a big, relatively slow memory (HBM) and hides its latency with caches and with tens of thousands of threads that take turns. Understanding that design is the clearest way to see what is unusual about Cerebras.

The memory hierarchy

SIMT: one program, many threads

A CUDA kernel runs as a grid of thread blocks. Each block is assigned to one SM and can share that SM's shared memory. Threads execute in warps of 32 in lockstep; if threads in a warp take different branches, the warp runs both paths with lanes masked off, so a fully divergent warp runs at 1/32 of peak. Two rules dominate performance:

  • Coalescing: thread i should read element i, so a warp's 32 loads merge into a few wide memory transactions.
  • Occupancy: keep enough warps resident that when one stalls on memory (hundreds of cycles), another is ready to run.

Latency hiding by occupancy

Each warp computes for C cycles, then waits L cycles for memory. The SM's scheduler issues from any ready warp. How many warps does it take to keep the math busy?

The wafer needs none of this: a PE's memory answers in one cycle, so there is nothing to hide. That is why a Cerebras PE runs a handful of tasks and 8 microthreads, while an H100 SM keeps up to 2,048 threads in flight.

SAXPY, twice

CUDA
__global__ void saxpy(int n, float a,
                      const float *x, float *y) {
  int i = blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) y[i] = a * x[i] + y[i];
}
// host: cudaMemcpy x, y to HBM
saxpy<<<(n + 255) / 256, 256>>>(n, a, x, y);
// cudaMemcpy y back
  • One thread per element; the hardware schedules them.
  • Data lives in one shared address space (HBM).
  • Think about: coalescing, block size, occupancy.
CSL (program 01)
var x: [N]f32;  var y: [N]f32;
const x_dsd = @get_dsd(mem1d_dsd,
  .{ .tensor_access = |i|{N} -> x[i] });
const y_dsd = @get_dsd(mem1d_dsd,
  .{ .tensor_access = |i|{N} -> y[i] });
fn saxpy(a: f32) void {
  @fmacs(y_dsd, y_dsd, x_dsd, a);
  sys_mod.unblock_cmd_stream();
}
  • One instruction per PE over its local slice.
  • Each PE owns private memory; no shared address space.
  • Think about: layout, which PE holds what, colors, tasks.

For SAXPY the GPU version is simpler. The difference grows with communication: on a GPU, threads in different blocks share data through HBM and kernel boundaries; on the wafer, PEs share data only by sending wavelets on colors you routed (Labs 2 and 3). Tenstorrent sits between: explicit NoC transfers, but large per-core memory and DRAM behind it.

Scaling out

Beyond one GPU, NVIDIA combines a proprietary scale-up fabric (NVLink/NVSwitch, 72 GPUs at ~130–216 TB/s in an NVL72 rack) with a separate InfiniBand or Ethernet scale-out network, and splits models with tensor, pipeline and data parallelism. A GB200 NVL72 rack holds ~13.4 TB of HBM3e at 576 TB/s aggregate Vendor via secondary. Its strength is capacity: a 70B FP16 model fits on one B200; on Cerebras it needs four wafers (Chapter 8).

Check yourself

A warp's threads read x[2*i]. What happens to bandwidth?

The accesses are strided, so a warp touches twice as many memory segments as needed; effective bandwidth roughly halves.

Memory latency is 400 cycles and each warp computes 20 cycles between loads. How many warps hide it?

About (C + L) / C = 420 / 20 = 21 warps per scheduler.

Why does the H100's 1,979 TF figure need care?

It assumes 2:4 structured sparsity. Dense BF16 is ~989 TF — the same trap as Cerebras's sparse 125 PF.
