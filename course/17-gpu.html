NVIDIA GPUs, the incumbent

A GPU solves the memory wall the opposite way from the wafer. It keeps a big memory with high bandwidth but high latency (HBM) and hides that latency with caches and with hundreds of thousands of threads that take turns: up to ~270,000 resident on an H100 Derived. Understanding that design is the clearest way to see what is unusual about Cerebras.

After this chapter you can

  • Draw an H100 SM (four sub-partitions, warp schedulers, Tensor Cores) and derive the 989 TF headline from it.
  • Explain SIMT, warp divergence, coalescing in 32-byte sectors, what limits occupancy, and why occupancy alone often cannot hide HBM latency.
  • Explain how tiling lets a matmul climb above the HBM roofline, and how modern Hopper kernels become producer/consumer pipelines.
  • Translate SAXPY between CUDA and CSL, and estimate a GPU's decode speed per user from bytes moved per token.
  • Say which parallelism runs over NVLink and which over InfiniBand, and why.

Inside an SM

An SM is four nearly independent sub-partitions sharing one block of SRAM. Each sub-partition has its own warp scheduler, a quarter of the register file, 32 FP32 lanes and one Tensor Core. Tap a block for what it does.

Where the 989 TF comes from

Each Hopper Tensor Core does 512 dense BF16 fused multiply-adds per clock, so an SM does 4 × 512 = 2,048 FMAs = 4,096 FLOP per clock Vendor via secondary. Then:

132 SMs × 4,096 FLOP/clk × 1.83 GHz ≈ 989 TFLOP/s   (dense BF16)

That matches the datasheet Derived. The 128 FP32 lanes per SM give only about 67 TF FP32 Vendor, H100 SXM datasheet, about 15× less Derived. Mind the clocks: the 67 TF is quoted at the 1.98 GHz maximum boost (132 × 128 × 2 × 1.98 GHz ≈ 67 TF), while the Tensor Core figure corresponds to 1.83 GHz, where the FP32 lanes give ≈ 62 TF Derived. The useful sentence: the FLOPs live in the Tensor Cores; everything else in the SM exists to keep them fed. A Hopper Tensor Core instruction (wgmma) is issued by a warpgroup of 4 warps; it always takes its B operand from shared memory, takes A from registers or shared memory, and accumulates a tile in registers Unverified, PTX ISA.

The memory hierarchy

Shared memory is a scratchpad the programmer manages explicitly, like a PE's SRAM. L1 is a hardware cache carved from the same 256 KB, which a PE does not have (Chapter 3). The fair GPU counterpart to the wafer's 21 PB/s is not HBM but aggregate register + shared-memory bandwidth. Shared memory has 32 banks of 4 bytes, about 128 B/clk per SM, giving 132 × 128 B × 1.83 GHz ≈ 31 TB/s Derived bank width unverified, with registers several times faster again. The real difference is capacity at that speed: ~66 MiB on an H100 versus 44 GB on a wafer.

Put the two ladders on one scale of cycles. A neighbour PE is 2 cycles away, but a PE ~400 router hops away is ~800 cycles away, as far as HBM is from an SM Derived. So wafer layout is a locality problem in the same way GPU tiling is: data that meets often must sit on PEs that are close (Chapter 4).

SIMT: grids, blocks and warps

A CUDA kernel runs as a grid of thread blocks. Each block is assigned to one SM and gets a slice of that SM's shared memory. Its threads are issued in warps of 32, and the SM spreads its warps over the four schedulers. Warps normally run in lockstep. Since Volta each thread has its own program counter, which changes forward-progress guarantees but not the cost below.

Divergence: if threads in one warp take different branches, the warp runs both paths one after the other with the inactive lanes masked.

Derived from the masking rule Derived. On the wafer every PE has its own instruction stream, so neighbouring PEs can take different branches for free; the lockstep cost exists only inside one PE's SIMD vector operation.

Two rules dominate GPU performance: coalescing (how a warp's loads become memory transactions) and occupancy (how many warps are resident to cover latency).

Coalescing: count the sectors

Global memory moves in 32-byte sectors, four to a 128-byte cache line Vendor, NVIDIA developer blog via search. A warp's 32 loads are merged into as few sectors as possible. When thread i reads element i of a float array, 32 × 4 B = 128 B = 4 sectors and every fetched byte is used.

Coalescing visualizer

Top: the 32 lanes of one warp. Bottom: each 128-byte line touched, split into four 32-byte sectors. Shaded sectors are fetched; the orange strip is the part actually used.

Stride 2 fetches 8 sectors for 4 sectors' worth of data, so effective bandwidth halves. Reading a column of a row-major float matrix puts every lane in its own sector: 32 sectors for 128 useful bytes, 12.5%. On a PE, a strided DSD wastes no bytes: SRAM is read per element, with no sectors or lines to over-fetch. What can slow it is where its operands sit. SRAM is 8 banks, and two source streams that start in the same bank run at half rate, up to 2× slower (Chapter 6) Measured, simulator.

Occupancy: what fits on one SM

All resident threads share the SM's 65,536 registers and 228 KB of shared memory, so the more each thread or block asks for, the fewer warps fit. At 32 registers per thread, 65,536 / 32 = 2,048 threads fit (full occupancy). At 64 it is 1,024 (50%), at 128 it is 512 (25%), and at 255 only about 8 warps Derived. A block that uses 100 KB of shared memory allows only 2 blocks per SM. The same squeeze exists on a PE, where code, data and buffers compete for 48 KB, but the PE gets single-cycle memory in return.

Latency hiding by occupancy

Model one scheduler (latency hiding). Each warp computes for C cycles, then waits L cycles for memory. While it waits, the scheduler issues from any other ready warp. One warp is busy C out of every C + L cycles, so W warps keep the scheduler busy a fraction min(1, W·C/(C+L)) of the time, and you need ⌈(C+L)/C⌉ warps to hide the wait. If a warp issues k independent loads before it needs the first result (instruction-level parallelism, ILP), it can compute k·C cycles per wait, and C becomes k·C in both formulas.

Little's law: occupancy alone often cannot saturate HBM Bytes in flight = bandwidth × latency. Assume an HBM latency of 500 ns, purely illustrative: 3.35 TB/s × 500 ns ≈ 1.7 MB in flight chip-wide, ≈ 12.7 KB per SM Derived. A coalesced 4-byte warp load moves 128 B, so each SM needs ~100 outstanding warp loads, more than its 64 resident warps. With 16-byte vector loads (512 B per warp instruction) it needs ~25. So real kernels keep bytes in flight, not just warps: ILP, vector loads, and asynchronous copies into shared memory (cp.async on Ampere, the TMA engine on Hopper, below).
The two models answer different questions. The widget asks whether the scheduler always has an instruction to issue; Little's law asks whether enough bytes are requested to fill HBM. A kernel can pass the first and fail the second.

The wafer needs much less of this. A PE's own memory answers in one cycle, so local loads need no hiding. Latency still exists on the fabric, where each router hop costs 2 cycles on WSE-3 and a PE that receives, adds and forwards costs ~9 (Chapter 4), but the wafer hides it differently.

Tiling a matmul: climbing the roofline

SAXPY does 2 FLOP per 12 bytes and is HBM-bound on every machine. So how does a GEMM ever reach the flat part of the roofline (ridge ≈ 295 FLOP/B on H100, Chapter 1)? By reuse. Each thread block owns a BM × BN tile of C. It marches along K, loading a BM × BK slab of A and a BK × BN slab of B into shared memory, and every loaded element is used BN or BM times. The accumulator tile stays in registers (on Blackwell, in a separate tensor memory).

Tile calculator (BF16 inputs, FP32 accumulator)

Intensity of one tile step is 2·BM·BN·BK FLOP over (BM+BN)·BK·2 bytes = BM·BN/(BM+BN) FLOP/B. The picture shows one step on 1024 × 1024 matrices.

Even a 256 × 256 tile reaches only 128 FLOP/B from global memory, below 295. The rest comes from the 50 MB L2: neighbouring blocks re-read the same slabs from L2, not from HBM. Now run the roofline check a second time, against L2. At 128 FLOP/B, peak needs 989 TF ÷ 128 ≈ 7.7 TB/s from L2 Derived, more than the >5.5 TB/s measured on the PCIe card, so L2 alone does not close the gap. Hopper kernels also use thread-block clusters with TMA multicast (below): one L2 read lands in two SMs' shared memory, so a 2-SM cluster sharing B behaves like a 256 × 512 tile, 171 FLOP/B, ≈ 5.8 TB/s from L2 Derived; and the SXM part has more L2 bandwidth than the PCIe card. Even so, tuned cuBLAS/CUTLASS BF16 GEMMs are usually reported at roughly 70–80% of 989 TF, so GEMM approaches peak rather than hitting it Unverified. The whole problem needs far less HBM traffic: for M = N = K = 8192 the minimum is 3 × 8192² × 2 B ≈ 403 MB for 1.1 TFLOP, about 2,700 FLOP/B Derived. The budget example 128 × 256 × 64 with 4 stages takes 192 KB of shared memory and 128 accumulator registers per thread across 256 threads: registers, shared memory and Tensor Cores are sized together. On the wafer, A and B tiles are placed in PE SRAM ahead of time and moved neighbour to neighbour by wavelets (Chapter 14, a SUMMA GEMM on a P × P grid): the GPU brings data to compute; the wafer places compute next to data. That does not make the wafer GEMM a solved problem; its limit just moves. In Lab 4, on a 4 × 4 grid of 32 × 32 f32 tiles on WSE-3, the row and column broadcasts take about 2% of each step, and the SDK's per-PE loop reaches only 32% of one f32 multiply-add per cycle (51% after an outer-product rewrite) Measured, simulator (Chapter 14). A GPU GEMM is bounded by feeding the Tensor Cores; the wafer's f32 GEMM by per-PE instruction efficiency.

Hopper: a kernel becomes a pipeline

"Many identical threads" describes 2012-era CUDA. A state-of-the-art Hopper GEMM or FlashAttention-3 kernel is explicitly spatial inside the SM. One warpgroup only moves data; the others only compute; they hand off through a ring of shared-memory buffers.

Related Hopper features: TMA (Tensor Memory Accelerator) copies 1D–5D tiles between global and shared memory from a descriptor built on the host. Thread-block clusters group blocks on neighbouring SMs, which can read each other's shared memory (distributed shared memory; the nearest CSL counterpart is in Appendix B's cluster row), and TMA can multicast one tile into several SMs Unverified background. Blackwell moves the accumulator out of registers into a per-SM tensor memory of 256 KB (128 lanes × 512 columns of 32 bits) Vendor, CUTLASS source and lets a single thread issue the MMA Unverified background, Colfax tutorials. The trend: each generation moves more of the kernel into asynchronous, explicitly scheduled engines. This rhymes with Tenstorrent's reader / compute / writer kernels and circular buffers (Chapter 16) and with CSL's async DSDs and task activation (Chapters 5–6). That analogy is this course's own, not a vendor claim.

Worked example: n = 1,000,000 gives ⌈n/256⌉ = 3,907 blocks; the last one has 64 active threads and 192 masked by the guard. If 8 such blocks fit per SM (2,048 threads), one "wave" holds 132 × 8 = 1,056 blocks, so the grid runs in about 3.7 waves Derived. The same n on the wafer Derived. Program 01's length is a compile-time parameter (param N: i16, set by --params=N:64 in commands.sh), and so is the rectangle: where CUDA picks a grid at launch, CSL fixes the layout when it compiles. Memory caps N. x and y take 8 B per element and a WSE-3 PE leaves about 44,500 B for data (Chapter 3), so ~5,500 elements per PE (Lab 3 links about 5,450 with two f32 arrays). n = 1,000,000 is 8 MB, so it needs at least ⌈10⁶ / 5,500⌉ ≈ 182 PEs, set beside the GPU's 3,907 blocks in 3.7 waves. All PEs then run one @fmacs over their 5,500 elements at the same time: ~5,500 cycles ≈ 6.5 µs at the 850 MHz the SDK benchmarks assume SDK clock, if x and y start in opposite halves of the 16-byte bank cycle, and twice that (~13 µs) when they start in the same bank, as program 01's do (Chapter 6). As in Lab 1, getting 8 MB on and off the wafer costs far more than the compute.

For SAXPY the GPU version is simpler. The difference grows with communication. On a GPU, threads in different blocks share data mainly through L2/HBM: atomics, or a kernel boundary. A kernel ends only when all its blocks finish, so the next kernel can safely read what they wrote, which makes the boundary a global barrier. Within a Hopper thread-block cluster they can also use distributed shared memory. On the wafer, PEs share data only by sending wavelets on colors you routed (Labs 2 and 3). Tenstorrent sits between: explicit NoC transfers, but large per-core memory with DRAM behind it.

One token, step by step

Decode is where the comparison with Cerebras bites (Chapters 1, 8, 9 and 18). For one layer of a Llama-style model a GPU runs roughly: RMSNorm → fused QKV GEMM → RoPE + append to the KV cache → decode attention over the cache → output GEMM → [TP all-reduce] → residual + RMSNorm → gate/up GEMM → SiLU × mul → down GEMM → [TP all-reduce] → residual. That is 10–14 kernels per layer, around a thousand per token for 80 layers, so serving stacks fuse kernels and replay them with CUDA graphs to avoid launch overhead Unverified background.

Llama-3.1-70B has 80 layers, 8 KV heads of dimension 128 and dmodel 8192 Vendor, model config.json via search. Its BF16 weights are ~140 GB, and its KV cache costs 2 × 80 × 8 × 128 × 2 B = 320 KiB per token Derived. At batch 1 every step reads all the weights, so step time ≥ bytes ÷ bandwidth:

Decode speed from bytes moved (Llama-3.1-70B)

Per step, each GPU reads its share of the weights once (shared by the whole batch) plus its share of every sequence's KV cache. This is a lower bound on step time: it ignores compute, all-reduces, kernel launches and activation memory.

One B200 at batch 1 needs ≥ 140 GB ÷ 8 TB/s ≈ 17.5 ms per token, at most ~57 tokens/s per user, and only ~40 GB is left for KV cache. Eight H100s with TP = 8 read 17.5 GB each, ≥ 5.2 ms, ~190 tokens/s at best before all-reduces and overheads Derived. Measured, the best DGX-H100 result in Cerebras's Hot Chips 2024 deck is 86 tokens/s, about 45% of that bound Vendor, HC2024 citing Artificial Analysis (Chapter 9). Batching raises aggregate throughput nearly for free, because the weight bytes are shared, but not per-user speed. Each sequence reads only its own KV cache, so attention intensity does not grow with batch. It is ~1 FLOP/B for plain multi-head attention; Llama-70B's grouped-query attention shares each KV head among 8 query heads, which gives ~8 FLOP/B with a BF16 cache and ~16 with FP8 Derived, still far below the 295 ridge: at batch 64 and 4,096 tokens of context the cache adds ~86 GB per step on top of the weights Derived. That is why grouped-query attention, FP8 KV caches and paged KV memory (vLLM's PagedAttention) exist. Four CS-3 wafers keep the weights in SRAM and pipeline layers across them (Chapter 8), which makes the 2,314 tokens/s per user on Llama 3.3-70B possible Indep, Artificial Analysis via interview. It is not automatic: Chapter 9 builds the per-token budget and shows that the launch-day kernel gives about 500 tokens/s, and that optimised GEMV and collectives plus speculative decoding took it to ~2,300. At large batch GPUs win back on cost per token, because every sequence shares the weight read; Chapter 18 compares prices.

Scaling out

Beyond one GPU, NVIDIA combines the proprietary scale-up fabric (NVLink/NVSwitch: ~130 TB/s across a GB200 NVL72 rack and ~216 TB/s on Rubin Vendor) with a separate InfiniBand or Ethernet scale-out network. Per GPU and per direction, NVLink 4 gives 450 GB/s and a 400 Gb/s NIC gives 50 GB/s, a 9× gap Derived. That gap decides where each kind of parallelism goes:

Worked example Derived: take one TP = 8 group of a larger 70B training job, on one HGX H100, and one microbatch of 4,096 tokens. (The whole job cannot fit on one board: with Adam, ~16 B per parameter ≈ 1.1 TB of state against 640 GB of HBM, so FSDP or PP spreads it over more boards.) Each all-reduce carries 4,096 × 8,192 × 2 B ≈ 67 MB; a ring all-reduce takes ≈ 2 × 7/8 × 67 MB ÷ 450 GB/s ≈ 0.26 ms, and 80 layers × 4 of them ≈ 83 ms. The compute is 6 × 70·10⁹ × 4,096 ≈ 1.7 PFLOP, ≈ 0.43 s on 8 × 989 TF at an assumed 50% utilisation. Communication is ~19% of compute over NVLink, but over 50 GB/s InfiniBand the same all-reduces would take ~0.75 s, longer than the compute. That is why TP never leaves the NVLink domain, and why NVL72 (72 GPUs in one domain) matters.

A GB200 NVL72 rack holds ~13.4 TB of HBM3e at 576 TB/s aggregate Vendor via secondary. Its strength is capacity: a 70B FP16 model (~140 GB) fits on one B200 with ~40 GB left for KV cache Derived; on Cerebras it needs four wafers (Chapter 8).

2026: the incumbent adds an SRAM decode chip

On 24 December 2025 Groq announced a non-exclusive licence of its inference technology to NVIDIA. Groq's founder Jonathan Ross, its president Sunny Madra and other staff moved to NVIDIA; Groq stays independent and keeps GroqCloud Vendor, Groq newsroom. The widely quoted price of ~$20 billion comes from a CNBC report and was not confirmed by either company Unverified, press report.

At GTC on 16 March 2026 NVIDIA showed the first product: the Groq 3 LPX rack, built from LP30 LPU chips (Samsung 4 nm), as a decode co-processor beside Vera Rubin NVL72. Each chip has about 500 MB of on-chip SRAM (512 MB in some reports) at ~150 TB/s, plus ~2.5 TB/s of scale-up bandwidth Vendor via secondary. Most reports, and NVIDIA's own localised LPX pages, give 256 LPUs per rack (32 trays × 8), ~128 GB of SRAM and ~40 PB/s; one report says 128 Vendor via secondary; that 128 is an error, and this course uses 256. NVIDIA calls the split Attention-FFN Disaggregation: Rubin GPUs do prefill and attention, which need the KV cache in HBM; LPUs run the decode FFN/MoE layers from SRAM; NVIDIA's Dynamo software routes work between them Vendor via secondary. NVIDIA claims 35× the throughput per megawatt of a Blackwell NVL72 for trillion-parameter models, a vendor projection Vendor via secondary.

Status, November 2026: at Hot Chips on 24 August 2026 NVIDIA said Groq 3 LPX is in full production (at Samsung Foundry), with Nebius as the first cloud customer Vendor via secondary. Its first performance figure cites Artificial Analysis at about 3,400 output tokens/s on Gemma 4 31B at 100K context Vendor, citing Artificial Analysis, via press. The comparison NVIDIA drew with Cerebras set 64 LPUs against two wafers on different endpoints, so it is only partly comparable Press analysis.

What it means, per chip: 150 TB/s ÷ 19.2 TB/s ≈ 8× the bandwidth of a Rubin GPU, for 1/576 of its capacity (0.5 GB vs 288 GB) Derived. Check yourself

A warp's threads read x[2*i] from a float array. What happens to bandwidth?

The warp spans 256 B = 8 sectors but uses only 128 B of them, so 50% of fetched bytes are wasted and effective bandwidth roughly halves (unless the other half is reused later from cache). Try it in the coalescing visualizer.

Memory latency is 400 cycles and each warp computes 20 cycles between loads. How many warps hide it on one scheduler, and can an H100 do that?

(C + L) / C = 420 / 20 = 21 warps per scheduler. An H100 scheduler holds at most 16 (64 per SM), so occupancy alone tops out near 16 × 20 / 420 ≈ 76%. To go further each warp must keep more loads in flight (ILP: with k = 2, ⌈420/40⌉ = 11 warps suffice) or prefetch into shared memory with async copies.

A kernel uses 128 registers per thread. How many threads fit on an SM, and what does that do to latency hiding?

65,536 / 128 = 512 threads = 16 warps, only 4 per scheduler: 25% occupancy. With C = 20 and L = 400 that hides about a fifth of the wait, so the kernel needs ILP or a smaller register footprint.

A warp runs if (lane < 16) A(); else B();. What does it cost?

Both paths run one after the other, each with half the lanes masked: the time of A plus B at 50% lane efficiency. The same branch across different PEs on the wafer costs nothing, because each PE has its own instruction stream.

Why does a GEMM get close to peak on an H100 when a single 256 × 256 tile only gives 128 FLOP/B?

Neighbouring blocks re-read the same A and B slabs from the 50 MB L2, so HBM traffic is much lower than per-tile traffic. Over the whole 8192³ problem the minimum HBM traffic gives ~2,700 FLOP/B, far above the ~295 ridge. A second check against L2 (989 TF ÷ 128 ≈ 7.7 TB/s needed, above the measured >5.5 TB/s) shows L2 is not quite enough on its own; cluster multicast makes the effective tile larger. Tuned GEMMs land near 70–80% of peak, not 100%.

Translate: which CSL concept plays the role of blockIdx/threadIdx, and which CUDA concepts have no wafer equivalent?

A PE's coordinates and the slice the host's memcpy gives it (set by the layout's rectangle). Thread blocks, shared memory between threads and a global HBM address space have no equivalent: each PE owns its 48 KB and talks to others only by wavelets.

Why does a 70B model fit on one B200 yet decode slower per user than on four wafers?

The 140 GB of weights fit in ~180 GB of HBM, but every token must read all of them: ≥ 140 GB ÷ 8 TB/s ≈ 17.5 ms, at most ~57 tokens/s per user. On four wafers the weights stay in SRAM, so per-user speed is set by the pipeline, not by HBM. Batching helps the GPU's aggregate throughput and cost, not per-user speed.

Why did NVIDIA pair Rubin GPUs with Groq 3 LPUs instead of just building a faster GPU?

Decode for one user reads every weight per token, so it wants bandwidth, not capacity; HBM gives ~19 TB/s per GPU, on-chip SRAM ~150 TB/s per LPU. But each LPU holds only ~0.5 GB, so attention and the KV cache (large, per user) stay on the HBM GPUs, and only the FFN/MoE weights are spread over hundreds of SRAM chips.

What does an NVL72 rack give that nine 8-GPU HGX boxes on InfiniBand do not?

One NVLink domain of 72 GPUs at 1.8 TB/s each (~130 TB/s), so tensor parallelism and expert all-to-alls can span all 72. Across HGX boxes the per-GPU link drops roughly 9× to InfiniBand, which is too slow for per-layer all-reduces.
