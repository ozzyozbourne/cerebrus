CSL and the toolchain

CSL, the Cerebras Software Language, looks like Zig. Its real content is a type system for hardware resources: colors, queues, tasks and descriptors. This chapter covers the three files every program has and how their names must match, the language, what cslc actually builds, how to read the outputs and decode the errors, the Python alternative (SdkLayout), and how to set the SDK up.

After this chapter you can

  • Read every line of a complete CSL program (all three files) and say what runs where and when.
  • Write the "contract" a new program needs: matching names, params and unblock_cmd_stream() across the three files.
  • Choose --fabric-dims and --fabric-offsets for any rectangle, and predict how many PE programs cslc builds and what lands in out/.
  • Compile and simulate with cslc and cs_python, find every output, and decode the common error messages.
  • Size arrays against the 48 KB per PE, and know which standard-library module to reach for.
  • Say when SdkLayout is the better way to lay out a program.
  • Set up the SDK in a fresh Linux environment.

Three files, three places

"A complete program consists of a host program … and at least two CSL code files, one of which defines the layout of the program on a set of PEs, and one or more of which define the programs running on the individual PEs" SDK 2.10.1, gemv-01. Grid coordinates are always (x = column, y = row), and sizes are width × height.

layout.csl

runs at compile time

  • size of the PE rectangle
  • which code file and params each PE gets
  • routes for every color (@set_color_config)
  • names the host may use

pe_program.csl

runs on each PE (one or more files)

  • arrays in the PE's 48 KB Vendor
  • DSDs, queues, tasks
  • RPC functions for the host
  • one compiled program per distinct PE (see "What cslc builds")

run.py

runs on the host (under cs_python)

  • SdkRuntime: load, run, stop
  • memcpy data in and out
  • launch RPCs
  • check results with numpy

Writing your own: the contract between the three files
  1. Every array the host touches: @export_name("name", [*]T, mutable) in layout.csl; a [*]T pointer (var if mutable is true, const if false) plus @export_symbol(ptr, "name") in pe_program.csl; rt.get_id('name') in run.py.
  2. Every host-callable function: @export_name("f", fn(args)void) in layout.csl; fn f(...) plus @export_symbol(f) in pe_program.csl; rt.launch('f', ...) in run.py.
  3. Every RPC must end, directly or through a task it starts, with sys_mod.unblock_cmd_stream().
  4. Every param declared in pe_program.csl must be passed in @set_tile_code's struct, and every param declared in layout.csl must be given with --params (unsigned integers only).
  5. Keep clear of memcpy's resources: colors 20–23, its task IDs and queue 0 (and 1 on WSE-3). See Chapter 7's table.
Breaking rule 1 or 4 is a compile error. Breaking rule 2's @export_symbol or rule 3 compiles cleanly and fails only at run time (see the error decoder below).

The language in one screen

Ordinary parts

  • Types: bool, i16, i32, u16, u32, f16, f32, arrays [N]f32, pointers *[N]f32 (knows its length) and many-item [*]f32 (does not; used for exports).
  • const / var, fn, for (@range(i16, n)) |i|, while (c) : (i += 1).
  • if is also an expression: const c = if (x % 2 == 0) c0 else c1;. A statement if with an else needs braces: if (v > m) { m = v; } else { … }. Without braces it is a compile error Measured; a lone if (v > m) m = v; is fine.
  • Anonymous struct literals .{ .N = N } pass named fields everywhere: @set_tile_code, @get_dsd, @import_module.
  • Builtins start with @: @as, @zeros, @bitcast, @get_dsd, @fmacs…
  • "CSL does not have a null pointer". "Arrays can only be passed to or returned from functions used at compile-time": a function that runs on the PE takes *[N]f32 or [*]f32 SDK 2.10.1, topic-01.

Hardware parts

  • param: compile-time constants from the layout or --params. PEs with different params become different PE programs.
  • comptime { }: bindings (@bind_data_task, @initialize_queue…) and exports, evaluated by the compiler.
  • Resource types name the hardware (table below). For a first single-PE program you need only mem1d_dsd.
  • @is_arch("wse3") picks per-chip code in one source file.
  • <layout> gives a PE its own coordinates at run time: @import_module("<layout>").get_x_coord(), so you need not pass .x = x as a param SDK 2.10.1, gemv-07.

Writing for both chips

All course programs build for WSE-2 and WSE-3 from one source. Three idioms do it (the full portability table is in Chapter 5); <memcpy/memcpy> itself switches to its wse2/ or wse3/ implementation the same way SDK 2.10.1.

// 1. queues exist only as bindable objects on WSE-3 (sdklayout-02)
if (@is_arch("wse3")) { @initialize_queue(out_q, .{ .color = @get_color(c) }); }
// 2. a data task is named by its color on WSE-2, by its input queue on WSE-3 (topic-12)
const recv_task_id: data_task_id =
  if (@is_arch("wse2")) @get_data_task_id(comm) else if (@is_arch("wse3")) @get_data_task_id(comm_iq);
// 3. a fabric DSD needs .fabric_color on WSE-2 only (program 03, pe_program.csl)
const out_dsd = @get_dsd(fabout_dsd, if (@is_arch("wse3")) .{ .extent = M, .output_queue = oq }
                                     else .{ .extent = M, .output_queue = oq, .fabric_color = send_color });
Most bugs are resource bugs Every bug we hit while writing this course's programs was about a resource, not arithmetic:
  • an export's mutability flag (true in the layout, a const pointer on the device; program 02): a compile error, decoded below;
  • a race where the host read results before the last data task ran (Chapter 7, copy vs streaming; program 02 in Lab 1);
  • two asynchronous DSD operations on the same microthread, which collide or stall (Chapter 5, Chapter 6; the Lab 3 rebuild with queues 2/3 aborts with "trying to term ut_instr[3], but it's not ours").
The scalar language is the easy part.

Where did my 48 KB go?

Every byte a PE uses (code, the memcpy runtime and its buffers, your arrays) sits in its own 48 KB SRAM Vendor. cs_readelf -m out/bin/out_0_0.elf prints exactly how much ("Display main memory used per PE"). For SAXPY, with two f32 arrays of N each Measured, cs_readelf -m:

So even an empty program uses about 4.2 KB on WSE-3 for code and the memcpy runtime, and overflow is a link error, not a run-time one. To find your own limit, bisect: for N in 5000 5600 5620; do cslc … --params=N:$N -o b$N; cs_readelf -m b$N/bin/out_0_0.elf; done.

    The fabric-size rule

    With --memcpy, your rectangle sits inside the memcpy frame (Chapter 7): 1 halo + 3 memcpy columns on the west, which is why your (0,0) is fabric (4,1), and 2 memcpy + 1 halo on the east, plus one halo row above and below. The wrapper's own check (_generate_memcpy in cslc) is SDK 2.10.1:

    • offset_x ≥ 4 + width_west_buf and offset_y ≥ 1;
    • fabric_w ≥ offset_x + W + 3 + width_east_buf and fabric_h ≥ offset_y + H + 1.

    At the usual offsets 4,1 that is: the rectangle must be at least 7 columns narrower and 2 rows shorter than the fabric. For an 8 × 4 rectangle: --fabric-dims=15,6 --fabric-offsets=4,1. A 6 × 2 rectangle needs 13,4; 12,4 fails with "Fabric dimension must be at least 13-by-4" Measured. On hardware the fabric is fixed (750 × 994 on a CS-2), so the rectangle can be at most 743 × 992 SDK 2.10.1.

    What cslc actually builds

    1. Wrapper checks and the frame. The Python wrapper checks the fabric and offsets against memcpy's needs and generates the west and east frame programs (out/west/, out/east/). Errors here are Python RuntimeError tracebacks.
    2. Evaluate the layout. cslc-driver runs layout {} at compile time; every @set_tile_code and @set_color_config becomes a concrete value. Errors: "failed to evaluate layout block".
    3. Group PEs. PEs with identical code, params and router configuration become one PE program.
    4. Compile and link each group. Semantic errors point at a line; memory overflow comes from the linker ld.lld ("ran out of PE memory", "Failed to link").
    5. Write metadata. out.json (the params) and bin/out_rpc.json (the export IDs the host looks up).

    Simulator outputs

    The simulator writes sim.log, sim_stats.json, simconfig.json and simfab_traces/ into the directory you ran cs_python from; the host's print output goes to your terminal. A real sim_stats.json from program 01 (WSE-3, a quiet rerun) Measured:

    "cycle_count": 7740,          # whole run: load, every memcpy, your kernel, idle tail
"fabric_x": 8, "fabric_y": 3,  # --fabric-dims
"hwtile_count": 10,           # tiles simulated as full PEs

    • Idle stop. The simulator stops after an idle window once the host has stopped; simconfig.json has "sunsetCount": 50, and most runs stopped after exactly 50 idle cycles Measured.
    • A deadlock and a success can both end "Stopped due to idleness". Only your host-side check (the assert_allclose) tells you which.
    • cycle_count is not fully repeatable. Quiet reruns gave 7,740 (WSE-3) and 6,826 (WSE-2) every time. First runs after a compile, and runs while other simulations loaded the machine, gave 7,786 to 11,004 for the same WSE-3 program, and 8,885 for WSE-2 with a 2,109-cycle idle tail Measured. The Chapter 11 review saw +1.4 % to +2.3 % for program 01 in parallel runs and up to about 4× on one variant, while in-kernel timestamps did not move Measured. The simulator keeps counting cycles while it waits for slow host commands. Run one simulation at a time when you compare totals.
    • To time a kernel, read the PE's own timestamp counter with <time> (topic-02), which stays stable under load, or difference two runs as Lab 3 does. Do not read a single cycle_count.
    • A fatal stop writes no sim_stats.json at all Measured. sim.log names the chip internally: FYN = WSE-2, SDR = WSE-3.

    When it hangs: a four-step procedure

    1. Read the run.py traceback. "received length … kernel stall" means some RPC never unblocked, or a task you waited for never ran.
    2. Print from the device. Add a <simprint> line at the entry and exit of each task, rerun, and look at the last line each PE printed: grep 'PE(' sim.log.
    3. Check the routes you think you set: --out-routes at compile time, or cs_readelf --routing out/bin/out_i_j.elf.
    4. Only then go instruction by instruction: the instruction trace below, or csdb (subcommands memory, register, trace, wavelet…; this course verified only its help screens).

    The other way to lay out: SdkLayout

    The SDK has a second, newer way to build programs, with five tutorials (sdklayout-01 to -05) SDK 2.10.1. Instead of layout.csl and cslc, a Python script under cs_python creates code regions, "paints" routes with symbolic colors, places regions anywhere on the fabric, and calls layout.compile() itself. "The SdkLayout engine will automatically find optimal routes" between ports you connect. memcpy is not used (memcpy_required=False), so there is no frame: running sdklayout-02 gave fabric_x: 2, fabric_y: 1, iotile_count: 0 and cycle_count: 81, against 8 × 3 and 7,740 for SAXPY with memcpy Measured.

    layout = SdkLayout(platform)
code = layout.create_code_region('./send_receive.csl', 'send_receive', 2, 1)
code.set_param(IntVector(0, 0), 'select', 0)
code.set_param(IntVector(1, 0), 'select', 1)

rt.load(); rt.run(); rt.stop()
rt.read_symbol(1, 0, 'buffer', dtype='uint16')

    Setting up the SDK

    1. Get the SDK. Cerebras distributes the SDK 2.10.1 tarball (it is not in a package manager). Unpack it into a directory such as ~/cerebras-sdk. It contains the wrapper scripts cslc, cs_python, csdb, cs_readelf, sdk_debug_shell and a 3.5 GB Singularity image (sdk-cbcore-2.10.1-….sif) with the compiler, runtime and simulator Measured. Unpack csl-extras-*.tar.gz inside it to get the tutorials and benchmarks.
    2. Install a container runtime. The wrappers call singularity. On Ubuntu, apt-get install singularity-container (SingularityCE 4.1.1) works Measured.
    3. Create env.sh and source it in every shell: 
      export PATH=$HOME/cerebras-sdk:$PATH
export TMPDIR=$HOME/cerebras-sdk/tmp    # cs_python fails under /tmp
mkdir -p "$TMPDIR"
export SINGULARITY_DROP_CAPS=CAP_SYS_RESOURCE  # only if root without CAP_SYS_RESOURCE
      In this course's cloud container, running as root without CAP_SYS_RESOURCE, every tool failed with "Requesting capability set … while permitted capability set is …" until that last line was added Measured. Run cs_python from a directory outside /tmp, with run.py in the directory you run it from.
    4. Smoke test: cslc --help, then bash commands.sh in a copy of programs/01-saxpy; it should print SUCCESS!.

    If you are using this course's repository, .claude/skills/cerebras-sdk/scripts/setup.sh does all of this idempotently. Then source ~/cerebras-sdk/env.sh; cd course/programs && ARCH=wse3 bash run_all.sh.

    Break it on purpose

    Copy programs/01-saxpy to a scratch directory outside /tmp and make one change at a time. Predict the message first; each takes under a minute.

    1. Change var y_ptr to const y_ptr.
      what you'll see "exported symbol mutability mismatch" at compile time.
    2. Drop --params=N:64 from commands.sh.
      what you'll see "only 'var' and 'extern const' variables may be uninitialized".
    3. Delete @export_symbol(saxpy);.
      what you'll see a clean compile, then "FATAL: Error: the function saxpy does not exist" from run.py.
    4. Delete sys_mod.unblock_cmd_stream();.
      what you'll see launch returns; the D2H copy then aborts with "could be a kernel stall".
    5. Set N:5620.
      what you'll see "ran out of PE memory" from ld.lld. Then try 5610 and run cs_readelf -m.
    6. Rebuild unchanged with ARCH=wse2 bash commands.sh and open sim_stats.json.
      what you'll see about 6,826 cycles instead of 7,740: same source, different chip; @is_arch and the memcpy library choose different code paths and timings.

    Check yourself

    In program 03, which file decides that PE (3,0) talks to PE (4,0) on color 1, and how does device code use the color?

    layout.csl, through @set_color_config on both PEs (tx EAST on (3,0), rx WEST on (4,0)). The device code receives the color as a param and uses it: on WSE-2 directly, on WSE-3 through an input/output queue it binds to the color with @initialize_queue.

    Program 03 passes each PE a role (first / middle / last) and send/receive colors that alternate by column. For P = 16, how many PE programs does cslc build, and why not 16?

    One per distinct combination of code, params and routes: first, last, and middle-even / middle-odd, so 4, the same as for P = 8. Compile time grows with the number of distinct combinations, not with the PE count. Passing .x = x to every PE would make 16; read coordinates at run time with <layout> instead. Different routes still split programs.

    You need a 10 × 3 rectangle with memcpy. What flags do you pass in the simulator, and what changes on a CS-2?

    --fabric-dims=17,5 --fabric-offsets=4,1 (width + 7, height + 2). On a CS-2 you recompile with --fabric-dims=750,994 (same offsets) and pass --cmaddr to run.py.

    Your program compiles, then run.py dies with "could be a kernel stall". Where do you look, in order?

    The RPC just before the failing memcpy: does every path call unblock_cmd_stream()? Then <simprint> lines in sim.log to see which PE stopped where; then the routes (--out-routes); then the instruction trace or csdb. Rerun once first: heavy host load can also trigger it. Do not trust "Stopped due to idleness" as success.

    You delete @export_symbol(saxpy). Does it compile?

    Yes. The function just never appears in out/bin/out_rpc.json, and rt.launch fails at run time with "the function saxpy does not exist".

    Which file shows you that cslc kept the route you asked for?

    The --out-routes table at compile time, or cs_readelf --routing on the ELF in out/bin/ that covers that PE (cs_readelf -r tells you which one).

    When would you pick SdkLayout over layout.csl?

    When you compose several code regions and want symbolic colors, automatic routing between ports and free placement, and you can live with streams to single-PE ports (or build adaptor regions). For one rectangle with memcpy copies and RPCs, layout.csl is simpler and matches most SDK examples.
